## Why

The PH01 exit gate requires tenant isolation and authoritative identity checks on the actual managed path; local substitutes are explicitly insufficient. This ticket carries [ADR-004](../../docs/architecture/ADR-004-TENANT-TRANSACTIONS.md) slice 3's managed obligations by reference to the [managed plan](../../evidence/APP-008/managed-plan.md) §Ordered managed run and §Required matrix, moved from APP-008 by [ADR-005](../../docs/architecture/ADR-005-PHASE-1-SEQUENCING.md); [ADR-008](../../docs/architecture/ADR-008-YC-DEMO-AND-BETA-MVP.md) defers the plan's recovery, pool-lifecycle, concurrency and drift rows to APP-080.

Window `88d1b19d` proved the procedure, migrations, seed and HTTPS surface on RDS. The managed qualification task refused before its first check, so tenant isolation and role bindings on RDS are still unproven.

## What changes

Re-scoped 2026-11-04. Window `88d1b19d` ran the original plan on RDS on 2026-10-30 ([record](../../evidence/APP-078/window/README.md), steps 0–11 and 13–14):

- approvals and ledger reconciliation;
- read-only observation and the catalog baseline;
- the pre-migration snapshot;
- migrations to version 7, applied twice and byte-identical;
- both organizations seeded twice, identically;
- the public HTTPS surface, with byte-identical uniform 404s;
- cleanup.

Releases have since migrated the same instance to schema 20, and every promotion probes liveness, readiness and the uniform denial (`ops/promotion/runner.py`). Step 12 never produced a result. The managed qualification task refused at its first case with `case_refused` and `checks: []`, twice. So the IAM role bindings, their refusal cases and the two-organization grant/RLS matrix have no managed result.

This ticket now delivers that verdict:

1. Diagnose the refusal locally. Rebase the diagnostics on `app086/qualification-diagnostics` (`ba21ced`) onto `main`. They name the pool, stage, step, storage error and SQLSTATE of a refused case, through hooks that compile only into the test executable. Review them, then reproduce or rule out the refusal against the local qualification fixture at the current schema. APP-086's lead hypothesis, still unproven: the unoptimized test-profile executable on 1 vCPU misses the 5-second readiness `ACQUIRE` deadline, with two 266 KB catalog comparisons per pool. A diagnostic image was pushed as `app078b-ba21ced-arm64` on 2026-10-30, but it predates schema 20; rebuild from the rebased source.
2. Fix or bound the cause.
3. Run the qualification task once on RDS as a qualification-only operation. No stack, image, schema or service change. Task hours are reserved under the canonical deployment state (ADR-017), and Victor's words are recorded for each AWS action.
4. Bind both runs' receipts in one independent review.

The original stack update, image publication and migration steps are not repeated: they ran, and later releases own schema changes. The verdict row moved here from APP-086, which depends on this ticket and so could never run it. APP-086 keeps its other residuals.

## Acceptance tests

- [ ] The 2026-10-30 refusal is diagnosed. The reviewed diagnostics from `ba21ced` are on `main`. A local qualification run at the current schema either passes or names the pool, stage, step and SQLSTATE of the refused case, and the cause is fixed or bounded with a test.
- [ ] The managed qualification task reaches a verdict on RDS at the current schema, covering:
  - **Role bindings:** four actual IAM-token connections bind exactly to their roles, with exact PostgreSQL users, flags, memberships and origin mode. Wrong user or token, expired material, wrong hostname or CA, and plaintext each refuse for the intended reason.
  - **Two-organization matrix:**
    - seeded publication and record positives;
    - same-local-ID and Finance-only canary negatives;
    - missing or malformed scope and wrong parent IDs;
    - cross-tenant composite foreign keys;
    - every granted relation under all four roles;
    - no direct workspace publication or record DML, and no privileged `SET ROLE`;
    - the worker's limited organization read;
    - denial for unknown actions, revoked, old-epoch or missing grants, registry/database mismatches, missing source visibility and tombstones.
- [ ] The run is qualification-only:
  - task hours are reserved under the canonical deployment state;
  - there is no stack, image, schema or service change;
  - every task is observed STOPPED;
  - cleanup is confirmed and the database is unchanged.

  If a required managed administrator operation is unavailable, record the limitation and obtain an equivalent reviewed real-RDS trial; never substitute a local result.
- [ ] One independent review binds the receipts of window `88d1b19d` (steps 0–11 and 13–14) and of the new run. A partial run or cleanup uncertainty keeps this ticket open.

The managed plan's pool-lifecycle, two-order concurrency and drift-and-readiness rows, and the snapshot restore drill, run in APP-080 before any real organization (moved verbatim by ADR-008). This ticket's gate record states that they have not run.

## Verification

**Locally:** the native qualification harness, the managed-qualification tests the diagnostics add, and the `just check` steps that cover `app/src/storage` (`test`, `clippy`, `py-qualification`).

**On RDS:** the qualification task, from an image built at the reviewed candidate, through the procedure the canonical deployment state allows for a qualification-only run. If no such procedure exists, write and review it first. APP-086 recorded that preflight lacked a qualification-only window kind, and the legacy local recipes refuse after the APP-167 cutover. Coordinate with the FormaStack owner so no fAuth operation overlaps.

**Records:** keep the commit, image digest and architecture, task-definition revision, RDS resource ID and engine, run UUID and the result line under `evidence/APP-078/qualification-<date>/`. Private files may hold endpoints, never credentials or raw environment.

Source obligations: C01, C11; design §§8, 10.5; SR1, SR3; ADR-004 request/operation states, fence ownership, pool lifecycle and migration/recovery.

## Migration and rollback

The qualification task creates and removes its own fixtures. Both 2026-10-30 runs confirmed cleanup with the database unchanged. It changes no schema, image or service, so there is nothing to roll back. If cleanup is uncertain, stop, investigate, and keep this ticket open.

The schema-1 snapshot `genui-app078-pre-migration-schema1-20261030` no longer exists: no manual RDS snapshot remains on 2026-11-04, and a schema-1 snapshot could not restore a schema-20 database anyway. APP-080's restore drill takes its own snapshot. Never widen IAM grants or bypass the RDS replacement/deletion guard.
