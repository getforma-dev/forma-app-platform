## Why

On 2026-11-15 at 13:06 UTC, `imports::sandbox::tests::protocol_and_identity_violations_are_failures` failed once (`app/src/imports/sandbox.rs:710`, the case whose stub body starts `/bin/cat > /dev/null`) on PR #144, which changed only a WAF template. A re-run of the failed job passed (run 43716303532). The stub reads stdin and then exits, crashes or misreports. On a busy runner the parent's write of the input can race the child's exit, so the observed refusal can differ from the expected one.

## What changes

Find which case failed and why. It is likely an `EPIPE` on the input write, classified differently from the expected refusal. Then make the test deterministic, for example by having the stub drain stdin fully before acting, or by treating a broken pipe after a complete write the same way. Change the production classification only if the race is real for users too.

## Log

- 2026-11-15 UTC — Seen once on PR #144 and passed on re-run.
- 2026-11-15 UTC — Root cause found and fixed on `fix/app-221-sandbox-stub`. Not the input pipe: the stubs drain stdin first, and a broken input pipe is never `Crashed`. `Crashed` was `Command::spawn` failing with `ETXTBSY`: the test wrote each stub with `std::fs::write` and executed it at once, and a child that another test thread forked meanwhile still held the stub open for writing until its own exec. Reproduced in Docker (Linux, `stress-ng` on 10 CPUs): 2 of 500 iterations failed with `Text file busy`, in two different cases of the same test. Fix (test only): the stub is written through a child process, so the test process never holds an executable open for writing; 500 of 500 after. Production classification unchanged: the parser host is never written at runtime. Evidence in `evidence/APP-221/`. Moved to In review.
