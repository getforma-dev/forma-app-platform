## Why

Victor, 2026-10-30: "Speaking of governing agents … capture all the logs and actions and users' rights … pre-auth to log them in, capture the identity of the user, then trace the access they do post-auth. Give agents identity and trace what they touch, to make sure they don't touch an HR app when they are supposed to only touch engineering … e2e the pre-auth, the policies and the post-auth … even user usage tied to agents they spin up."

Companies are deploying agents faster than they can govern them. Every agent action in Forma already passes through one governed path: MCP tools, then server-side authorization, then audited commands. That makes "which agent touched what, for whom, and was it allowed" answerable as a byproduct, which is an enterprise feature buyers pay for. Positioning: **agent access governance** or **AI activity audit** (the non-human identity space). This is not DSPM, which discovers sensitive data across a company's own cloud stores.

**Today.**
- *Pre-auth:* fAuth sign-in. Agent tokens are minted by a signed-in member and tied to their epoch.
- *Policy:* member rights. An agent never exceeds its member. Decisions are server-only. Filers cannot decide their own records (APP-113).
- *Post-auth:* audited writes. Agent attributions with "via" chips.

**Missing.** Agent-scoped rights, organization policies, read tracing and an admin view.

## What changes

1. **Agent identity.** Each agent token is a first-class *agent principal*: a name, a vendor or client label, the member who created it, its scopes and its expiry. Every audit and access event carries the actor (the member) and the agent (when acting through one).
2. **Scoped tokens, set when the token is minted.**
   - Allowed spaces or apps (for example Engineering only).
   - Allowed actions: read, draft, commit, decide, share, build from a folder.
   - Folders it may read.
   - Expiry (default 30 days, APP-113).
   - Enforced in the MCP layer before any storage call, and again in storage by actor kind. A scope can only narrow the member's rights.
3. **Organization policies.** Admins set rules, evaluated on every agent call:
   - "agents may never access <space>";
   - "agents may not decide";
   - "agents may not decide amounts over $N";
   - "agents may not read files in folders tagged HR";
   - a maximum token lifetime.

   Policies are typed rules, never free text, and every evaluation result is recorded.
4. **Access trace.** An append-only, hash-chained access log, the same pattern as the audit chains. Every agent call and every member request records:
   - the tool or route;
   - what it touched: app, work, record, file and view ids;
   - the outcome (allowed, refused, and which rule refused it);
   - its duration;
   - the session or token, and the member and agent.

   Reads are included. Sign-in events from fAuth link to the session, so one timeline runs end to end: from pre-auth, through policy, to everything accessed afterwards.
5. **Admin console** (an organization admin role):
   - an Agents page: who created each agent, its scopes, when it was last used, its volume, its refusals, and revoke;
   - a per-agent and per-member timeline;
   - a "touched" view: which apps, records and files, by sensitivity tag;
   - a refused-attempts feed, live;
   - export (CSV/JSON) and a webhook for security tools (SIEM, later).
6. **Demo moment (optional).** An agent scoped to Engineering tries the HR time-off app. It is refused, and the refusal appears live in the admin console with the agent and member named.

## Acceptance tests

- [ ] A token minted with scope "Engineering, read and draft" cannot run, draft, decide or share anything outside that scope, or decide anything at all. Each refused call returns the uniform refusal and appears in the access log with the rule that refused it.
- [ ] An organization policy "agents may not access HR" refuses an otherwise-allowed agent call. Removing the policy allows it. Both evaluations are logged.
- [ ] The access log records reads and writes for agents and members, with actor, agent, touched ids and outcome. Its chain verifies, and editing a row breaks verification.
- [ ] The admin console shows each agent's scopes, timeline, touched resources and refused attempts. Revoke takes effect on the next call. Export produces the same rows.
- [ ] A member's timeline links their sign-in to their requests and to the actions of the agents they created.

## Verification

A campaign: scoped and unscoped agents, policies, reads and writes, refusals, chain verification and export. A browser walk of the console. A security review of the new authority paths.

## Migration and rollback

Additive tables: agent scopes, organization policies, the access log. Scopes default to the member's full rights, which is today's behavior. Policies default to none.
