## Why

APP-169 stores a member's deliberate Card or App choice. Works saved before it have no row and are shown as Apps, and the legacy card placement and stack paths (`stacks.ts`, `startStacks`) are still loaded. Both need evidence and owner review before anything changes.

## What changes

1. **Existing ambiguous works:** an explicit, reversible migration or owner-driven classification. Never guess from the number of components; multi-component Cards stay atomic.
2. **Legacy placement and stacks:** usage evidence beyond a code audit (saved layouts, API calls), compatibility tests, then removal of the obsolete frontend and backend pieces with a documented rollback.

## Acceptance tests

- [ ] Existing ambiguous apps receive an explicit reversible migration; multi-component Cards remain atomic.
- [ ] Legacy placement/stack retirement has usage evidence, compatibility tests and a documented rollback.
- [ ] An independent review finds no blocker.

## Verification

Record focused tests, browser evidence and independent review before completion. Planning checks alone do not prove behavior.

## Migration and rollback

Any classification migration is reversible and owner-reviewed; removal of legacy components ships only after compatibility evidence.
