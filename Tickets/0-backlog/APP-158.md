## Why

The app document currently appends current-record collections after its admitted parts. A creator cannot deliberately place that list between a summary and a note, or define a safe filter control for it. A meal tracker should put its own records list in the app layout and explain which rows a filter selected, without a second record store or browser-only truth.

## What changes

Add a versioned, closed records-list component declaration naming an admitted records input/schema ID, permitted columns, stable ordering and finite filter controls. Resolve its concrete collection UUID from the current exact SavedWork bindings on the server; a reusable AppDefinition/template must not embed a live collection UUID. Use its stable component ID in the canonical layout. Render it through trusted native SSR and live props on the united canvas, member document, shared document and connected app. Previously admitted definitions keep their existing supplemental listing; a new explicit component replaces that collection's supplemental copy rather than duplicating the records.

The initial filter vocabulary is bounded text matching, enum choice and a half-open date range over declared compatible fields. Specify the text comparison, null and date semantics in the contract and use the same normalization on the server. A filter declares the exact component targets it affects. List-only filtering does not silently change an unrelated summary; shared filter targets use APP-025's context/epoch contract. Wire aggregate targets only when APP-159 can compute them authoritatively.

Read and filter the authorized server-side collection before applying a bounded page limit. Return the canonical filter, ordering, scope, snapshot identity and truncation/page information alongside the rows. This ticket does not implement aggregate values. Preserve the existing closed request-body convention; do not put filters, records or credentials into the work/share URL. Filter changes are reads and cannot create records, grants or saved app revisions.

The existing definition `links` relate declared views and inputs. They are not arbitrary click handlers and must not be silently repurposed as actions. APP-156 owns button-to-component actions. APP-020 owns grammar/admission and APP-025 owns linked filter epochs; this ticket implements their narrow records-list consumer without claiming their entire platform scope complete. No joins, arbitrary expressions, SQL, custom markup, export or receipt-photo analysis are included. Split the implementation before selection if it exceeds five focused days.

## Acceptance tests

- [ ] Create an admitted app with a note, records list and form in a deliberate order. Native and refreshed canvas/document/shared renderings preserve that order and show the collection once. A pre-extension definition still opens without a migration or duplicate list.
- [ ] Admission rejects unknown records input/schema IDs or fields, embedded live collection UUIDs, incompatible filter types, duplicate component IDs, foreign-work references, undeclared targets and excess filter/row bounds. Two works made from the same template resolve their own collection bindings without sharing records. Hostile labels and search text remain inert data; no generated SQL, markup or event code is accepted.
- [ ] Through actual audited commands, save meals at two restaurants on both sides of a date boundary. Text, enum and date filters return the exact expected rows through the authorized read path; clearing them restores the same scope. A matching row beyond the first unfiltered page is found or an explicit bounded refusal is shown, never a false empty result from filtering only the browser's current page.
- [ ] Deliberately exceed the result limit. The list exposes its actual page/truncation scope; a partial page is not presented as the whole collection. An empty authorized result, loading, failure, denial and partial result remain distinct. Record revision/time/commit metadata and snapshot/filter identity match the returned rows.
- [ ] Delay an old filter response across a newer filter, work or account context. The old payload cannot replace the current list, controls or receipt. Native initial state and subsequent live refresh use the same canonical filter; unrelated unsent forms retain their values and command identity.
- [ ] Member and view-only recipient reads retain their existing authority. Guessed collection/component IDs, other works and strangers are refused; filters reveal no unauthorized counts or choices. A slow read racing revocation releases no private rows, and ADR-014's five-second visible authority lease still masks shared content independently of data refresh.
- [ ] Filters work by keyboard with labels, announced result state and a clear reset action at narrow widths. Shared recipients receive read controls only, with no command, member record link, Ask or resharing authority added by this component.

## Migration and rollback

Version the definition/renderer extension and preserve pinned old definitions. A new component changes presentation and read parameters, not record ownership or work identity. If storage is necessary, add a separately reviewed additive migration; never rewrite admitted historical bytes. Disable new definitions/filters on rollback while retaining old renderer versions, saved records and current authorization.
