## Why

Existing sharing accepts only active members of the same organization, copies source permissions and automatically places work. An app share should grant one named person access to one live app without making them a Northstar member. The recipient decides whether to place a connected reference, and the sender controls whether that action is permitted.

## What changes

See ADR-014 for the scenario matrix and security decisions. Restricted named recipient, live, view-only, seven-day expiry and no canvas placement permission are defaults. Creation returns a non-authorizing link the owner can copy. Viewing requires a verified identity matching the invitation. Organization admission, paid workspace creation and app guest access remain distinct. Current rendered views and records of the exact saved work are the shared content; raw files, source APIs, commands, app editing, resharing and sibling works are excluded. Definition or source-binding changes pause the grant. Independent grants remain independent.

Implement additive migration 0017, durable verified accounts/share sessions, exact-work grants, idempotent acceptance, optimistic policy updates/revocation, an authenticated HTML app, and connected references on an account canvas and existing workspace canvas. Reuse the confined query engine with explicit guest receipt attribution. Never construct an owner TrustedRequest or silently admit a guest as an organization member. Keep legacy same-organization workflow sharing compatible and accurately labeled.

## Acceptance tests

- [x] Owner creates a named private share; defaults, clear scope, expiry and separate placement permission are visible. Create retries are idempotent; optimistic updates reject stale policy versions.
- [x] Existing same-organization and other-organization accounts open only the exact app; a new recipient completes identity-only signup and returns to that app. Home workspace session survives. No organization membership is created by acceptance.
- [x] Wrong account, forwarded link, anonymous request, expired/revoked invitation and replay with another identity cannot read or accept. Failures do not expose recipient/account existence.
- [x] HTML and typed live refresh use the actual persisted records and confined source query results, with guest-specific receipts. Forms, raw files/sources, sibling works, compose, export and resharing remain denied.
- [x] Owner record changes reach the recipient; reconnect, hidden/offline resume and bounded refresh reauthorize. Read revocation clears visible data; placement revocation removes linked cards while retaining permitted page access.
- [x] Adding to a canvas is explicit and separately authorized; no share event places an app automatically. The connected reference reads the original work and never copies/adapts it. Existing members and account-only guests have a usable canvas path.
- [x] Sponsor membership/access loss, organization shutdown, source revocation, publication/work-binding drift and session expiry fail closed, including when they race a slow query or response release. Overlapping independent grants are preserved.
- [x] Real PostgreSQL migrations/role checks, auth/provider contract negatives, guest query/record isolation, concurrency/idempotency and frontend/native tests pass. Independent Tier A review covers the complete change. Browser evidence identifies synthetic provider substitutes separately from actual provider signup.
- [x] Source, tickets and reviewed changes land on pivot/pitch-mvp. Hosted deployment and APP-139/140 recording remain separate acceptance.

## Verification

Run `just check`, relevant PostgreSQL sharing/query/auth campaigns and a real browser journey on owned worktree ports. Exact source/build identities, failures, fixes and limitations are retained in [evidence/APP-154](../../evidence/APP-154/README.md). Do not touch the owner servers on 4001–4003 or 4010. Provider management capability must remain server-only and be usable without service restart; a manual operator invite does not satisfy new-recipient signup.

## Migration and rollback

Additive migration 0017 and a new accepted catalog; never rewrite historical migrations. Existing member grants retain their authority. New share session/account storage is separate from membership. Revoke grants to disable new sharing; schema rollback to an older binary is not supported without its catalog compatibility decision. No AWS mutation is part of this task.
