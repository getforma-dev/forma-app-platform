## Why

APP-120 says an app is the only governed thing and that it contains cards. APP-141, APP-142, and APP-144 then treat that app as something created before the canvas, united into a page, and opened as HTML. Those tickets will drift if "app" is still only a library row plus some cards. This spike writes the definition they implement. It does not build the modal, the page, or the shell.

## What changes

Write `docs/planning/app-model/app.md`. Read APP-120, APP-106, APP-141, and `choose_authoring` before writing. The note answers these, each in its own short section, and says "not decided" where the code and Victor have not settled it.

1. **Identity.** An app is one admitted definition plus the saved work a member holds. It is not a card, not a widget, and not a stack. Distinguish the trusted organization, authoring container `app_id`, admitted `publication_id`, and saved `work_id` from the library address. Record reuse of the authoring container across generated works.
2. **Who it belongs to.** The owner is `genui.apps.owner_principal_id`; an `edit_definition` grant alone is not ownership. A library app is not an authoring target. A share grants use of the work. It does not make the recipient the owner. APP-145 is how a new member gets the first shell. This note states that. It does not design the grant.
3. **Where it lives.** Two views of the same app: the board, and the page. The page on the canvas is APP-142. The HTML address is APP-144, and it is the existing `/w/{app}/{work}` route. Creating it happens before either view, in APP-141.
4. **What it is not.** A widget. A folder. A stack. A focus modal. A unite frame that has not yet been adopted as the page.

No product code in this spike. No migration.
