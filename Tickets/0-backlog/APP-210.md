## Why

[APP-175](../4-done/APP-175.md) made the deployment contract changeable only through a committed, reviewed schema release. The contract covers the migrations, `runtime.py`, the Dockerfiles and their image contexts, and the CDK source. A CI test binds the committed release to `HEAD`. Automatic promotion refuses any other contract change ([Promote to beta](../../docs/pitch/BETA-PROMOTION.md), "Initial scope").

The release format required both the schema manifest and the contract to change: `schema_release.load` refused any release in which one digest was equal at both ends. A change to an image context with no migration therefore had no path except a separately reviewed operator delivery. Release C adds files to the qualification image context and keeps schema 24.

## What changes

- **`ops/promotion/schema_release.py`.** `load` admits a migration or a contract-only release. The contract always changes, the version never falls, and the schema manifest changes exactly when the version does. `migrates(release)` tells the two apart. `applicable` is unchanged; only its docstring now says "the one migration or contract change". The source pin is unchanged.
- **`ops/promotion/runner.py`.** Only a migration names, takes and compares a snapshot, and only a migration runs the migration task. A contract-only release's approval summary shows `preserved.schema: true` and the normal sequence. On success, any release (not only a migration) requires the policy version to equal its `from`. The baseline then takes the candidate's schema manifest and contract digests, and the policy version becomes `to`, which a contract-only release leaves unchanged. The release is recorded in the completed record and `verified.json`, without `snapshot_identifier` or `migration_task_arn` when nothing was migrated.
- **`ops/promotion/github.py`.** `validate_summary` requires `from_version == schema_version <= to_version`, `preserved.schema` and the snapshot/migration steps of the sequence to follow whether the versions differ, and, for equal versions, the committed spec's two schema digests to be equal.
- **`ops/promotion/schema_recovery.py`.** It refuses a contract-only release: `only an executing schema migration can be restored; reconcile a contract-only release as a normal promotion`. `maintenance abandon` is unchanged and tested.
- **Docs.** [BETA-PROMOTION.md](../../docs/pitch/BETA-PROMOTION.md) ("Initial scope" and "Contract-only releases"), the [ADR-017 amendment](../../docs/architecture/ADR-017-BETA-PROMOTION.md#amendment-2026-11-14-reviewed-contract-only-releases), [DEVELOPMENT.md](../../docs/DEVELOPMENT.md) and the [trial runbook](../../docs/operations/TRIAL-RUNBOOK.md) (section 3 step 9, release B's close-out, and section 3a, release C's approval checklist).

## Acceptance tests

- [ ] `schema_release.load` admits a contract-only release. It refuses identical ends, a kept contract (for either kind), a kept schema manifest with a moving version, a moving schema manifest with a kept version, and a falling version. The pin stays the source of every value. A test covers each case, and the removal of each rule is seen failing a test.
- [ ] In fake AWS, a contract-only release (24 → 24) promotes with exactly the normal mutations: no `create_db_snapshot` and no `run_task`. Its summary shows `{from_version: 24, to_version: 24, spec_sha256}`, `preserved.schema: true` and the normal sequence. Afterwards the baseline contract is the record's `to`, the schema manifest digest and policy version are unchanged, and the completed record and `verified.json` name the release. It refuses before the lock off its baseline contract, schema, policy version or expiry. A release changed or expired after preparation never stops a service. A prepared one abandons like a normal promotion. A policy version moved during execution admits nothing. `restore-after-failed-migration` refuses it with its own message and writes nothing.
- [ ] `validate_summary` accepts a contract-only projection with `preserved.schema: true` and the normal sequence. It refuses a migration's `preserved` or sequence for equal versions, equal versions off the policy version, and equal versions whose committed spec has two schema digests.
- [ ] A committed contract-only record bound to `HEAD` passes `CommittedReleaseTests` and the committed end-to-end promotion. It was simulated at release B's `HEAD`, and the tree was restored.
- [ ] An independent Tier A review covers authorization, contract drift and the failure paths, and finds no blocker. The branch merges only after release B has executed: a merge to `main` during release B's execution would make its execute refuse as superseded.
