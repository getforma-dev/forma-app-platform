## Why

A live poll, a quiz and homework all need two general rules the storage does not have ([APP-193 finding](../../evidence/APP-193/finding-2026-11-14.md), gaps G1, G2, G4): one entry per person per item that a resubmission replaces, and acceptance only while a referenced item is open and inside its window, judged on server time inside the commit.

## What changes

Exactly ADR-020 §5 and §6, in the files builder B1 owns: `app/src/storage/commands.rs`, `rules.rs`, `actions.rs`, `mod.rs`, `tests.rs` (the scan allowlist), the new `app/src/storage/participation_campaign.rs`, `scripts/dev/campaigns.tsv`, `app/src/commands/routes.rs`, `app/admin/src/canvas/commands.ts`.
- `Declaration` gains `requires` (guards with `via`) and `set_now`; `rules::Guard` gains `via` and `holds_at(state, now)`; `compose` takes the transaction instant (the same `now()` as `committed_at`) and stamps `set_now` fields.
- `judge_requires` runs after `compose` on the commit and the dry run: same-record guards on the composed state, `via` guards on the referenced record's current revision read with `current_state(lock: false)` under `own_rows` (unreadable or absent → `Denied`), `now` substituted by the transaction instant; a failing guard is `CommandResult::Refused(Refusal::RequirementNotMet)`.
- The `one_per_creator` match after the organization's commit-sequence lock and the requested row's lock: one statement over the creator's own rows (`creator_id = SCOPED`, `own_rows`, jsonb containment of the key pairs, newest first, `FOR UPDATE OF r`); a match with identical state is `Refused(Refusal::Unchanged)`; otherwise the commit writes the next revision of the matched record and the outcome names it. The dry run returns `DryRun::Valid { replaces }`.
- HTTP: 422 `{"code": "requirement_not_met" | "unchanged"}` in JSON mode; `Notice::Refused` in form mode; client copy in `commands.ts` ("Not saved: the item this refers to is no longer open." / "Already locked in: your entry already holds these values.").
- The `participation` campaign (Docker, like `private_entries_campaign.rs`): one general app admitted through the shipped path (ADR-020 §10's example), with an owner, a reviewer, two contributors through the organization-wide share and a guest.

## Acceptance tests

- [ ] A contributor's second create for the same key replaces the first: one record per key per creator, version 2, the outcome names the first record's id; a third with identical values answers 422 `unchanged` and writes nothing; two creators with the same key keep two records; 25 contributors × 50 keys commit within the statement budget (the match statement's time is recorded). The reviewer's summary counts one entry per creator per key.
- [ ] Twenty-five simultaneous creates by one creator for one key (the race campaign's pattern) leave exactly one record whose state is one of the submitted states, with every outcome naming that record; the organization's sequence lock and the matched row's lock are taken in the D7.9 order.
- [ ] With `requires: [state eq open, opened_at gte now−30s]` over the referenced item: an answer while open and inside the window commits; after a reviewer's `close` update it answers 422 `requirement_not_met`; after the window (the item's `opened_at` stamped by `set_now`, the clock advanced by waiting or by a stamped test item) it answers the same; a reference to an item in another member's `own` list answers the uniform 404; a `reopen` re-stamps `opened_at` and answers are accepted again. The dry run gives the same verdicts.
- [ ] Every check also fails with `authorization::BYPASS` set (the match reads other creators' rows; the `via` read ignores `own_rows`), the scan test `every_record_statement_carries_own_rows` keeps the new statements, and the existing `command`, `race`, `private-entries`, `workflows`, `actions`, `mcp` and `slack` campaigns stay green.
- [ ] An independent Tier A review and recheck (authorization, concurrency, the refusal codes' disclosure, contract drift) find no blocker; the review file is in `evidence/APP-203/`.
