## Why

A six-hour sample of the beta's app log on 2026-11-15: **1,500 lines, all `INFO tokio_postgres::connection`**, written as human-readable text with ANSI colour codes. No warning or error, and no app event. So no alarm can say "model calls are failing", "the daily AI cap is at 80 %", or "sign-ins are being refused". During the class, the first sign of any of these would be a student's complaint.

## What changes

The model-call events (`model.call`, `model.usage_threshold`, `model.call_failed`) and their source attribution are specified in [APP-222](APP-222.md) part A. This ticket owns the JSON log format, the request id, the other events and the alarm plumbing. Both ship in one release.

1. **JSON logs** in production, one object per line with no ANSI codes (`tracing_subscriber` JSON formatter): `timestamp`, `level`, `target`, `event`, `request_id` and the event's fields. Keep the existing rule that logs carry identities and codes, never a name, a note or content.
2. **Quiet the noise:** `tokio_postgres` at WARN; the readiness probe logs only on a state change.
3. **Key events**, each a stable `event` name: `model.call_failed` (provider status and error class), `model.daily_cap` (at 80 % and 100 % of the cap, and per member), `http.server_error` (5xx with request id and route template, never the raw path), `auth.signin_refused` (kind), `admission.refused` (code), and `parser.killed` (RSS or deadline).
4. **A request id** on every request, sent back as a header and logged with each event.
4a. **Where the AI calls come from.** `model.call_failed` and `model.daily_cap` carry `source`: `canvas`, `ask`, `folder`, `mcp` or `slack`. One model client and its caps serve every path, so a member's own assistant over MCP costs Forma model calls only through `forma_compose_app` and the folder tools; every other MCP tool runs on the member's own AI plan. The warning then says whether a spike is building in the canvas or an agent looping through MCP.
5. **Log-based alarms** in `observability.json`: CloudWatch Logs metric filters on those events, each with an alarm to the topic. Model failures over 5 in 5 minutes; daily cap at 80 %; any `parser.killed` spike; 5xx events. This is at most about 6 custom metrics at $0.30 each.

## Acceptance tests

- [ ] Every production log line parses as JSON with the fixed keys, and a test proves no ANSI escape reaches the log.
- [ ] Each key event is emitted by its path in a campaign test (model failure via the stub server, cap at 80 %, a forced 5xx, a parser kill), and none of them logs a name, note, record content or the raw path.
- [ ] Deployed: the metric filters match a synthetic event and each alarm reaches the inbox once.

## Verification

`just check`, the focused campaigns, and a CloudWatch Logs Insights query after the release.

## Migration and rollback

Log format only, plus the metric filters; roll back by fixing forward. The metric filters can be deleted independently.
