## Why

A preview and a truthful waking state could keep an app understandable while expensive execution starts. The reference screenshot shows that presentation, but does not establish the other product's deployment model, dedicated per-app servers, or cost savings. Forma needs its own measurements and decision.

Today a saved app is admitted data served by shared infrastructure. Sleeping one app cannot mean stopping the current application service: that would interrupt other apps, sign users out and end their event connections. This spike decides whether an independently idle resource exists or should exist, which costs it could actually remove, and what the user sees while it is unavailable. Choosing to keep the shared runtime and improve bounded caches/polling is a valid result.

## What exists today

- [The Rust service](../../app/src/main.rs) loads the FMIR modules once, binds shared member/guest page renderers, and creates one query Engine and Work service. The member `/w/{app}/{work}` and guest `/s/{share}` routes render authorized definitions and records; a saved app has no dedicated server.
- [The ECS application service](../../infra/src/stack.ts) uses a shared task with 2 vCPU and 8 GiB, deliberately deployed stop-then-start. Its scheduled expiry stops service compute, not retained database, load balancer, storage or keys. It is not app-idle handling. [The invitation broker](../../infra/src/shared-broker.ts) is a separate bounded service, not a per-app runtime.
- [Query execution](../../app/src/query/worker.rs) already uses per-request confined child processes, with at most two running per organization and four per task. Workers exit; revision caches, active clients and shared service capacity have different lifetimes.
- [Refresh-token custody](../../app/src/auth/vault.rs) and [the event hub](../../app/src/events/mod.rs) are process-local. A restart empties the vault, and multi-task event delivery needs an explicit shared mechanism. These are constraints to preserve or amend deliberately, not incidental implementation details.
- [Guest authority](../../app/src/storage/shared_access.rs), [guest query release](../../app/src/storage/shared_reads.rs) and [document release](../../app/src/sharing/live.rs) recheck current identity, share, sponsor, source and publication authority. A sleeping worker or cached preview must not bypass them.

## What changes

Produce a measured options report, a reviewed architecture decision and small follow-up tickets. This ticket does not deploy sleep/wake, introduce a dedicated server for each app, change token custody, or stop the shared service. Use an isolated synthetic environment for any experiments; the existing beta and owner instances remain unchanged.

Compare at least three options: retain shared rendering with bounded cache/polling cleanup; isolate expensive work behind an execution pool; and allocate a separately suspendable execution unit where measurements justify it. Define whether the unit is a saved work, app, organization or job, and account for shared sources, multiple works and concurrent viewers. An app page becoming hidden is not proof that its jobs or other viewers are idle.

Measure idle and active CPU, working set, cache/storage occupancy, request and authority-poll volume, model/query/job activity, cold and warm latency, errors and recovery. Separate attributable measurements from allocation estimates. Record workload, sample size, exact source and environment, p50/p95/p99 and limits. Compare net costs including always-available routing/auth, database, load balancer, broker, storage, logging and wake churn; do not infer a lower cloud bill from one process using less CPU. If prices enter the comparison, record dated official inputs and explicit assumptions. Reuse APP-067 telemetry and APP-069 load/budget work where available without claiming those broader tickets complete.

The decision must specify:

1. **Availability and presentation.** Keep stable member/share URLs and a reachable authentication/authority path. Define ready, idle, waking, unavailable and retry behavior for the reusable app renderer. Distinguish sleeping from expired access, disconnection and an actual outage. Select measured latency/availability targets before accepting a design; do not promise an instant wake. A preview names its snapshot time and stale state and never claims Live or a newly computed receipt.
2. **Isolation and authority.** Keep the shared authentication/session and routing service available. Decide the precise suspendable boundary and any required change to the single-task contract. Revalidate member/account epochs, entitlement, accepted share/version, sponsor/source liveness and publication/work/policy pins before a preview, wake and final response. Revocation or expiry during sleep/wake must refuse stale protected content. An unauthorized request must neither reveal private app state nor cause costly wake work.
3. **Preview privacy.** Define snapshot ownership, allowed fields, version binding, retention, deletion and invalidation. No shared public cache or persistent browser cache of protected records. A stable share locator is not authorization. A stale screenshot cannot replace a governed result or its receipt. Authority checks must remain available without waking expensive execution; document the behavior of an already-open page after revocation. Preserve ADR-014's five-second visible authority lease measured from request start, including masking while offline, hidden or unable to renew; a cached preview or slow wake cannot extend it.
4. **Wake concurrency and limits.** Define an idempotent wake request, durable generation/lease where needed, one effective wake per unit, fencing of late completions, bounded queues/deadlines, retry/cancel behavior and failed-start recovery. Include per-account/organization and global rate/concurrency/cost limits, fairness, abuse controls and a stop condition. One viewer must not suspend a unit still needed by another. Waking or suspending one app must leave unrelated apps and sessions usable.
5. **Commands and background work.** Preserve transactional command/audit outcomes and existing idempotency keys across a wake wait, client retry or worker failure. Separate UI inactivity from imports, workflows, webhooks and scheduled responsibilities; explicitly decide which continue, queue or refuse. Sleeping must not silently discard work or repeat a side effect. Model and query work should start only after current authorization and bounded admission.
6. **Follow-up ownership.** Identify the chosen experiment/design, rejected options, operational escape path and implementation tickets. Changes to custody or single-task assumptions require an explicit amendment to ADR-006/ADR-007; guest changes retain ADR-014. Coordinate deployment/recovery with APP-061 and recorded pitch debt with APP-097. Do not duplicate those obligations or assume a process-local event hub works across new tasks.

## Acceptance tests

- [ ] The report maps the actual shared Rust/FMIR service, per-request children, caches, event hub, vault and broker, with source references; it does not infer per-app compute from the reference screenshot.
- [ ] A bounded, reproducible synthetic measurement compares the stated options, retains exact source/environment/workload identities and reports costs, latency, errors and limits. Savings and availability targets are either supported by measurements or explicitly unproven.
- [ ] The reviewed decision names the execution/idle unit, selects an option or a measured no-change outcome, and defines reusable honest preview/wake/retry behavior at stable URLs.
- [ ] The proposed contract and qualification cases cover snapshot privacy, current authority before and after wake, revoke/expiry/source or definition change during wake, and refusal without costly unauthorized work.
- [ ] The proposed contract and qualification cases cover concurrent wake deduplication, stale generation/lease completion, crash/retry, bounded overload, command idempotency, background-job responsibilities and unaffected other apps/sessions.
- [ ] Any implementation is split into owned follow-up tickets with required architecture amendments and explicit resource/cost limits. The report records what remains unimplemented; no MVP acceptance is inferred from this spike.
- [ ] Independent review confirms the evidence and decision preserve identity, tenant isolation, receipt provenance and service availability. The existing shared service, beta configuration and owner instances were not stopped or changed by this spike.

These planning checks do not qualify runtime sleep/wake. The implementation tickets must run the accepted concurrency, failure, authority and availability cases on the actual chosen boundary before any deployment.

## Migration and rollback

No migration or runtime rollout belongs to this planning change. Any experimental resources must be isolated, bounded and removed through their recorded cleanup plan without touching shared beta state. A later implementation must separately review durable leases/snapshots or custody changes, compatibility, recovery and deployment. Reducing the current application ECS desired count to zero is not a per-app rollback or sleep mechanism.
