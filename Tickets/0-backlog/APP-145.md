## Why

A generated definition is published onto an app the member already owns. `composer_context` only chooses an owned app that has both `edit_definition` and `run`, and it never chooses a library app (`choose_authoring` in `app/src/storage/composer.rs`). The clean dev stand creates that shell before sign-in, with operator `create-app` plus `discover` and `run` (`app/src/dev/db.rs`). An invitation does not. A new member of an empty organization therefore gets `no_authoring_app` from `publish_rule_built` and from generation (`app/src/boxes/routes.rs`, `app/src/composer/mod.rs`). ADR-007 D7.3 states the current rule on purpose: creating an app and granting on it are operator actions, and a member who owns no such app can retrieve but not generate. The trial cannot start until that one case is allowed.

## What changes

On the member's own compose, when `choose_authoring` would return nothing, the server creates one authoring shell and then continues the same compose. It does not ask the operator.

1. The shell is an app row owned by this member, in a space the organization already has. It is not a library app and it is not a copy of a catalog definition. `create-app` is the shape: one transaction, the owner, and one `permission.granted` audit that names the app. This path also grants `run`, because `choose_authoring` requires `edit_definition` and `run`. `discover` matches the clean stand. No other permission is granted. `share_work`, `record_write` on someone else's work, and `edit_definition` on any other app are not included.
2. A second compose by the same member finds that shell and does not create another. A member who already has an eligible owned app is unchanged.
3. The shell is created only for the signed-in member, inside the transaction that already confirmed that identity. A stranger, a revoked member, and another organization get the uniform 404 and no row.
4. If the organization has no `owner_publish` policy, the compose still refuses `no_owner_publish_policy`. This ticket does not invent a publication policy. The clean stand's `backfill` is what provides that policy for a dev organization. A live empty organization that lacks it is a separate operator seed, named here and not silently inserted.
5. The published definition is still admitted whole, then `require_authored`, then the existing publish. Model output stays data. The shell is not a way to skip admission.

APP-141's description step calls this path and does not grow its own. APP-139's first-run trial depends on it. Review depth is Tier A (ADR-010 §4): the change grants `edit_definition` and `run`.

## Acceptance tests

- [ ] A signed-in member who owns no app composes once. One app shell exists afterward, owned by that member, with only `edit_definition`, `run`, and `discover`. One `permission.granted` event names that app.
- [ ] A second compose does not create a second shell. `choose_authoring` selects the shell, not a library app.
- [ ] A member who already owns an eligible app composes without a new shell.
- [ ] A stranger and a revoked member get the uniform 404. No app row is inserted for them.
- [ ] An organization with no `owner_publish` policy still refuses `no_owner_publish_policy`. The shell, if created, does not publish.
- [ ] The admitted definition is unchanged by the shell. A hostile reply is still refused and does not publish.

## Verification

Read `choose_authoring`, `create_app` in `admission_operator.py`, and `publish_planned` before writing the path. The campaign is the composer qualification plus one new-member case. Do not weaken an assertion to make the shell pass. Ports 4001–4003 and 4010 stay untouched.

## Migration and rollback

No migration. The shell is one app row and its three grants. Stopping the path stops creating shells. Shells already created stay until an operator removes them. Publication policy rows are not added or removed by this ticket.
