## Why

Victor, 2026-10-30: "Think of workflows that real companies use and need and let's make sure we are providing solutions for that." Expense claims is the library's only true request → approve workflow; the rest are views. Most companies run the same handful of approval processes in email, spreadsheets and ticket queues. Each of them is the same governed pattern Forma already proves: a typed request, a named approver, an audited decision, live for everyone, reachable from the canvas, Slack and any agent.

## What changes

Five record apps join the library (contracts/make_library.py, fixtures, catalog with routing metadata, slugs and categories, synthetic CSV history, pins regenerated), each with a create command, decide transitions, a records card, two or three views and rehearsed sentences in the demo organization:

1. **Time off** (`/pto`, People): `leave_request` {type vacation|sick|personal, start, end, days, note}; submitted → approved | rejected by the manager; views: upcoming time off, days taken by person.
2. **Purchase request** (`/purchase`, Finance): `purchase_request` {item, vendor, amount, cost_center, justification}; submitted → manager_approved → approved (finance) when amount > $5,000, else submitted → approved; any step → rejected. This is the multi-level approval; the second approver is the finance persona.
3. **Vendor invoice** (`/invoice`, Finance): `vendor_invoice` {vendor, invoice_number, amount, po_number?, due_date}; received → approved → paid, or → disputed; a `po_match` flag computed by the server from the purchase requests when a PO is given (mismatch shown, not blocking).
4. **Access request** (`/access`, Security): `access_request` {system, role, reason, expires_on}; requested → granted | denied by the system owner; view: active grants expiring this month.
5. **Deal desk** (`/discount`, Sales): `discount_request` {account, deal_amount, discount_pct, reason}; submitted → approved | rejected by the sales manager; discounts ≤ 10% auto-approve on create (a declared rule, audited like any decision).

Each works through the existing action path ("Book me off Nov 24–26 for Thanksgiving, Sarah approves"), the records card's Approve/Reject, Slack (`/forma …`, approver DM), and MCP (`forma_draft_record` / `forma_draft_decision`). A third persona, **Priya Natarajan** (finance), is used for the second approval step on the local stand; on beta she is mapped when a third account exists (until then the second step is decided by Sarah, labeled). The OpenAI half of the cross-vendor act is covered on the local stand by a Claude Haiku "second vendor" agent loop calling `/v1/mcp` (DS entry; real OpenAI when Victor adds the key).

## Acceptance tests

- [ ] Each of the five apps: a rehearsed sentence and one unrehearsed sentence (real Haiku, smoke) produce a correct typed draft; Confirm files one audited record; the approver sees it live on the canvas and in Slack (loopback stub) and decides it; the filer sees the decision live.
- [ ] Purchase request over $5,000 requires both approvals in order; a finance approval before the manager's is refused; under $5,000 one approval completes it.
- [ ] Deal desk ≤ 10% auto-approves on create with an audit event; > 10% waits for the manager.
- [ ] Vendor invoice with a PO that does not match the purchase request's amount shows the mismatch flag.
- [ ] The instant matcher picks each app from its intent examples and never from its negatives; `/pto`, `/purchase`, `/invoice`, `/access`, `/discount` work; the library pane lists them under their categories.
- [ ] A Haiku-driven MCP agent (local stand) lists pending items and drafts a decision as the approver; the commit is marked "via" its token label.

## Verification

make_library.py --check; library tests; cargo test; the actions campaign extended to all five apps (Docker, loopback model stub); real-Haiku smokes; a browser walk with screenshots.

## Migration and rollback

No schema migration (record apps are library data). On beta the operator re-runs `seed-library` (adds the five apps; existing ones exact-match) and `grant-library-access` for each persona; the source objects for the new apps' views are uploaded like the others.
