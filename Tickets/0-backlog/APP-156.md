## Why

A useful expense app can show its overview first and let “New expense” open the admitted entry form. Before this implementation, the member document displayed forms inline, while canvas Focus could move a card into a dialog. The definition's `links` validates `from_view`, `to_view` and `input_id`; no runtime action dispatcher consumes it. The new typed button targets and narrow builder controls below address that gap. A decorative button or a hidden command shortcut would misrepresent the app.

## What changes

Add a closed, versioned presentation-action declaration with stable action IDs, bounded plain-text labels and exact same-definition component references. Initial behaviors are navigation to a component and opening a component in an accessible dialog, including an existing admitted command form. Keep action declaration separate from the existing data/view `links`; retain their meaning and compatibility. No arbitrary URL, script, expression, HTTP endpoint, cross-app target or automatic command execution is admitted.

Actions are app-agnostic: the creator chooses a label, behavior and target independently of the app's domain. “Log meal” is only a reference example. The same implementation must open a customer-details modal, an inventory form or an informational component, and navigate to an app section, without expense/restaurant/app-name conditions. The component supplies its content and the action supplies the interaction. Future behavior kinds extend this common contract rather than adding special-case app buttons.

Provide one narrow builder target picker using the currently edited definition's eligible components. It exposes the action's label, target and presentation behavior, with an honest unavailable state when no eligible target exists. Saving uses the existing draft/admission/publication path and exact version checks. A target removed or changed during editing produces an actionable validation error; do not silently retarget to a similarly named card or another work. This is the target-picker slice of APP-033, not a replacement for the full editor or APP-034's general patch/undo roadmap.

Resolve an action only within the currently authorized exact work and its admitted publication. Opening a form does not submit it. The form keeps its existing command ID, field schema, collection/record binding, server initial/transition restrictions, expected record version and idempotency behavior. Explicit Submit alone uses the ordinary audited command endpoint. Reopening does not generate a new command or silently lose an unsent draft; an uncertain outcome retains its original request key and retry semantics. Navigation must not fabricate a success receipt.

The dialog has a name, initial focus, inert background, normal field tab order, Escape/close behavior and focus return to the triggering button. Use the same component state where possible rather than cloning two independently submitting forms. Entering or leaving Focus/Unite must not stack competing traps. On narrow screens it remains reachable and scrollable. An authorized read-only component may open for a guest; a command form or write CTA never grants guest write authority and is omitted or clearly unavailable under ADR-014.

## Acceptance tests

- [ ] Normal builder controls link a named button to a real component without source edits or a model inventing code. The admitted action survives publication/reload and resolves the same target on canvas and member standalone presentations.
- [ ] Configure actions in two unrelated apps through the same builder: an expense-entry form and a customer-details or inventory component. Change their labels and targets independently, open the appropriate modal and navigate to a section. Both use the same action dispatcher/renderer with no domain-name branch or hard-coded meal behavior.
- [ ] Unknown action/renderer versions or keys, missing targets, duplicate action IDs/component placement, excessive actions, arbitrary URLs/code, cross-work references and stale target edits refuse as a whole. Existing `links` fixtures retain their original semantics; old definitions without actions remain usable.
- [ ] “New expense” opens the exact declared form without a POST. Explicit submit produces one ordinary audited command and visible matching receipt. Open/close/reopen and interrupted-response retry preserve draft, expected version and idempotency key; duplicate submission cannot create another outcome.
- [ ] A target's removal, publication drift, revoked membership/write permission or stale record version shows an honest refusal and no replacement target or unauthorized result, including when the change races a pending modal/command response.
- [ ] Keyboard and screen-reader checks cover trigger, dialog title, field tab order, Escape, pending/uncertain outcomes and focus return on desktop and narrow widths. Nested Focus/Unite interactions neither lose the form nor create competing active copies.
- [ ] View-only guests can use only permitted read navigation. A forged button/target/body cannot submit a record, gain another work, expose a sibling component outside the approved publication or bypass current share expiry/revocation.
- [ ] Leave a permitted guest detail/info component open in a dialog while its share expires, is revoked or loses its authority lease. Protected content in the dialog and any overlay clears within the same ADR-014 lease as the page, even if the component was moved outside its original container or into the browser's top layer. Reopening or changing accounts cannot revive the old content.

## Migration and rollback

Record the exact contract edition/version and legacy compatibility before adding action fields. A new action or target changes admitted presentation content and follows immutable publication and explicit work adoption; existing guest shares remain pinned and pause when ADR-014 requires it. No automatic migration retargets an old action. Keep existing inline forms as the compatible fallback for definitions that do not declare actions. A renderer rollback must still understand already admitted action versions or fail explicitly; it must never execute an unknown action.
