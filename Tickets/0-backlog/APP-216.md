## Why

The 2026-11-15 cost audit (Cost Explorer, one AWS account, no organization) found the beta costing about **$6.95 a day, about $210 a month**, while nobody uses it, against $38 for all of October. After the A14 cleanup it is about $208 a month. The main costs a month: the main task $69, two RDS instances $39, six public IPv4 addresses $22, the load balancer $17, KMS $17, the fAuth host $14, cross-zone traffic $9, Secrets Manager $8, the WAF $7. The parts that can come down without losing a guarantee are below. Each one is its own pull request.

## What changes

1. **The readiness probe's database traffic (about $14 a month and about 9% of the database's CPU).** `app/src/readiness.rs:62` runs the full probe every 15 seconds: 5,760 helper runs a day, each probing S3, KMS and both database pools. With no requests, readiness is the only caller of the structural catalog comparison (`storage/pool.rs`, `CATALOG_RECHECK`: "a new connection and readiness always run it"), which pulls about 1.4 MB per pool per run. That is the steady 372 KB/s (31 GB a day of cross-zone traffic), plus about 15,500 S3 writes and 31,000 KMS calls a day. Fix: compute the catalog digest inside PostgreSQL and compare 32 bytes, with the same comparison (an ADR-004 amendment to A5). Then make the readiness interval a deployment setting with today's 15 s as the default, and measure before changing it. Do **not** turn on S3 Bucket Keys as a shortcut: they change the KMS encryption context from the object to the bucket, which the per-organization key policies may depend on.
2. **The main task's size as a deployment setting, sized from the parser bounds (about $5–25 a month).** The task runs 2 vCPU and 8 GB around the clock. Idle it uses 3.4% CPU and about 160 MB, but that is not its sizing case: each parser host may use up to 2.5 GiB before the supervisor kills it (`supervise.rs`), and two may run at once (APP-215's parser bound). So memory must cover the parser bound times the RSS line plus the service, about 6 GiB today. Make cpu and memory stack parameters (the rule of A13: sizes are configuration, not constants for one scenario). Derive the memory from the parser settings and refuse a size below them. Then measure: 2 vCPU and 6 GB, or one parser at a time and 4 GB.
3. **The idle cost after the Dec 14 stop (about $105 a month with nothing running).** The services go to zero at the stop, but both RDS instances, the load balancer with its two addresses and the WAF, 12 KMS keys, about 18 secrets, the fAuth host and its address keep billing. Write and test a "park" procedure: final snapshots, delete the instances, the load balancer and the WAF, keep the keys. About $15–20 a month parked. Also write the matching "unpark". Decide by Dec 14 (follow-up A17).
4. **Cheaper equivalents, for the production environment (ADR-013).** None of these is a beta change, and each is a decision with a trade-off:
   - Secrets Manager (about $8 a month) to SSM Parameter Store SecureString (free standard tier).
   - One KMS key for the per-environment configuration secrets. Keep the per-organization keys.
   - fAuth's own RDS micro (about $14 a month) to a database on the main instance (VPC peering needed).
   - One EC2 host with Caddy, as fAuth already runs, instead of Fargate plus a load balancer and its addresses (about $100 a month down to about $25). This loses rolling deploys, and the promotion pipeline is built on ECS.
   - Cloudflare's free plan in front, for DDoS and rate limiting, instead of the AWS WAF ($7.20). This adds another vendor in the data path.
   - The fAuth host on `t4g.small` (ARM, about $1.50 a month less) once its image builds for arm64.
   - Reserved instances or Savings Plans, only once the production shape is fixed.
