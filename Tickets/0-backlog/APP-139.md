## Why

Reviewers will not accept a canvas that already holds apps and records. The link has to admit one new member into an empty organization, show an empty canvas, and carry one real workflow: describe an app, add one record, share it. That member is the only person on the canvas. The recipient does not already have an account. Opening the share takes them through identity-only signup and verified sign-in, then explicit acceptance. They arrive with no other apps and view the same live app without joining the owner's organization. A stranger cannot access its content. The entry for the first member is an invite, not a public signup. The recorded video of this path cannot run past three minutes. Someone using the link may take longer. The link is not cut to fit the recording.

## What changes

The later [ADR-014](../../docs/architecture/ADR-014-LIVE-APP-SHARING.md) and APP-154 supersede the original membership assumption: the recipient becomes a verified app guest, not a Northstar member. APP-154 owns the share authority, identity-only arrival and connected canvas implementation; this ticket qualifies that path in the complete trial.

Verify the first authoring transition implemented by APP-145. `Workspace::composer_context` stays read-only; intentional compose uses `prepare_composer`, selects an eligible owned app or creates the first shell, and retains the existing publication-policy requirement (`app/src/storage/composer.rs`). The clean dev stand still pre-creates a shell (`app/src/dev/db.rs`), so this trial must instead reach first compose through a real invitation/sign-in with no pre-created app. APP-145 owns that grant transaction; this ticket does not duplicate it. No server-side layout store or second demo mode.

Then a short guide on the empty canvas names the next moves. It does not read `GENUI_DEMO_MODE` and it does not use a rehearsed sentence. The app appears through compose and admission. The record is the existing command path. The share has to reach someone who is not a member yet. APP-154 now provides the separate private guest share path and identity-only signup. The legacy `share_work` route remains for same-organization workflow compatibility. The new recipient sees only accepted, still-authorized shares; acceptance does not create organization membership or place a card. The empty-canvas guide names Create → save a record → share a live page. No server-side layout store or second demo mode is added.

APP-154 implements a bounded operator invitation broker so in-product shares can start provider signup without a service restart. APP-140 now owns its actual service/configuration rollout. The hosted audit found fAuth permits one exact callback per client: each sharing-enabled organization needs a distinct `shared_client_id` registered for `/auth/shared/callback`, while the existing member client keeps `/auth/callback`. Missing guest-client configuration fails closed before creating a flow. Local provider tests now enforce that exact contract. No provider capability or management key enters browser state or the ordinary app's role.

The seeded two-window rehearsal stays in APP-096, APP-098, APP-105, and APP-110. It is not this trial.

## Acceptance tests

- [x] One invite admits a new member into an organization with no library apps, no placed cards, and no records. The canvas opens empty.
- [x] That member can describe one app and see it appear through the existing composer and admission path, including when they owned no app at sign-in.
- [x] That member adds one record through the existing command path. A shown number carries its receipt. Nothing uses `GENUI_DEMO_MODE` or a rehearsed sentence.
- [ ] The first member is the only person on the canvas. They share the app with someone who does not already have an account. The recipient completes verified identity-only signup/sign-in and explicit acceptance, arrives with no other apps, and sees the live app without organization membership. The unauthenticated landing is neutral and content/API access by a stranger is denied.
- [ ] A sanitized click log of the try-it link exists, and a recording of the same path stays within three minutes. Neither contains a credential, invite token, or model key. The link is not required to finish in three minutes.

- [ ] The pending share binds the organization, saved work, intended verified recipient and bounded permissions. An expired/revoked/replayed invite, wrong recipient or revoked sharer cannot grant access; retrying acceptance grants once. Share context survives signup without becoming a bearer grant to the work. Acceptance resumes the exact saved work and does not expose sibling works that share the same authoring app. Independently review this authority change (Tier A).
- [ ] The recipient opens the authorized view-only app page. If the owner enables Allow adding to canvas, the recipient explicitly adds a connected reference to their own canvas. A committed owner change reaches the open recipient view through reauthorized live updates; record measured latency and reconnect recovery. The app guest cannot write records; separate organization/member workflow authority remains independent.

- [ ] A recipient invited by an authorized in-product share can complete actual provider signup without an operator creating the invite by hand or restarting/redeploying the service. Capability delivery, failure recovery and revoke/expiry remain bounded and independently reviewed; no provider invitation secret enters browser state or logs.
