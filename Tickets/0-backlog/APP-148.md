## Why

APP-103 built weather, calculator, and clock. APP-120 added note and folder to the widget list and said a widget is ad hoc and per member. APP-143 wants to ask a widget, and APP-144 says a widget has no page. Those tickets need one definition of a widget so a calculator is not quietly turned into an app, and a folder is not quietly dropped from the list.

## What changes

Write `docs/planning/app-model/widget.md`. Read APP-103, APP-120, and `POST /v1/ask` in `app/src/composer/talk.rs`.

1. **Definition.** A widget is one member's one-off object on the board. Its presentation has no component hierarchy or app-page entry. Do not infer that its backing storage has no `app_id`: Notes uses an admitted app and saved work, and a folder can have an app association. The kinds today are weather, calculator, clock, note, and folder. Note keeps its private records and is still a widget to the member, as APP-120 says.
2. **What it can do.** It can be placed, restyled where it already has fields, and asked about once APP-143 adds a widget scope. Its widget presentation cannot be united into an app page or given components. Notes backing work and folders keep their existing authorized sharing paths.
3. **Boundary with an app.** An app presents admitted work. A widget is a presentation category and may still have governed backing; existing authorization must remain. Formation on a folder produces an app. That app is then an app. The folder remains a widget. This note states that handoff. It does not redesign it.
4. **Ask.** Today's ask scope is `card`, `app`, or `canvas`. There is no widget kind. The note says APP-143 is the ticket that adds it, and only for weather, clock, and calculator until a later ticket says otherwise.

No product code in this spike.
