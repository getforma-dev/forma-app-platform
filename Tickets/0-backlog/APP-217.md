## Why

Every refusal is `application/problem+json`. A person who opens a link in a browser sees the raw body, for example `{"code":"not_found","status":404}`. That happens with a mistyped link, a page that needs sign-in, a guest link that was turned off, a form that was open too long, an upload over the limit, a sign-in flood and an outage. For the class of Nov 28–30, those answers should say what happened and what to do next. The ADR-006 uniform refusal must stay intact, and every program caller must keep the exact JSON.

## What changes

1. **The layer** (`app/src/http/errors.rs`, installed in `http::uniform` and `uniform_with_many` just inside `finish`). It acts only on a top-level navigation: `Sec-Fetch-Mode: navigate` with `Sec-Fetch-Dest: document`, or, with no fetch metadata at all, a `GET`/`HEAD` whose first `Accept` media range is `text/html`. It also needs a refusal it recognizes: exactly one `Content-Type: application/problem+json`, a body of known length of at most 4 KiB, and exactly `{"code","status"}` for 404 `not_found`, 403 `cross_site`, 413 `payload_too_large`, 429 `too_many_requests` or 503 `unavailable`. Then the body becomes the rendered page. The status and every refusal header stay, in their order: `no-store`, `nosniff`, `no-referrer` and `Retry-After`, with `Content-Length` and any `Allow` dropped. The page's `text/html` type, nonce CSP, `Permissions-Policy` and opener policy follow. The header map is built fresh, never edited in place, so the wire order is the same for every way a path can miss. Anything else passes through untouched. A failed render, a page that is not a 200 HTML page with a policy, and a body the layer does not recognize each leave the original refusal byte for byte. The one exception is unreachable in practice: a body of known length that fails to read has already lost its bytes, so it answers a fresh 503 `unavailable`, never a partial body.
2. **The viewer** (`auth::cookies::viewer`). The variant is `member` when the workspace session cookie is present, `guest` when only the shared-session cookie is present, and `signed_out` otherwise. Cookies are read as everywhere else, so a duplicated or malformed cookie counts as no cookie. No session is resolved and no store is called. Only the 404 page varies by viewer.
3. **The page** (`app/admin/src/error/app.tsx`, `app/admin/src/styles/error.css`). It is bound as `error` like `denied`, with props `{status, title, text, signIn, workspace}`, and the closed copy is chosen in `pages::ErrorProps::new`. `SsrErrorPages` renders it. No route serves `/error`: the manifest route exists only to carry the page's CSS. The page has no script, form or cookie. The surge is CSS only: a label around the mascot, and a visually hidden checkbox placed after the buttons, so the Tab order is the brand link, the buttons, then the toggle. The styles reach the checkbox through `.lab:has(...)`. All motion sits inside `prefers-reduced-motion: no-preference`, and the dark scheme follows `prefers-color-scheme`.
4. **The mascot** (`app/admin/src/brand/forma-isotope.svg`). This is Victor's getforma.dev brand asset, byte for byte (SHA-256 `eb08ca0c…`, 141 KB, pure vector with no script and no external reference). `build.ts` copies it into `dist/` after each build, beside the font, because the build copies only `.woff2` from `fontDir`. It is served from `/_assets/forma-isotope.svg` without a hash and is revalidated by its ETag, like the font. `svgo` is not a pinned dependency, so the file is not optimized.
5. **The binaries** (`main.rs`, `dev/mod.rs`) bind the page before `finalize` and wrap the composed router with `ErrorPageLayer::new(pages, auth::cookies::viewer).serve(..)`. The qualification-harness composition gets it too. The HTTP smoke now sends one navigation to a protected path.
6. **The image allowlists.** Both image contexts admit every source by name. The root `.dockerignore` gains `app/src/http/errors.rs`, `app/admin/src/error/app.tsx`, `app/admin/src/styles/error.css` and `app/admin/src/brand/forma-isotope.svg`. `app/qualification/Dockerfile.dockerignore` gains `app/src/http/errors.rs`. The managed qualification's source bundle (`storage/managed_qualification.rs`) binds `errors.rs`. **This changes the deployment contract digest** from `main`'s `3493b0a68b08…` to `8578d6ac6fc9…`. A new page cannot avoid it, because its source files must enter the service context. This change is therefore not an ordinary promotion: it ships inside a reviewed contract-only release ([APP-210](APP-210.md)), with no migration and schema 24 kept.

## Acceptance tests

- [x] For each viewer variant and the same navigation headers, six requests give one themed 404 that is byte-identical apart from the per-response nonce: an unknown path carrying a marker in its path and query, `GET /admin` without access, `GET /admin?notice=<marker>`, `DELETE /admin`, `POST /admin/members/%FF/remove` and `POST /admin/members/<marker>/remove`. The page is `text/html` with the full CSP (`frame-ancestors 'none'`, `default-src 'none'`), `no-store`, `nosniff`, `no-referrer` and HSTS, with no `Set-Cookie`, no `Allow`, no script, no form and no marker. The same requests with `cors`/`empty`, an image, an iframe or `Accept: */*` stay the exact JSON bytes (`tests::browser_navigations_get_one_themed_404_whatever_the_path`, the real FMIR page; `http::errors::tests::navigations_get_the_page_and_everyone_else_the_exact_refusal`).
- [x] For the same request headers, the themed 404's headers go out in the same order whatever the path. A wrong method's `Allow` no longer reorders them (review MAJOR). JSON answers leave the new composition byte for byte and in the same header order as `main`'s `uniform` (`http::errors::tests::{navigations_get_the_page_and_everyone_else_the_exact_refusal, without_the_extension_every_answer_is_as_before}` against a replica of the old composition; `tests::browser_navigations_get_one_themed_404_whatever_the_path` with ordered comparisons and the exact header order).
- [x] An older browser (no fetch metadata, `Accept: text/html`) gets the page. `Accept: */*` and `Accept: application/json, text/html` get the JSON (both tests above; `http::errors::tests::a_navigation_is_navigate_to_a_document_or_an_old_browser_asking_for_html`).
- [x] 403, 413, 429 and 503 keep their status and headers and show their own words, identically for every viewer. 429 keeps `Retry-After` and shows the wait in plain words, such as "about 5 minutes" (`tests::the_other_refusals_are_their_own_page_for_everyone`; `http::errors::tests::{the_other_refusals_keep_their_status_and_headers_and_name_no_viewer, the_wait_is_plain_words_from_retry_after}`).

## Migration and rollback

No migration, no contract edition, no infrastructure and no operator change. The deployment contract changes only through the two image allowlists (item 6), so promotion needs a reviewed contract-only release. `build.ts` and the browser stage of `app/Dockerfile` are unchanged. Reverting the branch restores the JSON body for browser navigations and the previous contract digest.
