## Why

A typed view over records answers the uniform 404 when the list changes while the view runs: `record_query::release` returns `Denied` on a stale snapshot. The canvas then shows "You don't have access to this card". In class, any submission that lands while a view runs would show that to students. The APP-195 campaign found it.

## What changes

- `record_query::release` returns a typed `Stale` when the list moved, and keeps `Denied` only for a binding mismatch.
- The route re-captures once within the handler deadline. If the list is still stale, it answers `409 {"code":"stale"}`, which the canvas shows as "Updating…" and re-reads. It never answers the uniform 404.
- A revocation during the retry is still the 404.

It ships in release B; a fix-forward deploy before Nov 26 is allowed, since there is no migration.

## Acceptance tests

- [ ] A commit between capture and release gives `Stale`, never `Denied`. A changed binding or permission still gives `Denied`, and the route never answers 404 for a stale list.
- [ ] The route re-captures once, then answers `409 stale`. The canvas shows "Updating…" and re-reads. The guest page shares the 409 mapping; MCP maps `Stale` to its `stale` error output.
- [ ] A light Tier A check confirms no new disclosure: the answer is reached only after admission and carries no ids or values. The evidence is in `evidence/APP-198/`.
