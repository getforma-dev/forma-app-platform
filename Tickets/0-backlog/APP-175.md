## Why

Beta auto-promotion refuses any change to the schema manifest or deployment contract ([BETA-PROMOTION.md](../../docs/pitch/BETA-PROMOTION.md), `ops/promotion/runner.py` `bundle`). Each of PR #83 and #84 adds a migration, and `pool.rs` makes the service require the exact schema version, so merging either freezes every later beta release until the database is migrated and the idle promotion baseline admits the new manifest and contract. Schema 20 crossed that gap on 2026-11-04 by hand (snapshot, migration, baseline edit; [APP-167 log](../4-done/APP-167.md)); there is still no reviewed, repeatable procedure on `main`.

## What changes

Victor chose on 2026-11-05 to teach the promotion pipeline a reviewed schema-release mode, so the migrations ship with the one beta approval on the CI-qualified images. This replaces the earlier plan of a separate preflight, operator migration and baseline-admission helper. The procedure is [Schema releases](../../docs/pitch/BETA-PROMOTION.md#schema-releases); the decision is the [ADR-017 amendment](../../docs/architecture/ADR-017-BETA-PROMOTION.md#amendment-2026-11-06-reviewed-schema-releases).

1. **A committed, pinned release.** `ops/promotion/schema-release.json` names the baseline (schema 20 manifest and contract digests), the candidate (schema 22 digests), the unchanged CDK source digest and an expiry. `ops/promotion/schema_release.py` parses it strictly and pins the evidence path, both versions and the expiry in source. A CI test binds the file's `to` digests and infrastructure digest to `HEAD`. `candidate.infrastructure_digest` hashes `infra/src/*` and the four `infra/` project files in the contract's row format.
2. **Preparation.** `Runner.bundle` accepts a changed schema manifest or contract only when the release matches the baseline, policy schema version, qualified source, candidate manifest version, infrastructure and expiry, before the lock. The packet records `schema_release` with a deterministic snapshot name; the approval summary shows `schema 20 → 22` and the file hash, `preserved.schema: false` and the two added steps. New scan findings need a disposition bound to the release's `to` contract, as in a normal promotion.
3. **Execution.** The release is rechecked at execution start. After every final recheck, while beta still serves, a journaled manual RDS snapshot (bounded wait for `available`); a snapshot failure leaves the phase `prepared` and the release abandonable, keeping the snapshot. The final rechecks run again, then the outage: stop, the change set, the stopped boundary, one journaled run of the stack's migration task on the candidate image (bounded wait; exit 0, the candidate digest and `EssentialContainerExited` required), the stopped boundary again, activation. A migration failure keeps both services stopped and the lock held, with no activation, retry or replay. Execute carries one 55-minute budget that clips every wait.
4. **Admission.** On success the baseline takes the candidate's schema manifest and contract digests, the policy schema version becomes 22, and the completed record names the release hash, snapshot and migration task.
5. **Bootstrap.** The execute role gains only `ecs:RunTask` on the migration task family on this cluster, `iam:PassRole` of its two roles to ECS tasks, `rds:CreateDBSnapshot`/`rds:DescribeDBSnapshots` on the database and `forma-schema-release-*` snapshots, and `rds:AddTagsToResource` on those snapshots alone. Victor applies this once; nothing is applied by the change.
6. **Abandonment and restore.** `maintenance abandon` accepts one pre-outage snapshot in a prepared release, reads back an unknown outcome by name, and never deletes a snapshot; `release-rolled-back` refuses once a migration is journaled. `maintenance restore-after-failed-migration` (operator, hash-bound, fenced, plan then apply) returns the stack to the previous release after a migration that never started or stopped with a known non-zero exit code, and requires it healthy.
7. **Records.** The BETA-PROMOTION section, the ADR-017 amendment and [evidence/APP-175/SCHEMA-RELEASE.md](../../evidence/APP-175/SCHEMA-RELEASE.md).

## Migration and rollback

The approved promotion performs the migration. If it fails before committing, the database stays at 20 and recovery is operator reconciliation and a reviewed rollback promotion of the prior images. After it commits, the default is fix-forward; restoring the snapshot together with the previous images is a separately reviewed recovery.
