## Why

Two databases in this account are still PostgreSQL 16.13. The beta app database `genuisyntheticfoundation-database…` (`db.t4g.small`) has automatic minor upgrades off. The GateWasm staging database in stack `GatewasmStagingDatabaseStack` (`db.t4g.micro`) has automatic minor upgrades on, which is how that instance can drift from the pin without a reviewed change. Both were available on 2026-11-03 with no pending maintenance. Local dev and the current app pins use the same 16.13 image, `postgres@sha256:5d143123fdf80462d1778cd4f24b9f7ca13c87174bca19141fb194c5a1ebca59`. A historical local migration run used a different image and reported 16.15. That run did not change RDS.

On 2026-11-03 RDS in `us-east-1` offers PostgreSQL 16.3, 16.4, and 16.9 through 16.15. **16.15** is the newest 16 minor. The image promotion cannot apply it: that path may change only task images, services, and the stop schedule. The stack policy also denies replacing or deleting the database. Upgrading inside the current release would be the change that can break beta.

## What changes

Start only after [promotion run 41711515143](https://github.com/getforma-dev/forma-app-platform/actions/runs/41711515143) on `c192a90` has sealed, or after the release that supersedes it has sealed, and after `ops.promotion.maintenance inspect` shows no active lease.

1. Re-read the RDS PostgreSQL 16 versions in `us-east-1`. Upgrade both instances to 16.15 if it is still the newest offered minor. If RDS then offers a newer 16 minor, stop and record that version before changing either engine. Do not move to PostgreSQL 17 in this ticket. Use one version for both databases.
2. Snapshot each database first. Keep each existing identifier, endpoint, storage, encryption, deletion protection, backup retention, and parameter group. Each change set must be an in-place engine modification. Refuse it if CloudFormation would replace or delete the database.
3. Turn automatic minor upgrades off on both instances and apply the explicit version. GateWasm is included because its switch is still on. Do not leave it on after the upgrade.
4. GenUI is stack `GenuiSyntheticFoundation` in this repository. GateWasm staging is stack `GatewasmStagingDatabaseStack`, owned in `getforma-dev/gatewasm`. Change that stack in its own repository and change set. Do not try to edit it from this app template.
5. Upgrade one database at a time. GenUI first, then GateWasm. Sign-in depends on GateWasm, so expect a short auth interruption and confirm `auth-staging.getforma.dev` answers again before closing the ticket.
6. After the GenUI instance is available on the new version, move every current 16.13 pin to one inspected image digest whose `postgres --version` is that same minor. The copies today are `compose.dev.yaml`, `app/src/storage/qualification.rs`, `app/operator/check_image.py`, `app/operator/test_operator.py`, `app/qualification/local_harness.py`, `app/runtime/qualify_tenant_schema.py`, `app/runtime/qualify_migration.py`, `app/runtime/test_admission_operator.py`, and `evidence/APP-007/restore-local-sql/qualify.py`. Update the CDK engine in `infra/src/stack.ts` to the same version. Update the GateWasm stack's engine pin in the same commit series, in that repository. Do not reuse the historical 16.15 digest `ca0bd484…` unless inspection shows it is the intended image.
7. Re-run the migration qualification and the tenant-schema qualification on that digest. A local dev volume created on 16.13 can start on a later 16 minor. Do not reset it as part of the pin change.

## Acceptance tests

## Verification

Record the before and after engine version, snapshot identifier, and change-set summary for both databases, plus the qualification commands. Both upgrades are operator changes with Victor's approval. Neither is an automatic image promotion. Planning checks do not prove the upgrade.

## Migration and rollback

The application schema is unchanged. Rollback of either engine is a restore from that database's snapshot, not a task-image rollback. Do not start either upgrade while a promotion lease is held. A failed GateWasm upgrade must not be followed by the pin change.
