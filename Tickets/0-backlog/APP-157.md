## Why

APP-122 already judges an app theme with closed mode, accent and density tokens. That original path keeps its theme in an in-memory map and applies attributes to canvas cards; it remains separate from the new published presentation implemented below. A user opening the same app should see its intended appearance without rerunning Shape in each browser. Visual consistency must not remove receipts, obscure permission states or turn styling into executable content.

## What changes

Choose and document a small finite appearance vocabulary for the coherent app shell: reuse the current mode/accent/density tokens where suitable, with trusted accessible defaults. App-wide defaults belong to the admitted published presentation and are applied consistently to sections, controls and components. Any member-only local preference must be explicitly separate, must not overwrite the owner's published default and must not leak to guests. Do not store a shared default only in localStorage or reuse the saved-work display-name endpoint for appearance.

Add typed/versioned persistence through existing immutable definition admission and publication, plus a bounded direct picker and the existing Shape proposal/confirm path. Preview is clearly temporary; only the explicit authorized save/publish step changes the published appearance. Reload, another browser and authorized member/guest pages resolve the same default for the same publication. Existing definitions without appearance metadata keep the current safe default. Appearance changes retain exact-work identity and records, but are definition changes: guest grants remain subject to ADR-014 publication/digest pinning and do not silently adopt a new theme revision.

Trusted styles own color values, spacing, typography and component states. Reject raw CSS, HTML, scripts, URLs, arbitrary font/network loads, unknown keys/versions and unsupported tokens. Ensure contrast, visible focus, error/refusal states, receipt affordances and reduced-motion preferences cannot be hidden by a theme. Do not add a freeform design editor, alter data/query/command semantics, redesign library navigation or implement sleep/wake in this ticket.

## Acceptance tests

- [ ] A member previews and explicitly saves a bounded app appearance through normal controls or a reviewed Shape proposal. The admitted publication round-trips and produces the same default on canvas, member `/w` and guest `/s` authorized for that same publication after reload in an independent browser. An older pinned share is not silently updated for this check.
- [ ] Old definitions retain safe defaults. Unknown versions/keys/tokens, raw styles, markup, external resources and oversized payloads refuse without a partial save; compatibility fixtures preserve existing definition meaning and identity.
- [ ] Stale publication edits or absent edit/publish authority refuse. A guest or unrelated member cannot change the app theme through forged requests, and an unsaved preview never changes another browser's appearance.
- [ ] Theme publication preserves record values, commands, receipts and sibling works. Existing private shares retain their approved publication/digest and pause under ADR-014 when applicable rather than silently adopting changed definition content.
- [ ] Every supported token combination keeps text/control contrast, focus indicators, error/unavailable states, receipts and reduced-motion behavior usable on desktop and narrow widths. A theme cannot suppress protected-data invalidation or imply denied write access.
- [x] Retained native/browser evidence and independent review distinguish temporary local preferences from published defaults and identify the exact source/contract versions. No general-purpose CSS or full design-system customization is claimed.

## Migration and rollback

Prefer an optional, explicitly versioned admitted presentation field; preserve existing definitions and safe defaults. Do not mutate an immutable publication or bypass its digest for cosmetic convenience. If a storage change is required, add a separately qualified migration rather than changing schema 18 or old catalog pins. Disabling new theme authoring must not erase records or make accepted definitions executable; a compatible renderer fallback or explicit refusal is required.
