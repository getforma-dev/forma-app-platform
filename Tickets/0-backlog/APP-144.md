## Why

APP-142 is the app as a page on the canvas. Victor also wants that same app to be a page in the ordinary sense: a document you open, scroll, fill in, and submit. The canvas stays the board. This is the other view of the same saved work.

## What exists today

`GET /w/{app}/{work}` is already the work page (`app/src/query/routes.rs`, `work_page`). A live session is required. A query string is the uniform 404, because filters travel in bodies. The page is server-rendered from the work outline: the views and, when the member can write, a "New {schema} record" link per collection (`page::record_links`). The form posts to the same path. A link back to the canvas is `canvas_href`, `/canvas#g-{work}`. APP-005's full-page work view is this route. It is not yet the united app page, and the canvas does not offer it as "open this app as a page."

The model does not render this page. The trusted renderer does. That rule stays.

## What changes

1. From the app on the board, or from the APP-142 page, the member opens the page. The address is `/w/{app}/{work}` for that saved work. No new path is invented. No query string is added.
2. The HTML is the admitted app, in declared order: its views and its form, as one document. The renderer is the existing work-page renderer, extended to show those parts as the page rather than only the legacy run form. A generated definition cannot insert a tag, a script, an inline style, or a URL the renderer did not already allow.
3. The member scrolls, fills the form, and submits. The submit is the existing audited command route, the same one the canvas card uses. A governed number carries its receipt. A refused command leaves the page in place and shows the refusal. It does not navigate away.
4. The page offers a way back to the canvas for this work (`/canvas#g-{work}`), and the canvas offers a way to this page. Focus may open one part larger. Fan-out still belongs to APP-142 and still returns the parts to the board. The page and the board read the same saved work. A record added on one is visible on the other after refresh.
5. The address is what a share hands someone. APP-139 owns a recipient who has no account yet. This ticket does not change who may open the page: a member who cannot read the work gets the uniform 404, the same as today.
6. A widget has no `/w/...` page. Opening a widget stays on the board.

## What this ticket does not do

- It does not let the model, or the member, supply the HTML.
- It does not add a public unauthenticated page.
- It does not move filters into the URL.

## Acceptance tests

- [ ] The page address is the existing `GET /w/{app}/{work}`. A query string is still the uniform 404. No second path is added.
- [ ] The HTML is the trusted work-page renderer showing that app's admitted parts in order. A generated definition cannot add a tag, a script, an inline style, or a URL the renderer did not already allow.
- [ ] Submitting the form uses the existing command route. A governed number carries its receipt. A refusal stays on the page.
- [ ] A record added on the page is visible on the board for that work after refresh, and the reverse. Fan-out still returns the parts to the board.
- [ ] A member who cannot read the work, and a widget, get no page. The stranger's answer is the uniform 404.

## Verification

Read the work-page renderer and APP-142 before adding the address. One fresh-browser check on a worktree port: open the page, submit, and return to the board. Ports 4001–4003 and 4010 stay untouched.

## Migration and rollback

No migration. Removing the address leaves the app on the canvas as APP-142 describes it. Saved records stay.
