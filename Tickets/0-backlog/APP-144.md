## Why

APP-142 is the app as a page on the canvas. Victor also wants that same app to be a page in the ordinary sense: a document you open, scroll, fill in, and submit. The canvas stays the board. This is the other view of the same saved work.

## What exists today

`GET /w/{app}/{work}` is already the work page (`app/src/query/routes.rs`, `work_page`). A live session is required. A query string is the uniform 404, because filters travel in bodies. The page is server-rendered from the work outline: the views and, when the member can write, a "New {schema} record" link per collection (`page::record_links`). The form posts to the same path. A link back to the canvas is `canvas_href`, `/canvas#g-{work}`. APP-005's full-page work view is this route. It is not yet the united app document. Existing canvas app cards already offer "Open full page" (`canvas/render.ts`, `canvas/app.tsx`); the united-page header still needs that entry.

The model does not render this page. The trusted renderer does. That rule stays.

The November 1 implementation slice adds native inline create forms and current record tables, preserved source-query views/receipts, the united-header **Open page** link, and live enhancement. `Accept: application/json` on the same `/w/{app}/{work}` returns the same typed document after the same final authorization and publication checks. The browser builds a closed DOM vocabulary; it never parses response/model HTML or changes CSP. Commands use the existing audited route and idempotency keys. Unsent forms survive updates; an unavailable work clears forms and records.

This slice is deliberately incomplete: the existing `WorkOutline` includes qualified runnable source views, and the canvas helpers supply collection forms/records. It does not yet reproduce the full definition's `default_layout`, interleave every admitted view/form/note/status part, or render every additional primitive. The general admitted-parts/order acceptance stays unchecked. Existing query-run parameters and no-JavaScript record-form fallback remain as before. The unknown-recipient journey remains APP-139; no permission is added here.

## What changes

1. From the app on the board, or from the APP-142 page, the member opens the page. The address is `/w/{app}/{work}` for that saved work. No new path is invented. No query string is added.
2. The HTML is the admitted app, in declared order: its views and its form, as one document. The renderer is the existing work-page renderer, extended to show those parts as the page rather than only the legacy run form. A generated definition cannot insert a tag, a script, an inline style, or a URL the renderer did not already allow.
3. The member scrolls, fills the form, and submits. The submit is the existing audited command route, the same one the canvas card uses. A governed number carries its receipt. A refused command leaves the page in place and shows the refusal. It does not navigate away.
4. The page offers a way back to the canvas for this work (`/canvas#g-{work}`), and the canvas offers a way to this page. Focus may open one part larger. Fan-out still belongs to APP-142 and still returns the parts to the board. The page and the board read the same saved work. A record added on one is visible on the other after refresh. For the requested connected experience, the open document must also consume the existing reauthorized live updates for this exact work, preserve unsent form values and receipts, and recover after reconnect.
5. The address is what a share hands someone. APP-139 owns a recipient who has no account yet. This ticket does not change who may open the page: a member who cannot read the work gets the uniform 404, the same as today.
6. A widget has no `/w/...` page. Opening a widget stays on the board.

## What this ticket does not do

- It does not let the model, or the member, supply the HTML.
- It does not add a public unauthenticated page.
- It does not move filters into the URL.

## Acceptance tests

- [x] The page address is the existing `GET /w/{app}/{work}`. A query string is still the uniform 404. No second path is added.
- [ ] The HTML is the trusted work-page renderer showing that app's admitted parts in order. A generated definition cannot add a tag, a script, an inline style, or a URL the renderer did not already allow.
- [x] Submitting the form uses the existing command route. A governed number carries its receipt. A refusal stays on the page.
- [x] A record added on the page is visible on the board for that work after refresh, and the reverse. Fan-out still returns the parts to the board.
- [ ] A member who cannot read the work, and a widget, get no page. The stranger's answer is the uniform 404.

- [ ] An owner commit reaches the open recipient document without manual reload through the existing reauthorized event path; measure latency and verify reconnect/revocation behavior. It must not overwrite an unsent form.
