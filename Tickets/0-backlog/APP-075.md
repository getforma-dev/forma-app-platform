## Why

APP-008's schema, roles, pools and authorization are proven only on local PostgreSQL 16.13. The PH01 exit gate requires tenant isolation and authoritative identity checks on the actual managed path, and local substitutes are explicitly insufficient. This ticket carries [ADR-004](../../docs/architecture/ADR-004-TENANT-TRANSACTIONS.md) slice 3's managed obligations, moved here by [ADR-005](../../docs/architecture/ADR-005-PHASE-1-SEQUENCING.md), so the schema 2 foundation is qualified on RDS without serializing APP-073/010 behind a cloud window.

## What changes

Finish the frozen test-only [managed-entry draft](../../evidence/APP-008/native/managed-entry/HANDOFF.md) (`app/src/storage/managed_qualification.rs`) and its [incomplete independent review](../../evidence/APP-008/native/managed-entry/independent-handoff-review.md); add the focused closed-manifest, pin, deadline, private-file and sanitized-failure tests; run the confined local positive with the exact accepted RDS hostname as an internal Docker alias and an owned synthetic CA at the fixed path. Build a separate immutable qualification image from the production modules' `cfg(test)` executable with a private credential-refresh supervisor reusing `runtime.refresh/load/atomic_write`; package `apply_migrations`, `verify_schema_catalog`, `tenant_seed.seed`, the contract validator and exact fixtures for the separate migration identity; qualify the run-scoped advisory-beacon two-process race coordinator locally first. Then, inside one reserved window outside any auth rehearsal and with the service stopped, run the [managed plan](../../evidence/APP-008/managed-plan.md): observe and reserve, compare the schema 1 catalog before mutation, take and restore the pre-migration snapshot, apply every reviewed landed migration (0002 and any later one the source pins at that time, because the production binary refuses any other schema version) once and once again, seed the two fixture organizations, run the full matrix, qualify the production HTTPS surface from the exact managed image, then stop every task and clean up.

Never point the Docker-only `native_postgres_campaign` at RDS. The production service receives no test login, fixture endpoint or enabling header. The operator password and the four application role credentials stay in separate actors and separate task definitions. Keep the production bounds: two connections per role, eight total, five-second acquisition, three-second transactions, two-second cleanup. The declared RDS resource ID is a control-plane binding, not SQL attestation; the fixed-path CA hash proves self-consistency only, and the real package independently pins the reviewed RDS bundle with no mounts or overrides.

Keep this a reviewable L slice; the local entry/package/coordinator work and the single managed window are separately reviewable steps. Migrations landed after this window belong to APP-076.

## Migration and rollback

The pre-migration snapshot is schema 1; the known compatible service candidate is the qualified `8f8c34b` image. Switching the image back while the source remains schema 2 is not rollback. After a failed transactional migration, prove the source stayed at the exact version 1 baseline; after a committed upgrade, use a reviewed forward fix or the snapshot restore with an explicitly compatible image and a separately reviewed cutover. Never widen IAM grants or bypass the RDS replacement/deletion guard.
