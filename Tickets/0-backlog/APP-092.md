## Why

The pitch needs the canvas where the member already is: the signed-in workspace, with no organization picker.

## What changes

Mount the GenUI runtime canvas as an island on the workspace page, in the clone. The page is rendered under the session's tenant scope; the canvas receives only the data and definitions that scope authorizes; the organization comes from the session, never from the client. Measure the island (size, load) without gating on a budget (ADR-011 §4).

## Acceptance tests

- [ ] A signed-in member sees the canvas on the workspace page; an anonymous or non-member request gets the uniform 404 and no canvas assets.
- [ ] The canvas never offers or accepts an organization selection; the tenant is the session's.
- [ ] The island's measured size and load time are recorded as pitch debt for APP-097, not gated.
- [ ] Canvas content shows no value without its receipt where a governed number is displayed (see APP-094).

## Verification

Browser check in installed Chrome on the clone, plus the negative requests; sanitized screenshots and measurements only.

## Migration and rollback

Additive page change in the clone; removing the island restores the SSR workspace.

Scope widened by Victor in chat: the canvas is the signed-in workspace itself, `GET /canvas`, holding every saved work the member may open as a group of cards (its runnable views and its record forms), with an intent bar ("What do you need?") and an empty state of business intents. The page is Forma 3.2 native SSR (`app/admin/src/canvas/app.tsx`, `query::canvas`), `require_ssr` at start, `no-store`, and its content reads without JavaScript; one island (the intent bar) activates it and the board (`canvas/board.ts`) lifts the server-rendered cards onto the GenUI runtime canvas vendored from `forma-genui-runtime` 93c3871 (`app/admin/src/canvas-vendor/`, README records the source and the one added method). Look and interaction adapted from Forma Generative UI (`a108203`). Authorization is the work page's (`routes::member`, `Data::openable_works`, `Data::work_outline`): anonymous, pre-access, forged and foreign callers get the uniform 404, and so does a query string; the organization comes from the session and the page offers no picker. `GET /workspace` links "Open the canvas" and, per work, "Open on canvas" (`/canvas#g-{work}`). New JSON route `GET /v1/canvas/works/{app}/{work}` returns one group for the island to place (the composer and realtime seams), under the same listing authorization. Measured, not gated (ADR-011 §4): `/canvas` ships Forma 25,631 of 28,420 B and 50,060 B of JavaScript (gzip -9; canvas ceiling 373,760 B); first results 749 ms after navigation and placement of a new app 6 ms after the server answers, on the local stand. Pitch debt for APP-097: (1) the view layout (card positions, camera) is kept in browser localStorage per app/work, labeled "view layout only" on the page, never on the server; (2) the default layout re-flows client-side as results arrive; (3) the intent bar calls a stub seam (`compose.ts` `composeIntent`, `POST /v1/compose`) that answers "not connected" until APP-093 lands; (4) the live-update client (`live.ts`, server-sent events per organization) subscribes only when the server is configured with `GENUI_CANVAS_EVENTS_URL`; (5) the vendored canvas adds one public method (`moveItemTo`). Evidence (local, synthetic identities): Rust page test `canvas_page_renders_groups_cards_and_receipts_without_javascript`, route tests in `query::canvas::tests` (uniform 404 for anonymous, forged and pre-access sessions on both routes, nothing reaching the engine), and the Docker campaign `storage::query_qualification::canvas_campaign::native_canvas_campaign` (real sign-in; the canary member's canvas shows none of Northstar's works and 9 foreign, anonymous and forged requests get the uniform 404 with no dispatch; an app shared later appears).
