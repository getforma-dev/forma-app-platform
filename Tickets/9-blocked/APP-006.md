## Why

A principal, tenant or service-scope mistake can expose another organization’s work; this boundary must be proven before dependent integration. This ticket delivers: revalidate fauth contract and integration prerequisites.

## What changes

Confirm published/current deployment identity, registered client/PKCE/JWKS/tenant claims, key custody and failure behavior; retain adapter replacement seam; link rather than duplicate FORMA-247/248 follow-ups.

Keep this a reviewable slice: M means approximately 1–3 focused days. Re-estimate before selection and split the ticket if it exceeds five focused days. The estimate is a planning bound, not a delivery date.

Scope excludes production deployment and real customer data; this is a synthetic qualification. Upstream framework/auth changes remain with the FormaStack team.

## Acceptance tests

- [ ] Attach FormaStack-owned FORMA-247 evidence for the deployed login service, environment client registration, tenant branding and redirect/PKCE behavior at a pinned revision.
- [ ] Exercise issuer/audience/signature/expiry/kid/tenant claim verification and key refresh failure against the intended adapter contract; an unknown or invalid principal is refused.
- [ ] Record the deploy identity, bounded key-refresh behavior and live-service rollback/fallback boundary without bypassing authenticated membership or introducing a fake organization picker.

## Verification

Use positive/negative principal fixtures, two-tenant API/role tests and deployed identity or token traces with secrets redacted. Record the exact commands, environment, pins, expected/actual results and remaining limits in this ticket’s Log and `evidence/APP-006/` when implementation runs. Run this qualification in a small isolated, reproducible spike harness using the published packages; it does not wait for the full app scaffold. APP-007 later integrates the accepted contracts and checks. Do not substitute the planning-board check for runtime evidence.
