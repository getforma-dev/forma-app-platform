## Why

Merging currently runs tests but cannot deploy beta. Deployment depends on workstation-local qualified ARM64 images and a private ledger. A trusted promotion stage should deploy a reviewed merge with one approval and retain the same trial and release safeguards.

## What changes

A merge to the active trunk starts exact-source CI verification and unprivileged ARM64 qualification. A restricted preparation stage publishes the qualified bytes and prepares an immutable runtime-only change set. One protected beta approval releases execution and live verification. Canonical private state and an exclusive deployment lease replace workstation-only authority; legacy manual mutation paths must not fork that state. Dedicated OIDC and CloudFormation roles exclude the current administrator execution role.

## Acceptance tests

- [x] Exact merged source passes required push CI; all three ARM64 images qualify and their exact bytes/digests are promoted without rebuilding.
- [x] A concrete immutable release/change-set packet is visible before the single approval; stale/foreign/fork/modified artifacts and approvals refuse.
- [x] OIDC trust and environment branch/reviewer protection restrict deployment; Actions cannot reuse the administrator CloudFormation role or modify identity/secrets/schema.
- [x] One canonical encrypted private ledger/journal and whole-deployment lease preserve every previous window and budget; supported manual and Actions entrypoints cannot race or fork state. Actual cutover/readback and CAS denial probes are recorded in `evidence/APP-167/canonical-cutover.json`.
- [ ] Execution verifies exact change-set scope/ARN, both-service stopped boundaries, durable activation intent and healthy running digests/TLS probes; unknown outcomes reconcile without blind replay.
- [x] Rejection, cancellation, concurrency, malformed packet, schema mismatch and injected failure cases are tested; independent review findings are repaired.
- [ ] Actual GitHub-triggered approved promotion reaches AWS beta with original trial/alias/data preserved and sanitized evidence retained.

## Verification

Use focused unit/integration tests with recorded failing denial cases, workflow validation, repository checks, independent Tier A review, restricted-role bootstrap review, then one genuine merge-triggered promotion through the protected environment. Local tests or a workflow file alone do not pass the final acceptance item.

## Migration and rollback

No application migration is permitted by this stage. Preserve the original local ledger during verified import; switch authority only after matching hashes/history and enforcing manual-path refusal/coordination. Promotion failure holds a durable reconciliation record. Restore a compatible qualified runtime through a new reviewed window; do not assume database rollback or recreate trial identities.
