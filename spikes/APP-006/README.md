# APP-006 local identity consumer

**Local candidate only; APP-006 remains Blocked.** This reusable Rust library verifies the FORMA-247 baseline and an explicitly selected FORMA-248 access-only key-set profile. It returns an external identity, which the future application adapter must resolve to an invited subject and current membership before minting any session. It grants no application authority and does not implement APP-009. Its loopback issuer is a test fixture, not a replacement sign-in service.

## Source contract and integration seam

[`source-contract.json`](source-contract.json) binds inspected immutable Git blobs from `getforma-dev/gatewasm` at `f65c1948181554d30ad62549e35717eb8132f4f6`, the FORMA-247 reviewed source head. The upstream ticket reports a later merge, but that merge object was not available in the inspected local object database; this qualification does not claim its tree identity or a deployment. Selected files and byte hashes can be rechecked with `verify_source.py --checkout PATH`. CI without that separate repository checks the retained public fixture hashes and explicitly records that it has not rechecked upstream objects.

| Upstream file at that pin | Consumer obligation |
| --- | --- |
| `handoff/forma-247/README.md`, `handlers/token.rs` | Register a tenant/client's exact callback; tenant `/t/<slug>/auth/authorize` uses authorization code, S256 PKCE and state. Only the backend exchanges the one-use code at `/t/<slug>/auth/token`. Browser receives code/state, never access or refresh tokens. Client and redirect are exchange inputs, not inferred JWT audience. |
| `jwt/signing.rs`, `config.rs` | JWT is `EdDSA` with `typ=JWT` and `kid`. Claims: `sub`, `email`, nullable `name`, optional `tenant_id`, `iss`, string `aud`, integer `exp`/`iat`, `roles`, `auth_method`, `mfa_verified`, optional `cnf`. Issuer/audience are deployment settings (legacy defaults `gatewasm` / `gatewasm-app`); access lifetime defaults to 900 seconds but must be supplied from the intended deployment. |
| `jwt/keys.rs`, `handlers/jwks.rs`, `types.rs` | `GET /auth/jwks` has one public access key: `kty=OKP`, `use=sig`, `alg=EdDSA`, `crv=Ed25519`, unpadded base64url 32-byte `x`; `kid` is unpadded base64url of the first eight SHA-256 bytes of the public key. Cache-Control is `public, max-age=3600`. |

The public API is `Verifier::new(Config)` then `verify(token, expected_tenant)`. The owning server shares **one verifier per configured issuer per process**. `Config` explicitly selects `Forma247` or `Forma248AccessOnly` and supplies the exact expected issuer/audience, approved HTTPS `/auth/jwks` URL and maximum access lifetime. `expected_tenant` comes from trusted server-side tenant/client context, never a request body/header/picker. The result contains only issuer, subject, tenant, kid and issuance/expiry; role/email/name assertions never become app permissions. Debug and refusal codes contain no claims, tokens or endpoint values.

The intended app seam is: real hosted backend token exchange → this verifier → app-owned invitation/current membership resolution → session adapter. The latter three integration boundaries are not exercised against a deployed service here. A correctly signed unfamiliar subject returns an **external identity**, not an authenticated app principal. Thus APP-006's unknown-app-principal acceptance remains open until the membership consumer is qualified; the test explicitly avoids pretending a fabricated membership map proves it.

## FORMA-248 access-only compatibility

Initial inspection of `22652f8ef44bfb48184485045bf0f7f71eaf8e03` found current/next/previous access keys plus the immutable SSF key in the same unmarked public JWK set. That historical ambiguity remains recorded in the source manifest. GenUI requested an explicit selector, and the FormaStack owner supplied **`dfe7896826c4e1e3a616246fe6022d311cb38519`**: `handlers/jwks.rs`, `jwt/keys.rs` and `handlers/mod.rs` now publish access current/next/unexpired previous keys only at `/auth/jwks`, with the event key exclusively at `/ssf/jwks`. The JWK wire shape and cache headers are unchanged; there is no invented purpose field. `jwt/kms.rs` bounds previous keys to eight. The changed handlers, source tests and handoff have exact hashes in the manifest; their local inspection does not claim upstream independent review or CI.

The explicit `Forma248AccessOnly` consumer profile accepts at most ten unique, individually validated access keys and atomically replaces the whole set. It retains acceptance of a one-key legacy public endpoint, while the managed current/next/previous configuration has 2–10 keys; cardinality alone proves no custody. `Forma247` remains a strict single-key profile. Both fetch **only** `/auth/jwks`; no caller can substitute `/ssf/jwks` or combine key sets. The new tests use current/next/previous synthetic access keys and a separate SSF signer. A genuine SSF signature over otherwise-valid access claims and `typ=JWT` fails access-key selection, both initially and after an allowed refresh; a rewritten access kid fails signature verification. Ordinary `secevent+jwt` is also refused.

Prepublished next keys verify from the fresh cache during cooldown, and old/new access keys coexist during overlap. Retirement becomes visible only after an allowed authoritative key-set replacement or cache expiration: public JWKs do not contain retirement timestamps, so a still-fresh cached matching key remains usable subject to token expiry. This is not immediate revocation. The issuer owns its publication, lifetime, fleet-drain and retirement rules; GenUI has not exercised those against KMS or a deployed service. A future contract change requires a new source binding and requalification; runtime profile selection is not an availability fallback.

## Bounded behavior and refusals

| Boundary | Implemented policy |
| --- | --- |
| Token | At most 8 KiB, exactly three canonical unpadded base64url segments; fixed Ed25519 verification over the original signed bytes; 64-byte signature; fixed header fields. External `jku`/`jwk`, alternate algorithms/types, duplicate or unknown JSON fields and malformed encodings fail. |
| Claims | Exact issuer and string audience; bounded nonempty subject and tenant; signed tenant equals the trusted expected tenant. Integer timestamps only, strict `exp > now`, `exp > iat`, future `iat` at most 60 seconds, lifetime no greater than the explicitly configured cap. Expiry is rechecked after fetch. Non-null `cnf` is refused because DPoP proof validation is not implemented. No expiry grace. |
| Transport | Exactly the configured HTTPS endpoint in production, TLS verification enabled, no redirects, system proxies, automatic request retries or decompression. The private test constructor permits only loopback HTTP. Token bytes are never sent to JWKS. Connection timeout 1 second; whole verification deadline 2 seconds starting before parsing and including mutex wait, DNS/connect/response/body, signature and final identity-release check. A partial-body trickle cannot restart the deadline. These local caps are stricter than design §6.7's 2-second connect / 5-second fAuth request maxima. |
| Key body | Require 200, JSON content type, no encoded response, at most 64 KiB from both Content-Length and cumulative streaming. Closed public-key shape and profile-bounded key count; reject duplicate kids and any invalid member before installing the set; independently recompute `kid` from the 32-byte public key. No private fields. |
| Freshness | Require one usable Cache-Control, at most one Age, clamp max-age to 3600 seconds, subtract Age. Expiration starts before the request, not at response arrival; no stale grace. The key generation and freshness are checked again under the cache mutex at identity release, after the final awaited lock and token/deadline checks; a replaced or expired key lease is refused. |
| Fetch budget | At most one attempted refresh every 60 seconds per shared verifier, including failed, canceled and unknown-kid attempts. The mutex covers refresh, so simultaneous misses share the budget. A new kid arriving during cooldown is refused, even when rotation is legitimate; an already cached matching fresh key still works. This is not a distributed fleet quota. |
| Failed refresh | An allowed attempt invalidates the previous key before I/O. Failure or cancellation leaves no sign-in authority. An attacker with a syntactically valid unknown kid can therefore cause new sign-ins to fail during an issuer outage until the next permitted successful fetch. This deliberately favors fail-closed sign-in over retaining previously fresh authority after a failed authoritative refresh; it is an availability tradeoff, not cache poisoning. Unknown kids never get installed, and cannot extend cache lifetime without a successful authoritative response. |

Deadlines use Tokio timers with a final monotonic release fence, not a real-time OS scheduling guarantee. The HTTP future is canceled on deadline; a platform resolver may finish its already started system lookup independently. No detached issuer refresh task can later install keys. Input limits and one shared attempt budget bound work; application-wide login admission/rate limits remain integration work. Existing app sessions are outside this crate and cannot be created, revoked or extended by it.

## Verification and reproduction

Requires Python 3.11+, Rust 1.93.1 (recorded `rust-toolchain.toml`), and at most two Cargo build jobs. All tests exercise this candidate verifier, with ephemeral real Ed25519 keys and actual loopback HTTP transport. They cover positive identity, wrong signature/issuer/audience/tenant, integer/expiry/iat constraints, role non-authority, duplicate JSON, unsupported token types, malformed/oversized bodies, redirects, slow trickle, concurrent refresh budget, cancellation, key replacement/cooldown, prepublished multi-key overlap, retirement after observed replacement, SSF cross-purpose refusal, outage/recovery and no stale grace. Long cache intervals are advanced through private test state; network and lock deadline trials use real elapsed time.

`claims-247.json` has the actual source field names/types with conspicuously synthetic values. `jwks-247.json` applies the actual source JWK shape to the public key from [RFC 8032 §7.1 test 1](https://www.rfc-editor.org/rfc/rfc8032.html#section-7.1); its expected kid was computed independently with Python hashlib. No private key, signed JWT, browser credential or real identity is retained.

From this directory:

```sh
python3 qualify.py --output ../../evidence/APP-006/local
# Optional extra read-only source recheck, when the independent upstream repo is available:
python3 verify_source.py --checkout /Users/victorvillacis/dev/Forma/work/FORMA-247/gatewasm
```

The runner records exact source hashes, toolchain, registry licenses/checksums, command output and exit codes. It runs `cargo fmt --all --check`, `cargo clippy --locked --all-targets -- -D warnings` and `cargo test --locked -- --test-threads=2 --nocapture` with `CARGO_BUILD_JOBS=2`. The workflow performs the same checks on Ubuntu and retains artifacts. Local results are in [APP-006 evidence](../../evidence/APP-006/README.md); CI is only passed when an actual run receipt is recorded there.

Dependencies are exact released versions with a Cargo lock: base64 0.22.1, ring 0.17.14, serde 1.0.229, serde_json 1.0.154 and Tokio 1.53.3 match versions already used in this app; reqwest 0.12.28 is also locked by the inspected auth repository. The fixed [ring Ed25519 verifier](https://docs.rs/ring/0.17.14/ring/signature/index.html) keeps cryptography outside our parser; [reqwest's client controls](https://docs.rs/reqwest/0.12.28/reqwest/struct.ClientBuilder.html) supply verified TLS, total timeouts and explicit redirect/retry/proxy policy. Serde derives enforce closed/duplicate-field refusal. Cargo resolver 3 keeps the declared Rust 1.85 floor compatible while the tested toolchain is 1.93.1. No framework or app dependency upgrade is made.

## Remaining acceptance

[APP-006](../../Tickets/9-blocked/APP-006.md), design [§6.1, R15, TH2, §10.5](../../design/forma-generative-app-platform-v2/design.md), and [PH01 quality gates](../../docs/planning/QUALITY-GATES.md) still require a deployed revision/image/health receipt; approved GenUI callback and registered tenant/client; real PKCE/state/one-use/backend exchange; sanitized observed issuer/audience/lifetime/JWKS and tenant behavior; app unknown-principal/membership denial; hosted outage/recovery and rollback boundary. The known GateWasm environment was deleted, and this work does not rebuild it. The access-only source compatibility profile locally covers key selection/overlap, but KMS custody, real fleet publication/drain, live rotation and the observed deployed endpoint separation need their own evidence. No acceptance box, board status or Phase 2 predecessor changes follow from this local candidate.
