# Security review: the Forma company app platform (design.md, 2026-10-22)

Reviewer: a fresh security reviewer with no prior knowledge of the project. Read: `design.md` sections 4 (SR1 to SR12), 7, 10, appendix D, with sections 6, 8, 9 and 11 for consistency; rendered pages 24, 26, 29 and 31; `reference/CHECKLIST.md` R6, R16, R21; `reference/GUIDE.md` section 3 item 10. Nothing else.

Severity: **blocking** fails a gate item outright or leaves a top-ranked requirement (N7, N8) unprotected; **major** is a design gap or inconsistency a professional would close before build; **minor** is a wording, placement or completeness fix.

Counts: 1 blocking, 9 major, 14 minor.

## Verdict

This is a serious threat model, well above what most design records carry: boundaries keyed to the DFDs, a trust-level table that includes service identities, six invariants with enforcers, an entry-point table, an asset table that counts caches and logs, an attack tree for the top goal, a data dictionary with a key-lifetime table, a security-event table, fail-closed stated for the controls, crypto-shredding designed, and every one of M1 to M49 restated in an SR with a test. The record's structural choices (typed definition with no URL, path, id or grant type; one authorization point; disjoint database roles; receipts re-authorized before release; the fenced commit) are the right ones for a multi-tenant platform with a model in the loop.

It does not pass R6 as it stands: 21 of 28 threat rows (appendix D) drop the threat grammar, the invariant, the existing-control and the response columns. And four design-level gaps need an answer before the model's residuals can be believed: the node-local plaintext revision cache that no store, dictionary or shredding step names; the parser sandbox's "no network, no credentials" claim with no mechanism on Fargate; the assistant's `query` tool, whose results may re-enter the provider request; and the operator's own identity and sign-in, which the operator-access design never specifies. Hold for the fixes below; no rewrite is needed.

## Blocking

**B1. R6, appendix D (TH8 to TH28).** The 21 register rows carry "the threat in one clause", no invariant, no existing-control column, no response column and no status column. R6 requires each threat to be a full statement (source, prerequisites, action, impact, asset) citing a boundary and an invariant, with existing controls separate from mitigations and a response type per row; GUIDE 10.4 says the appendix holds "the rows beyond the top ones", not a thinner table. As written, TH12 (fAuth's cookie behaviour), TH25 (Forma's nonce CSP, marked [built] inside the mitigation cell) and TH6-adjacent rows mix built controls into proposed mitigations, so the likelihood ratings "against [built] controls" cannot be checked. **Fix:** give appendix D the same columns as 10.4 (the invariant and response columns are one token each; the statement can stay compact by naming source and prerequisites in the first clause: "A builder (TA3) with a seat can ... which leads to ..., impacting AS3"); move [built] items into an existing-control cell; add a response token (mitigate, accept) and status per row rather than the one sentence in the header.

## Major

**1. R16, sections 5.2, 6.1, 6.7, 11.4 versus 7.2 step 2, 7.3 step 2, 10.2 entry table.** Sections 5.2 and 6.1 say published apps serve from the workspace server's own `SELECT` of publication rows and the control plane is off the hard path (6.7, 11.4: "control plane down ... published apps serve"). Flow 2's F29 and flow 3's F44 route the current-publication read and the record-schema compatibility check through P3, and the entry-point table lists F29 and F44 as calls to the control plane. One of the two is wrong; the difference decides whether B3 is on the published-app path (SLO1, blast radius, TH8's elements). **Fix:** pick one. If P2 reads publication rows, redraw F29 and F44 as P2 to DS1, drop P3 from diagrams 05 and 06, and remove F29/F44 from the entry table's control-plane row; if P3 serves them, correct 5.2, 6.1, 6.7 and 11.4 and add the control plane to the hard chain.

**2. R21 data dictionary, 10.2 assets, section 8 crypto-shredding; sections 6.3 and 11.2.** The data task holds "50 GiB of disk for every live revision", decrypted under each organization's key "into a local cache keyed by digest", plus a 2 GiB in-memory result cache across organizations. Neither is a DS element, neither appears in the data dictionary or the asset table, and the deletion story (key disabled, objects unreadable) does not reach a plaintext copy on an ECS task's ephemeral disk. TH17 names backups, cached data keys and restored environments, not this cache; TH9's confinement to "that organization's directory" presumes a per-organization directory layout the record never states. AR2 says a compromised data service reads every revision, and this cache is why. **Fix:** add DS7 "revision cache (local, decrypted)" to diagram 05 and the dictionary (Confidential; Fargate ephemeral storage encryption; a directory per organization, `0700`; evicted on tombstone, key disable or deletion; wiped on task replacement; capacity and eviction policy); extend TH17 and M34 to it; add it to AS4's reach list; add the eviction check to the restore and deletion drills (SR11's test).

**3. TH4 / M8, section 6.4, SR5.** "A child process with no network and no credentials" is asserted, not designed. On Fargate every process in a task shares the task's network namespace, the task-role credentials endpoint (`169.254.170.2`) and the NAT route; custom seccomp profiles and privileged namespaces are not available. A parser exploit therefore reaches the worker's provider key and S3 under the organization's context unless the sandbox is a separate container or task with no task role and an egress-denying security group, with bytes carried across a channel the record names. TH4 is a High/High row whose residual Low rests on this. **Fix:** state the mechanism (a separate ECS task or container with no task role, security group with no egress, bytes in and out by the host over a local channel; or a syscall filter proven in CI if the runtime allows it), and make SR5's test include "the sandbox cannot reach the credentials endpoint, S3 or the provider host"; until demonstrated, TH4 residual Medium.

**4. D13, 6.4, TH19 / M38, N8, SR4.** The assistant has a `query` tool. If a tool result (rows, totals) returns to the model's context, the next provider request on F12 carries evidence outside the policy's named fields, which contradicts 7.1's "never evidence" and N8, and makes injected text a one-step exfiltration (AG5: steer the model to query, then read the result back). The explainer's path is defined (a receipt and the policy's named fields); the query tool's is not. **Fix:** state that assistant tool results go to the canvas under the member's session, that the model receives only the receipt (and policy-named fields) and never rows, enforce it in the worker's request builder (M38's refusal before egress), and add it to SR4's test corpus.

**5. New threat; SI2's enforcer list; D10, 6.1 ("a timeline as SVG strings", "SVG from strings").** Definition strings (titles, labels, notes, descriptions) are proposed by the model, edited by builders, and rendered to other members, the reviewer's inbox first; evidence values flow into labels. No row covers stored markup or script delivered through a definition or an evidence cell into another member's browser (STRIDE T/E across B1 on F18, F19, F38, F39; SI2). SVG assembled from strings is the sharp case. 10.2 names "the renderer library's typed props, which take no markup" as an SI2 enforcer while excluding the island from the TCB; an invariant cannot rest on client code (ASVS 1.4.4). **Fix:** add TH29: a builder, the model or an injected cell with a seat can place markup in a string field, leading to script or links in a reviewer's or practitioner's browser, impacting AS1, AS3; prevent: the view server builds SVG from numeric props only, every string escaped at render, string fields bounded in length and charset at admission; detect: a hostile-definition corpus in CI; existing: Forma's nonce CSP and `frame-ancestors 'none'` [built]. Move the SI2 enforcer from the renderer library to the view server's prop resolution.

**6. SI5, SR10, M22, 6.3.** Three roles (`workspace`, `control`, `data`) append their event kinds into one hash chain per organization. A chain needs a serialized previous-hash; the record never says how three concurrent writers get it. Either every record command and session event takes a per-organization chain lock (a contention point the capacity numbers do not carry) or the chain forks and verification fails. **Fix:** one chain per (organization, writer kind), each head anchored every 15 minutes, or a single audit-sequence row per organization with its lock named and costed; state which in 6.3 and M22.

**7. R21 operator access; 10.5, TH7 / M14, AS8.** The operator (TL5) is the highest-privilege human and the record never says how they authenticate: which identity provider (an fAuth tenant? the AWS console?), whether a hardware key is required for the operator session, how the just-in-time grant is requested and recorded, and who the "named outside reviewer" of breakglass CloudTrail is. Under A8 (one founder) that reader may not exist, which makes TH7's residual Medium rest on an unnamed control. **Fix:** design the operator sign-in (provider, MFA or hardware key, session lifetime, same cookie rules), the just-in-time request and approval record, and name the breakglass reader's role (counsel, advisor, a customer's administrator) and what happens when there is none, as an explicit clause in AR1.

**8. 10.4 scale versus ratings (R6, R24).** The record's own line says Low likelihood is "a compromised role, vendor or key" and High "needs only a seat, a file or text". By that line TH2 (fAuth key), TH6 (vendor), TH7 (operator credentials), TH8 (compromised role) and TH11 (compromised role) are Low, yet rated Medium; TH5 (a builder patching after approval, existing control "none"), TH9 (a typed query from any seat, confinement proposed not built) and TH20 (shared work or export from a seat, nothing built) need only a seat, yet are rated Medium, Medium and Low. 13.1 ranks on the same scale. **Fix:** either widen the definition (Low: a compromised key or vendor; Medium: a compromised role, a phished member, a mistake) or re-rate. Rows I would re-rate on the current wording: TH5 to High/High, TH9 to High/High, TH20 to High/Medium; impact of TH19 (Confidential data to a third party) and TH22 (rows in logs the operator and every role can read, outside the organization's governance) to High, since both cross the organization's governance exactly as a cross-organization leak does; both already carry a preventative and a detective, so the status column survives.

**9. TH4 existing control.** "The prototype's 5 MiB, 2,000-row browser cap [built]" is a donor prototype's control (section 2), not one in this system; rating likelihood against it understates the row. **Fix:** "none"; likelihood stays High.

## Minor

1. **F49 (adoption), F29/F44.** No row covers adoption: a compare-and-set to an incompatible publication, or a rollback that revives access (R10 says blocked). Add a line to TH5 or a short row, and a one-line reason for the response arrows (F47, F48, F50, F51) having none.
2. **TH22, TH27** cite elements but no boundary or flow; R6 asks for a crossing.
3. **SR grouping and wording.** M36, M37 (index isolation) and M39 (shared work, export) sit under SR11 "minimised and shredded" rather than SR1 or SR7; M44 (job lease) under SR12; M49 (deletion hold) under SR9; M40 (fenced commit) under SR2. SR9 reads "destructive changes two-person after 24 hours", which fuses M14 (two people) with AR1 (a 24-hour hold instead of a second person); write both.
4. **Sign-in handoff** (6.1, 10.5, TH3): state the algorithm allowlist (EdDSA only, no `none`, no RSA fallback), `iat`/`nbf` skew, that the pre-session cookie is deleted and the session id freshly minted at the callback (fixation), and that any return-to path is validated. M3 says "an invited `sub`"; since membership is the platform's own (D6), say "a `(tenant_id, sub)` with a membership row this organization's administrator created", which also sharpens TH2's blast radius to existing members.
5. **Service tokens** (10.5, M16): say how a callee obtains and trusts the caller's hourly certificate and KMS public key, and bind a token to one request (`jti` plus a body digest), since AR3's plaintext makes a 5-minute replay to the same callee cheap.
6. **10.5 "the only long-lived secret is the provider's key"** versus the secrets table, where the fAuth client secret lives a year.
7. **SA4 as an explicit accepted risk**: an administrator can switch policy to owner publication and publish alone, add themselves as reviewer where policy allows, or remove the last administrator; say what the platform refuses (last administrator, self-approval) and record the rest as AR12 with the audit as the control.
8. **Exports and uploads**: add a detective on export volume per principal (exfiltration by a legitimate member is the common case); say A4's byte cap is enforced at P2 before F4 streams to S3, and that file names are never used as keys (the digest is).
9. **Assets and entry points**: the migration credential (table owner, `BYPASSRLS`) and the canary organization's own credential are assets with no row; the release path into the VPC (tag, OIDC role, task definition) is an entry with no entry-table row.
10. **TH12** fuses two sources with different likelihoods: a removed member (High, a seat) and a stolen cookie (Medium, phishing); split or rate on the higher.
11. **Approval over a synthetic preview**: the reviewer approves a digest whose behaviour on real data they have not seen unless policy allows a read preview; make it an explicit accepted risk beside AR11.
12. **TCB**: 6.3 puts DuckDB "in the trusted base" but SI1's enforcers omit P4's confinement; add it, or the TCB statement in 10.2 is incomplete.
13. **Restore drill**: the isolated account receives every organization's data; say who reaches it and that the just-in-time rule applies there too.
14. **Explainer output** is free text shown to the member; AR11 covers proposals, extend it to explanation text as a social-engineering channel (an explanation that tells the practitioner to approve or export).

## Checks that hold

- Trusted computing base: SI1 to SI6 with enforcers, the composer, model, index and island excluded (10.2); consistent with 6.1 to 6.4 except minor 12 and major 5.
- Entry-point table, asset table, trust levels with service identities: present and keyed to flows.
- Operator access: just-in-time with the administrator's one-hour approval, sealed breakglass behind a hardware key with CloudTrail to an outside reader, two-person for deletion, key disablement, mass sign-out and permission-table changes; AR1 accepts the one-person case (major 7 for the gaps).
- Data dictionary with flows and retention; per-hop protocol; key hierarchy; key-lifetime table with rotation triggers and emergency paths; security-event table with tamper protection; fail-closed stated per control in 10.6 and matched by 11.4 ("nothing fails open"); revocation at scale through the epoch; crypto-shredding in section 8 (major 2 for the cache).
- Sign-in: authorization-code with PKCE S256 on the back channel as a registered client, `state` on a 10-minute pre-session cookie, offline EdDSA verification by `kid`, one key-set refetch a minute failing closed, the token never re-presented, `__Host-` `HttpOnly` `Secure` `SameSite=Lax` cookie, `Sec-Fetch-Site`/`Origin` on state changes, `frame-ancestors 'none'`.
- Service tokens: 5 minutes, caller, callee, organization, principal, epoch; callee re-reads membership (SA2); disjoint database grants; 15-minute IAM database tokens.
- DuckDB confinement: typed operations compiled from the admitted tree, read-only instance, autoload off, no `httpfs`, external access limited to a directory, 2 threads, 1 GiB, deadline, per-query S3 session scoped to the prefix; hostile-view corpus in CI.
- Idempotency: key scoped to (organization, principal, work, command, key), outcome checked before the version, a changed payload 409, the pre-activation key minted per render per principal, 24-hour outcomes; consistent across 6.3, 7.3, 9, TH16.
- Audit: insert-only grants by role and kind, `owner` only by breakglass, hash chain anchored to Object Lock compliance mode every 15 minutes, 30-minute alert, AR9 names the window (major 6 for the writer serialization).
- Prompt injection: untrusted text only in delimited data fields, five tools with no publish or policy tool, whole-output validation against a grammar with no URL, path, id or grant type, admission re-check, inputs bound under the binder's authority, the explainer refusing numbers absent from the receipt, the user submitting every mutation, adversarial suite each release, AR11 for the valid-but-wrong case (major 4 for the query tool).
- SR1 to SR12 cover M1 to M49 completely, each with a test, inspection or demonstration; M5 marked deferred and lowering nothing.
- Shared responsibility, non-Byzantine assumption with one-binary consequence, internal callers untrusted, risk profile, DPIA paragraph, actors including insiders, future management, compulsion and an acquirer, attack tree for AG1, maintenance trigger with an owner: all present.
