## Findings

### Blocker

**B1. The `pitch` CI campaign fails on this revision.**
- **What I reproduced:** `pitch` runs in `.github/workflows/pitch.yml:56`. Its adapted-work check expects the exact chip list (`app/src/storage/pitch_qualification.rs:854`). The adapted work now also binds a catalog source, so it gets "Sample data". The label is correct here, but the assertion was not updated.
- **The next failure, found by reading but not run:** the same campaign then calls `equivalent_reads` (`pitch_qualification.rs:1550-1551`). That function asserts that the batched and serial outlines are equal (`canvas_campaign.rs:108`), and `WorkOutline` derives `PartialEq` (`queries.rs:918`).
  - `work_outline` sets `sample_data` (`queries.rs:1125-1132`).
  - `work_reads` never does. It builds outlines through `outline_of` and `outline()`, which hard-code `false` (`queries.rs:621-630`, `:1074`; `actions.rs:332-345`).
  - Maya "holds the whole library" there (`pitch_qualification.rs:1538-1539`), so every library work will differ.
  - The `canvas` campaign passes only because its works use non-catalog sources.
- **Fix:** compute `sample_data` in `work_reads` too (see M1), then update the `:854` expectation.

### Major

**M1. The chip is missing wherever the outline comes from `work_reads`, and after "Back to standard".**
- **SSR `/canvas`:** the page builds its restored and pending groups from `read_works` → `work_reads` (`query/canvas.rs:1700`, `:1746`). Their outlines carry `sample_data: false`, so `assemble` adds no chip (`:1493-1495`).
  - The island adopts these server-rendered groups as they are and does not fetch them again (`admin/src/canvas/board.ts:1621-1633`).
  - So on first paint, a library work holding records that wait for the member's decision has no "Sample data" chip. That is the expense-approval path. The same app placed later through the JSON route (`ensureAppGroup`, `board.ts:716-735`) does have it.
- **"Back to standard":** this button calls `swapGroup(…, ['retrieved'])` (`board.ts:1230`). When labels are given, `buildGroup` ignores the server's `origins` (`render.ts:456-458`), so the chip is dropped.
- **Fix:** one batched `work_bindings` statement over `readable_keys` in `work_reads`, which fixes the SSR page and B1 together. In `buildGroup`, keep a server `sample` origin even when composer labels are given.

**M2. `forma_list_apps` marks every listed app as sample data, including the member's own apps.**
- `sample_library` depends only on the compiled-in catalog (`mcp/tools.rs:482`). It is set on every entry (`:508`), and the summary says "Library apps start on sample data." (`:534-535`). That happens in every organization, even one with no library seeded.
- `context.library` is not limited to catalog apps. It holds every app the member may discover and run whose inputs can be bound (`storage/composer.rs:379-410`).
- The member's authoring shell has `discover` and `run` (`migrations/0016_authoring_shell.sql:57`). Once it publishes a generated definition bound to the member's own folder upload, that app is listed with `sample_data: true`. A fixture app such as Northstar's outbound app is also marked, though it reads no catalog source.
- This is the reverse failure: the member's own data called sample. `forma_run_view` gets it right because it uses the work's bindings.
- The MCP campaign cannot catch this: it has a single library app, and that app is a catalog app (`mcp_campaign.rs:600-604`).
- **Fix:** set the flag per entry, either by membership of the entry's `definition_digest` in `library_sidecar()` or from the sources the entry would bind.

**M3. The box 5 tick overreaches.** The note says "Every synthetic item is now labelled in every mode". The code does not support that:
1. The SSR canvas and "Back to standard" (M1).
2. The work page `/w/{app}/{work}` and the live-shared pages show no origin chip and no synthetic note, in any mode.
   - They read outlines through `work_reads` (`query/routes.rs:812-818`; `sharing/live.rs:645`).
   - No page under `admin/src/work`, `shared`, `sharing`, `workspace` or `record` mentions "synthetic", "sample" or `cv-origin`.
   - Every canvas group links to the work page with "Open page ↗" (`render.ts:452`).
3. Other synthetic fixture data in the fixture organizations is outside `library_sample_sources`:
   - Northstar's events and inventory (sources `…006e` and `…0070`). They are uploaded only from the `synthetic: true` app011 manifest (`operator/operator.py:355`).
   - Spend Review (`…00d2`, `runtime/tenant_seed.py:54-56`).
   - With the switch off, or in the unlisted Canary organization, these works show unlabeled. The new canvas negative check (`canvas_campaign.rs:390-400`) asserts exactly this for the Northstar events work.
4. The argument "the page-wide note covers it in demo mode" holds only on the canvas (`app.tsx:319`):
   - Slack replies and the work page carry no note.
   - DS-44's gate is the switch alone (`directory.rs:69`, `demo::is_on()`), but the note also needs a listed organization (`is_demo_org`). The persona names are covered only if the private names file lists principals of listed organizations only. Nothing checks that.

Recommendation: untick box 5. Either narrow its claim to "canvas groups fetched as JSON, and MCP view runs", or fix items 1–3. Record whatever remains of items 2–4 under DS-84 (or as new DS entries) with an owner.

### Minor

- **m1. The catalog is parsed on every call.** `library_sample_sources()` parses the 175,186-byte catalog into a `serde_json::Value` on every `work_outline` and `forma_list_apps` call. In `work_outline` that happens inside the open data transaction (`queries.rs:1125`). The codebase already caches catalog derivations in `OnceLock` (`composer/matcher.rs:260`, `:406`, `:435`, `:450`); do the same here. The added SQL statement is cheap: the primary-key prefix `(organization_id, app_id, work_id)` limits it to one work's few bindings, and the cost is acceptable.
- **m2. A doc comment moved.** The new function took over `/// The sidecar entries by definition digest.` as the first line of its own doc (`queries.rs:1661`), so `library_sidecar` (`:1690`) is now undocumented.
- **m3. The label keys on the source id only (`queries.rs:1127`).**
  - **Member uploads cannot collide:**
    - folder sources get random UUIDs (`boxes/register.rs:159`);
    - sources are per organization (`0002_tenant_foundation.sql:117-120`), and the query filters by organization;
    - RLS is tenant scope only (`0002:219`).
  - **An operator can:** `register-source-revision` can add a revision with other content to an existing catalog source id (`admission_operator.py:1174-1223`), and `create-bound-work` can bind it (`:1226` onward). The result would be labeled sample.
  - **Fix:** matching the catalog's `(source_id, revision_id)` or source digest would make the label exact. This is unlikely and operator-only.
- **m4. The chip labels the whole app.** All 20 library apps bind one synthetic source plus one records input (`catalog.json`). The chip sits on the app card of a group whose records card, ledger and forms hold the member's own filed records. "Sample data" can read as "this whole app is sample". Consider wording such as "Views use sample data", or a mark on the view cards. This is a product call for Victor's QA.
- **m5. Test gaps.**
  - The MCP checks run in the demo organization (`mcp_campaign.rs:862`: `synthetic == true`), so the new outside-demo sentences are untested.
  - No MCP check shows a non-catalog work or app with `sample_data: false`. Such a check would have caught M2.
  - The unit test checks the catalog ids and the chip's literal text, not the binding query. The `origin-kind` test does fail without the change, which is good.
- **m6. The comparison could be firmer.** `source_id::text = ANY($4::text[])` is correct:
  - uuid text is lowercase, and so are the catalog ids;
  - `records` bindings have a NULL `source_id`, which gives NULL and is excluded.

  `source_id = ANY($4::text[]::uuid[])` would avoid the per-row cast and the dependence on case. This is a nit.

### Checked and fine

- **Scope and authorization:** the binding query runs after the `record_read` precheck and fence, inside the same transaction as the outline (`queries.rs:1095-1127`). It reveals only the bindings of a work the member can already read.
- **Folder-built and data-from-file works** bind random-id sources, so they correctly carry no chip.
- **Generated or adapted apps bound to catalog sources** do get the chip on the JSON route.
- **Rendering:** the SSR template renders `origin.kind` directly (`app.tsx:424-427`). The island maps the text through `originKind`, and "sample data" is checked first (`render.ts:438`). The united-window chips reuse the text, which maps the same way (`app-window.ts:61-62`).
- **History:** the ticket history is appended, not rewritten. The old "not met" sub-bullet stays, and the new note and log entry are dated.
- **Board and hygiene:** the board check passes, and the diff has no hygiene issue.

## Verdict on box 5

**Changes requested.** The JSON-route chip and `forma_run_view` are built correctly. The box is not met as written:
- B1 turns the `pitch` CI campaign red.
- The label is absent from the SSR canvas, "Back to standard", the work page and the shared pages (M1, M3).
- MCP's listing can call the member's own apps sample data (M2).
- Synthetic fixture data outside the library catalog stays unlabeled when the switch is off (M3).

Box 5 should stay unticked until at least B1, M1 and M2 are fixed and the claim is narrowed to what the code labels, with the rest recorded as DS-84 residual.
