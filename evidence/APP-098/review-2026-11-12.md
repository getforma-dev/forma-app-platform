**M1. Box 1's tick overreaches on DS-02's display names, and its reason contradicts the repository.**

Box 1 says that "with it off no planned shortcut (DS-01 to DS-04) runs". DS-02 is "Seeded demo personas with display names…". Its names half is DS-44:

- `app/src/directory.rs:20-23` reads only `GENUI_DISPLAY_NAMES_FILE`/`_JSON`, and `storage/sharing.rs:144-145` applies them. Neither reads the switch.

- The "operator feature, not a shortcut" reclassification appears only in the box note (`APP-098.md:215`).
- What changes §1 (`APP-098.md:30`) says every shortcut reads the switch and no other flag.

As written, then, a DS-02 path runs with the switch off whenever the names variable is set.

The stated reason is "real beta members get their names from it; gating it would remove their names". Nothing in the repository supports it, and the deployment contract says the opposite:

- The names file is the persona file. `docs/pitch/DEPLOY-RUNBOOK.md:88` lists Diego Ramos and Sarah Chen.
- The stack refuses the file in a clean trial with "A clean trial does not accept sandbox persona display names" (`infra/src/stack.ts:172-174`). `infra/test/shared-broker.test.ts:32-39` tests this ("clean profile refuses … persona names").
- `ops/beta/deploy.sh:93-104` passes the file only to windows without a clean trial. In exactly those windows the stack turns the switch on (`infra/src/stack.ts:351-353`). The clean service has no names variable (`shared-broker.test.ts:41-45`).

There is also no test for DS-02. Build configuration shows that the persona table is compiled only into `dev-stand` builds:

- `app/Cargo.toml:55-60`
- `app/src/lib.rs:21-22`
- `app/Dockerfile:29` builds without features, and the crate has no default features.

That is true, and it is a fair stronger gate, but it is an inspection, not "a test shows".

To make the tick honest, do one of the following:

- **(a)** Reopen box 1 and leave the DS-44 decision to Victor or APP-097.
- **(b)** Keep the tick, with all three of these:
  1. A corrected reason. In a deployment built by the stack, display names are never shipped with the switch off: `stack.ts:172`, :351-353, and `shared-broker.test.ts:38`, :44-45 show it. In code, the names path stays ungated.
  2. A dated note on DS-44 that records its reclassification: its new class and its owner.
  3. The decision recorded in `docs/planning` or an ADR amendment. AGENTS.md says "Record new decisions in docs/architecture or docs/planning".

## The DS-03 gate: checked and correct

- **The gate.** `demo_for` requires the composer's list and `crate::demo::is_demo_org`, which in turn needs `GENUI_DEMO_MODE` on and the organization in `demo.rs`'s list (`composer/mod.rs:216-219`; `demo.rs:65-70`). The organization comes from the resolved session (`member.organization()`), never from the request body. This is the same gate DS-53 uses, so it is the right one.
- **The only path to `nearest`.** `route_for` (`mod.rs:298-330`) is the only producer of `nearest`. `route()` (`mod.rs:285-292`) has no production caller; only tests use it.
  - **Chooser.** A near tie under `Pin::Chooser` answers `First::Choose` (`routes.rs:324-352`): the member picks and nothing is written. A near tie always has two or more ranked candidates, because `CONFIDENT` − `MARGIN` = 0.43 ≥ `CHOICE_FLOOR` (0.35). A chooser request that is not a near tie falls through to the gated `route_for`.
  - **MCP.** `compose_app` → `compose_for` → `compose_instant(Pin::Free)` meets the same gate (`mcp/tools.rs:685`; `routes.rs:173`).
  - **Slack** has no compose path.
  - **Folders** build through generation or DS-73's rehearsed definition (`boxes/routes.rs:1321-1326`, :1438), never through the matcher.
- **The refusal outside demo.** `Err(Unavailable)` matches `if !composer.enabled()` and becomes `Refused::ComposerUnavailable` (`routes.rs:368-374`). The route answers 503 `composer_unavailable` (`routes.rs:1239-1241`). The canvas shows "The composer is not available on this server right now. Nothing was placed." (`compose.ts:80-83`, :107), and MCP answers `composer_unavailable` (`tools.rs:690-693`). This matches the module contract (`routes.rs:15-16`) and the earlier no-candidate refusal. With a model configured the branch is never reached, so deployments with a key are unchanged.
- **Campaign expectations.**
  - Composer campaign: its keyless compose already expected `ComposerUnavailable` (`composer_qualification.rs:273-277`), so that intent had no candidate. Unchanged.
  - Pitch campaign: its keyless compose expects `Tailoring::Kept`, which only a `matched` pick can give (`pitch_qualification.rs:1284-1291`; `routes.rs:407`). Unchanged.
  - MCP campaign: its compose runs with the switch on and is still answered.
  - Template pins (`composer_qualification.rs:1093-1114`, `record_components_campaign.rs:102-104`) do not route.
- **Concurrency.** The new test passes the flag directly and does not touch the process-wide switch, so it needs no `lock_for_tests`. The `demo.rs` tests that do touch the switch hold the lock.
