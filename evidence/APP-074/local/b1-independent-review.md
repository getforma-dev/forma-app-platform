### Findings (Part A)

#### Minor

**m1 — The supervisor's and composer's validation is looser than the service's decoder in two places; a value both accept and the service refuses crash-loops the task instead of denying.** `runtime._exact_origin` (`runtime.py:342-355`) accepts `https://exa mple.com` and `https://ex%41mple.com` (probe: `True` for both; also `https://ex{ample.com`, `https://example.com.`); the service's `exact_origin` (`auth/mod.rs:101-108`) with the pinned `url` crate refuses the first two (scratch-crate probe: `false`, `false`; `{` and the trailing dot are accepted by both). `_VALID_ID` (`runtime.py:334`) is any lowercase hex UUID; `storage::valid_id` (`storage/mod.rs:94-105`) also requires the version nibble `4|7` and variant `8-b`, so an `organization_id` or `registry_version` such as `…-1000-0000-…` passes `auth_configuration()` and is refused by `AuthConfig::decode` (`mod.rs:124`) and `Registry::load` (`registry.rs:49,54`). The composer validates with `rt.auth_configuration` only (`window_requests.py:216`), so such a value would be written in 5.9; at 13.1 `serve()` writes the two files, the child `refuse()`s at `main.rs:369` or `:358` and exits 1, `serve()` returns its code (`runtime.py:946`), the task stops and ECS restarts it until the circuit breaker. Not permissive, but the only sign-in configuration path can take the whole service down with no pre-write detection, and the runbook's 15.1 note ("compare the task's log") is the first place it would show. *Fix:* `_VALID_ID = re.compile(r"[0-9a-f]{8}-[0-9a-f]{4}-[47][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}")` (the pattern already exists twice in the file, `:193` and `:976`); in `_exact_origin` require `url.hostname` to match the dot-separated lowercase hostname-label pattern (labels of 1 to 63 letters, digits and inner hyphens; written out in `runtime.py`) (or an IPv4 literal) and refuse any `%` in the value; add the three probe strings and a version-1 UUID to `test_the_document_is_validated_whole_with_the_services_bounds`. Better still, have the composer also run the service's own decoder over the composed files (a `cfg(test)`-free `AuthConfig::load` + `Registry::load` check behind a `genui --check-auth-configuration <dir>` flag, or a Rust unit test in CI that decodes `window_requests_test`'s composed fixture), so the two validators cannot drift again.

**m2 — The whole-value cross-check allows two bindings for one routed organization, which the service resolves as "no sign-in for that organization", silently.** `auth_configuration()` (`runtime.py:419-421`) compares organization *sets* and unique `(issuer, tenant)` pairs; `{A→t1, A→t2}` beside one route for A passes. `Registry::tenant_for` (`registry.rs:83-93`) returns `None` for more than one binding, so `provider_tenant()` is `None`, `registered()` is false, and every `/auth/callback`, `/workspace` and `/auth/pending` of organization A is refused before the database, while `POST /signin/{handle}` still starts a flow and a PAR (`routes.rs:153-196` never consults the registry), so the user reaches fAuth and then the neutral failure. Fail closed, no log line names the cause. The composer cannot produce it (a duplicated `genui_org_uuid` refuses as a duplicate route), so the exposure is a hand-written or edited value. *Fix:* `require(len(registry["bindings"]) == len(config["organizations"]))` next to `runtime.py:420` (with set equality that is exactly one binding per organization), a `bad` case with one organization under two tenants in `test_the_document_is_validated_whole_with_the_services_bounds`, and a `tracing::warn!("auth.registry_ambiguous")` once at startup when `tenant_for` would be ambiguous for any routed organization (`Auth::new`, `mod.rs:352-372`, has both the config and the stores).

**m3 — D7.8: `bind-provider-tenant` writes an authority-bearing row with no audit event, and the residual is carried nowhere.** The row decides which provider tenant can mint pre-access and workspace sessions for an organization (ADR-006's registry/database agreement, `admission.rs:221-229`), which is not the backfill's "genesis heads are the record" case (ADR-007 D7.19). D7.8's kinds are closed; D7.19 does not list `provider_tenant_bindings` writes on existing organizations among the operator's writes. APP-084 item 6 (`Tickets/0-backlog/APP-084.md:35,41`) names `register-source-revision` and `create-bound-work` but not this command, so the README's "a `provider_tenant.bound` kind is an ADR-007 amendment if wanted" (`evidence/APP-078/prep/README.md` B1) is the only trace, and ADR-010 §5 ("no residual lost") is not met. For Phase 1 the two Nov 2 bindings are recorded by RUNBOOK 10.4's retained output and CloudTrail's RunTask overrides, which I accept. *Fix (Tier C, before the window):* add `provider_tenant.bound` (with `outcome_digest` over the canonical `{issuer, provider_tenant_id, binding}`) to APP-084 item 6 under the same D7.8 amendment and migration; one dated sentence in ADR-007 D7.8 or D7.19 that `bind-provider-tenant` writes no event until that migration and that the window's two bindings are recorded by the runbook and CloudTrail; `verify` to cover the kind when it lands.

**m4 — Structured query log: a dispatched child that fails has no terminal event, so dispatches cannot be reconciled.** `Engine::execute` logs `query.dispatch` (`worker.rs:536-544`) and then returns `Failed(Deadline|Killed|Engine)`, `NarrowTheQuery` or `Refused(_)` (from `run_child`, the late check at `:556`, the exit status at `:559`, `parse_result`) with no line; the routes log only `query.released`/`query.release_denied` (`query/routes.rs:228-261`); a receipt the contract rule refuses (`receipt::build` → `None`, `routes.rs:357-359, 628-631`) logs nothing; direct `Engine::execute` calls have no release. The campaign's own numbers show it: 139 `query.dispatch` against 25 + 5 terminal lines, and the check asserts only `dispatched == launched` (`query_qualification.rs:2111-2116`). An operator reading the log cannot tell a child killed at its memory line, a nonconforming receipt or a protocol failure from a run still in flight. *Fix:* one `query.failed_after_dispatch` line with `code = refusal_code(&error)` on every error path after the dispatch line in `Engine::execute` (and `code="receipt_nonconforming"` where `receipt::build` returns `None` in both routes); campaign assertion `dispatched == released + release_denied + failed_after_dispatch + direct_runs`.

**m5 — The composer hides the `ten_` ids and the `iss` that `bind-provider-tenant` then puts on argv; the two texts contradict each other.** The composer refuses to print tenant ids, client ids and the issuer (`window_requests.py:219-222`; the test asserts their absence), RUNBOOK 5.9 says the value is "never pasted into a … task override", and RUNBOOK 10.4 then places `$TEN_<org>` and `$ISS` in the RunTask override (CloudTrail, the operator log), which APPROVALS A11 acknowledges. ADR-006:58 treats `ten_` ids as identifiers, so this is not a leak; it is an inconsistency and a transcription step (0.5 → `$PRIV/approvals.md` → 10.4) that can disagree with the secret. *Fix (recommended):* `bind-provider-tenant --organization <uuid> --from-auth-configuration` reads the `(issuer, provider_tenant_id)` pairs of that organization from the `AuthConfiguration` secret itself (`OperatorRole` already holds `GetSecretValue` on it; `GENUI_AUTH_CONFIGURATION_SECRET_ID` as the capability secret's ARN is delivered today), validates the value with `runtime.auth_configuration`, and binds exactly what the registry will name: no identifier on argv, and registry/database agreement by construction. Otherwise, say in RUNBOOK 5.9 and `infra/README.md` that the `ten_` ids and `iss` are identifiers that do appear in overrides and CloudTrail, and let the composer print them.

**m6 — `bind-provider-tenant` does not refuse a `(issuer, tenant)` pair already active for another organization.** The primary key is `(organization_id, issuer, provider_tenant_id)` (`0002_tenant_foundation.sql:25-30`), so tenant T can be bound to two organizations in the database. The registry's unique-pair rule and `binding_active`'s exact triple keep it inert for sign-in, so no authority leaks; it is only ever an operator mistake that the command accepts silently. *Fix:* before the insert, under a scope-free read (the command runs under organization scope, so use the operator's own catalog-level read or a `genui_private` helper), `require(no active row WHERE issuer=%s AND provider_tenant_id=%s AND organization_id<>%s, "provider_tenant_bound_elsewhere")`.

#### Nits

- n2 — Secret rewrite serialization: the capability secret's read-modify-write is serialized by the database advisory lock; the auth configuration secret has a single writer (the window's `put-secret-value`), so no lock is needed; the runbook's "`{}` or stop" check in 5.9 is the right guard.
- n3 — `native_query_campaign` failed once at `stores.readiness()` with `Deadline` when run third in a sequence of Docker campaigns and passed alone; APP-076's runbook should run the campaigns one at a time with a cold-start allowance rather than treat the first `Deadline` as a product failure.
- n4 — `evidence/APP-074/local/README.md:35` still says the session campaign has 18 checks; it has 19 since `8b30122` (20 at `e712b8e`).
- n5 — `window_requests.auth_configuration` composes `issuer`/`audience` from the private file without type checks of its own and relies on `rt.auth_configuration` to refuse them; fine, but a `KeyError`/`TypeError` from an unexpected shape would print the key name through `main`'s `KeyError` branch (`window_requests.py:366-368`): harmless (field names only), noted.

### New surface: the reload-restore cookie (`__Host-genui_run`)

What I tried and what held (`cookies.rs:22-30, 53-79, 91-96`; `csrf.rs:80-113`; `query/routes.rs:385-436, 491-520, 771-780`):

- **CSRF.** The state-changing request is still the token-checked, same-origin `POST /w/{app}/{work}` (`routes.rs:727-748`: fetch metadata, then the `csrf` field verified against the session cookie, exactly one `csrf` field). The `GET` runs only parameters that browser itself submitted; `SameSite=Strict` keeps a cross-site navigation from carrying the cookie. A *same-site* link (another `*.getforma.dev` host) would carry it, but the result is only the member's own last run re-executed under her own authority, with the parameters she chose: no attacker-chosen effect.
- **Replay across sessions and works.** The tag is HMAC over `app \0 work \0 session-cookie \0 canonical-parameters` under the process key (`csrf.rs:80-88`); app and work are canonical UUIDs and the session cookie is `[A-Za-z0-9_-]+`, so the `\0` framing is unambiguous. A cookie presented with another session cookie, on another work, after a process restart, or with one changed parameter byte is `Restore::Invalid` and cleared (`routes.rs:413-436, 493-496`); `run_tags_bind_work_session_parameters_and_process_key` and `the_run_cookie_restores_only_this_sessions_run_of_this_work` cover each case; campaign "reload restores" exercises another work and a tampered cookie with no dispatch.
- **Fixation.** `__Host-` can be set only by this origin over HTTPS with `Path=/` and no `Domain`, and a valid value needs the process key and the victim's session cookie value; without either the cookie is ignored and cleared. A fixated value could at most make the victim's page run a query the attacker chose under the victim's authority, and that is exactly what the HMAC over the session cookie prevents.
- **Parameters are judged again.** The decoded bytes must be forma-json-v1 (`admission::decode`), pass `parse_parameters`, and re-encode to the same bytes (`routes.rs:426-434`): a tag over parameters the form would refuse (the review's concern) verifies but does not run; every restored run passes `run_query` and `release_result` again (campaign: a `source_read` revocation between execution and release of a restored run renders both views denied; a revocation before the reload makes the page the uniform 404).
- **Size bounds.** `read_bounded` with `RUN_MAX_VALUE` 2,560 and the 4 KiB total `Cookie` bound (`cookies.rs:53-79`); `run_cookie_value` refuses a value over the bound (`routes.rs:395`) and the form bounds the destination at 256 scalar values (`:99, 567`), so the cookie always fits beside the session cookie; the opaque cookies keep the 128-character bound (`the_run_cookie_reads_under_its_own_bound`).
- **Clearing.** `clear_all` includes `RUN` (`auth/routes.rs:62-71`), so sign-out and sign-out-all clear it; the callback's new-arrival path does not (it clears `PRELOGIN`/`SESSION`/`PRE_ACCESS` only, `:455-475`) — harmless, since the new session cookie invalidates the old tag and the page clears the stale cookie on its next `GET` (`Restore::Invalid`). Max-Age 600 is refreshed only on a successful restore (`:502-505`).
- **No value in logs or URLs.** The log lines carry identities and codes only (m4 above is about completeness, not disclosure); the campaign's secrecy assertions (window bound, destination, client address, cookies) passed in my run; a query string on the page is the uniform 404 (`routes.rs:478-481, 737-739`).

No finding against the cookie. One observation (not a finding): `Restore::Invalid` is answered with a cleared cookie but no log line, so a forged-cookie campaign against the work page is invisible; the page is behind a live session, so this is low value, and a `tracing::info!("query.run_cookie_ignored")` would be cheap if wanted.
