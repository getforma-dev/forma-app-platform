## What changed

| Area | Change |
| --- | --- |
| Invitation entry | `app/src/auth/invite.rs` (new). `GET /invite` renders the entry and reads nothing from the request. `POST /invite/validate`: fetch metadata (403) → limits (429) → 4 KiB body (413) → exactly one `code` field (anything else: neutral) → `code_digest` → `resolve_code` (D7.2; a store failure here is 503, code-independent) → the organization's provider route → the code's provider invitation capability → fresh PKCE (verifier sealed) → `begin_flow(FlowKind::SignUp { code_digest, handoff: Some(invitation_id) })` (D7.1 `reserve_code` in the flow's transaction: 10 minutes, not counted, ≤ 10 live per code) → backend PAR with `invite_token` → `303` to `{auth_origin}/t/{slug}/auth/authorize?client_id&request_uri` with the `__Host-genui_prelogin` cookie. A failed PAR discards the flow. Every other refusal is the one neutral page (400). Safe log events `invite.validate` (outcome, stage) and `invite.par` (failure class) carry no value. |
| Signup handoff | The pre-login flow row is ADR-006's bounded signup handoff: code (through its presignup reservation), server-bound organization, provider invitation reference (`signup_handoff_id` = the GenUI invitation id), 10-minute expiry, single use. No new table or migration. |
| Capability custody (read side) | The service reads APP-073's capability directory (`GENUI_PROVIDER_CAPABILITY_DIR`, same-UID 0700, checked at startup; absent: no code obtains a handoff). A file is used only if it is a same-UID 0600 regular file, single link, ≤ 4 KiB, `deny_unknown_fields` record of format `forma:fauth-invite-capability:v1` for this organization and invitation id, token and remote id `tinv_`-shaped, provider expiry ≥ now + 300 s, and its `code_digest` equals the validated digest (constant-time); exactly one match or none. Bounded scan (4,096 entries, 256 files of the organization). Since `0867883` the directory is the one `runtime.py serve()` writes from the injected secret, and its mode is re-checked per lookup (review M1, m10). |
| Operator (write side) | `provider_management.write_capability(…, code_digest=None)` and `admission_operator.create_remote` record the code's stored `sha256:` digest (never the code) in the capability. Unit test updated. Superseded at `0867883`: the record goes into the environment's Secrets Manager secret (`CapabilitySecret.add`), never a host file (review M1). |
| Trusted proxy (D7.14) | `app/src/http/proxy.rs`: `TrustedProxies` from `GENUI_TRUSTED_PROXY_CIDRS` (canonical CIDRs, ≤ 16, no `/0`, malformed refuses startup); the rightmost hop of the last `X-Forwarded-For` line is believed only when the socket peer is trusted; otherwise (and with none configured) the peer is the client. | Pages | `app/admin/src/invite/app.tsx` (native, no JavaScript): labeled code field (`autocomplete=off`, `maxlength=128`, `required`, `autofocus`), `aria-describedby` pointing at the help text or, when shown, the `role=alert` refusal/limit; the submitted code is never rendered. ## Decisions made in this slice (for review)

1. **Neutral, not itemized, refusals.** The ticket says "honest pending/invalid/expired/exhausted/rate-limited states"; ADR-006 (later, route-level) requires malformed, unknown, expired, revoked, exhausted and foreign codes to receive the same neutral answer, and plan Task 8 names `…answer_identically…`. The page therefore names all possibilities in one honest sentence ("It may be mistyped, expired, revoked or already used"); rate-limited and pending (after signup, `/auth/pending`) are distinct states; a store outage before any code is judged is 503.
2. **The flow row is the signup handoff**; `signup_handoff_id` holds the GenUI provider-invitation id (no migration).
3. **Capability lookup by recorded code digest.** `genui_workspace` cannot read `access_codes` or `provider_invitations`; the operator now writes the code's stored digest into the capability file and the service matches it. Older capability files without it are never handed off.
4. **Trusted proxies are configuration, not code**: `GENUI_TRUSTED_PROXY_CIDRS`, none by default (local and smoke runs ignore every forwarded header); infra sets the ALB subnets.
5. **The invitation limit renders the page** (429 with `Retry-After`) rather than problem JSON, because it answers a browser form; transport refusals (403, 413, 503) stay problem JSON.
6. **No GenUI-side email comparison.** The provider binds the invitation to its email (merged contract); GenUI cannot read the intended-email digest from the service role and does not add a second, fragile check at the callback.
7. A provider PAR failure leaves the presignup reservation live until its 10 minutes lapse (`genui_workspace` cannot release it; D7.1 bounds it at 10 per code).

## Limits

- Synthetic loopback issuer plus the loopback management stand-in; since `0867883` the operator writes each capability into a loopback Secrets Manager stand-in (`local_secrets.py`, real boto3), the supervisor's own writer materializes the service's files after each operator command (as if the task restarted), and the test copies each invitation token from the service's file into the issuer (one simulated provider). Not the deployed fAuth or AWS; hosted PAR, real mail, the live secret injection and browsers are APP-076 (installed Chrome) and APP-079 (Safari, Firefox). M1's browser behaviour is confirmed only there.
- ~~Hosted capability delivery is open~~ (superseded at `0867883`): the capability secret is injected into the service task (ADR-003 amendment 2026-10-30, review fixes above). A capability issued, revoked or reconciled after the task started reaches the service only at its next start; the operator forces a new deployment after `issue`. The operator host's own AWS credentials need `GetSecretValue` and `PutSecretValue` on the secret for `issue` and `reconcile` (outside the stack; APP-076's runbook).
- In-process limits (D7.5, D7.18); local password authentication over TLS, not RDS IAM. D7.18 assumes stop-then-start, but the service pins `minHealthyPercent 100`/`maxHealthyPercent 200`, so a deployment briefly runs two limit tables and two sealing keys (review n4; pre-existing, the infrastructure owner's).
- Review m5: neutral refusals are byte-identical but not time-identical. An unknown code costs one `resolve_code` transaction; a known code that is expired, revoked or exhausted also pays the capability scan and, with a capability, the `begin_flow` transaction. A holder of a code can tell "issued but unusable" from "never issued"; with 160-bit codes nothing is enumerable and no other organization is disclosed, so no padding is added.
- Review m6: the global invitation budget (200 attempts a day, checked before any code is judged, ADR-006's value) is a cheap whole-service lockout: ten IPv4 addresses at 20 a day each with garbage codes close invitation entry for a sliding day, and the operator's only lever is a task restart (which also ends every session). Faithful to ADR-006; APP-076's runbook names it, and ADR-006's owner is asked whether the global window should count only codes that `resolve_code` finds.
- Review m9: the JSON bounds (64 KiB, 256 KiB on the command route) are proven on `http::bounded` only; no mounted route reads JSON at this tip, so "JSON bodies over 64 KiB receive the uniform problem response" holds for no route yet. APP-012 and APP-013 each add a route-level 413 test.
- The route-level race repeat and the provider fault exercise are APP-082's (ADR-010).
- Independent review: [independent-review.md](independent-review.md) (Tier A, 2026-10-30) with its dispositions; nothing pushed; no CI.
