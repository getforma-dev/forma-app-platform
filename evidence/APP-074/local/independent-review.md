## Findings

### Major

**M1 — No hosted channel delivers the provider invitation capability to the service (open question 1).** The service reads `GENUI_PROVIDER_CAPABILITY_DIR` (`app/src/auth/invite.rs:173-179`; absent: every code is neutral). The task definition sets no such variable (`infra/src/stack.ts:144-152`), has a read-only root file system, user 65532, `enableExecuteCommand: false` (`stack.ts:154-155,179`) and only the ephemeral `/run/genui` volume (`stack.ts:142,160`), which `runtime.py` fills with the credentials and the deny-all registry only. The operator therefore cannot "place Victor's capability where the service reads" it, as README:91 proposes. Plan Task 8's consumed interface (`docs/planning/PHASE-1-EXECUTION-PLAN.md:193`) was "APP-073 record → secret reference read by the Python helper into a private file"; that half is not implemented and not recorded as a deviation. Ownership is also inconsistent: ADR-003's custody amendment (`ADR-003:45`) still says "Until APP-074 moves capabilities into AWS Secrets Manager", while ADR-010 (`ADR-010:109`, accepted §8 item 4) and APP-084 item 1 give the move to APP-084 "before invitations go beyond the demo principals". Under the accepted custody default (0600 file on the operator's Mac) the deployed service has no copy at all, so on 2026-11-02 Victor's own code would get the neutral page; ADR-010 row 1 needs "invite code validated by digest; fAuth signup" on the live deployment. (`GENUI_AUTH_CONFIG_FILE` and a non-empty identity registry have no hosted channel either; that is APP-076/078's, but the capability is the one this slice owns.)
*Fix (owner decision, before APP-076):* bring the Secrets Manager move into the Nov 2 path: one secret under the tenant key holding the capability records (bounded, e.g. 64 KiB), injected as an ECS secret `GENUI_PROVIDER_CAPABILITIES_JSON`; in `runtime.py serve()` pop it from the environment before anything else, validate each record against the Rust `Record` shape (`invite.rs:58-70`), write `{organization}.{invitation}.capability` files 0600 into a fresh 0700 directory under `/run/genui`, export `GENUI_PROVIDER_CAPABILITY_DIR` to the child only, and remove the directory on exit; add the conditional secret, its read policy and an infra test. Then amend `ADR-003:45` to name the real owner, correct plan Task 8's interface line, and give APP-076 the acceptance line "the deployed task reads the code's capability and hands off". If Victor keeps the Mac-only custody, record that invited signup is unavailable on the deployed task, which ADR-010 row 1 does not currently allow.

**M2 — Redemption floods hit no limit; forged cookies drive unbounded database work.** `GET /auth/callback` (`app/src/auth/routes.rs:345-358`) checks no limit before `complete_flow` (`app/src/storage/sessions.rs:461-466`), which opens a transaction and runs a `DELETE` for any capability-shaped `__Host-genui_prelogin` value whose first 16 bytes are any version-4 or version-7 UUID (the organization id is not secret, ADR-006 amendment (3); it need not even exist) with a 43-character `code` and `state`. ADR-003 §public entry requires "server-side IP, account/admission and global rate bounds to signup, login and code redemption"; item 4 says "Signup/login/redemption floods hit finite server-side IP and account/admission/global limits". Redemption happens at the callback (ADR-006 Flow 2; D7.1 `record_pending_admission`, `admit_redemption`), and README:34 covers only the invitation and sign-in starts. With ADR-004's two workspace-role connections and a 5-second acquisition, an anonymous callback flood can starve every sign-in, invitation entry and admission, which then fail at the 5-second deadline (reasoned from the pool bounds, not load-tested). Forged `__Host-genui_session` and `__Host-genui_pre` values on `GET /workspace` and `GET /auth/pending` cost one transaction each in the same way (`routes.rs:417-436`, `pending.rs:64-73`, `sessions.rs:720-731`).
*Fix:* in `callback`, before `callback_query` and the cookie read, `auth.limits.admit(&[(&format!("callback:{class}"), limits::CALLBACK_ADDRESS), ("callback:global", limits::CALLBACK_GLOBAL)])`, answering the neutral failure page with 429 and `Retry-After`. Size the windows at the sum of the starts that precede a legitimate callback, so no real return is refused: `CALLBACK_ADDRESS = &[per(15, 60), per(80, 3600)]`, `CALLBACK_GLOBAL = &[per(800, 3600)]`. Also refuse, before any transaction, a cookie whose organization has no binding in the in-memory closed registry (`Workspace::provider_tenant`). Add a unit test (the 16th callback from one class answers 429 with no database or provider call) and a campaign line, and record the values in ADR-006's callback row as an amendment, since ADR-006 lists no callback limit. Optionally count failed (`Absent`) cookie lookups on `/workspace` and `/auth/pending` per class.

**M3 — Item 2's route-family evidence counts unmounted paths and implies query and record are implemented.** Campaign check 9 probes nine `/v1/*` and `/w/*` paths (`app/src/auth/invite_tests.rs:1273-1291`); none is mounted at this tip (P4), so 63 of the 70 probes measure the router fallback, which answers any unknown path identically for anyone; only the seven `/workspace` probes reach a protected handler. The admitted-member loop checks only import, generation and export (`invite_tests.rs:1329`), and the check text (`:1356`) and README:32 call those three "the unimplemented families", which implies query and record are implemented. The ticket asks for refusals "by actual protected page/API routes" and says "not-yet-implemented capabilities remain denied/unavailable and cannot be counted as an implemented feature".
*Fix:* run the admitted-member loop over all nine non-workspace paths (they answer 404 for members too); restate the check and README:32 as "only `/workspace` is a mounted protected route at this tip; the query, record, import, generation and export paths are not mounted and answer the uniform fallback 404 to every principal, members included; none is counted as implemented"; and add to APP-012 (plan Task 9) the obligation to re-run the seven-principal probe against its mounted `POST /v1/work/{app}/{work}/queries/{view}` and `GET /w/{app}/{work}` before item 2 is claimed for the query family.

### Minor

**m1 — The synthetic issuer does not model three refusals of the real contract.** (a) `Issuer::login` (`app/src/auth/synthetic_issuer.rs:403-410`) completes an invitation-bound request for any subject and leaves the invitation pending; fAuth's hosted sign-in on such a request requires the invitation's email and consumes it in the code transaction (`hosted_code.rs:309-330`, `invitation()` at `:239-258`). (b) `register` (`synthetic_issuer.rs:344-351`) overwrites an existing user; fAuth answers 409 for an existing email and leaves the invitation and request untouched (`hosted_code.rs:407-415`). (c) The invalid-invitation PAR error is `invalid_invitation` (`synthetic_issuer.rs:517`); fAuth's is `invalid_invite_token` (`hosted_code.rs:18-22`), and its 1,000-pending PAR bound (`par.rs:154`) is not modelled. GenUI never reads these bodies, and no current check relies on (a) (the campaign's `login` calls use sign-in requests), but a future test would see behavior fAuth refuses. *Fix:* in `login`, when `par.invitation` is `Some`, require the invitation pending, of this tenant and with `users[subject].email` equal to its email, then mark it `Accepted`, else refuse and count; in `register`, refuse without consuming when a user with that email exists; rename the error; add a campaign assertion that an existing identity's sign-in on another email's invited request is refused with the invitation still pending.

**m2 — A client byte earlier in the forwarded line moves the request into the shared `unknown` class.** `client_address` requires the whole last header line to be visible ASCII (`app/src/http/proxy.rs:116-118`, `to_str().ok()?`). A client behind the load balancer that sends `X-Forwarded-For: \xff` gets `unknown` (P1) after the balancer appends its address, so it can alternate between its own bucket and the shared one (twice its per-class budget; the shared bucket otherwise holds only requests with an unparseable hop). Whether the ALB forwards obs-text is unverified; `drop_invalid_header_fields` checks names, not values. *Fix:* parse only the rightmost element from bytes: `let hop = last.as_bytes().rsplit(|b| *b == b',').next()?; std::str::from_utf8(hop).ok()?.trim().parse().ok().map(canonical)`, with a unit test for `b"\xff, 203.0.113.9"` → `v4:203.0.113.9`.

**m3 — The load balancer's forwarded-header behavior that `proxy.rs` depends on is not pinned.** The rightmost-hop rule assumes the ALB's default `append` mode with no client port. `preserve` would make the rightmost hop client-controlled; `routing.http.xff_client_port.enabled` would turn every hop into `ip:port`, which parses as `unknown` (P1), collapsing every client into one class. Neither attribute is set (`infra/src/stack.ts:174`), and the multi-line order (P1's second case) depends on how the ALB merges a client-sent line. *Fix:* `alb.setAttribute('routing.http.xff_header_processing.mode', 'append')` and `alb.setAttribute('routing.http.xff_client_port.enabled', 'false')`, both asserted in `infra/test/security.test.ts`; APP-076 sends two client `X-Forwarded-For` lines and an obs-text byte through the live ALB and records the class each gets.

**m4 — The limited page is not honest for the day and global windows; outages answer raw JSON to a form.** Every 429 renders "Too many attempts from your network. Wait a few minutes, then try again." (`app/admin/src/invite/app.tsx:29`), including the 20/day class window and the 200/day global window, whose `Retry-After` reaches 86,400 s. A store outage before judgment (`invite.rs:427-430`) and the deadline (`http/mod.rs:96-100`) answer `application/problem+json`, which a native form shows as raw text. *Fix:* word the notice "Too many attempts right now. Try again later." (or pass a `global` prop and say so); render the invite page with an "unavailable, try again" notice and status 503 for `Refusal::Unavailable`.

**m5 — Neutral refusals are byte-identical but not time-identical (P2).** An unknown code returns after one `resolve_code` transaction (`invite.rs:315-320`); a known code that is expired, revoked or exhausted also pays the directory scan (`:325-328`) and, when its capability is present, the `begin_flow` transaction with `reserve_code` (`:337-350`). The campaign's revoked code keeps its capability (`invite_tests.rs` check 3), so it pays both. A holder of a code can tell "issued but unusable" from "never issued". With 160-bit codes nothing is enumerable and no other organization is disclosed, so I would not pad. *Fix:* record it in README §Limits; if wanted, hold neutral responses to a fixed floor (for example 250 ms from receipt).

**m6 — The README does not record that the global budget is a cheap whole-service lockout (ADR-006 values, by design).** 200 admitted attempts a day across the service, checked before any code is judged (`app/src/http/limits.rs:34-36`, `invite.rs:387-405`): ten IPv4 addresses at 20/day each, with garbage codes, close invitation entry for everyone for a sliding day; the operator's only lever is a task restart, which clears the in-process counters and signs everyone out. The implementation is faithful to ADR-006; the consequence belongs in the record. *Fix:* add it to README §Limits and APP-076's runbook; ask ADR-006's owner whether the global window should count only codes that `resolve_code` finds (digest and lookup are cheap and already behind the per-class limit).

**m7 — Open question 4 understates the leaked-code case.** A leaked code plus the invitee's email lets an attacker register with the attacker's password (the provider accepts the invited email, `hosted_code.rs:375-439`); fAuth then mails the verification link to the real invitee. If the invitee confirms it, which an expecting invitee is likely to do, the attacker's credential belongs to a verified identity whose pending admission (bound to that `sub`, ADR-006 Flow 2) redeems at the attacker's next sign-in through `/signin/{handle}` (Flow 4). That is access, not only denial of service, and a later provider password reset by the invitee does not end the attacker's GenUI session (up to 12 hours). *Fix:* correct README:94; APP-076's runbook tells invitees not to confirm a verification mail for an account they did not create and gives the operator's response (revoke the code, `revoke-entitlement`, provider `revoke-sessions`, reissue); ask FormaStack to show the account's creation time on the confirmation page.

**m8 — Check 9's "no provider dispatch" omits logout.** The dispatch tuple is PAR, exchange and registration (`invite_tests.rs:1293-1297`, `:1345-1352`); the expired principal's lookup ends the record and revokes its refresh token through provider logout (`routes.rs:430-433`), which ADR-006 requires. *Fix:* include `logout` in the tuple and say "no PAR, exchange or registration; the expired session's destruction revokes its refresh token once, as ADR-006 requires".

**m9 — The JSON bounds of item 5 are proven only on the helper.** `http::bounded` (`app/src/http/mod.rs:113-115`) is unit-tested, but no mounted route reads JSON at this tip, so "JSON bodies over 64 KiB … receive the uniform problem response" holds for no route yet. *Fix:* say so in README:35 and give APP-012 and APP-013 a route-level 413 test.

**m10 — The capability scan's bounds fail silently.** Entries past 4,096 are never read and more than 256 files of one organization refuse every code of that organization (`invite.rs:220-234`), with no log; a directory that later loses its 0700 mode is not noticed (checked once, `invite.rs:158-171`). *Fix:* `tracing::warn!(entries, files, "invite.capability_scan_bound")` with counts only when a bound is hit, and re-check the directory's owner and mode in `scan` (one `symlink_metadata` per lookup).

**m11 — The injected qualification secret can now only break the service (open question 3).** `runtime.py:63-71` pops `GENUI_AUTH_QUALIFICATION_CONFIG_JSON` and refuses in every mode, so a non-empty `QualificationConfigSecretArn` (`infra/src/stack.ts:51-54`, read policy `:136-140`, injection `:165-168`, test `infra/test/security.test.ts:289`) crash-loops the service until the circuit breaker rolls it back. Fail-closed is right; offering the parameter is not. *Fix:* remove the parameter, the conditional secret, the read policy and the test expectation (the harness runs as its own image under D7.13), or pin `allowedValues: ['']`; until then APP-076's runbook keeps it empty.

### Nits

- **n2** `http::form` answers any body-read error, not only an oversize body, with 413 (`http/mod.rs:105-108`).
- **n3** ADR-003:45 (custody amendment) still names APP-074 for the Secrets Manager move; ADR-010:109 moved it to APP-084 (fold into M1's fix).
- **n4** D7.18 (stop-then-start, `minHealthyPercent 0`) is what keeps the in-process limits well defined, but `infra/src/stack.ts:180` and `infra/test/security.test.ts:126` pin 100/200, so a deployment runs two limit tables (and two sealing keys) at once. Pre-existing and outside this diff; route to the infrastructure owner.

## Open questions

1. **Capability delivery to the managed task** — a real gap with no owner; see **M1**. It must be settled before APP-076 runs; "the operator places the file" is not possible on this task definition.
2. **Neutral versus itemized states** — accept the single neutral sentence. ADR-006's `POST /invite/validate` row (`ADR-006:32`) is the specific route contract and requires "the same neutral answer"; ADR-003's "clear pending, denied, expired, exhausted and retry states" (`ADR-003:57`) is met by `/auth/pending`, the callback's denial page, the 429 page (once m4 makes it honest) and one sentence naming expiry and use. Itemizing would leak only to holders of a 160-bit code, so both readings are safe and the neutral one is stricter. Because ADR-006 calls ADR-003 controlling, pin the reading in one line (an ADR-006 amendment or APP-074's log).
3. **`GENUI_AUTH_QUALIFICATION_CONFIG_JSON`** — the refusal is correct; remove the parameter or pin it empty (**m11**). Not a blocker while the parameter stays empty.
4. **Leaked code plus email** — not only denial of service; see **m7** for the verification-click path to access and the runbook and provider asks.
5. **GenUI does not check the email itself** — keep decision 6. At `1bf5d3b` fAuth compares the invitation's normalized email on hosted registration and hosted sign-in, in the transaction that consumes the invitation and issues the code, and on the legacy registration API as well (P5). The README's reason is incomplete (the operator could write an email digest into the capability as it now writes the code digest), but a second GenUI comparison would need parity with fAuth's `normalize_email` and adds nothing the provider does not already enforce atomically. Make the synthetic issuer model the sign-in binding (**m1**) so local evidence reflects it.

## Claims I failed to refute

- Refusal order: fetch metadata (403), limits (429, no budget consumed by refusals), 4 KiB body (413), exactly one `code` field, then digest, database, capability file, reservation and PAR (`invite.rs:381-418`, `:308-376`); limited valid codes reach nothing (check 4).
- Validation is by digest of the normalized code and consumes no redemption slot: `redeemed_count` 0, no pending admission, one live 10-minute `presignup` reservation bound to the pre-login cookie's context digest (`sessions.rs:420-428`), flow kind `signup` with the invitation id.
- The backend PAR carries the capability's `invite_token` in the form body only; the browser receives a 303 with exactly `client_id` and `request_uri` (`no-store`, `no-referrer`) and the one `__Host-` pre-login cookie; provider failures are a fixed enum (`provider.rs` `Failure`); the `request_uri` shape check matches fAuth's (`par.rs:158-161`).
- No client organization, tenant, role(s), redirect, destination, `return_to` or `invite_token` field is accepted; cross-site, foreign-`Origin`, metadata-less and duplicated-metadata posts answer 403; a Canary code reserves nothing under Northstar's scope and its capability is not found there.
- Unknown, malformed, expired, revoked, exhausted and invitation-less codes receive byte-identical 400 pages (headers included) with no PAR, reservation or flow; a used code replays nothing; a wrong state consumes the flow; a cross-organization code and state are refused; a handoff past 10 minutes admits nothing.
