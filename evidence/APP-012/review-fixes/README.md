## Reload restores (ADR-010 §1 act 4)

Mechanism: **POST/redirect/GET with a run cookie.** `POST /w/{app}/{work}` validates (fetch metadata, body bound, session, synchronizer token, no query string, `work_outline` authorization, the closed form) and, when the parameters are valid, answers `303 See Other` to `GET /w/{app}/{work}` with `Set-Cookie: __Host-genui_run=<tag><base64url(canonical parameters)>; Path=/; Secure; HttpOnly; SameSite=Strict; Max-Age=600`. The tag is the process key's HMAC (`csrf::CsrfKey::run_tag`) over the work path (`app`, `work`), the session cookie and the canonical parameter bytes, so the cookie restores only that work's run for that session. The GET, when the cookie verifies and decodes to exactly the normalized parameters (`parse_parameters` accepts them and re-encodes to the same bytes), runs every runnable view exactly as the POST used to (`run_query`, the engine, the receipt, `release_result` before the body) and refreshes the cookie; an absent cookie renders the idle page; a foreign (another work, another session, another process key), tampered or non-normalized cookie is ignored and cleared (`Max-Age=0`). A refused form still renders directly with 422 and leaves the cookie untouched. The page bounds the form's destination at 256 characters so the cookie always fits (`cookies::RUN_MAX_VALUE` 2,560; the JSON route keeps the contract's 2,000-character text bound); `clear_all` on sign-out clears the run cookie too.

Why this and not a `Path`-scoped cookie: `__Host-` requires `Path=/`, so the work path is bound through the tag instead. CSRF and fetch-metadata rules (design §9 M45, ADR-006): the state-changing request is still the token-checked, same-origin POST; the GET changes no state and runs only what that browser itself submitted. `SameSite=Strict` means a cross-site link to the page never carries the cookie, so such a link renders idle and runs nothing. The browser's re-submit dialog never appears because the page the member sees is the GET. Filters stay out of URLs (a query string is still the uniform 404). Unit tests: `the_run_cookie_restores_only_this_sessions_run_of_this_work`, `run_tags_bind_work_session_parameters_and_process_key`, `the_run_cookie_reads_under_its_own_bound`. Campaign check "reload restores": after the 303, two GETs show the same 1,140,000 and five buckets with a fresh run and release each (dispatch +2 per reload; the same pinned state and parameters reproduce the same receipt identity), a `source_read` revocation between execution and release of a restored run renders both views denied, a revocation before the reload makes the page the uniform 404 (fails closed), the cookie on another work of hers and a tampered cookie are ignored and cleared with every view idle and no dispatch.

- No image was built; APP-078 rebuilds the candidate with these sources.
