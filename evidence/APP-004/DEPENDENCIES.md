# APP-004 dependency and packaging decision — 2026-10-28

The final candidate uses **calamine 0.37.0, csv-core 0.1.13, quick-xml 0.42.0, ZIP 9.1.3 with one local Cargo manifest change, and Wasmtime 36.0.19**. Exact transitive versions/checksums, resolved features and license expressions are in `build-metadata.json`; the WASM-only feature graph is `guest-features.txt`. The manifests and Cargo lockfile are authoritative. ZIP is MIT; its published license and all published source files are retained.

## Why the current ZIP package is patched

The unmodified ZIP 9.1.3 wasm32 dependency enables getrandom's `wasm_js` feature. The initial compiled module therefore imported `__wbindgen_placeholder__::__wbindgen_describe`, and the host correctly refused it. `initial-test.log` records that failure. Setting the official unsupported backend while leaving the JavaScript feature enabled produced a getrandom compile error involving `Error::WEB_CRYPTO`. This is recorded as a failed experiment, not an accepted build.

The accepted packaging experiment deletes only the wasm32 getrandom dependency's `features = ["wasm_js"]` line from ZIP's normalized Cargo manifest. The ZIP source is unchanged. `.cargo/config.toml` selects `getrandom_backend="unsupported"` for the wasm32 target; host builds retain their ordinary entropy support. The read-only parser has no randomness requirement. A future unexpected randomness call must return an error, not obtain a new host interface. The final compiled module is checked for **zero imports**, rather than inferring isolation from Cargo feature names.

This choice follows getrandom's published warning against libraries forcing its JavaScript feature on non-web WASM users. The unsupported backend is an explicit supported configuration for code that does not need random bytes. See [getrandom WebAssembly guidance](https://docs.rs/getrandom/0.4.3/getrandom/#webassembly-support) and its [backend documentation](https://docs.rs/getrandom/0.4.3/getrandom/index.html#unsupported-backend). The artifact is a locally patched packaging candidate, **not** a newly published ZIP version or an upstream fix.

`vendor/provenance.json` records the registry archive SHA-256 checked against the public sparse registry index, original file hashes, selection/yank status, and the modified manifest hash. `verify_vendor.py` verifies all 66 original files, reconstructs the original manifest, and verifies the exact one-line patch. The repository contains the full published source rather than an owned replacement ZIP reader. The deliberate local patch must be independently reviewed and requalified when changed or removed.

## Older candidate was rejected

An intermediate calamine 0.36.1 / ZIP 8.6.0 build had zero imports and passed most initial tests. It is **not** the final selection. Reviewing ZIP's complete published advisory list exposed reader-specific issues in addition to extraction vulnerabilities. Retaining an older release plus an expanding collection of mitigation claims was less maintainable than the current published reader with a small feature-packaging change.

The reachability review below preserves the decision. It is not an exception allowing ZIP 8.6 in the final build, and not a blanket dependency-security pass.

## Runtime and parser choices

Wasmtime 36.0.19 is a supported LTS branch compatible with Rust 1.93.1; the current 50 series would require a newer Rust toolchain. [Wasmtime's release policy](https://docs.wasmtime.dev/stability-release.html) describes its LTS policy. [Interruption documentation](https://docs.wasmtime.dev/examples-interrupting-wasm.html) distinguishes deterministic instruction fuel from epoch deadlines; the spike exercises both and reports their independent budgets. No `wasmtime-wasi` dependency is included.

Calamine's published 0.37 source eagerly reserves shared strings while constructing `Xlsx`; preflight therefore validates declaration counts, actual strings and actual expanded bytes **before** constructing it. The selected-sheet `worksheet_cells_reader` API avoids dense-range allocation. Calamine's float classification is not used for numeric storage: raw numeric XML is converted to exact coefficient/scale or integer-string values. See [Xlsx API](https://docs.rs/calamine/0.37.0/calamine/struct.Xlsx.html).

csv-core writes through caller-provided finite output buffers. Its documented permissive parser never reports syntax errors, so the spike explicitly names that dialect and separately checks UTF-8, field/record/column/cell budgets and provenance. It does not claim strict RFC validation. See [csv-core Reader](https://docs.rs/csv-core/0.1.13/csv_core/struct.Reader.html).
