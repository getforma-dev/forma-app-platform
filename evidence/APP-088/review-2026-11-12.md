### Nits

- **n1.** `Plan:225` still says `WorkerScope` reads the epoch and takes the fence in "one statement", which is the superseded design claim. One statement still works with the retake, and the ledger's new text (:79) does not require it. Mark it, for example "(one statement is allowed but does not close the race; amendment R-m3)".

- **n5.** Ledger :81 ("Two epoch advances inside one step's transaction therefore end the job visibly") describes a case the fence's own lock mostly prevents. When `lock_member_authority` misses on the epoch, it has already taken `FOR SHARE` on the membership row (0002:252–254), and that lock lasts to transaction end. No further epoch advance can commit before the retake, so the retake succeeds whenever the membership is active, and M2's rule holds fully. Also, a `lock_timeout` (55P03) inside the fence aborts the transaction. That is not a refused recheck: the job falls back to lease reclaim. One clause would keep APP-015 from classifying it as `authority_revoked`, and `fence_miss_with_active_membership_retakes_once` can assert success deterministically.
- **n6.** An implementation note for APP-015's SQL review: the reclaim's locking `SELECT … FOR UPDATE SKIP LOCKED` must restate `lease_expires_at < now()`. PostgreSQL then re-checks the predicate after a concurrent reclaim commits, so a second claimer cannot reclaim a row that was just reclaimed.
- **n7.** The plan's `Started` enum (:223) has no variant for the ledger's branch where `release_job` releases nothing on a refused recheck at start and the transaction rolls back (:87). `Finished` has `Fenced`.
