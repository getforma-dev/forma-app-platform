## New findings

- **N1, MINOR: `POST /me/name` has no rate limit.** `member_name.rs:63-82` never calls `auth.limits.admit_member_write`. APP-113's rule (`http/limits.rs:58-63`, `MEMBER_WRITES` 120/hour) is that every route that changes rows and has no window of its own shares that window. Every *changed* name is an UPDATE plus one `member.named` event, appended to the organization's admission chain under the `audit_heads` row lock (`0023:357-392`). Failure scenario: a member scripts alternating names ("A", "B", "A", …) with their own valid token. Each request writes an audit row, with no bound. Every one of them takes the organization's admission head lock, which invitation redemptions, consent records and admin removals also need. Nothing leaks, but the audit chain grows without bound and admission writes queue behind it. Fix: admit one member write before `store.set` and answer 429 (or 303 with a notice).
- **N2, MINOR: the name rules still allow blank-looking names, and names are not unique.** `directory.rs:105-110`. These pass `usable_name`: U+3164 HANGUL FILLER and U+115F/U+1160/U+FFA0 (Lo), U+2800 BRAILLE PATTERN BLANK (So), names made only of combining marks (e.g. U+0301) or variation selectors (Mn), and U+2028/U+2029 inside a name. `trim` removes them only at the ends, and they are not Cc or Cf. Failure scenario 1: a member saves "ㅤ" (U+3164). The prompt treats it as a name, and the admin table, share lists and Ask show a blank label. Failure scenario 2: nothing in 0023 or the definer stops two members from both saving "Sarah Chen" exactly. Impersonation needs no invisible character at all, so the docstring's aim ("so one name cannot pass for another") is not achieved. The Cf rule still has real value: it stops bidi controls from reordering the text around a name. Fix: either require at least one letter or number that is not a filler (the review's suggestion) and soften the docstring, or record that display names are not unique and not an identity, and that the admin table's principal key is the identity.
- **N3, NIT: M3 leaves a narrow race.** `composer/routes.rs:429` (`reached`) and the transform's `take` are separate steps. `DailyCap` itself is sound: both methods hold the same mutex, and a refused `take` records nothing, so spend can never pass the cap. Failure scenario: with `limit - 1` calls used, two pinned compositions that need the transform both peek `false` and both place the standard work. One transform takes the last slot. The other's `take` fails, and `Tailor::run` (`:908-947`, `:963`) turns `model_daily_cap` into a silent `Tailoring::Kept`, the pre-fix behaviour. The window is the time to `retrieve` one standard work. Fix: let `Tailor::run` tell `model_daily_cap` apart (an `app.kept` reason the canvas can show), or note the edge case in APP-184.
- **N4, NIT: the canvas query gate is pinned only by the campaign, and a crafted link shows the notice.** With `Some(_) => false` at `query/canvas.rs:1739`, all 429 lib tests still pass. Only `org_admin_routes_campaign.rs:289` (CI `tenant-foundation`) catches it. Separately, `needs_name: name_notice || …` (`:1843`) means a link to `/canvas?name=invalid`, or the browser's Back button after a successful save, shows a member who already has a name the "That name can't be used" notice and the prompt. This is a nuisance only: the notice is constant and nothing is written. Adding a unit or SSR-route test for the gate would make it cheap to keep.
- **N5, NIT: ZWJ and ZWNJ are refused.** U+200C and U+200D sit in the rejected `200B..200F` range, and `directory.rs:279` deliberately tests U+200D. Persian names that use ZWNJ (the half-space key on a Persian keyboard) and emoji ZWJ sequences such as 👩‍🏫 are refused with "no invisible or control characters", which the member cannot see. Either accept this as a known limit or allow ZWJ/ZWNJ between two letters.
- **N6, NIT: outage answers to plain form posts are raw JSON.** These are the same kind of answer as m2: a storage outage on `/me/name` (`member_name.rs:126`, 503 `problem+json`) or on Remove (`org_admin.rs:356`), and a deadlock when two admins remove each other. The caller is locked `FOR SHARE` (`lock_member_authority`) and the target `FOR UPDATE`, so PostgreSQL aborts one of the two. That is the right outcome: both are never removed. But the aborted admin sees a 503 JSON body.

Checked and found sound:
- **Org-admin standing is live on every request.** `is_org_admin` runs `precheck(AdminPolicy)`, which reads `organization_permissions`, the membership, the epoch and the entitlement (`storage/authorization.rs:421-429`, `:591-592`). The overview and the removal fence that permission and re-check it inside the definer (`0023:417`, `:460`).
- **Remove refuses self and the last admin in SQL.** The last-admin check counts only active admins other than the target, so it cannot be reached by removing someone else while the caller is an active admin.
- **CSRF and route order.** Same-origin is checked before the session on both POSTs. Tokens are bound to the form and the cookie. A non-admin gets the uniform 404 before the form body is read (`org_admin.rs:285-290`). Nobody can set another member's name.
- **Security headers.** The `/admin` SSR test asserts `no-store` and `frame-ancestors 'none'` (`main.rs:2112-2116`).
- **The per-address limits.** They are pinned (`limits.rs:313-322`), and the callback windows are asserted to equal sign-in plus invitation (`:344-354`).

### The four questions

- **The notice values are a closed set, so no oracle and no open redirect.** `/canvas` accepts exactly `name=invalid`, `name=limited` or `name=unavailable` (`NameNotice::ALL`, compared to the whole query). `/admin` accepts exactly `notice=` followed by one of `removed`, `unconfirmed`, `self`, `last_admin`, `not_member` or `unavailable` (`org_admin.rs:96-105`, `strip_prefix` then an exact match). Every Location is built from these constants, and none carries request input. Both pages check the session before the query, so an anonymous caller gets the uniform 404 whatever the query. A notice is text the query chose, not server state, so it reveals nothing. A crafted `/admin?notice=unavailable` link only shows a constant notice, the same nuisance already accepted for N4.
- **The 503 `/admin` page leaks no member data.** `outage()` takes no store argument. Its props are constants: "Your organization", an empty summary, the outage words, `members: []`, `has_members: false` and `empty: false`, so neither the table nor "No members yet." shows. The only other prop is the sign-out token for the caller's own cookie. The organization name is not read. The page is identical whether the caller is an admin or not, since at `Standing::Outage` the store could not say, so it does not reveal the caller's standing. It goes through the same SSR renderer as the normal page (`no-store`, CSP; the SSR test at `main.rs:2112-2116`). During a partial outage, a non-admin can tell that `/admin` exists (503, not 404). That was already true before the fix (503 `problem+json`), and the route is public in the source. The unit test asserts the outage page's props and that nothing is read before the admin check.
- **The N2 rule and 0023's CHECK cannot disagree so that the database refuses a name Rust accepted.** The definer and the column CHECK refuse when `length` is outside 1–80, `~ '[[:cntrl:]]'` matches, or `<> btrim`. Here is why none of the three can fire on a name Rust accepted:
  - **Length:** the route trims, and Rust counts chars; PostgreSQL's `length` on UTF-8 counts code points. They agree. On the pinned image, 80 × U+1F331 gives `length` 80.
  - **`btrim`:** by default it strips only U+0020, and Rust's `trim` strips all White_Space first. Storage trims again (`storage/org_admin.rs:199-200`).
  - **`[[:cntrl:]]`:**
    - *Pinned image (`en_US.utf8`):* it matches only Cc. In round 1 it matched U+0085 and not U+2028, U+200B, U+202E or U+3164.
    - *C locale:* ASCII controls only.
    - *ICU:* `u_iscntrl` is Cc, Cf, Zl and Zp.
    - Rust now refuses Cc, Cf (the 15.1 table, unchanged in 16.0), U+2028 (all of Zl) and U+2029 (all of Zp). So Rust refuses a superset under all three providers.
  - **Spot check on the pinned image:** `é`, `Anaㅤ`, `🌱`, `Zoë O'Brien` and `Ana ` all gave `cntrl = f` and the expected lengths. Only `Ana ` gave `btrim` a different answer, and Rust trims it before storage.
- **Sharing `MEMBER_WRITES` doesn't starve other writes in an unexpected way.** The key is `writes:{org}:{principal}`. All 13 callers pass the caller's own organization and principal; the live-sharing account uses a separate `shared:` namespace. So no member can spend another member's window, and starvation can only be self-inflicted. There is one ordering detail. The slot is taken after the same-origin and session checks, and before the token and name checks, as the other write routes do. `csrf::same_origin` accepts only `Sec-Fetch-Site: same-origin` or an exact `Origin`. So only the member's own same-origin requests can spend the slot, including requests with a bad token or an invalid name. The two effects are symmetric: a member who changes their name 120 times in an hour blocks their own folder, share and notes writes until the window slides, and 120 other writes in an hour block the name prompt (R2-b).
