## Corrections to the release B schema record

The integration review ([record](review-integration-2026-11-14.md)) found three NITs in [SCHEMA-RELEASE.md](SCHEMA-RELEASE.md). Evidence files are not edited after the fact, so the corrections are here:

- **NIT-1, at "The 0024 preflight question".** `canonical_jsonb` fails on *any* jsonb parse error, not only the two named: `22021` (invalid UTF-8), `22P02` (invalid JSON), `22P05` (for example a `\u0000` escape, which forma-json-v1 can write) and the like. Each fails the transaction whole and exits 1, so the answer stands. The stronger reason no stored record schema can carry one is the closed grammar: a record schema has only ids (id, version, fields of id, value_type and nullable). The review checked it at `a8d93c31`, `90c7d3b8`, `cc23c557` and the release tree.
- **NIT-2, at "No other statement in 0023 or 0024 depends on existing rows".** Two more CHECKs are validated over existing rows:
  - the re-added `work_permissions_permission_check` (`0024:114–116`). It passes because its set is a superset of catalog-v22's;
  - `work_shares_grantee_or_role`, which reads the old `grantee_id` as well as the new `role`. It passes because `grantee_id` was NOT NULL until `0024:121`.
  
  No constraint at catalog-v24 is deferrable except 0002's four keys.
- **NIT-3, the same section.** "No role can query beta's database before the outage" overstates. The operator task connects as `genui_migration` (`stats`, `list`). What holds is that no reviewed command can run the preflight's query, as the rollback section already says for the version read.

**NIT-6.** PR #124's body heading "Operator steps after merge" now reads "Operator steps around the merge (runbook §2–3)", with a note on the PR that says it was corrected and why. The renewal had to land within 24 hours before the merge, as this timeline shows it did.
