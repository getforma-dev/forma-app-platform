## How it works

- **Cookies** (`__Host-`, `Secure`, `HttpOnly`, `Path=/`, `SameSite=Lax`): pre-login 600 s, pre-access 1,800 s, workspace 43,200 s, organization hint 2,592,000 s. A value is `base64url(organization ‖ 32 random bytes)`: the leading 16 bytes only select the RLS scope (D7.5 tenant-leading rows need it before any lookup); the row is found by the SHA-256 digest of the whole value, so a re-scoped or forged value finds nothing (campaign check 9).
- **Sign-in** (`POST /signin/{handle}`): fetch metadata → limits (10/min and 60/h per address class, 600/h global) → 4 KiB body → handle digest → `resolve_handle` → per-organization route → fresh PKCE (verifier sealed under the process key) and `state` → flow row → PAR without `invite_token` → `303` to `/t/{slug}/auth/authorize?client_id&request_uri`. Unknown, malformed and failing handles answer the same neutral page (400), with no provider call.
- **Callback**: the flow is deleted on first use whatever follows; exchange; `token_shaped`; the reviewed verifier with the registry's tenant for the flow's organization; `sub == user.id`, `exp`/`expires_in` agreement; vault entry; `mint_pre_access` (registry agreement, active binding; a signup flow records its 24 h pending admission in the same transaction). `email_verified` false → `303 /auth/pending`. True → `complete_admission` (a live pending admission of this identity → APP-073 `admit_redemption`; else a current membership and active entitlement) → `mint_session` under `lock_member_authority` (rechecks membership, entitlement, identity and binding; consumes the pre-access row so a second completion mints nothing; transfers the refresh reference; `session.signed_in` on the workspace chain) → `303 /workspace`. Otherwise the neutral denial (403) with sign-out only. Any refusal after a parseable exchange logs the provider session out.
- **Pending and resend**: ADR-006's mapping exactly; the GenUI-side 60 s per-account cooldown and 5 per 24 h answer `unavailable` with no provider call; a lapsed pending admission, a verified identity, `already_verified`, a provider 401/404, a failed refresh or a missing vault entry destroy the pre-access record and `303` to `/signin/{handle}` (handle from the routing hint only when it resolves to the same organization; otherwise `/signin`).
- **Sign-out**: `advance_member_epoch` directly (D7.9) then delete the row, one transaction; then provider logout. Sign-out-all: one advance, every session of the member deleted, each token revoked. Receipts: the revoked token's refresh answers `401 invalid_grant`; the old cookie admits nothing.
- **Protected requests** (`GET /workspace`): `resolve_session` under the fence; idle 1 h, absolute 12 h, inactive membership or organization, expired or revoked entitlement, inactive binding, another registry identity or a missing vault entry delete the row (and revoke its token) and answer the uniform 404; `last_seen_at` is written at most once a minute; no provider call per request.
- **Expiry sweep** every 60 s per registry organization (`FOR UPDATE SKIP LOCKED`, so it never waits on a sign-out holding rows).

## Decisions made in this slice (for review)

1. **Cookie values carry their RLS scope.** `base64url(organization ‖ 32 random bytes)`; only the digest of the whole value is stored. D7.5's tenant-leading rows need the organization before any lookup, and D7.2 allows no third non-RLS index.
2. **Refresh tokens never enter a row.** D7.11 ("referenced from the session row") controls over the plan's `refresh_token_ciphertext` column: rows hold `refresh_token_ref`; the sealed tokens live in the process-memory vault. The PKCE verifier is stored as ciphertext (ADR-006 "encrypted at rest").
3. **A workspace session needs its vault entry**, so a restart signs every member out (D7.18) and no live session outlives its provider-logout capability. A pending user after a restart is sent to a fresh sign-in by the resend route.
4. **`TrustedRequest` carries the current epoch.** One sign-out advances the epoch (fencing in-flight work of every session of the member) but does not end the member's other sessions; sign-out-everywhere does.
5. **Statuses**: neutral sign-in failure 400 (the same page for every cause), denial 403 with the pre-access cookie and sign-out only, `303 /auth/pending`, `303 /workspace`; the protected entry is `GET /workspace`.
6. **Provider routing** comes from the private file `GENUI_AUTH_CONFIG_FILE` (auth and app origins, literal issuer and audience, per-organization tenant slug and client id), read after the organization is known (D7.2); absent, every sign-in fails neutrally.
7. **One pre-access record per browser**: a new arrival destroys (and revokes) the record the browser's earlier cookie named.
8. **`issue-handle --handle`** installs an exact, already-issued handle so one routing value can be registered with fAuth once and installed per environment; every handle change writes `handle.rotated` (D7.8's only handle kind).
9. **Signup flows** are created by APP-074's invitation entry through `begin_flow(FlowKind::SignUp { code_digest, .. })`, which reserves the code bound to the flow's own context digest in one transaction; APP-009 exercises it only through a labeled local stand-in.
10. The flow's client address class is stored, not enforced (ADR-006 lists no refusal for it).

## Limits

- The provider is the `cfg(test)` synthetic loopback issuer: simulated PAR, hosted page, token, refresh, logout and resend; never the deployed fAuth. Hosted routes in browsers, real mail, forwarded-IP forgery and the invitation limits are APP-074/076.
- The campaign renders through a test page renderer; the SSR pages are covered by the binary test, the HTTP smoke and the image qualification. No browser was used.
- Local password authentication over TLS, not RDS IAM; synthetic identifiers; the live registry is APP-076's.
- Rate-limit windows and the vault are in-process (D7.5, D7.18); the trusted-proxy rule takes the rightmost `X-Forwarded-For` unconditionally until APP-074 restricts it to the load balancer's peers.
- The storage-level concurrency check constructs a `VerifiedIdentity` directly (the verifier crate's type has public fields); the route path always obtains it from the verifier.
- No independent review; nothing pushed; no CI.
