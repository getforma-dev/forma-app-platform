### Is the drop reasonable?

Yes. Fences were P3 and never built, and nobody asked for a container. ADR-018 removed their per-app use. The current direction is the first-run trial, and Victor does the browser QA, so a new canvas surface has a real cost. A new ticket can bring fences back. Those reasons support the decision. Two of the four reasons as written need correcting (M1).

### Findings

**Major**

**M1. The addendum overstates what exists and leaves out APP-150** (ADR-018:30, :31, :33, :35).
- Nothing today lets a member group things on the canvas. `/arrange` is an automatic tidy. Library categories are fixed and live in the pane. Folders hold files.
- ADR-018 is a Reference document, so a later reader will take "grouping is already covered" as fact.
- The addendum has not landed yet, so it can still be edited in place. Suggested text:
  - **The per-app purpose is gone.** ADR-018 keeps each app whole, so no fence is needed to collect an app's components. What remains is a group of several apps and widgets that the member names.
  - **Nobody is asking for that grouping.** `/arrange` tidies whole apps into rows, the Library sorts apps into fixed categories, and folders hold files and the apps built from them. None of these is a named region on the canvas. No ticket or note since October 30 asks for one.
  - **Reopening:** APP-150 (Victor, 2026-11-01) will let a member mark sections of the board and jump to them. Those sections are bookmarks, not containers. A reopened fence should build on APP-150's section instead of adding a second region model.

## APP-116: every reader sees the tool and duration

### What the code does

- **The query.** `Workspace::agent_attributions` (agents.rs:253–283) reads each attribution of one work with its token label.
  - A LEFT JOIN LATERAL also reads `tool` and `duration_ms` from the access log (agents.rs:263).
  - It takes the first allowed row from the same token where `tool` equals `$5`, which is `mcp::tools::COMMIT`.
  - That row's `touched_records` must contain the record, and the row must fall in or after the attribution's second.
- **The route.** The records route calls this only after `Data::list_records` has authorized the reader (routes.rs:824–846).
  - `records_document_with` adds `via_tool` and `via_ms` for the record's current version only (routes.rs:786–793).
  - No other route sends these fields. `record_search.rs:64` uses the listing without attributions.
- **The canvas.** The call appears in two places:
  - in the tooltip of the via chip, which is always shown (records.ts:171–173);
  - in the activity chip, only when timings are on and a new version arrives live (records.ts:156; timing.ts:113–135).
  - `agentCall` accepts only a tool name matching `forma_[a-z_]{1,40}` and a finite, non-negative number.
- **The owner's view.** The owner's activity route still filters by `token_id` and `principal_id` (storage/governance.rs:425).
- **The campaign.** The MCP campaign checks the cross-member case both ways:
  - Sarah reads Diego's Claude commit (mcp_campaign.rs:751–764);
  - Diego reads Sarah's OpenAI decision (:812–821).

### Is "every reader sees tool and duration" accurate?

Yes, in the data. Every member who passes `list_records` on the work gets both fields for the current version. On screen, the call is always in the via chip's tooltip, and it appears in the activity chip only when timings are on. The closure's Limits section already says so (closure :27).

### Privacy

The reasoning is sound.
- **Tool name.** It is always `forma_commit`, because the join filters on that name (agents.rs:263). It tells a reader nothing beyond the "via Claude" label they already see.
- **Duration.**
  - It is measured from just after token authentication to the tool's return (mcp/mod.rs:466, :435).
  - For `forma_commit` it covers the commit transaction (tools.rs:1117), the attribution insert, and one `share_work` per named approver (tools.rs:1145–1186).
  - It reveals nothing about record values.
- **Another member's token activity.**
  - A reader learns only the duration of the one commit already labeled on a record they can read. Other calls, touched ids, refusals and counts stay behind the owner filter.
  - If an access-log write fails (mod.rs:436–443), the record could show a later allowed `forma_commit` by the same token on the same record. That is the same token and the same record, so the effect is only on the display.
- **Timing side channels.**
  - A commit's duration includes waits on the organization-wide sequence lock, so a long value hints that other commits were running in the organization.
  - The same listing already carries the organization-wide `commit_sequence` (routes.rs:757), which shows that more directly.
  - Approver shares add a few milliseconds each, which is less than the normal variation of a commit.
  - I found no channel worth closing.

### Findings

No Major findings.

**m7. Reversing the decision takes more than a one-line filter** (closure :46). The MCP campaign checks cross-member visibility at mcp_campaign.rs:758 and :818. A reversal would also change those checks and the closure's acceptance mapping (:19).

**m8. The decision lives only in evidence and one ticket log line.**
- AGENTS.md:11 asks for new decisions in docs/architecture or docs/planning, and evidence is read only from a path in a ticket or ADR (AGENTS.md:25).
- Readers learn about the via chip in docs/pitch/CONNECTIONS.md:20 (Reference). One dated sentence there, linking the closure, would make the rule easy to find.

**m9. The stated reasons could be more exact (optional).** They could say that the tool is always `forma_commit`, so only the duration carries information. They could also say what the duration contains, as described above.

### Verdict for APP-116

**No blocking findings.** The decision, as built, matches the code, and its privacy reasoning holds. m7–m9 are suggested edits to the written record, not to code.
