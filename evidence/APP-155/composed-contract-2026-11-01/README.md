# Composed app contract and exact-work adoption

This packet qualifies the APP-155–157 contract/storage seam and its APP-158/159 declarations in the local `codex/composed-app-implementation` candidate. Victor's explicit request to implement APP-155–160 supersedes the tickets' earlier after-trial sequencing. It does not establish hosted delivery, real-provider acceptance or the complete APP-160 presentation journey.

The additive contract edition is `impl-2026-11-01.2`. Optional version-1 `presentation` metadata declares bounded sections, plain-text descriptions, app-agnostic actions (`navigate` or `dialog` to an exact component) and finite mode/accent/density/font tokens. Data `links` keep their meaning. Definitions without presentation retain the layout fallback. Five closed records renderers and scoped filters reference exact admitted records inputs/schemas; reference fields may be displayed but are not qualified sort keys. Existing retained fixture bytes and digests remain unchanged. Record-component receipts use their own kind/domain; they do not impersonate source-query receipts.

`GET/POST /v1/work/{app}/{work}/presentation` addresses one existing saved work. A save requires the exact publication, admitted digest and work version, current owner plus `edit_definition`, and current owner-publish policy. It admits the full cloned definition before the existing Workspace draft and Control publication operations. The final Workspace adoption locks that exact work, rechecks entitlement after waiting, verifies the private organization/app/work and binding premises, and compares all content except presentation. One transaction updates the work and its collection/binding publication pins and appends the workspace audit event. Record values, collection identities and sibling works remain intact; old live-share pins fail closed on the changed publication/version.

Draft/publication and adoption are deliberately separate existing roles. A race after publication can leave an audited unused immutable publication. The loser never partially adopts a work or copies records. The browser must reconcile an uncertain result before any new edit; neither this packet nor the endpoint claims an atomic transaction spanning draft/publication/adoption.
