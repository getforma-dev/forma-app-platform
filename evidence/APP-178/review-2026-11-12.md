## Findings

### Blocker

**B1. Box 1's restore clause is not met for connected links, and the closure's justification is inaccurate.**
- The check asserts that restoring the organization does *not* bring the link back (`shared_campaign.rs:1009-1017`).
- The closure calls this the same as re-enabling placement (`closure-2026-11-12.md:14`). It is not.
  - A placement change bumps `version` (`shared_access.rs:443`), so the old link always fails `access.version == grant_version` (`:540`).
  - A suspension leaves the version unchanged. The link is removed only if `linked_apps` runs during the window (`:546`). That happens on the canvas listing or on opening any shared page (`sharing/live.rs:476,626`).
  - What the guest sees after a restore therefore depends on whether they looked during the suspension.
- Management meanwhile reports the grant as "paused" (`shared_access.rs:181-186`), and ADR-014 keeps each reference's identity (`ADR-014:22-23`).
- Box 1 says "restoring the organization restores access". The check proves this for view access only.
- A test should not lock in this behaviour before a product decision. Victor should decide, and the decision should be recorded in `docs/architecture`. Then either reword box 1 to match, or change reconciliation to hide paused links rather than unlink them (a product change with its own ticket).

### Major

**M1. Box 2 "does not reveal whether the recipient has an account" is shown only for a signed-in caller who matches the invitation.**
- The check compares `accept_live_share` for an expired key with an unknown key, for an existing account (`:1097-1111`).
- The path for a caller with no account or session is `shared_auth_target` (`shared_access.rs:319`), which `auth/shared.rs:203` uses to start sign-in. It is not asserted.
- Under (c) it returned `Ok` for the expired key. Only the acceptance assertion caught the mutation.
- Fix: assert that `shared_auth_target` refuses an expired key exactly as it refuses an unknown key. Ideally also check that HTTP returns the same 404 for both.

### Minor

- **m1. Vacuous resolve assertion** (`:1113-1119`). The invitee never accepted, so `resolve_access` refuses whatever the expiry, as (c) showed. The check text "or resolved" (`:1120`) over-claims. Fix it by expiring an *accepted* grant and asserting that resolve and release refuse, or drop the words.
- **m2. The overlapping case has only one placed grant.** The second grant has `allow_add=false` (`:907`), so no second link exists that could survive. A reconciliation bug that unlinks by `(account, organization)` would pass. ADR-014:22 says "each connected reference retains its own share identity". Fix: let both grants place, link both, and assert that the second link survives.
- **m3. The `linked_apps` disjunction** (`:989`) also accepts `Err(Denied)`. It is not vacuous in practice: had `linked_apps` refused before reconciling, the link would survive, and the post-restore `is_empty` assertion (`:1009-1017`) would fail. Still, tighten it to `Ok(empty)`.
- **m4. "(audited)" is not asserted.** The check text (`:1033`) claims the unlink was audited, but no audit row is queried.

## Holds

- **Bracketing.**
  - Shutdown: both grants release before; both release after; reads and resolve succeed later (`:1056-1066`). Diagnostics under (a) show `o.status` is the only gate.
  - Expiry: `pending_share` is true before (`:1086-1095`), the invitee is the matching account, and the backdate keeps `created_at < expires_at`.
  - The unknown key keeps a valid UUID shape (`storage/mod.rs:165`), so its refusal comes from the row lookup, not the parser. Both refusals are `Err(Denied)`, a unit variant, so they are equal at the store level, as claimed.
- **The race step** is a deterministic interleaving: authorize and compute, then suspend, then release. It is the same pattern as APP-154's revocation check, and it exercises the release-time `check_guest` that protects against a slow query. It does not commit a shutdown while a guest transaction is open (limitation only).
- **Two independent grants.**
  - They are distinct rows (`:911`) with distinct idempotency keys and different placement permissions.
  - The exact `GuestAccess` equality (`:1067`), reads and release prove the second is intact.
  - Both come from the same sponsor; grants from two different sponsors are not exercised.

## Per-box verdicts

2. Expired invitation: **partly met.** "Cannot be accepted" is met and proven by mutation. "Reveals nothing" is shown only for the signed-in matching caller (M1).
3. Overlapping grants: **met** for view access, proven by mutation; the links gap is m2.
4. Mutations: **met.** All three reproduce. Review clause: not met while B1 and M1 are open.
