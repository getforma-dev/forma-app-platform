## MAJOR-1 in detail

### The reserved code

Exit codes already in use:
- in `runtime.py`, 0, 1, 2 (argparse) and 3 (`object`'s write-once conflict);
- `serve` returns its child's code;
- the Rust binary uses 1, 124 (managed qualification timeout) and 75 (the dev binary's reload, `app/src/dev/mod.rs`);
- CPython uses 120 for a failed flush at shutdown, and a signal gives 128+N.

The review suggested 75, but 75 is already the dev reload code, and as sysexits' `EX_TEMPFAIL` it suggests "retry", which is the wrong advice here. **4** is the next unused small code.

`runtime.py`'s module notes now list every mode's codes. `migrate` has exactly three:
- 0: committed;
- 1: refused or failed before the COMMIT was sent;
- 4: the COMMIT may have reached the server.

`schema_release.MIGRATION_COMMIT_OUTCOME_UNKNOWN` pins the value, and a test reads it from `runtime.py`.

### A second post-commit path the review did not name

The new process test closes stdout right after a successful commit. Before the fix, `print` only buffered the completion line, and the flush at interpreter shutdown failed. CPython then exits **120** whatever the program's own status was (`Py_RunMain` and `Py_Exit`). 120 was inside the restore's accepted 1–127.

So the fix does three things:
- it flushes the completion line inside the guard;
- it leaves through `os._exit(4)`;
- it narrows the restore to exactly exit 1, not "1 to 127 except 4".

Mutation R2 shows why `SystemExit(4)` is not enough: the unflushed buffer then turns it into 120.

### Fix-forward without a command

The runbook now:
- says to stay on the candidate and keep the lock;
- reads the schema version with the candidate operator image's documented `verify-catalog` (the `to` catalog) and `verify-catalog-baseline` with `--version` set to `from`;
- says what to do at each outcome.

No command runs those reads while the lock is held:
- `ops/promotion/admission.py` (merged from main) runs operator-task overrides, but `reviewed_state` refuses while `active` is set;
- `admission-stats` proves only the image's latest catalog, so it cannot tell `from` from "neither";
- the legacy `ops/beta/run-step.sh` is fenced after the cutover.

The runbook says this plainly. The read is a separately reviewed operator action. So are fixing forward onto the candidate and restoring after a read that shows `from`.

## Limits

- **Synthetic proof.** The proof uses a stand-in psycopg over the runner's MigrationRecorder. It shows how `runtime.py` maps a failure at or after the COMMIT, but it does not reproduce an RDS failover. No AWS or database was used.
- **The operator's own `migrate` is unchanged.** `app/operator/operator.py migrate` has the same lost-acknowledgement class: it commits, and a failure exits 1. Its only runner is the legacy window flow, which is fenced after the cutover. That flow treats only exit 0 as success, and no restore reads its exit code.
- **Fix-forward has no command.** Reading the version while the lock is held, activating the candidate, and restoring after a `from` read are all separately reviewed operator deliveries. The runbook says so, and invents no command for them.
- **The scanner is not re-read at execute.** This is MINOR-2, documented by decision.
- **No full `just check`.** The Python, schema-pin, board, shell and `fmt` steps ran (above). Not run here: clippy, clippy-dev, the Rust tests, http-smoke, MSRV, admin, infra (npm), contracts, schema-qualifier and campaigns-ci, which need the admin build, Node dependencies or Docker in this worktree; `catalog` failed for that reason. No Rust or TypeScript file changed. CI covers them on the PR.
