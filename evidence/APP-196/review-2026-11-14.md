# APP-196 Tier A review: the schema restore command and the scan-delta binding (2026-11-14)

**Reviewer:** Claude (Opus 5.5), an independent subagent. It had not written or reviewed this code before.

**Base:** `origin/main` at `92d8e673d009910971875dfa3265431aba383982`, in a separate worktree on branch `review/app-196`. The main checkout was not touched.

**Verdict: no BLOCKER. One MAJOR, five MINOR and seven NIT.**

The restore command cannot release the lock, or record a restore, on a database that has moved. The previous image proves the exact catalog and version on every connection, and the command keeps the lock if that proof fails.

The command's central guarantee is stated too strongly, though. An exit code from 1 to 127 does not prove that the migration did not commit. A COMMIT whose acknowledgement is lost also exits 1. In that case the command restores the previous release onto a migrated database, and the restored release can never become healthy. Beta then stays down in a state that no runbook text covers.

Fix MAJOR-1 before release B's candidate image is built, because the migration runs on the candidate image. The MINOR findings are cheap and worth doing in the same pass.

## Findings

### MAJOR-1: An exit code from 1 to 127 does not prove the migration did not commit

**Where:**
- `app/runtime/runtime.py:915–919` and `1267–1269`;
- `ops/promotion/schema_recovery.py:66–73` (and the claim in its docstring, lines 11–16);
- `docs/pitch/BETA-PROMOTION.md:61`, `:68` and `:71`;
- `evidence/APP-175/SCHEMA-RELEASE.md:30`.

**What the code does.** `migrate()` runs `apply_migrations` inside `with psycopg.connect(...) as connection:`. In psycopg 3.3.6, `Connection.__exit__` calls `self.commit()` when the block exits cleanly (`psycopg/connection.py:175–176`). The completion line is printed after that. Any exception in `__main__`, including one raised by the commit itself, becomes `SystemExit(1)` (lines 1267–1269). `migration_outcome` accepts any `EssentialContainerExited` exit from 1 to 127 as proof that "the transaction did not commit" (lines 69–73).

**Failure scenario.**
1. Release B's migration applies 0023 and 0024, and the client sends COMMIT.
2. The server commits.
3. The connection drops before the acknowledgement arrives, for example in an RDS failover or a network reset. psycopg raises `OperationalError`.
4. The task exits 1 by itself, with `stopCode` `EssentialContainerExited`. A failing completion print at line 919 after the commit gives the same exit.
5. `execute` keeps beta down with the lock held, which is correct.
6. `restore-after-failed-migration` then accepts the observation and restores the previous release onto a database that is now at 24:
   - it creates and executes `forma-restore-<id>`;
   - it proves the services stopped and records `restore-activation-intended`;
   - it activates both services.
7. The previous image (schema 22) refuses every connection, so `/health/ready` stays 503 and its ALB target never becomes healthy. The restore refuses, either in `settle_services` or at the boundary's target-health check. The lock is kept and `restore-outcome.json` is recorded.

Nothing writes to the database:
- the pool refuses before any application statement;
- the broker has no database connection.

The cost of this failure:
- beta stays down for the restore's own waits too (up to 1200 + 900 + 900 + 900 s);
- both services are left at desired count 1, with the main service failing readiness (scenario 4);
- the stack is on the previous release while the database is on the new schema;
- the only correct recovery is to fix forward onto the candidate, which has no command and no runbook text.

The runbook says the opposite:
- "a migration that fails leaves the database at version 20" (line 61);
- line 68 treats an exit by itself "with a code from 1 to 127" as safe, and only "a task stopped from outside or ended by a signal (137, 143)" as one that "can have stopped on either side of the commit".

**Proof (scenario 8).** `LostCommitTests` loads the real `runtime.py` and executes its real `__main__` block with `migrate`. It uses a fake `psycopg` whose `__exit__` sends the commit and then raises `OperationalError`, which is the lost acknowledgement. Result: `SystemExit(1)`, with `{'applied': True, 'commit_sent': True}` recorded. The existing `test_previous_release_that_never_becomes_healthy_keeps_the_lock`, plus scenario 4, show the state that follows.

**Fix.**
1. In `migrate()`, commit explicitly in its own `try`. Make any exception from the commit onward, including the completion print, exit with one reserved code meaning "commit outcome unknown" (for example 75).
2. Make `migration_outcome` refuse that code with "commit outcome unknown; reconcile, fix forward if the catalog moved".
3. Add a test of both halves and see it fail first.
4. Correct `BETA-PROMOTION.md` lines 61, 68 and 71, and add a paragraph for a restored release that never becomes healthy:
   - the database has probably moved, so do not retry the restore;
   - keep the lock;
   - fix forward with a separately reviewed operator delivery.
5. The fix must be in the candidate image that release B migrates with, so it must merge before release B prepares.

### MINOR-1: A failed phase write after the plan receipt locks the restore out for that state

**Where:** `ops/promotion/schema_recovery.py:142–145`.

**What the code does.** The plan receipt is the immutable `restore-plan-<first 16 of the reviewed state hash>.json`. Next comes the CAS write to phase `restoring`.

**Failure scenario.** The phase write can fail without changing the state:
- a transport failure before S3 accepts the PUT;
- the operator's process killed between the two writes.

Either way, the reviewed state hash is unchanged. Every later `--apply` for that state then fails on the existing receipt (`412`) before any mutation. No command changes the state while the phase is `executing`, so the restore stays unavailable while beta is down, unless someone edits the canonical state by hand.

**Proof (scenario 6).**
1. The first state write fails once with `ConnectionError`. The state digest is unchanged and no AWS mutation was made.
2. A second `apply` of the same reviewed hash refuses with `RuntimeError(412)`, still with no mutation.

**Fix.**
- Name the plan receipt per attempt (for example the state-hash prefix plus a `uuid4`), and record that name in the phase CAS beside `restore_plan_sha256`, which is already recorded.
- Add scenario 6 as a test and see it fail first.

The comment "a refused attempt never blocks a later review" (line 141) is true only if the state changes between attempts.

## Verified as sound

**Restore preconditions.** Each one refuses with no state write and no AWS mutation. The suite's 19-case test covers most of them, and B1–B4 and scenarios 2, 3 and 5 cover the rest. The preconditions are:
- the exact reviewed hash, checked at plan and again before the first write;
- phase `executing` with the schema release in the packet;
- every journal entry `confirmed`;
- the four required entries, with no duplicates, and only prepare-time names, the four required names or `schema-migrate`. This allowlist is stricter than "nothing after the migration".
- the `schema-migrate` entry itself:
  - none is accepted;
  - an intent refuses;
  - exit 0 refuses;
  - a missing exit code, a missing observation, a start with failures, an observation naming another task, one not STOPPED, a signal code (137, 143) and `stopCode` other than `EssentialContainerExited` all refuse.
- operator identity: not the prepare, execute or CloudFormation role, and not inside GitHub Actions;
- the run's identity (first attempt, push to `main`, the trusted workflow, the candidate SHA), the run being completed, and the 65-minute fence;
- the stack on the candidate's parameters, with both services settled at 0, every task definition and schedule exact, and the restricted role on the stack;
- no pending change set;
- the template's hash and its stored object both equal to the baseline;
- the previous parameters differing only in images and expiry, with desired count `'0'`;
- the previous expiry more than an hour away.

**The second proof holds.** The previous image's pool verifies the exact reviewed catalog, then the version, on every new connection, before any application statement:
- `pool.rs:338–347` (`verify_admission`) and `599–611`;
- `catalog.rs:9` (`catalog-v22.json`).

Readiness runs that admission on each role pool (`readiness.rs:81` → `pool.rs:765–770`). The main service's ALB target uses `/health/ready` (`stack.ts:427`), and the restore's final boundary requires every target healthy. The broker has no database connection (`shared-broker.ts:40`).

The restore therefore cannot reach `restored` on a moved or partly moved database, and it writes nothing to it. This is the property that keeps MAJOR-1 from being a blocker.

**Restore execution.**
- The change set `forma-restore-<id>` carries the baseline template's own object, all previous parameters, `CAPABILITY_IAM`, the restricted execution role and a deterministic client token.
- `guards.changeset` limits it to task-definition, service and schedule modifications. The change set's template is read back before execution.
- Execution is journaled, with a deterministic request token, and `UPDATE_COMPLETE` is required.
- Both services are proven stopped on the previous images and the immutable `restore-stopped.json` is written before the activation intent. The intent is written by CAS before either activation, and each activation is journaled.
- Health is proven with the live registry's exact digests (`registry_override`), container health and every ALB target healthy, followed by the public probes.
- On success, the failed window is abandoned and the previous window counts its whole reservation again. The baseline digests and the schema policy are unchanged, and the stack role is recorded.

**Failures in between.** Each one was traced. All of them keep the lock, and none replays:

| Failure | What follows |
| --- | --- |
| Lost CreateChangeSet or ExecuteChangeSet response | The journal keeps an intent. |
| Change set outside the runtime | Never executed (tested). |
| Rollback | Refused, with the services stopped (tested). |
| A stack, settle or health wait expires | Refused. |
| Expiry within 10 minutes | Refused before the activation intent. |
| Lost activation response | The journal keeps an intent. |
| A probe fails | Refused, with the outcome recorded. |

The command cannot be run a second time:
- the phase gate refuses it;
- `Store.operation` refuses a repeated name or any pending intent;
- every state write is a CAS on its ETag;
- every receipt is If-None-Match;
- the SDK makes one attempt per call (`aws.py:13`).

**Scan-delta binding.**
- All three call sites pass the candidate's `bundle.source.deployment_contract_sha256`. Mutating any of them to the baseline's fails the suite (S1–S3).
- When findings are introduced, the disposition's contract is compared per role, so a disposition for one contract cannot be used for another.
- Each predecessor digest is bound to the live registry, so the committed November 14 disposition is inert after release A.
- `test_scan` binds the JSON's contract to the schema-release pin.
- Expiry is enforced at every evaluation (S5): preparation, the start of execute and each final check.
- A CRITICAL among the current findings refuses even if the predecessor had it (S6), and `publish()` refuses it as well.
- A disposition that expires after the snapshot leaves the phase `prepared`, so the release can be abandoned. The schema-release equivalent is tested, and the final checks share that path.

**Runbook.** The restore section's preconditions, sequence, phases, change-set name, role, receipts and lock behaviour match the code. Exceptions:
- MAJOR-1 (the exit-code guarantee);
- MINOR-5 (stale disposition counts);
- NIT 1–3.

### 1. The exit-code contract holds

Traced through `migrate()` and `commit_migration()` in `app/runtime/runtime.py`, psycopg 3.3.6 and CPython's shutdown.

**Before the COMMIT, every path exits 1.** These all reach `__main__`'s `except Exception` and become `SystemExit(1)`:
- an import or argument failure;
- the environment or manifest checks;
- a refused connect;
- any failure inside `apply_migrations`. Its `except BaseException` closes the connection without committing, and the server aborts an open transaction on disconnect.

A failure at module import is an uncaught exception, which is also exit 1. All of these happen before a COMMIT exists.

**From the COMMIT onward, nothing can exit 1.** `commit_migration` wraps `commit()`, `close()` and the flushed completion line in `except BaseException`. Every failure there, including `KeyboardInterrupt` and `SystemExit`, ends in `os._exit(4)`, behind a `try/finally` that survives a failing stderr write.

There is no code between `apply_migrations` returning and `commit_migration` entering its `try`. After a successful flush, shutdown has nothing left to flush, so it cannot turn the exit into 120.

**Signals.**
- Handlers are installed only in `serve` (line 1052).
- The migration container runs `python3 /app/runtime.py migrate` as PID 1, with no init (`infra/src/stack.ts:456`). An ECS stop's SIGTERM is therefore not delivered: there is no handler, and the process is PID 1. The stop ends in SIGKILL, which gives 137.
- SIGINT, which ECS never sends, would give 130 after the commit, or 4 during it.
- None of these can give 1.

**`os._exit(4)` is safe there.** It skips:
- the flush of a stdout buffer that holds nothing more;
- atexit handlers, of which there are none;
- closing the connection, which process exit does anyway. Whether the server commits does not depend on it.

The one evidence line, `migration_commit_outcome_unknown`, is flushed to stderr before the exit. The builder's mutation R2 (below) shows why `SystemExit(4)` would not do: its unflushed buffer turns into 120.

**So `EssentialContainerExited` with exit 1 still means nothing committed**, on one premise that no test guards: no migration file contains statement-level transaction control (NIT-R1). A scan of 0001–0022 found none. The only DEFERRABLE text is in `0002`'s foreign keys, and the only `END;` statements are PL/pgSQL bodies.

### 2. Is "exit 1 only" too strict?

**For the program's own exits, no.** Every genuine failure before the COMMIT exits 1, with three narrow exceptions:
- 120, if the log pipe itself is broken during shutdown;
- 130 for SIGINT;
- 2 for an argument error, which cannot happen with the task definition's fixed command.

Refusing those costs nothing in practice.

**Two strandings sit outside the exit-code rule.**

**MINOR-R1: a COMMIT the server refuses exits 4, although the server rolled back.**
- **Where:** `runtime.py` `commit_migration` (`except BaseException` around `connection.commit()`).
- **What happens:** the schema has `DEFERRABLE INITIALLY DEFERRED` foreign keys, `0002_tenant_foundation.sql:135`, `145`, `174` and `179`, on work publications and internal records and revisions. A migration that writes rows violating one of them fails *at* COMMIT. The server returns an error (class 23) and rolls back. psycopg raises from `commit()`, and the task exits 4.
- **Proof:** a scratch run of the real `runtime.py migrate` gives `exit 4` with `{"commit_sent": true, "rolled_back_by_server": true}`. It uses `test_runtime.FAKE_PSYCOPG`, with a `ForeignKeyViolation` (`sqlstate 23503`) raised from `commit()`.
- **Failure scenario:**
  1. Release B's 0024 ("private entries and share roles") backfills rows under one of those keys.
  2. A beta row violates it.
  3. Execute keeps beta down, the restore refuses exit 4, and the read shows `from`.
  4. Then "restoring the previous release … is a separately reviewed operator delivery; neither has a command".

  Before the fix this exited 1, and the restore worked.
- **Fix:** run `SET CONSTRAINTS ALL IMMEDIATE` as the last statement before the COMMIT, inside the guarded block that exits 1. PostgreSQL checks pending deferred constraints, and deferred constraint triggers, retroactively at that statement. A violation then fails before any COMMIT is sent, and the semantics of the transaction up to that point do not change.

  Add a recorder test (the statement comes after the final catalog proof and before `commit`) and a process test (a refusal there exits 1 with no `commit_sent`). See both fail first.
- **Severity:** MINOR now. It becomes MAJOR if 0023 or 0024 write rows that a deferred constraint covers, so APP-194's review must check.

**NIT-R2: a RunTask that returned only failures still refuses** (`schema_recovery.migration_outcome`, "migration start is not one known task"). A confirmed RunTask response with no task and a failure entry proves no task exists, so nothing ran. Accepting it as "never started" would keep the restore available for ENI or capacity failures.

`TaskFailedToStart` with no exit code is less certain. It can stay refused. Both are refusals inherited from APP-175, not regressions.

### Does the check break a migration that relies on deferral?

No. The statement runs once, after every migration of the release. So it checks exactly the rows that COMMIT would have checked. Rows written out of order and resolved within the migration's own transaction still pass, as the out-of-order case above shows.

Only rows still violating at the end fail, and those would have failed at COMMIT anyway, now with exit 1 instead of 4. It is also transaction-scoped, so runtime transactions are unaffected.
