## Findings

1. **Read operations created apps and grants.** `composer_context` is also called by `GET /v1/commands`, MCP listings and record draft resolution, and Slack. The new shell code made those operations write an app, three grants and an admission audit before an explicit compose. The existing MCP denial-footprint assertion caught this in [Pitch CI run 41315800777](https://github.com/getforma-dev/forma-app-platform/actions/runs/41315800777). Fixed by keeping `composer_context` read-only and using `prepare_composer` only in explicit app and folder compose. The member fence and stored authoring choice are unchanged.
2. **The new schema was absent from image contexts.** The service image could not compile its embedded `catalog-v16.json`, and the service/operator allowlists omitted migration 0016. This caused [Foundation 41315800725](https://github.com/getforma-dev/forma-app-platform/actions/runs/41315800725), [Parser release 41315800727](https://github.com/getforma-dev/forma-app-platform/actions/runs/41315800727) and [Tenant 41315800722](https://github.com/getforma-dev/forma-app-platform/actions/runs/41315800722) failures. Added the required files to the service, operator and qualification contexts. Migration SQL, catalogs and their checksums are unchanged.
3. **The MCP campaign retained the superseded no-owned-app rule.** After finding 1 was repaired, its next assertion expected an active member's own compose to return `not_found`. APP-145 deliberately permits that member to create an authoring shell. The updated case requires exactly one canary-owned unpublished shell, three permitted grants, one permission audit, no source/work grant, and no Northstar change. All unauthorized/cross-tenant denials remain. The no-model stand returns `could_not_compose` for that legitimate request.


4. **A queued first compose could create a second shell after publication.** The candidate read preceded the advisory lock, while the SQL helper only reuses unpublished shells. A deterministic regression held the advisory lock, let a second first-compose queue, created and published the first shell through the existing admission/publication path, then released the waiter. Before the fix the waiter returned a different app id (campaign failed in 15.93s). `prepare_composer` now acquires that same member advisory transaction lock before reading candidates; it reuses a shell even if it was published while waiting. The SQL helper's lock is reentrant. Read-only context does not take this advisory lock. The SQL helper still only reuses unpublished shells: callers creating on behalf of a member must keep the full authoring selection inside this lock.


5. **Entitlement expiry during the advisory wait could still create a shell.** The member fence checks entitlement before the additional wait. A held-lock regression expired a new member's entitlement while their preparation was queued, then released the lock. Before the fix it returned an authoring shell instead of `Denied` (18.85s). `Permit::recheck_entitlement` now reuses the existing `clock_timestamp()` query immediately after advisory acquisition, under the still-held membership/epoch fence. The regression requires denial with zero app, permission or grant-audit rows. Membership revocation/epoch and unknown-principal checks remain.
