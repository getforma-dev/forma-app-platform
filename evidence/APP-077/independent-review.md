## Findings

### Blocker

None.

### Major

**M1. On AWS, the 412 → `HeadObject` re-read needs `kms:Decrypt`, which `OperatorRole` does not have, so every rerun refuses and a partial upload can never be completed.**
`app/operator/operator.py:410` calls `head_object(..., ChecksumMode="ENABLED")` and `:411` requires `ChecksumSHA256`. The S3 HeadObject API reference says that for general purpose buckets, when checksum mode is enabled on an object that was uploaded with a checksum and encrypted with a KMS key, the caller "must have permission to use the `kms:Decrypt` action to retrieve the checksum". Every object this tool writes is like that (SSE-KMS plus `x-amz-checksum-sha256`). `infra/src/stack.ts:270` grants only `kms:GenerateDataKey`. The first run succeeds. Any later run gets 412 on `original`, and then the HEAD is denied (→ `object_write_refused`) or comes back without a checksum (→ `existing_object_differs`). So the README's claims (§Acceptance 3, "a rerun completes a partial upload and leaves equal objects unchanged"; the S3Tests) hold only against `local_s3.py`, which does not model this rule. This settles half of open question 7. The outcome is safe (a refusal, never a write), but the recorded recovery answer is false for the target environment.
*Fix:* in `infra/src/stack.ts`, inside the tenant loop (next to `:270`), add
`operatorRole.addToPolicy(new iam.PolicyStatement({ actions: ['kms:Decrypt'], resources: [keys[i].keyArn], conditions: { StringEquals: { 'kms:ViaService': `s3.${this.region}.amazonaws.com` }, StringLike: { 'kms:EncryptionContext:aws:s3:arn': bucket.arnForObjects(`o/${tenant}/s/*`) } } }))`
and add the same two conditions to the existing `kms:GenerateDataKey` statement (m3). Then extend the CDK test at `infra/test/security.test.ts` ("operator task role … reaches only B1 source objects") to expect exactly `kms:GenerateDataKey` and `kms:Decrypt` under those conditions. Teach `local_s3.Stub` to refuse a checksum-mode HEAD of a KMS object unless the test grants decrypt, and add a test that a rerun without the grant refuses. Correct README §Acceptance 3 and open question 7. The alternative, dropping `ChecksumMode` and comparing ETags, does not work: for SSE-KMS objects the ETag is not the MD5 of the data.

**M2. D7.10's "records real digests, replacing the seeded placeholders" is not implemented, has no recorded owner, and the upload writes at the placeholder revision's immutable key.**
ADR-007 D7.10 (`docs/architecture/ADR-007-PHASE-1-WRITE-AUTHORITY.md:74`, last sentences) says the operator package "records real digests, replacing the seeded placeholders for the Northstar organization". Plan Task 9 (`PHASE-1-EXECUTION-PLAN.md:208`) repeats this for `source_revisions` and `work_bindings`. `upload-sources` only prints them (`operator.py:339-350`). The seeded row keeps `normalized_digest` `bb16c6e4…c119` and `row_count` 5, while the real object is `0c2582d8…a082` with 6 rows. D7.10's fetch, unchanged by ADR-009 B1, verifies `source_revisions.normalized_digest`, so APP-012 would refuse the uploaded Parquet. The author is right that an in-place rewrite is wrong: the composite FKs at `app/migrations/0002_tenant_foundation.sql:147,160,187` reference `normalized_digest`, the seed is exact-match idempotent, and ADR-009 D9.3 says nothing is rewritten. But the tool also commits a choice: it writes `o/…001/s/…006e/r/…006f/{original,part.parquet}` with `If-None-Match: *` and no delete grant. If the resolution is "a new revision row", the `…006f` key keeps bytes that contradict that revision's row forever.
*Fix (recommended; no managed seed exists yet):* make the seed edition carry the real `content_digest` `6e0f0ed7…4647`, `normalized_digest` `0c2582d8…a082` and `row_count` 6 for revision `…006f`, with every chained digest that follows (a reviewed fixture/contract edition change). Then make `plan_sources` refuse unless the plan's digests equal the seeded ones, replacing `seeded_placeholders` with an equality check, so the DB and the objects cannot disagree. If Victor prefers a new revision instead, change `SOURCES` to that revision id before any managed upload. Either way, record in APP-077 and APP-078 that `upload-sources` must not run in the managed window until this is decided, and name the owner (APP-012 per plan Task 9). APP-077 owns the guard.

**M3. Keeping `admission issue` out of ECS is documentation only; nothing stops a RunTask command override from writing the raw code into CloudWatch.**
`app/operator/overrides.json` lists `admission issue` under `not_ecs_overrides`, which is correct reasoning (open question 4): the task's stdout is the awslogs group (`stack.ts:278`, one-month retention). But ECS accepts any `command` override, and `operator.py:455-457` passes every `admission` argv to `admission_operator.main`, which prints `{"code": encode_code(raw)}` (`app/runtime/admission_operator.py:443`). The managed context can be detected for certain: Fargate always sets `ECS_CONTAINER_METADATA_URI_V4`.
*Fix:* in `operator.py` `main`, before dispatching `admission`, refuse with a fixed code (for example `issue_refused_in_managed_task`) when `os.environ` contains `ECS_CONTAINER_METADATA_URI_V4` or `ECS_CONTAINER_METADATA_URI` and `rest[0]` is `issue` or `reconcile`. Add a unit test and an image-check refusal case. APP-078 still chooses the delivery channel, and once it exists this guard is the place to admit it.

### Minor

**m1. The `admission` passthrough skips the pre-connect identity checks.** `operator.py:455-457` never calls `database_environment()`. `admission_operator.connect()` (`app/runtime/admission_operator.py:284-292`) refuses only a `/` host and takes `PGUSER` and `PGDATABASE` as given. I confirmed that `operator.main(['admission','list',…])` with `PGUSER=genui_workspace PGDATABASE=postgres` reaches `psycopg.connect(user='genui_workspace', dbname='postgres')`. TLS is still verify-full, and `begin()` refuses the identity after authentication, so nothing leaks. But the README's "Database commands require `PGUSER=genui_migration` … before any connection" is not true for `admission`. *Fix:* in `main`, call `database_environment()` before `admission(args.rest)` unless `args.rest[0] == "defaults"`, and add a mocked-connect test like `test_database_environment_is_checked_before_any_connection` for an admission command.

**m2. The host and CA guards can be sidestepped into a non-TLS connection.** `operator.py:115` (and `admission_operator.py:288`) refuse only a leading `/`. libpq also treats a host starting with `@` as a Unix socket (Linux abstract namespace), and treats a comma-separated list such as `db.example.test,/var/run/postgresql` as several hosts tried in order. `sslmode` does not apply to Unix-socket connections. Both values pass `database_environment()` (probed). `PGSSLROOTCERT=system` is also accepted, which swaps the pinned RDS bundle for the OS trust store. The task definition fixes these values, so exploiting this needs RunTask environment overrides. *Fix:* require `re.fullmatch(r"[A-Za-z0-9]" r"(?:[A-Za-z0-9.-]{0,251}[A-Za-z0-9])?", PGHOST)` and require `PGSSLROOTCERT` to be an existing regular file (not `system`). Inside ECS (see M3's detection), additionally require it to equal `/etc/ssl/certs/rds-global-bundle.pem`. Apply the same check in `admission_operator.connect`, or route it through the operator's check (m1).

**m3. The new grants could be narrower.** `stack.ts:270` grants `kms:GenerateDataKey` with no `kms:ViaService` or `kms:EncryptionContext:aws:s3:arn` condition, so the role can obtain plaintext data keys directly from KMS. They are useless against existing objects (bucket keys are off), but the grant is not bound to S3 or to the role's prefix. `stack.ts:269` `s3:PutObject` is unconditional, so a non-conditional PUT can still add versions. *Fix:* condition the KMS statements as in M1. Add `conditions: { StringEquals: { 's3:if-none-match': '*' } }` to a PutObject-only statement (keeping `s3:GetObject` in its own statement), and confirm S3's enforcement of that condition key on an identity policy as an APP-078 observation. Neither is required by the controlling text.

**m4. The documented overrides cover only APP-073's commands.** At `34a42eb` the image's `admission` channel also has `provision`, `create-app`, `grant-permission`, `revoke-permission`, `revoke-creator-authority`, `revoke-membership` and `revoke-entitlement`. The ADR-007 2026-10-29 amendment makes `grant-permission` the S05 builder's path. None is documented in `overrides.json`, so APP-078 has no reviewed size or shape for them. *Fix:* add one example override per command APP-078 will run (all are command-only and far below 8,192 bytes), or record in `overrides.json` that only the listed ones are in scope for APP-078.

**m5. `/run/operator` writability on Fargate is unproven.** `TMPDIR=/run/operator` (Dockerfile:65) is the scratch for `upload-sources`. The image makes it 65532 0700 and declares `VOLUME`. On Fargate the task's bind-mount volume (`stack.ts:274,285`) must keep that ownership, or `tempfile` fails as UID 65532. The local check used a tmpfs with `uid=65532`, so it did not prove this. It is the same pattern APP-075 uses. *Fix:* list it as an APP-078 observation (`upload-sources --plan` first).

**m6. `-I` makes the `PYTHON*` variables inert.** Dockerfile:65 sets `PYTHONUNBUFFERED=1`, but under `-I` stdout is block-buffered to the awslogs pipe. Output is flushed at normal exit, but a SIGKILL after `admission` commits but before exit loses the receipt. *Fix:* use `["python3", "-I", "-u", …]` in the Dockerfile, `overrides.json` and `stack.ts`, or drop the inert variables and document it. Relatedly, `unittest discover -s app/operator` puts `operator.py` first on `sys.path`. It works only because the stdlib `operator` is already imported by then. Consider moving the tests to load from a sibling directory, or document it.

**m7. The evidence record is stale for the merged tree.** README §Identity (`admission_operator.py aa76c5de…`, `tenant_seed.py c9073aee…`, manifest `b3cc8070…`, image `a3b07f93…`), the runtime test count, open question 5 and the merge message do not describe `34a42eb`. *Fix:* re-record README §Identity and §Commands at `34a42eb` (this review's numbers above can be cited), mark open question 5 resolved, and keep the old run as history.

## Claims I tried and failed to refute

- **The operator task has no application role-assumption or database-role grant.** `OperatorRoleDefaultPolicy` has exactly four statements (S3 Get/Put on each `o/<t>/s/*`, `kms:GenerateDataKey` on each key). The task env carries no role ARN, no `GENUI_DATABASE_ROLES_JSON` and no `GENUI_TENANTS_JSON`. The code calls no `assume_role`, `refresh`, `serve` or `scoped_session` (image check static scan). `s3_client()` refuses `AWS_ROLE_ARN`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_PROFILE` and `AWS_ENDPOINT_URL*` (`operator.py:425-426`), and the image sets `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` to `/dev/null`.
- **No access outside the tenant prefix.** Keys are built only from UUID-checked ids (`operator.py:309-311`), and each must start with that tenant's configured prefix (`:398`), which must equal `o/<org>/` (`:370`). IAM allows only `o/<t>/s/*`. B1 layout `o/{org}/s/{source}/r/{rev}/{original,part.parquet}` matches ADR-009 D9.3. Of the bucket-policy interaction, the stub proves only the deny for another tenant's key; the real denial is an APP-078 observation.
- **SSE-KMS and checksum headers are correct for the bucket policy.** The PUT sends `ServerSideEncryption=aws:kms` and `SSEKMSKeyId=<tenant key ARN>`, exactly the two values the bucket policy compares (`s3:x-amz-server-side-encryption`, `…-aws-kms-key-id`). `ChecksumSHA256` is base64 of the raw SHA-256 of the same bytes whose hex digest is reported. The response must echo the key and checksum (`:414-415`).
- **The digests are correct.** `content_digest` and `normalized_digest` are SHA-256 of the exact original and Parquet bytes (ADR-009 D9.3 M6). The Parquet is ZSTD, one thread, row groups of 100,000, ordered by time then original record, round-trip checked, deterministic across macOS and the linux image. `contract_digest` equals the seeded work binding.
- **PGPASSWORD is handled correctly.** It arrives only as an ECS secret through `MigrationExecutionRole`, is read only into `psycopg.connect(password=…)`, and is never in argv or output. Generic exceptions print a fixed code (`operator.py:463-465`). The parser child runs with `env={}`. The image check asserts the synthetic password never appears in any output.
- **The image is allowlisted and pinned.** `Dockerfile.dockerignore` is `**` plus exact re-includes, and each directory re-include is followed by its `/**` exclusion (checked by `check_image.allowlist` and the test against tracked files). Both bases are pinned by digest, and pip runs with `--require-hashes --only-binary=:all:`. The parser stage equals the service image's except the two manifest paths. As in the service image, `rustup target add` at build time is checksummed by rustup but not hash-pinned in the repository.
- **Overrides are sized correctly and match the entry point.** All 12 documented overrides are `containerOverrides[{name: operator, command}]` only, at most 206 bytes, and parse inside the image. The entry point is identical in all four places.
- **The template diff contains only conditional additions** (reproduced independently above).
- **Seed and migrate refuse before they connect.** `seed` validates every envelope (`tenant_seed.make_bundles`) and `database_environment()` runs before `psycopg.connect`. The only exceptions are the passthrough (m1) and the socket-shaped hosts (m2).
