# APP-208: the multi-select field, checks and break-and-restore proofs (builder B6, 2026-11-14)

Branch `release/c-b6-multiselect`, built on `release/c-participation` at `51810561` (B0–B4 and release B integrated; B5's composer branch is not merged here and `composer/*` is untouched). The implementation commit under proof is `4eeb9084`; the campaign phase was corrected in `b5005e08` (the proofs below ran at that commit). ADR-020 §9 and its §17 clarifications 28–34 are what it builds; the grammar is B0's (edition `impl-2026-11-14.2`, unchanged).

## What was built

- **Storage.** `storage::commands::compatible` gains the `multi_enum` arm: members `type` and `values`; `values` a non-empty array of at most 32 strings, each a declared value, at strictly increasing declared positions (`ordered_subset`). Any other order, a repeat, an unknown id, an empty set, an extra member or an enum literal is refused with the uniform refusal; null is judged by the field's nullability, so a required multi-select is a non-nullable field.
- **Forms.** A `multi_enum` field renders one checkbox per declared value in declaration order, the held ones checked, every box named `value.<field>`, after a hidden empty `value.<field>` sentinel, on the record page (`admin/src/record/app.tsx`), the canvas form card (`admin/src/canvas/app.tsx`, `canvas/render.ts`) and the document form (`admin/src/work/app.tsx`, `work/render.ts`). `commands::routes::from_form` composes one typed value from the group in posted order (`form_multi_enum`; the sentinel alone is null) and refuses a scalar posted twice. The canvas client (`canvas/commands.ts` `multiEnumValue`) composes the same value from the checked boxes through the echoed spec: declared values only, in the spec's order, each once; nothing checked is null. `commands::FieldRow.choices` carries the declared values with the held ones selected; `pages::FieldRowProps` and `query::canvas::FormFieldProps` gain `has_checkboxes` (never `has_choices` or `has_text` for the field).
- **Computation.** `record_engine.py` counts a row once per selected value in a `record_ranking` by a `multi_enum` `group_field` (population and totals count rows once; null is `Missing value`) and refuses a `records_list` order over the field before any row (`multi_enum_order_refused`); `selection` re-judges the stored value as an ordered subset. `record_query::scalar_row` projects the field as its values joined by `", "` after the same re-judgment; `query::worker::ColumnType::from_value_type` types it `Text`; `query_engine.py` admits the type as a `VARCHAR` column of a records input only (`RECORD_COLUMN_TYPES`), never a source's, and qualifies no literal of it.
- **Display.** `commands::multi_enum_text` (values joined by `", "`) serves the record page's row text, the canvas records card (`actions::resolve::display`) and the record-components cell (`query::record_components::shown`, text and title).
- **Campaign.** The `record-components` campaign gains a multi-select phase over the contract specimen's `multi_select` definition, installed through the shipped path at the stored edition (version 1, `coverage` dropped from the inputs); `computed_in` generalizes B2's `computed` to a named app.

The APP-208 campaign checks:

- APP-208 storage: a selection in declaration order commits and is stored canonically; another order, a repeat, an unknown id, an empty set, null on the required field, an enum literal and an extra member are each refused (the uniform refusal, nothing written)

- APP-208 ranking: over four rows selecting [red, blue], [blue], [red, green, blue] and [green, blue], a reviewer's ranking by tags counts blue 4, green 2, red 2 (a row adds one to each option it selected) while its population and total count the four rows once; the list's cell carries the typed selection and reads "red, blue"; the trend and the matches summary run beside it

- APP-208 x D7: a contributor's ranking by tags, list and typed query count only their own rows (Ben: blue 3, green 1, red 1 over three rows), a reviewer's every member's (fails under bypass)
