## Operation state machine

`genui.provider_invitations` rows (0003: operation `create`|`revoke`, state `pending`|`confirmed`|`failed`|`unknown`, `remote_invitation_id`, `intended_email_digest`, `provider_role`, `updated_at`):

- **Create.** `issue --provider-email … --provider-role user --provider-issuer … --provider-tenant …` first proves the operator identity and catalog (`begin`), then checks that the management key's own tenant (`GET /manage/config`) equals the code's bound provider tenant and is `invite_only` — before any lock or write. In the code's transaction it locks the binding row `FOR UPDATE` (serializing invitation-bearing issuance per tenant, and refusing `provider_tenant_busy` after the 3 s lock timeout while a reconcile holds it), refuses `provider_invitation_exists` while another invitation for the same address belongs to a code that can still admit (because fAuth's create would revoke it), and inserts the `create` row `pending`. After COMMIT, the send deadline is recorded and committed first: `updated_at` of the pending row becomes `clock_timestamp()` + 15 s (the 10 s request deadline + the 5 s `create_send_margin_seconds`), only for a row never armed before (`updated_at = created_at`), so one row is sent at most once. A second short transaction then holds the row `FOR UPDATE SKIP LOCKED` and sends exactly **one** create, unless more than the margin has passed since the deadline was recorded (then the row is `failed` / `send_window_passed`, nothing sent). No request for the row can therefore reach fAuth after its recorded deadline. When the answer arrives it locks the code (D7.1: organization `FOR SHARE`, then the code `FOR UPDATE`): the capability file is written only if the code is still active and live and no revocation is recorded (otherwise `code_no_longer_usable`, and the invitation is revoked at once, review m1); the file is written before the database (so a crash leaves a pending row that reconcile confirms from the file) and the outcome is recorded in the same transaction, `updated_at` = the outcome's `clock_timestamp()`:

| fAuth answer | Recorded | Reason |
| --- | --- | --- |
| 201 meeting the server-only contract (well-formed id and token, same address and role, `status` pending, parseable expiry, `email_delivery` `suppressed`, no `invite_url`) | `confirmed` + remote id; capability stored | created |
| 201 with a well-formed id that breaks the contract (role, address, status, delivery, `invite_url`, token or expiry) | `confirmed` + remote id; **no** capability; a `revoke` row is recorded and sent at once | it exists remotely and must never be handed off |
| 201 without a well-formed id | `unknown` | it exists; its id is unknown |
| 400, 401, 403, 404, 429 | `failed` (+ sanitized `provider_error` code) | returned before any write |
| connect or TLS failure | `failed` (`not_sent`) | the request never left |
| any other status (3xx, 5xx), timeout, connection drop, oversize | `unknown` | it may have been applied |

  The code is committed and printed once whatever the provider outcome; `issue` then reports `provider_invitation: {invitation_id, operation, state, remote_invitation_id, capability_stored, detail}` (plus `revocation` when a confirmed create was not stored). Nothing after the code's COMMIT can stop it from being printed (review m5): the revocation that follows an unusable create runs inside a guard that reports `provider_phase_incomplete` (its revoke row is committed, so `reconcile` sends it), any other failure or an interrupt of the provider phase reports `provider_invitation.detail = provider_phase_incomplete`, and the command no longer ends with the connection context's COMMIT (which raised on a broken connection). If the process is killed outright, the code is lost unprinted: the operator finds it with `list` (its invitation `pending`) and revokes it. A `failed` or capability-less create leaves a code that cannot hand off a signup: the operator revokes and reissues.
- **Provider expiry versus code expiry (review m4; documented, not enforced).** GenUI never sends `expires_in_hours`, so every invitation lives fAuth's default **72 h** (`management.rs:1715`), while a code lives 14 days by default and up to 30 (`extend` included). After 72 h the invitation is `expired` upstream and its capability is gone (the sweep destroys it at the recorded provider expiry), so the code can no longer hand off a signup even though it is still `active`. **Re-invitation is always revoke + reissue:** revoke the old code (or let `reconcile` record the provider's expiry, below), then `issue` a new invitation-bearing code for the address; `extend` never renews an invitation. Chosen over refusing longer codes at `issue` because codes without invitations keep the D7.17 bounds unchanged and an invitation-bearing code's useful life is visible in `list` (its create's `remote_invitation_id` and the revoke row `reconcile` records).
- **Revoke.** `revoke` commits the local code revocation and a `revoke` row per non-failed create first (unchanged), then — only if `GENUI_PROVIDER_*` is configured — destroys the code's capability files, checks the tenant and sends the revocation. Without configuration it reports `provider_phase: not_configured`; the local revocation never waits for, and is never undone by, the provider. Revocation is idempotent upstream, so `pending`, `unknown` and `failed` revocations are sent again by `reconcile`: 200 or 404 `invite_not_found` → `confirmed`; 400/401/403/429 → `failed`; not sent → stays `pending`; other → `unknown`. A revocation whose create is still `pending`/`unknown` waits (`awaiting_create_reconciliation`); one whose create `failed` is `confirmed` with nothing to revoke.
- **Reconcile** (`reconcile --organization …`, new closed subcommand, migration identity, provider configuration required):
  - (0) **One run at a time per organization and provider tenant (review M1(b)).** A second connection, after the same identity and catalog proof, holds every `provider_tenant_bindings` row of the organization `FOR NO KEY UPDATE NOWAIT` for the whole run; a concurrent run refuses `reconcile_in_progress` before anything is read or written, and invitation-bearing `issue` refuses `provider_tenant_busy`. `NO KEY UPDATE` rather than `UPDATE`: it conflicts with another guard and with `issue`'s `FOR UPDATE`, but not with the `FOR KEY SHARE` that foreign-key checks take on the binding (pending admissions in `code_reservations` and this run's own invitation rows reference it), so admission is never blocked by a reconcile. `NOWAIT`: the guard never waits, so it is in no wait cycle.
  - (1) locks the organization `FOR SHARE` and every code that is revoked, exhausted or expired and has a non-failed create but no revocation `FOR UPDATE`, and records its `revoke` row (every writer of revoke rows holds the code row first, so the `NOT EXISTS` cannot race);
  - (2) destroys every capability whose code is no longer usable, whose revocation is recorded, whose create failed or is unknown to the ledger, or whose recorded provider expiry has passed, and every partial write older than the grace (review m6) — before any provider call;
  - (3) **creates.** Every `pending`/`unknown` create of the key's tenant whose `updated_at` (its recorded send deadline, or its outcome time) is older than the 120 s grace and that no other process holds (`SKIP LOCKED`, at most 100) is locked and judged in one transaction, never by creating again:
    - a row whose capability file exists takes its remote id from the file (written from a 201 that met the contract) → `confirmed` / `capability_record` (review M1(d)); the crash between the file and the outcome UPDATE never costs the capability;
    - a row whose `updated_at` is more than the provider lifetime (72 h) + 300 s skew in the past → `failed` / `expired_unconfirmed`: whatever it created can no longer be pending, and the code's revocation then closes `confirmed` / `nothing_to_revoke` (review m3; `failed` for a create therefore means "definitively not created, or nothing it created can still be used");
    - otherwise the provider's list decides, paged 200 at a time back to the oldest window (at most 50 pages, else `provider_inspection_incomplete`). An invitation is **eligible** when no operation already holds its id and `invited_by_user_id` is null (a management-key create, review M1(c)). Every unresolved create of the tenant has a **window** [`created_at` − 300 s, `updated_at` + 300 s], open above only for a create not held by this run that has not yet recorded a deadline. A row is `confirmed` / `found` with the one eligible invitation in its window **only if no other unresolved create's window holds that invitation** (one-to-one, review M1(a)); `failed` / `not_found` when its window holds none; otherwise it stays as it was (`ambiguous_remote_match`) until the lifetime rule above closes it.
    - A create confirmed without its capability (the lost response held the only token) can never be handed off, so its revocation is recorded at once and sent in step (5) (review m2).
  - (4) **drift (review m7).** Confirmed creates of codes that can still admit and have no revocation are compared with the same list: an invitation fAuth already `revoked` (another create for the address, the console) or `expired` (its sweeper), or one older than the 72 h lifetime + skew, gets its revocation recorded `confirmed` (`remote_revoked`, `remote_expired`, `provider_lifetime_ended`: no pending invitation with that id remains, the same postcondition as a 404 on revoke) and its capability destroyed; an `accepted` one (the invitee registered) has spent its token, so its capability is destroyed (`remote_accepted`) and the ledger keeps the confirmed create.
  - (5) **revocations** (`pending`/`unknown`/`failed`, at most 100, including those recorded above) are sent again; a revocation whose create is still `pending`/`unknown` waits (`awaiting_create_reconciliation`).
  - The output also reports `capability_directory_class` (review M2 evidence; see below). **Reconcile never creates.**
  - **Assumption:** the GenUI database clock and fAuth's clock agree within the 300 s skew (both NTP-disciplined). The window is bounded on both sides, so a skew beyond it can turn a match into `not_found`; that is why the review's probes, which age only GenUI's rows by 900 s, now see `not_found` where the tests (which age both sides, `fake.shift`) see the true answer.
- **Audit.** Provider operation state writes no audit event: D7.8's operator kinds are closed and name none. The rows' state and `updated_at` are the operation record; adding kinds is an ADR-007 amendment plus a migration (the operator RESTRICTIVE policy enumerates kinds), recommended by the review before APP-076 and not part of this slice (review m8).

## Secret handling: the private capability file

The `invite_token` is written only to `GENUI_PROVIDER_CAPABILITY_DIR/<organization_id>.<invitation_id>.capability`: first to a hidden `.<organization_id>.<invitation_id>.<random>.partial` created with `O_CREAT|O_EXCL|O_NOFOLLOW`, mode 0600, written and fsynced, then hard-linked to the final name (the link fails rather than replace an existing capability) and the partial unlinked, so the final name only ever holds a complete record and a concurrent sweep never reads or deletes a half-written one (review m6). The directory must be absolute, not a symlink, owned by the operator's effective user, without group or other access (0700), and **not inside a folder a sync client copies off the host** (review M2, interim): any path component, of the configured path or its real path, naming iCloud Drive (`Library/Mobile Documents`, `iCloud Drive`), macOS File Provider storage (`Library/CloudStorage`, where current Dropbox, Google Drive and OneDrive clients live), `Dropbox`, `Google Drive`/`My Drive` or `OneDrive…` is refused `provider_capability_directory_synced`. `reconcile` reports the directory's path class (`temporary`, `home`, `other`; never the path); every run in this record used the per-user temporary directory, class **`temporary`** (asserted in `test_reconcile_propagates_expiry_and_exhaustion_and_ends_the_capability`). The refusal cannot see Time Machine, APFS snapshots, iCloud "Desktop & Documents" on the original `~/Desktop`/`~/Documents` paths, or other backup agents. The row references it through its primary key; there is no new column. The token is never written to PostgreSQL, standard output or error, the campaign report or this evidence; `list` shows only invitation ids, states and remote ids.

**Why a file rather than encryption at rest in the database.** 0003's `provider_invitations` has no capability column, so database encryption would need a migration, a new catalog and the D7.12 renumbering of every planned migration, plus an encryption key whose custody is the same problem in another place. With the file, the capability never enters PostgreSQL — PostgreSQL's dumps, WAL, backups, snapshots and replicas cannot carry it. **Correction (review M2):** the file is access control (0600), not encryption, and no ADR or approval names it as ADR-003's "approved secret store"; whether it may serve as that store in Phase 1 is the coordinator's ADR-003 decision, and this slice does not change the storage model. The operator host's own backups, local snapshots and sync clients **can** copy it (only sync folders are refused, above), and unlink removes the name, not the bytes on disk.

**Readers and lifetime.** Readers: the operator's OS account (and the host's root). Lifetime: destroyed by `revoke` before the provider is contacted when the file exists; a create still in flight when `revoke` commits never writes it (review m1). `reconcile` destroys it once the code is revoked, expired or exhausted, a revocation is recorded, the create failed, fAuth's own expiry (72 h, recorded in the file) has passed, or fAuth reports the invitation revoked, expired or accepted; one invitation per address per live code.

**Limits of this Phase 1 channel.** (1) The bytes are plain on the operator host's disk; the host's disk encryption is the only at-rest protection — this is not KMS or Secrets Manager custody (FORMA-248). (2) The GenUI service on Fargate cannot read it: APP-074's `POST /invite/validate` needs the token for PAR, so the server-to-server handoff into an approved secret store with bounded readers belongs to APP-074/076. (3) One operator host, no replication: losing it loses the capabilities, and the operator revokes and reissues. (4) File names carry the organization and invitation ids (non-secret identifiers).

**Other secrets and inputs.** The management key comes only from `GENUI_PROVIDER_MANAGEMENT_KEY_FILE` (absolute, regular, not a symlink, owned by the operator, no group/other bits, ≤ 1 KiB) or `GENUI_PROVIDER_MANAGEMENT_KEY` (both set is refused); it must match `mgmt_[A-Za-z0-9_-]{8,256}` and never appears in argv (the closed parser has no option for it and its usage refusal echoes nothing), repr, output or files GenUI writes. `GENUI_PROVIDER_URL` must be `https://host[:port]`, or `http://` only to `127.0.0.1`, `localhost` or `::1`, with no userinfo, path, query or fragment; TLS uses the system trust store with hostname verification. Every refusal prints a fixed reason code. The intended address is still an `issue` argument (slice 2's interface), so it is personal data visible in the operator host's process table; only its digest is stored.

## Implementation choices and residual risks (for review)

1. **Grace, locks and a recorded send deadline instead of a distributed claim.** The issuing process commits the send deadline, then holds its create row for the call; reconcile uses `SKIP LOCKED`, the tenant guard and a 120 s grace counted from the deadline. After the review fixes a suspended process can no longer send after its deadline (it records `send_window_passed` instead), so the old failure — reconcile judges `failed`, the late create succeeds — is closed. Residual: a process suspended *after* sending, long enough for PostgreSQL to end its session, has its outcome judged by reconcile from the list (`found` → the invitation is revoked as capability-less, m2); when it resumes, its outcome write fails (`outcome_unrecorded`) and any capability it wrote is destroyed by the next sweep (revocation recorded). Nothing usable is lost that was not already unrecorded.
2. **404 on revoke is `confirmed`.** The tenant is verified first, and 404 `invite_not_found` means no pending invitation with that id remains in the tenant — the postcondition revocation needs, whether it was revoked, accepted or expired.
3. **A `failed` create keeps its code**, and the code is printed once; the operator revokes and reissues. `issue` exits 0 whenever the code committed; the provider outcome is in `provider_invitation.state`.
4. **`revoke`'s `provider_revocations_pending`** keeps slice 2's meaning (revocation rows recorded at revocation); the per-operation states follow in `provider_revocations`.
5. **No audit event for provider operations** (D7.8 closed; an amendment would add kinds such as `provider.invitation.created`).
6. **Only the operator's organization** is visible to reconcile (RLS scope), so remote ids are de-duplicated per organization; each organization has its own provider tenant.
