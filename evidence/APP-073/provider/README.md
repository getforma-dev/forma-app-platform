## Operation state machine

`genui.provider_invitations` rows (0003: operation `create`|`revoke`, state `pending`|`confirmed`|`failed`|`unknown`, `remote_invitation_id`, `intended_email_digest`, `provider_role`, `updated_at`):

- **Create.** `issue --provider-email … --provider-role user --provider-issuer … --provider-tenant …` first proves the operator identity and catalog (`begin`), then checks that the management key's own tenant (`GET /manage/config`) equals the code's bound provider tenant and is `invite_only` — before any lock or write. In the code's transaction it locks the binding row `FOR UPDATE` (serializing invitation-bearing issuance per tenant), refuses `provider_invitation_exists` while another invitation for the same address belongs to a code that can still admit (because fAuth's create would revoke it), and inserts the `create` row `pending`. After COMMIT, a second short transaction holds that row `FOR UPDATE SKIP LOCKED`, sends exactly **one** create, writes the capability file (before the database, so a crash leaves a pending row that reconcile confirms with its capability present) and records the outcome in the same transaction:

| fAuth answer | Recorded | Reason |
| --- | --- | --- |
| 201 meeting the server-only contract (well-formed id and token, same address and role, `status` pending, parseable expiry, `email_delivery` `suppressed`, no `invite_url`) | `confirmed` + remote id; capability stored | created |
| 201 with a well-formed id that breaks the contract (role, address, status, delivery, `invite_url`, token or expiry) | `confirmed` + remote id; **no** capability; a `revoke` row is recorded and sent at once | it exists remotely and must never be handed off |
| 201 without a well-formed id | `unknown` | it exists; its id is unknown |
| 400, 401, 403, 404, 429 | `failed` (+ sanitized `provider_error` code) | returned before any write |
| connect or TLS failure | `failed` (`not_sent`) | the request never left |
| any other status (3xx, 5xx), timeout, connection drop, oversize | `unknown` | it may have been applied |

  The code is committed and printed once whatever the provider outcome; `issue` then reports `provider_invitation: {invitation_id, operation, state, remote_invitation_id, capability_stored, detail}`. A `failed` or capability-less create leaves a code that cannot hand off a signup: the operator revokes and reissues.
- **Revoke.** `revoke` commits the local code revocation and a `revoke` row per non-failed create first (unchanged), then — only if `GENUI_PROVIDER_*` is configured — destroys the code's capability files, checks the tenant and sends the revocation. Without configuration it reports `provider_phase: not_configured`; the local revocation never waits for, and is never undone by, the provider. Revocation is idempotent upstream, so `pending`, `unknown` and `failed` revocations are sent again by `reconcile`: 200 or 404 `invite_not_found` → `confirmed`; 400/401/403/429 → `failed`; not sent → stays `pending`; other → `unknown`. A revocation whose create is still `pending`/`unknown` waits (`awaiting_create_reconciliation`); one whose create `failed` is `confirmed` with nothing to revoke.
- **Reconcile** (`reconcile --organization …`, new closed subcommand, migration identity, provider configuration required): (1) locks the organization `FOR SHARE` and every code that is revoked, exhausted or expired and has a non-failed create but no revocation `FOR UPDATE`, and records its `revoke` row (every writer of revoke rows holds the code row first, so the `NOT EXISTS` cannot race); (2) destroys every capability whose code is no longer usable, whose revocation is recorded, whose create failed or is unknown to the ledger, or whose recorded provider expiry has passed — before any provider call; (3) settles at most 100 operations, creates first: a `pending`/`unknown` create older than the 120 s grace (well above the 2 × 10 s provider phase of `issue`) and not held by another process (`SKIP LOCKED`) is judged only from the provider's list, paged 200 at a time and stopped at the first invitation older than the row's `created_at` − 300 s (at most 50 pages, else `provider_inspection_incomplete`). An invitation matches when its address digest and role equal the row's, it is inside the window and its id is not already attributed to another row: exactly one → `confirmed` with that id; none → `failed`; more → stays `unknown` (`ambiguous_remote_match`, the operator procedure with FormaStack decides). **Reconcile never creates.** A create confirmed this way has no capability (the lost response held the only token), reported `capability_stored: false`.
- **Audit.** Provider operation state writes no audit event: D7.8's operator kinds are closed and name none. The rows' state and `updated_at` are the operation record; adding kinds is an ADR-007 amendment.

## Secret handling: the private capability file

The `invite_token` is written only to `GENUI_PROVIDER_CAPABILITY_DIR/<organization_id>.<invitation_id>.capability`, created with `O_CREAT|O_EXCL|O_NOFOLLOW`, mode 0600, fsynced, in a directory that must be absolute, not a symlink, owned by the operator's effective user and without group or other access (0700). The row references it through its primary key; there is no new column. The token is never written to PostgreSQL, standard output or error, the campaign report or this evidence; `list` shows only invitation ids, states and remote ids.

**Why a file rather than encryption at rest in the database.** It is the simpler option consistent with ADR-003's "encrypt or use the approved secret store": 0003's `provider_invitations` has no capability column, so database encryption would need migration 0005, a new catalog and the D7.12 renumbering of every planned migration, plus an encryption key whose custody is the same problem in another place. With the file, the capability never enters PostgreSQL — dumps, WAL, backups, snapshots and replicas cannot carry it — and its end of life is a real unlink instead of a row update that WAL and backup retention keep.

**Readers and lifetime.** Readers: the operator's OS account (and the host's root). Lifetime: destroyed by `revoke` before the provider is contacted, and by `reconcile` once the code is revoked, expired or exhausted, a revocation is recorded, the create failed, or fAuth's own expiry (72 h default, recorded in the file) has passed; one invitation per address per live code.

**Limits of this Phase 1 channel.** (1) The bytes are plain on the operator host's disk; the host's disk encryption is the only at-rest protection — this is not KMS or Secrets Manager custody (FORMA-248). (2) The GenUI service on Fargate cannot read it: APP-074's `POST /invite/validate` needs the token for PAR, so the server-to-server handoff into an approved secret store with bounded readers belongs to APP-074/076. (3) One operator host, no replication: losing it loses the capabilities, and the operator revokes and reissues. (4) File names carry the organization and invitation ids (non-secret identifiers).

**Other secrets and inputs.** The management key comes only from `GENUI_PROVIDER_MANAGEMENT_KEY_FILE` (absolute, regular, not a symlink, owned by the operator, no group/other bits, ≤ 1 KiB) or `GENUI_PROVIDER_MANAGEMENT_KEY` (both set is refused); it must match `mgmt_[A-Za-z0-9_-]{8,256}` and never appears in argv (the closed parser has no option for it and its usage refusal echoes nothing), repr, output or files GenUI writes. `GENUI_PROVIDER_URL` must be `https://host[:port]`, or `http://` only to `127.0.0.1`, `localhost` or `::1`, with no userinfo, path, query or fragment; TLS uses the system trust store with hostname verification. Every refusal prints a fixed reason code. The intended address is still an `issue` argument (slice 2's interface), so it is personal data visible in the operator host's process table; only its digest is stored.

## Implementation choices and residual risks (for review)

1. **Grace and locks instead of a distributed claim.** The issuing process holds its create row for the whole call; reconcile uses `SKIP LOCKED` and a 120 s grace. Residual: if the issuing process is suspended long enough for PostgreSQL to end its session while it holds the row, a reconcile may judge the create `failed` before the request is sent; when the process resumes and the create succeeds, its outcome write fails (`outcome_unrecorded`), and the next reconcile destroys that capability because the row says `failed` — leaving an orphan pending invitation that nobody holds a token for, which fAuth expires after 72 h.
2. **404 on revoke is `confirmed`.** The tenant is verified first, and 404 `invite_not_found` means no pending invitation with that id remains in the tenant — the postcondition revocation needs, whether it was revoked, accepted or expired.
3. **A `failed` create keeps its code**, and the code is printed once; the operator revokes and reissues. `issue` exits 0 whenever the code committed; the provider outcome is in `provider_invitation.state`.
4. **`revoke`'s `provider_revocations_pending`** keeps slice 2's meaning (revocation rows recorded at revocation); the per-operation states follow in `provider_revocations`.
5. **No audit event for provider operations** (D7.8 closed; an amendment would add kinds such as `provider.invitation.created`).
6. **Only the operator's organization** is visible to reconcile (RLS scope), so remote ids are de-duplicated per organization; each organization has its own provider tenant.
