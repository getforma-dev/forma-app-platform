### Major

**M1. The new guards are not wired into CI, and the `runtime.py` pin is dead at runtime.**

- No workflow runs `scripts/check-schema-pins.py`, `unittest discover -s scripts`, or `unittest discover -s app/runtime`. `.github/workflows/tenant-foundation.yml:42-46` runs `qualify_tenant_schema.py` and the native campaign only; `fixtures.yml:30` runs `reset_trial.py`. The plan's review-focus item 1 (`PHASE-1-EXECUTION-PLAN.md:34`: "a repository check asserts the … pins agree") and D7.12's "`scripts/check-schema-pins.py` fails unless every place … agrees" are satisfied only when someone runs the script by hand. The 38 runtime tests, including the five new runner tests and the generator-cap test, are likewise local-only evidence.
- The pre-merge runner refused a manifest whose `database_version` disagreed with the image's own constant (`a0a75a8:runtime.py:319`, `manifest["database_version"] == DATABASE_SCHEMA_VERSION`). The merged runner never reads `DATABASE_SCHEMA_VERSION` (`runtime.py:25` is its only occurrence; `probe_database` now compares to the manifest, `runtime.py:285,292`). Confirmed by trace: `migration_sources` on a synthetic three-version manifest with the constant at 2 is **refused by the old runner and accepted by the new one**. The constant survives only as a string for the pin script to find, so with CI not running that script a partial pin update is caught by nothing before `migrate` upgrades the database and `pool.rs:494` refuses every connection — exactly the failure mode the plan pinned to this task.

Fix (both halves):
1. `.github/workflows/tenant-foundation.yml`, after the venv step: add `app/runtime/.venv/bin/python -m unittest discover -s app/runtime -v`, `app/runtime/.venv/bin/python -m unittest discover -s scripts -p 'test_*.py' -v` and `python3 scripts/check-schema-pins.py` as steps before the schema campaign.
2. Make the image pin load-bearing again without breaking the synthetic-manifest tests: in `migrate()` (`runtime.py:471`) and `probe()` (`runtime.py:300`), the two production entry points, add `require(migration_manifest(migration_directory())["database_version"] == DATABASE_SCHEMA_VERSION)` before connecting. `apply_migrations`/`probe_database` stay manifest-driven so `test_probe_and_default_catalog_proof_follow_the_manifest_version` and the N-version tests keep passing. If the team prefers the manifest alone as the Python pin, drop `DATABASE_SCHEMA_VERSION` from `runtime.py` and from `check-schema-pins.py:19-20` instead of keeping a pin that nothing reads; D7.12 makes the script's list authoritative, so either choice is in-policy, but the current state (listed pin, never read) is neither.

### Minor

**m1. The cap move is derivable in the generator but hand-edited in four other sites, and none of them is pin-checked.** `generate_schema_catalog.py:29` derives `limit = max_output_bytes*4//5` from `catalog-query.json`, so 524,288 gives exactly D7.12's 419,430. But the same bound is a literal at `runtime.py:364` (catalog file bytes), `runtime.py:370` (`max_output_bytes == 262144`), `app/src/storage/catalog.rs:10` (`BOUND`), and inside the SQL text of `catalog-query.json` (`octet_length(body)<=262144`), plus the test literal 209715 in `test_runtime.py` (`test_generator_refuses_snapshot_over_80_percent_cap`). Nothing asserts the SQL literal equals `max_output_bytes`. Fix: a `CATALOG_BOUND = 262144` constant in `runtime.py` used at lines 364 and 370; extend `check-schema-pins.py` with a second agreement group (catalog-query.json `max_output_bytes`, its `octet_length(body)<=N` literal, `catalog.rs` `BOUND`, `runtime.py` `CATALOG_BOUND`). This is 0003's slice per D7.12, but the pin group belongs to the runner task because the script is Task 3's deliverable.

**m2. The generator's refusal does not say which measure tripped.** `generate_schema_catalog.py:58-59` takes `max(len(raw.encode()), len(readable(value).encode()))` and reports "exceeds N bytes". Measuring both is correct (see Claim 4 below), but when the readable file is the binding measure the message points the reader at the database body. Fix: report both lengths in the `ValueError`.

**m3. Identical catalogs would refuse forever on the ledger path, and nothing checks distinctness statically.** `proven_catalog_version` requires exactly one match (`runtime.py:402`). D7.12's rule that every `000k` ALTERs both CHECKs to `k` guarantees distinct catalogs, but the rule is not enforced mechanically: a 0003 that forgets the ALTERs fails on the database CHECK itself (see Claim 3), while a 0003 that ALTERs to the wrong number, say 9, is baked into `catalog-v3.json` by the generator and the per-step proof passes. Fix: in `catalog_resources` (`runtime.py:375`) `require` that `documents[1:]` are pairwise distinct, and in `check-schema-pins.py` assert that for every `k >= 2`, `catalog-vk.json`'s constraints section contains `schema_version_version_check` with `CHECK (version >= 1 AND version <= k)` and the `schema_migrations` version CHECK with the same bound (`catalog-v2.json:308` shows the shape).

**m4. Version-literal carriers outside the pin list.** `app/src/storage/qualification.rs:882` (`SET version=3` as the unsupported future), `:884` (`SET version=2; … CHECK(version BETWEEN 1 AND 2)` restoring the live constraint) and `:991` (`SET version=2`) carry the current version and must move with 0003 (884's `BETWEEN 1 AND 2` restores the live constraint, so it becomes `BETWEEN 1 AND 3`, unlike the runner's baseline). They fail loudly in the native campaign when stale, so this is not a silent carrier, but D7.12 says "every place that carries the schema-version literal". Fix: either add a `CURRENT_SCHEMA_VERSION` const in `qualification.rs` and format these statements from it, adding that const to `check-schema-pins.py`, or record in the script's docstring that native-campaign fixtures are deliberately excluded. Also: the plan says "eight pins" (`PHASE-1-EXECUTION-PLAN.md:34`) while the script lists five and D7.12 makes the script authoritative; correct the plan wording to "the pins the script lists". Checked and not carriers: `.dockerignore` (`migrations/**`, no literal), `infra/scripts/auth_schema_preflight.py:132` (embeds `catalog-v1.json` for the role-foundation preflight, a version-1 contract by design), `infra/scripts/managed_sql_trial.py:166` (version-neutral), `pg_advisory_xact_lock(1819409017, 2)` (fixed lock key, not a version).

## Claims I tried to refute and could not

**Claim 1 (behavior preservation).** With the real two-migration manifest, the old and new runners issue **identical statement-plus-parameter sequences** on all three paths: fresh (21 statements), legacy version 1 (19), repeat at version 2 (11). Identical outcome and trace on eleven adversarial databases: ledger present but catalog is v1 (Refused at statement 9, before any ledger read); ledger present, catalog matches nothing; ledger missing row 1; ledger present but version row 1; altered recorded sha; legacy v1 with catalog drift; legacy v1 with version row 2; fresh with namespaces present; catalog drift after 0002 on the upgrade path (Refused after 19 statements, same as old); ledger table present without the version table; autocommit connection. `probe_database` and default-version `verify_schema_catalog` traces are identical for version rows 1/2/3 and catalogs v1/v2. The advisory lock is the same statement at the same position (after the identity check, before `to_regclass`; `runtime.py:433-436` vs `a0a75a8:398-401`); origin-mode and `SET LOCAL search_path` are the first two statements on both; the frozen 0001 hash is still required (`runtime.py:349`); the catalog proof still precedes every ledger/version read (`runtime.py:446-448`); `migrate()` is textually unchanged (same connect options, same caller-owned transaction). The only acceptance-set difference is the dropped constant check (M1); it changes no statement on the two-migration manifest.

**Claim 2 (N-version logic).** From recorded `k`, `sources[recorded:]` runs `k+1..N` inside the caller's one transaction (`runtime.py:457-466`); `verify_schema_catalog(version)` runs after each step except the last, whose proof is the final `verify_schema_catalog(latest)` at `:468`, so every version is proven once. A mismatch raises `Refused` before the next `connection.execute(source)`; the unit test `test_apply_migrations_proves_each_intermediate_version_before_the_next` confirms `applied() == [3]` after a v3 drift on a v2→v4 upgrade, and the exception propagates to psycopg's context manager for rollback. Manifest refusal: duplicates and gaps fail `item["version"] == version` under `enumerate(…, 1)` (`:344`); wrong file numbering fails `int(named.group(1)) == version` (`:346`); sha mismatch fails `:348`; stray `.sql` fails `:351`; catalog names are fixed to `catalog-v1..vN` (`:360-362`); `database_version` must be an int in `[2, 9999]` equal to `len(migrations)` and `len(catalog)-1` (`:332-334`). Recorded-version detection: on the ledger path the candidates are `range(2, N+1)` and exactly one must match (`:402`); a database matching none, or matching v1, is refused before the ledger or version row is read, and the ledger must then equal `sources[:recorded]` exactly with the version row equal to `recorded` (`:447-449`). I could not construct a database that is accepted at a version its catalog does not prove.

**Claim 3 (ledger bound).** `initialize_migration_history` writes `BETWEEN 1 AND %d` with `LEDGER_VERSION = 2` on both the column CHECK and `schema_version_version_check` (`runtime.py:413-418`, `:29`), independent of N; the test asserts two occurrences of `CHECK (version BETWEEN 1 AND 2)` on a three-version manifest and on the real one. The generator creates the ledger at the same point as the runner: after the v1 snapshot and immediately before executing 0002 (`generate_schema_catalog.py:47-48`), matching the runner's init-then-`sources[1:]` order (`runtime.py:455-458`); the generator test asserts the ledger statement precedes the 0002 text. A hypothetical 0003 without its CHECK ALTERs is caught — but by the database, not the proof: `INSERT INTO genui_meta.schema_migrations(version,…) VALUES (3,…)` (`runtime.py:459`; generator `:50`) violates `CHECK (version BETWEEN 1 AND 2)` (SQLSTATE 23514) and aborts the transaction before any snapshot or proof. The implementer's claim is therefore true and stronger than stated; the residual gap (ALTER to the wrong number) is m3.

**Claim 4 (generator guard).** The 209,715-byte refusal is measured on **both** lengths: `len(raw.encode())` where `raw` is the string the database returned for the `jsonb::text` body, and the readable file's UTF-8 length (`generate_schema_catalog.py:34-38, 58`). D7.12's body-length requirement is met; the file measure is additionally justified because the native side bounds the embedded file too (`catalog.rs:27`, `EXPECTED.len() > BOUND`) as does the runtime (`runtime.py:364`). The guard cannot pass a snapshot the database would refuse: the query returns NULL above 262,144 (`catalog-query.json` final SELECT), the generator raises at `:37` on a non-string, and 209,715 < 262,144. The guard refuses snapshots the database accepts only in the intended headroom band and when the readable form alone exceeds 209,715 while the body does not (the readable form writes compact rows with 4-space indents, so the two are close in size; for `catalog-v2.json` the file is 123,415 bytes). Byte counting is consistent: psycopg decodes UTF-8, `.encode()` re-encodes UTF-8, `octet_length` is UTF-8 on this image, Rust `len()` is UTF-8. The cap move: the generator's limit follows `max_output_bytes` automatically (524,288 → 419,430); the other sites are hand edits (m1).

**Claim 5 (pin check).** Covered pins: `app/migrations/manifest.json` `database_version`; `app/runtime/runtime.py` `DATABASE_SCHEMA_VERSION`; `app/src/storage/catalog.rs` `EXPECTED` include; `app/src/storage/managed_qualification.rs` `CATALOG` include; `app/src/storage/pool.rs` `verify_schema_version` `!= N` literal (`check-schema-pins.py:16-27`). Each must appear exactly once (`:34-38`), the manifest value must be an int, and all five must agree; the tests prove a single-site mismatch, a missing site and a duplicated site all exit 1. Carriers outside the list are in m4; none is silent.

**Claim 6 (tests).** Counts above; all green. The two-migration refusal test (`test_exact_two_migrations_and_original_bytes_are_required`) is retained and still refuses `database_version: 3` with two files (now via the length rule rather than the constant).

Added beyond the plan, all appropriate: `LEDGER_VERSION`, `migration_manifest()`, `proven_catalog_version()`, `MIGRATION_FILE`, three extra runner tests (`…_proves_each_intermediate_version_before_the_next`, `…_refuses_unproven_or_altered_history_before_writes`, `…_probe_and_default_catalog_proof_follow_the_manifest_version`) and `test_missing_or_duplicated_pin_refuses`. Not delivered: see m5 and M1 (CI wiring is implied by "a repository check asserts", not by a named step).
