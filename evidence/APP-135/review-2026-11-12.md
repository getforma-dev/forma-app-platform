## Findings

### Blocker

None.

### Major

**M1. The new note message names a cause that is false on the transient failure paths.** `findWork` returns `false` for any non-OK answer and for a network error (`notes.ts:105-121`). `refresh` does the same for a failed records read or a missing `note` collection (`notes.ts:128-142`). `newNote` shows one message for all of these (`notes.ts:384-387`). These include a 429 from the member write limiter on `POST /v1/notes` (`actions/routes.rs:127-133`) and 503s for a store outage (:150, :162, :207). The old text ("not available to you right now") was vague, but it was true in every case. The new text tells a member who does have the Notes app that "this workspace does not have" it. Fix: have `findWork` distinguish a 404 from other failures. Show the new copy only on a 404. Otherwise say notes could not be reached and to try again. Add one admin test for each branch.

**M2. On walked paths, several failures are visible only to screen readers.** `announce` writes to `#cv-activity` (`render.ts:47-50`), which is `class="sr-only"` (`app.tsx:744`). The following paths report there and nowhere else:
- **Create an app (template), the "Compose, template" row.** The dialog closes (`create-app.ts:150`). Then every message goes to `#cv-activity` (:151-154, :157): "Composing your app…" and any refusal. That includes `could_not_compose`, `composer_unavailable` (an edited template description with no model), `too_many` and `failed` (`compose.ts:73-84`, :106-112). A sighted member sees the dialog close and then nothing.
- **Notes outside the bar.** The Library's Widgets → Note "+ New note" and "Add" (`library.ts:500`, :511) and the More menu's "New note" (`app.tsx:854`, `controls.ts:211`) call `newNote` and send its answer only to `announce`. On a clean workspace the new message is therefore invisible from these entry points. The Note row and the menu item are offered even when the Notes app is absent. `startNotes` already makes the `GET /v1/notes` that could hide or disable them (`notes.ts:456`). Only `/note` from the bar shows the message (`notes.ts:420-421`).

The register's "Notes: Fixed" and the log's "Nothing else on the walked paths fails silently" (:117, :141) do not hold for these entry points. Acceptance box 2 (:37) stays unmet for them. Fix: send these reports to a visible line (the bar status or the dialog's own status), and gate the Note entries on `/v1/notes`.

**M3. The Do verdict ("Works", :111) misses that a named approver can never resolve with the demo off.** `match_approver` skips any member without a directory display name (`actions/resolve.rs:290-302`, "Labels without a display name never match a name"). Display names load only with the switch on (`directory.rs:78-93`). On the clean profile the walked sentence "…, Sarah approves" therefore drafts with no approver, and nothing is shared for approval (`actions.ts:159-174`). The card says "No approver named" (`actions.ts:220`), which is untrue: a name was given, and no member matched it. This is the kind of demo-only dependency the ticket exists to find (APP-098 DS-44, proper fix APP-097). Record it as demo-only and say what a non-demo member gets. Also change the chip to say that no member matched the named approver. Neither response field nor approver was recorded for the probe, so the register cannot show what was observed.
