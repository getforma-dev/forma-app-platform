## Minimal implementation sequence

1. **Freeze the application contract before changing behavior.** Keep invited signup's browser response code-only and preserve legacy registration. GenUI owns a restricted, server-side “verification pending” state after backend exchange returns `user.email_verified:false`; that state must not activate membership or grant application-resource access. The browser receives no fAuth access/refresh token. Specify the exact ordinary GenUI sign-in entry route and authenticated pending-state resend route with its owner. The operator-only qualification routes are not substitutes. Existing JWT claims, issuer/audience and KMS/SSF contracts remain unchanged.

2. **Make controlled delivery outcomes truthful.** In `email.rs` and the dispatch/resend callers, distinguish suppressed, unconfigured, provider-accepted and failed outcomes. Keep registration committed if delivery fails; do not recreate the user or reuse its consumed invitation. Replace detached, unobservable success assumptions with bounded delivery handling and an explicit authenticated resend recovery path. No background retry service or new mail-provider abstraction is required for this slice. A resend must use the authenticated account's stored address and tenant, enforce the existing server limiter plus a bounded per-account cooldown, and return a fixed sanitized outcome. Never claim mailbox receipt from a successful API/SMTP send. Provider error strings must not leak credentials, message bodies or verification links into logs. First implement/test against an owned loopback SMTP capture with synthetic `.test` addresses and external egress disabled.

3. **Bind and consume the verification challenge safely.** Use a narrowly scoped migration/helper for a random challenge stored by hash, bound to user, normalized email, tenant and the trusted initiating client/return context. Rotate/invalidate the previous challenge on resend. Verify and consume atomically with a wall-clock expiry recheck after lock waits; exactly one successful transition may emit the verification event. Wrong tenant, expired/replayed challenge, changed email and concurrent resend/consume must not mark the wrong account verified. Preserve existing legacy callers through a documented migration path; do not silently retain a second weaker unscoped path for the new hosted flow. For this disposable staging follow-on, expire pre-change pending challenges and require resend rather than retaining old plaintext capabilities indefinitely.

4. **Return safely, using a fresh sign-in.** Prefer a same-origin confirmation page followed by an explicit verification action, so mail scanners merely opening the link cannot activate the account. Keep the capability on the auth side; serve verification responses with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, no third-party assets or capability-bearing analytics. After verification, clear the capability from the displayed URL and offer “Continue to GenUI” to the exact server-configured HTTPS entry route. Persist the initiating client association from the validated hosted request, not a `return_to` supplied in the mail/browser request; recheck the current tenant/client configuration before offering the destination. The existing broadly validated `login_redirect_url` is not sufficient as this security boundary. A removed client falls back to a safe tenant sign-in page. Do not send a bare user to `/auth/callback`, auto-authenticate the clicked profile, forward a verification token to GenUI, reuse old state/code/PKCE or infer membership from a success page. A fresh GenUI-initiated authorization flow establishes the current identity and verified metadata in any browser/profile.

5. **Qualify and review before any deployment.** Auth owns backend/schema/hosted-page/email/config changes and its tests; GenUI owns pending-state UI, backend resend mediation, the ordinary sign-in route, membership and activation. Supply a precise consumer handoff and obtain its reviewed interface; make no GenUI edits from this lane. Run required local checks and CI, independent review, and a new source-bound image qualification for changed product bytes. Preserve the currently qualified no-SMTP image as history/rollback. A rollback that cannot enforce the new activation contract closes admissions; it must not treat pending users as verified.

## Evidence required before a controlled-mail trial

- **Local transport:** capture the actual message in memory and prove exact invited recipient, sender, branded tenant and auth-only link. Positive delivery control; suppression/unconfigured/provider refusal/timeouts cannot be labeled delivered. No external SMTP or provider calls. Reuse the existing SMTP harness rather than introducing another service.
- **Verification integration:** correct tenant/user/email binding; successful one-use transition; invalid, expired, replayed and wrong-tenant links; two simultaneous consumes and resend races; expiry during a row-lock wait; one sanitized event; no activation on a link-preview GET. Assert an unverified account remains unverified after every refusal. Tests should use the real message link, not set `email_verified` directly as proof.
- **Application boundary:** before verification, backend metadata is false and GenUI denies activation/resource access. After mailbox confirmation and a fresh PKCE flow, metadata is true, subject/tenant match the intended invitation, and GenUI independently checks current membership/entitlements. A `verified=true` query, webhook, stale earlier response, another browser's existing session or another tenant's verified user cannot pass activation.
- **Browser/return/privacy:** test slow mail past the original five-minute request, resend, expired link, different browser/profile, removed client and tampered destination. Chrome, Firefox and native Safari must eventually exercise the actual return; WebKit alone is not Safari acceptance. Assert no access/refresh material enters browser responses/storage, and no challenge, mail body or credentials appear in server/provider/browser evidence. Preserve the redirect-log regression. Local mock browser success is not external-mail delivery.
- **Release evidence:** targeted Rust/integration/frontend tests, required full CI and unchanged warning budget, independent review, and image/source/asset/runtime identity. Use `CARGO_BUILD_JOBS=3`, at most two test workers and one browser worker; isolated owned ports/data only. Record failures honestly and retain source-bound sanitized receipts.

## Later controlled-mail trial and cleanup

This is a **separate follow-on** from the currently approved six-hour/$5 synthetic **no-SMTP** rehearsal. It neither starts that clock nor extends its scope, cost allocation or ready flags. The existing plan deliberately omits SMTP and does not prove mailbox activation. A `.test` SMTP sink proves local protocol behavior, not internet delivery.

Before a real delivery trial, root and GenUI must agree on a small allowlist of team-controlled test inboxes, a verified sender/domain, one existing transport, exact return/pending-state routes, message-count/time/spend limits, operational ownership and cleanup. Do not choose a provider, request DNS records, restore deleted credentials or use real customers through this plan. The checked-in infrastructure already maps an optional SMTP secret; it does not by itself wire a Resend secret or prove a live sender. Select only the minimum typed configuration for the chosen trial, with managed credentials, least-privilege reads and sanitized accepted-use evidence consistent with FORMA-248. [Existing SMTP wiring](/Users/victorvillacis/dev/Forma/work/FORMA-247/gatewasm/infra/lib/constructs/service.ts:133).

In that separately admitted trial, capture only delivery disposition/message identifier, controlled-recipient alias, source/image, tenant/client and timestamps in public receipts. Mail contents, raw links and inbox access remain private and short-lived. Witness receipt in the controlled mailbox, confirm the link, then execute the fresh GenUI login and activation checks; do not manually set the database flag. Finish by revoking the dedicated refresh sessions, expiring pending challenges, removing owned test accounts/invites/messages, removing only newly added mail configuration/credentials/DNS records if any, verifying transport is again disabled where intended, and reconciling costs and outstanding cleanup. A delivery/provider failure leaves activation blocked and produces a failed/incomplete receipt, not a fallback login.

## Genuine decisions/dependencies

The recommended return semantics are fixed here: verify the mailbox, then **start a new ordinary GenUI sign-in**, including when the link opens in another profile. The remaining application decision is GenUI's exact sign-in/pending-verification/resend route contract and how it retains restricted server-side state without granting membership. The later operational decision is the controlled inbox/sender/transport and its separately scoped trial limits. Neither is needed to approve this plan, and no additional product feature or current paid-window change is implied.
