## Tenant and client identifiers

Client IDs can be selected offline. The receiving GenUI agent has accepted `northstar-platform` for `northstar` and `canary-platform` for `canary`; these IDs are selected offline but remain unregistered until `POST /manage/oauth-clients` registers each against its actual tenant management key. IDs accept ASCII letters/digits/`-`/`_`, max128, and may not end in `-hosted`. Exact matching registration is idempotent201→200; a changed name/callback or another tenant's existing ID gives409. Registration returns the actual `tenant_id`. No client secret is required by the current PKCE flow. See `crates/server/src/handlers/management.rs:862–930` and `handoff/forma-247/config.example.json`.

**fAuth tenant IDs cannot be fixed through the supported provisioning API.** `CreateTenantRequest` has name/slug/owner email/providers/limits/signup mode, no ID field. Creation generates `ten_<random UUID>` (`crates/server/src/handlers/management.rs:277–284,386`); users similarly receive `usr_<random UUID>` (`crates/server/src/handlers/hosted_code.rs:430`, management user creation). Neither a tenant nor a subject is a bare application UUID.

GenUI's fixture IDs `00000000-0000-4000-8000-000000000001` and `00000000-0000-4000-8000-000000000002` therefore **must not be compared directly to JWT tenant_id** or assumed to equal fAuth IDs. GenUI should retain those internal storage IDs if its schema requires them and install an explicit trusted mapping from `(issuer, actual fAuth tenant_id)` to the correct application organization, after provisioning returns the real IDs. Root relayed explicit receiving GenUI confirmation (chat `01a18398-5fb1-7e22-82a6-141b013a1c3e`): Northstar maps to `00000000-0000-4000-8000-000000000001`; Canary maps to `00000000-0000-4000-8000-000000000002`. Each actual fAuth tenant ID remains unknown until provisioning. The API does not support supplying chosen fAuth IDs; direct database editing or stripping prefixes is not the handoff.

The public provisioning receipt can contain slug, actual `ten_…` ID, chosen client ID and exact redirect. Private transport is needed only for management credentials, user passwords and invitation/session capabilities. Prefer a mapping record containing `app_organization_id`, `fauth_tenant_id`, `fauth_tenant_slug`, `client_id`, `issuer`, `audience`, and `redirect_uri`. Reject any unmapped/mismatched verified tenant before app resource access. The same explicit mapping is required for the canary rejection check.

## Backend callback and token response

Invitation-first registration uses authenticated backend `POST /manage/invites` with explicit role and `delivery_mode:"server_only"`, then tenant PAR with the raw invitation only in the backend body. The browser gets only opaque `request_uri`, a nonce-bound hosted request and finally code/state. Hosted registration returns201 `{redirect_uri}`; existing login returns200 `{redirect_uri}`. GenUI binds/verifies fresh state and PKCE verifier in its own pre-login session. The exact registered callback is fixed above.

The backend exchanges JSON at `/t/<slug>/auth/token`:
`{grant_type:"authorization_code",code,code_verifier,client_id,redirect_uri}`. A successful response contains `access_token`, `refresh_token`, `token_type` (Bearer for this non-DPoP plan), `expires_in`, `expires_at`, and `user:{id,email,name,avatar,email_verified,roles,auth_method,mfa_verified}`. **The subject is signed JWT `sub`; it must equal token-response `user.id`. There is no `user.sub` or top-level response `sub`. The user JSON does not contain tenant_id; obtain it from verified JWT claims and the trusted mapping.** Source: `crates/server/src/handlers/token.rs:306–324`; `crates/server/src/jwt/signing.rs:11–29,57–69`.

`user.email_verified` is authoritative backend response metadata read from the database. It is not a JWT claim; authentication currently succeeds while false. GenUI must keep the response and any pending verification state server-side and enforce its own activation policy. Current hosted email claims are `auth_method:"password"`, `mfa_verified:false`; the adapter refuses required-MFA accounts/tenants rather than bypassing MFA.

Token exchange and refresh also return issuer refresh-cookie headers for existing clients (`crates/server/src/handlers/token.rs:284–291,738–751`). **The GenUI BFF must not forward fAuth token JSON or those Set-Cookie headers into its browser response.** Store the refresh token securely on the backend and issue only GenUI's own opaque app session. The real callback probe must test this boundary, not intercept it with an issuer-only stub.

## Refresh, logout and revocation

- Backend refresh: `POST /t/<slug>/auth/token` JSON `{grant_type:"refresh_token",refresh_token}`. Use the tenant route. Refresh checks tenant ownership; `client_id`/redirect are not required or a separately enforced refresh binding. Response rotates the refresh token and returns fresh user metadata, including current `email_verified`/roles. Serialize refresh per app session and replace the stored token atomically. Reusing a consumed explicit refresh token yields401 `invalid_grant` and revokes its family; do not blindly retry a potentially completed request with the old token (`crates/server/src/handlers/token.rs:389–445,650–724,767–785`).
- A signing failure within refresh rolls back its consume/insert transaction, so the same still-valid token can retry after recovery. Authorization-code consumption precedes signing; a failed code exchange requires a fresh hosted start. Distinguish these cases in the outage trial.
- Backend logout: `POST /t/<slug>/auth/logout` with JSON `{refresh_token}`; a bearer access token is optional for event attribution. It returns204 and issuer-cookie clears, revokes the supplied token hash, and does not itself erase GenUI's session (`crates/server/src/handlers/auth.rs:1490–1532,1587–1595`). GenUI must clear/revoke its own opaque session. Prove subsequent refresh denial; HTTP204 alone is not the negative receipt.
- Tenant-management revocation: `POST /manage/users/<actual usr_id>/revoke-sessions`, authenticated by that tenant's management key, revokes all that user's tenant refresh rows and returns `revoked_count` (`crates/server/src/handlers/management.rs:1780–1821`). There is no general RFC7009 revoke endpoint in the current router.
- Already-issued signed access tokens are not immediately invalidated merely by logout or refresh revocation; offline JWT verification can remain successful until expiry. GenUI's own current session/membership/epoch authorization must enforce immediate app access denial. Optional SSF/webhook delivery is not a substitute for proving the application session boundary.

## Mailbox verification and approved synthetic scope

Hosted invited registration creates a verification token expiring after24 hours and dispatches a verification email after account/code commit (`crates/server/src/handlers/hosted_code.rs:430–447`). `server_only` suppresses the invitation email; it does not by itself suppress this separate verification dispatch. The selected staging configuration has no SMTP/Resend credentials, so delivery is a no-op; the local proof explicitly suppresses mail. `crates/server/src/email.rs:41–78` returns success even when delivery is suppressed/unconfigured. A response saying email sent is therefore not delivery evidence.

The existing verification link is `/t/<slug>/auth/verify-email?token=…` (`crates/server/src/email.rs:254–265`). Successful verification marks the user verified and clears the token, then serves an HTML page that navigates to `/platform/login?verified=true` after two seconds (`crates/server/src/handlers/auth.rs:1846–1928`). **It does not resume the original PAR/PKCE request, does not invoke the beta callback, and cannot be made to do so by passing an arbitrary redirect.** No new continuation route was added. `/t/<slug>/auth/resend-verification` is access-token authenticated/rate-limited, replaces a24-hour token, and returns a message (`crates/server/src/handlers/auth.rs:1931–1993`). After proof, a fresh hosted login or successful backend refresh returns `user.email_verified:true`; the JWT still has no mailbox claim.

For real-mail activation later, select/authorize a controlled inbox, configure a working managed transport and verified sender/domain, prove actual receipt and one-time/expired-link behavior, and agree a safe app-owned return step that starts fresh state/PKCE or updates the pending backend session. The current return page is fAuth platform login. Existing SMTP can be configured through the reviewed optional managed-secret hook; Resend is supported by runtime config but is not wired into the current staging CDK secret inputs. Do not add transport/domain work to the no-SMTP synthetic window implicitly.

Under the approved operator-gated synthetic rehearsal, prepare explicit tenant/client mappings, private seeded credentials and backend-owned invitation/PAR/session handling; test false mailbox metadata and deny ordinary activation while false. Any permitted synthetic bypass must be explicit, limited to the operator fixture and excluded from external-beta/real-organization readiness. This scope can prove hosted identity/PKCE and custody without proving mailbox delivery. Real external-beta mailbox activation and the actual return journey remain separate acceptance prerequisites.
