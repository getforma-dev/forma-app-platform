# FORMA-247 hosted authentication handoff

This directory is a reviewed delivery artifact for GenUI to incorporate beside its demo. It does not modify the application repository. `config.example.json` is explicitly synthetic and loopback-only. The confirmed application origin is `https://beta.getforma.dev` with exact callback `https://beta.getforma.dev/auth/callback`; the example remains loopback-only. The separate auth origin and a working GenUI callback/test environment are still prerequisites before hosted provisioning.

## Contract

Register a tenant-scoped client with `POST /manage/oauth-clients` authenticated by its management key. The body is `{client_id, name, redirect_uri}`. One exact HTTPS redirect is permitted per identifier (loopback HTTP is allowed only when the issuer itself runs over local HTTP). Identical requests return 200 after the first 201; differing configuration or another tenant's identifier returns 409. Client identifiers ending in `-hosted` are reserved for fAuth's existing hosted login. `GET /manage/oauth-clients` lists only the authenticated tenant's clients.

Start the password code flow by navigating the browser to `/t/<slug>/auth/authorize?provider=email&client_id=...&redirect_uri=...&response_type=code&code_challenge=...&code_challenge_method=S256&state=...`. The platform must generate and bind a fresh high-entropy state and verifier to its own secure pre-login session. fAuth redirects to its existing branded sign-in page with a browser-bound, five-minute request. Credentials are checked by the existing password handler, including its rate limiter and account lockout. Success returns only a callback URL containing a one-use, 60-second code and the unchanged state; no access or refresh token is returned to browser JavaScript for this flow.

The platform validates state, then posts JSON to `/t/<slug>/auth/token` from its backend with `grant_type: authorization_code`, `code`, `code_verifier`, `client_id` and the exact `redirect_uri`. The backend stores the returned refresh token securely and keeps browser sessions opaque. Verify `alg=EdDSA`, `kid` against `/auth/jwks`, exact configured `iss` and `aud`, expiry, and `tenant_id`/`sub` before using roles. The existing default issuer/audience are deployment settings (`gatewasm` / `gatewasm-app`), not inferred URL values. Use the deployed receipt. Canary tokens must never authorize a Northstar resource.

This first password code adapter refuses tenants with an enabled MFA policy, individual MFA-enabled users, and compliance-required MFA. The demo selects `mfa_policy: off`; disabling a real account's MFA to make this flow work is not supported. Provider federation retains its existing flow. No passkey UI is added. Browser-bound requests use one cookie per tenant, so starting another sign-in in the same browser/tenant supersedes the previous pending request. Requests are rate limited and capped at 1,000 pending records per tenant.

## Invitation-first account creation

This extension creates identities only for an existing fAuth invitation. It does not add GenUI organizations, membership rules, invite/trial codes or product entitlements. The selected beta identity tenant remains `invite_only`; even an `open` tenant cannot use hosted code registration without a bound invitation.

An authorized backend creates the identity invitation with `POST /manage/invites`, JSON `{email, role, delivery_mode: "server_only"}`. The role must be explicit: `user`, `admin`, or a role owned by this exact tenant. Provider/platform roles are refused. The response is 201 with invitation metadata, `invite_token` and `email_delivery: "suppressed"`, no `invite_url`, and no email send. Keep that raw token in the backend's invitation ledger. The default `delivery_mode: "email"` retains the legacy administrative flow and its invitation URL; do not use it for the server-only integration.

The backend pushes form-encoded parameters to `/t/<slug>/oauth/par`: `provider=email`, registered `client_id`, exact `redirect_uri`, `response_type=code`, `state`, `code_challenge`, `code_challenge_method=S256`, and the fAuth `invite_token`. A valid pending invitation returns 201 `{request_uri, expires_in: 60}` with `Cache-Control: no-store`. fAuth retains only the invitation hash in this email PAR record. Neither raw invitation tokens nor PAR handles are logged by these handlers. The browser navigates only to `/t/<slug>/auth/authorize?client_id=...&request_uri=...`. The handle is single use and is consumed atomically with creation of the five-minute browser-bound request; failed validation or a full request queue leaves it unconsumed until its original expiry. A failed/expired handle must be restarted through the backend.

The hosted page derives `hosted_registration_allowed` from the current request, browser nonce, registered client/callback, pending invitation and MFA policy. It exposes no invitation token or authoritative role/email to JavaScript. Registration posts `{authorization_request, email, password, name?}` and receives **201 `{redirect_uri}`**, containing only the usual code/state callback. Login stays **200 `{redirect_uri}`**. The browser must not send an `invite_token` on either hosted submission; such input is refused, not applied through the legacy invitation path. Empty/expired continuations fail closed. The ordinary legacy registration API remains token-bearing for existing clients and must never be used as a hosted fallback.

Registration locks and rechecks the current tenant, invitation, email and role; user/credential creation, invitation consumption, hosted request consumption and code issuance commit together. No refresh row/token, access token or refresh cookie is created until the backend exchanges the code. Duplicate identities get 409 without consuming the invitation/request, so the existing member can choose sign-in. Hosted sign-in consumes the bound invitation and applies its trusted role in the same transaction as code issuance. Revoked, expired, used, wrong-email, wrong-tenant and privileged-global-role invitations cannot create identities or grant roles. Capacity is checked inside the serialized hosted registration transaction; this does not claim to serialize every legacy management writer. Security expiry uses the actual clock after lock waits.

The GenUI backend validates state, exchanges the code and verifies the JWT exactly as in existing-user login. Its token response includes `user.email_verified`; the JWT does not. GenUI owns any activation/mailbox-proof gate and must not infer mailbox verification from successful password authentication. Existing verification/reset navigation does not automatically resume an application authorization request. Real mailbox delivery and application return behavior need separate qualification if used. The controlled synthetic phase may use suppressed or trapped mail only when explicitly identified as such.

PAR and hosted request records are each bounded to 1,000 pending records per tenant and use the existing login rate limiter. One browser nonce cookie per tenant means a newer start supersedes an older browser continuation. Never place raw fAuth invitation tokens, access tokens, refresh tokens, management keys or PKCE verifiers in URLs, client storage, public receipts or logs. The opaque PAR handle, browser request handle and authorization code remain short-lived front-channel capabilities; the reverse proxy must redact query strings in request logs.

## Provisioning

Use Python 3 with standard-library modules. `FAUTH_PLATFORM_KEY` and password variables named in the config must be supplied through the approved secret environment. The script prints a public receipt only. Hosted runs read/write tenant management keys through AWS Secrets Manager using the current CLI identity and selected region; use a dedicated least-privilege secret prefix. Secret values never appear in process arguments, tickets or receipts.

```
python3 provision.py --config reviewed-hosted-config.json --region us-east-1 --secret-prefix forma-demo/management
```

Run twice and retain both public receipts. A tenant that exists without its recorded secret, a mismatched subject/role, wrong password, changed client redirect, or missing environment input stops the run; there is no silent key rotation, password reset, or fallback. Existing users' passwords are not changed. Each synthetic login probe is immediately logged out. Both tenants are invite-only, email-only, and use explicitly selected branding, origins and callbacks. OAuth provider buttons remain hidden without credentials for that tenant.

For disposable local evidence only, pass `--synthetic-secret-file /absolute/private/path.json` (0600; loopback issuer required). Treat this file as a secret, keep it outside Git, and remove it with the disposable environment. The checked-in example contains no passwords or tokens.
