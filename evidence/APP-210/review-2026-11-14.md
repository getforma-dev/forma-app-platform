## Focus answers

### 1. A schema change cannot ride a contract-only record

`load()` admits two shapes only. The contract always differs. `from.database_version <= to.database_version`. And the schema manifest differs if and only if the version differs.

`applicable()`, which is unchanged, still requires all of these:
- the baseline's two digests equal `from`;
- the candidate's qualified source digests equal `to`;
- the policy version equals `from.database_version`;
- the candidate's committed `app/migrations/manifest.json` hashes to the source digest, and its `database_version` equals `to`;
- the checkout is the candidate commit.

For a contract-only record, therefore, the candidate's manifest is byte-identical to the baseline's, at the same version. `migrates()` is derived from the versions, and those are bound to the manifest by the iff rule. A release with equal versions can never run, or skip, a migration that its manifest needs.

Each pairing was tried:

| Pairing | Refused by |
| --- | --- |
| Equal versions with a moved manifest | `load` (B3) |
| A moving version with a kept manifest | `load` (B3) |
| A falling version | `load` (B2) |
| Identical ends, or a kept contract | `load` (B1) |
| A contract-only record whose candidate's manifest moved, at version 24 or at 25 | `applicable`, before the lock (R1) |
| Committed manifest bytes that differ from the qualified source digest | before the lock (R2) |

The database itself can change only through the migration task, and only `migrating` releases run it. The last line of defence still holds too: the previous image's pool proves the exact catalog and version on every connection (APP-196 review).

### 2. An infrastructure change cannot ride it either

`infrastructure_sha256` is still pinned in source and compared exactly in `load`. `applicable` still requires `infrastructure_digest(repo)` to equal it.

A contract-only record whose candidate's CDK source moved refuses before the lock (R3). So does another checkout (R4).

The promotion never deploys the candidate's CDK at all. It applies `baseline.template` with runtime-only parameters, and `guards.changeset` limits the change set to existing task, service and schedule resources. So infrastructure cannot move through this path in any case.

### 3. The outage safety is the normal path's

A contract-only release runs exactly the normal execute path:
- every pre-execution recheck, including the scan binding to the `to` contract and the release recheck;
- one final-check pass;
- the 30-minute outage reserve, which is unconditional;
- the stop and stopped proof, the change set, the stopped-after-execute boundary, the activation intent, the health wait and the healthy boundary.

It takes no snapshot and runs no migration. The test asserts the five normal mutations, with no RDS call and no `run_task`.

The baseline moves only in `finish`, after the healthy boundary, the public probes and `verified.json`. `finish` requires `policy.schema_version == record.from_version` for every release now (B12). A policy moved during execution admits nothing, for both kinds: the test leaves the phase `activation-intended` and the baseline contract unchanged.

### 4. Execute and restore interactions

- **No schema journal entries.** `snapshot_schema` and `migrate_schema` are the only writers of `schema-` entries, and both are gated on `migrating` (B9, B10). The lifecycle test asserts that none of `schema-snapshot.json`, `schema-migrate.json`, the two observations, `stopped-after-migration.json` or `schema-release.json` exists.
- **Abandon.** `pre_outage_snapshot` returns `None` when no `schema-` entry exists, so a prepared contract-only release abandons as a normal one (tested by the builder).
- **Release after a rolled-back update.** `release-rolled-back` refuses only once `schema-migrate` is journaled, so a contract-only release whose stack update rolled back is released as a normal promotion would be.
- **Restore.** The restore refuses a contract-only release first, with its own reason (B17). That is correct: no migration exists to have failed, and its failures are a normal promotion's.
- **The noted `KeyError` (NIT-1).** If a `schema-snapshot` entry ever appeared in a prepared contract-only release, `abandon` would raise `KeyError('snapshot_identifier')` at `maintenance.py:123`. R5 shows it fails closed: no state write and no AWS mutation, and the CLI prints its generic refusal. It is unreachable today.

  **Fix:** add `schema_release.migrates(release)` to the `require` at `maintenance.py:115`, so it refuses by name, plus a one-line test.

### 5. The summary cannot mislead the approver about the sequence

`validate_summary` derives `migrating` from the projected versions. It binds those versions, the spec hash and the `to` contract to the committed file. For equal versions it also requires the spec's two manifest digests to be equal. It then requires `preserved.schema` and the sequence to follow.

So a migration can never be presented as contract-only, and a contract-only release can never claim a snapshot or a migration (B13–B16).

The builder is right that a contract-only summary differs from a normal one only in `schema_release`, and in a contract the summary does not compare with the baseline's. Mistaking one for a normal release is harmless, because the outage sequence is the normal one. What the summary cannot show is *which* contract paths changed. Only the reviewed record says that.

**Is the checklist enough?** The section 3a checklist is enough, with one correction (NIT-2). Its `spec_sha256` and contract lines compare the summary with the candidate's own committed file. `validate_summary` already enforces that, so the check is tautological. The comparison that catches an unreviewed record is against the values stated in release C's reviewed evidence record: the file hash and the `to` contract, as release A's record stated them. BETA-PROMOTION already says "Approve only if those match the reviewed record". The trial runbook should say the same.

## Findings

- **NIT-1:** `maintenance.pre_outage_snapshot` refuses a contract-only packet with a `KeyError` instead of a named refusal (above). It fails closed and is unreachable today.
- **NIT-2:** trial runbook section 3a step 2 checks `spec_sha256` and the contract against the candidate's own file. Check them against release C's reviewed evidence record instead (above).
- **NIT-3:** the promotion code does not prove `app/migrations/` unchanged; CI and hash checks at use do.

  A contract-only record admits any change to the contract other than the manifest and the CDK source. That includes an edited migration body, or a catalog or extra `.sql` file that the unchanged manifest does not account for. Nothing in the promotion code compares the tree under `app/migrations/`. Three things protect it:
  - the manifest's per-file SHA-256s, which `runtime.migration_sources` and `catalog_resources` check when the files are used;
  - the native pool's embedded catalog;
  - CI's exact-migrations test in `app/runtime/test_runtime.py`.

  Every effect fails closed. A changed catalog would make the pool refuse at activation, with the lock held. A changed applied migration would make the next migration's ledger proof refuse, with exit 1.

  **Fix:** release C's own review should confirm `git diff --stat <live candidate> <release C candidate> -- app/migrations` is empty, and its evidence record should say so.
- **NIT-4:** the contract-only off-baseline test has no infrastructure, checkout or moved-manifest case. Each passes through the unchanged `applicable`, and R1–R4 show they refuse. Add them as subtests of `test_a_contract_only_release_off_its_baseline_refuses_before_the_lock`.

## Verified as sound

- **Rules and pin.** `load`'s three shape rules, the unchanged source pin and the unchanged `applicable`.
- **The two design gaps the builder found are fixed correctly.**
  - `CommittedReleaseTests`' wrong-policy set is now `{from+1, from-1, to} - {from}`. For a migration this is the old set, so nothing is weakened. For a contract-only release it is `{from+1, from-1}`.
  - The summary's sequence check now follows `migrating`.
- **Snapshot naming.** `same_release` and `prepare` name a snapshot only for a migration, and `same_release` still compares a contract-only release exactly (B7, B8).
- **Records.** The completed record and `verified.json` carry the release projection without `snapshot_identifier` or `migration_task_arn`.
- **Docs.** The ADR amendment, BETA-PROMOTION's "Contract-only releases" paragraph and DEVELOPMENT's sentence match the code. The workflow references none of these fields.
