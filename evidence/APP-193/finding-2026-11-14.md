# APP-193: live interaction from general primitives (finding, 2026-11-14)

Spike by Claude (Opus 5.5). Code read on the unmerged branch `trial/w4-private-entries` at `64234d10` (contract edition `impl-2026-11-14.1`); line numbers below are on that commit and may move when W4 merges. This file is a recommendation. The go/no-go decision is Victor's, recorded by 2026-11-24 (ticket acceptance 2). The ticket was not edited.

## Short answer

- **Shared current item, live:** yes, with today's primitives. A one-row shared list that the owner changes through a `reviewer_only` update reaches every member's page by push (a server-sent-events hint, then a re-fetch).
- **Private responses with a live reviewer summary:** yes. Counts per choice and per item update for the owner as answers arrive. Each student sees only their own answers.
- **Timed answers:** no. Nothing refuses a second answer, a late answer or an answer after a deadline. The grammar has no server time or countdown.
- **Leaderboard:** no. There is no per-person score, and by D7's rule no summary over an `own` list can show other people's entries to a non-reviewer.
- **Scale:** at the same instant, the database pool admits 8 callers; a ninth is refused at once. 25 answers spread over 1 second all commit. 25 at the same instant lose 17 to an immediate refusal, which the command route answers as 503. The same cap hits the page refreshes that every shared commit triggers.

**Recommendation: NO-GO for a game-style quiz on Nov 29.** The class uses formative quizzes: an `own` responses list plus a reviewer summary. That path works in storage (W4's 34-check campaign and this spike). It still depends on the composer work listed under question 6.

## What was run

A throwaway Rust test in a scratch worktree from `64234d10` (local branch `spike/app-193`, not pushed; see Limits). It was modelled on `storage/private_entries_campaign.rs` and used the same disposable Docker database and the shipped admission, publication, share and command paths. The test called the storage API directly; there was no HTTP or browser. It had 1 owner and 25 contributors, who reached the app through the organization-wide contributor share. It ran three times on 2026-11-14:

```
GENUI_QUERY_PYTHON=$PWD/app/runtime/.venv/bin/python cargo test --locked -p forma-app-platform --lib \
  storage::live_quiz_spike::native_live_quiz_spike -- --ignored --exact --nocapture
```

Result: `test result: ok. 1 passed` each time (15.7 s, 21.6 s, 16.5 s).

The app (general words, no classroom names):

- `items`: a shared list with `label` text, `number` integer and `state` enum `open|closed`. Commands: `post_item` (create, `initial` state `open`, `reviewer_only`) and `advance` (update of all three fields, `reviewer_only`).
- `responses`: `visibility: "own"`, with `item` integer and `choice` enum `a|b|c|d`. Command: `answer` (create).
- Views: `records_list` of items; `record_summary` count of responses; `record_ranking` count by `choice`; a typed `table` aggregating count by `item` and `choice`; and the `answer` form.

## 1. Current item

**Exists.** A shared list (no `visibility`) holds one record that the owner posts and then changes with an `update` command marked `reviewer_only` (`admission/validate.rs:1575-1598`; enforced in `storage/commands.rs:810`). Contributors are refused (measured). One design detail matters: use an `update`, not a declared transition. The creator of a record can never fire a declared transition on it (`storage/commands.rs:887`, the APP-113 rule), so an owner could not "close" an item they posted that way.

**How a member's page learns of a change:**

1. The command route announces `record.committed` (`commands/routes.rs:475-484`) on the in-process hub (`events/mod.rs:1-53`).
2. Delivery is judged once per event for the organization: whether each subscriber can open the work, and the row rule on the committed revision (`storage/sharing.rs:391-430`, own rule at `:409-414`). A shared-list commit reaches everyone who can open the work (measured 26 of 26).
3. The browser's single server-sent-events stream gets the hint, which carries only the app and work ids (`app/admin/src/canvas/live.ts:9-39`, `:124-175`).
4. The work page re-fetches the whole document (`app/admin/src/work/document.ts:209-213`). The canvas re-runs the cards it shows (`app/admin/src/canvas/board.ts:1484-1505`).

This is push. Polling is only the fallback: the work page refreshes every 30 s while visible (`document.ts:194-197`), and a re-opened stream is reported as lagged so the page re-reads everything (`live.ts:150`).

**Latency:** measured server-side parts only, all local: the delivery read takes 62–67 ms and one summary read 94–97 ms. A page refresh costs several data transactions (document and listing, one per form, the record components, one per data view in parallel; `query/routes.rs:674-925`, `:1158-1215`). End-to-end time from commit to updated page was not measured.

## 2. Responses

- **An `own` list:** exists (`validate.rs:966-976`; one row rule `storage/authorization.rs:772-800`). Measured: a student's summary and typed query see only their own rows; the owner sees all.
- **References the current item:** partly. A `reference` field may target the items input (`validate.rs:1912-1928`). The commit checks only its shape, not that the record exists (`storage/commands.rs:748-755`). A form shows a reference as a free-text box that expects a record UUID (`query/canvas.rs:868-899`; `app/admin/src/canvas/commands.ts:48-49`), so people cannot fill it in. The spike used a typed item number instead.
- **One response per person per item:** **gap.** Each create carries a record id chosen by the caller (`storage/commands.rs:71`, `:100`), and a form mints a fresh random one on every render (`query/routes.rs:706`). Composing a record judges only that record's own fields (`storage/commands.rs:799-899`). Measured: a second answer to the same item commits. The idempotency key stops only a repeat of the same submission.
- **Refuse after the item closes:** **gap per item.** A guard is `field comparison literal` over a field of the same record (`validate.rs:1662-1679`, `:2478`; `storage/rules.rs:1-13`). A response therefore cannot read the item's state. Measured: an answer after `closed` commits.
  - A coarse whole-work gate does exist: switching the organization-wide share from contributor to viewer refuses every write at once and keeps the own rows readable (migration 0024 `set_work_everyone`, `app/migrations/0024_private_entries_and_roles.sql:227-300`; `storage/sharing.rs:258-325`; measured). It is a storage API only. No route calls it on W4 (`sharing/mod.rs:204-257` shares person by person, `Audience::Member` at `:214-221`), and none did on `trial/w2b-share-dialog` at `da49efe9` when checked.

## 3. Timing

**Nothing exists.** `timestamp` is a field type (`validate.rs:85-87`), but every guard compares against a fixed literal (`validate.rs:89-92`, `:1662-1679`): there is no "now". No renderer counts down (`validate.rs:52-67`, and nothing in `app/admin/src`). Each revision stores `committed_at` (`storage/actions.rs:118`), but no view or query can read it as a field, so answer speed cannot be scored.

**The smallest general primitive is not a server-time field by itself.** A guard on the response record compares a value the student just wrote. Server time is useful only inside a guard over the *referenced* item (gap G2 below), for example `closes_at gt now`. A manual close by the owner, through the same G2 guard, gives the same fairness without a clock. A countdown display would only be cosmetic.

## 4. Live summary and leaderboard

- **Reviewer summary, live:** exists. `record_summary`, `record_ranking` (count by a text or enum field; `validate.rs:2041-2049`, `:1213-1225`) and typed views over a records input all read a snapshot under the row rule (`storage/record_components.rs:293`, `:302`; `storage/record_query.rs:134`). A student's answer event reaches its creator and the reviewers only (measured: 2 of 26). The owner's page therefore refreshes on every answer, and students' pages do not.
- **A non-reviewer sees an aggregate of others' entries:** **gap, by design.** Under W4's rule every summary, rank and typed query over an `own` list counts only the viewer's own rows unless the viewer is a reviewer. A public leaderboard therefore needs an explicit "published aggregate" primitive.
- **A per-person score:** **gap.** `record_ranking` groups by a field of the record (`validate.rs:2041-2049`), and no view can group by the person who created it. The only per-person split is the expense ledger's, which is money-only (`query/canvas_ledger.rs:167-182`). Nothing computes "correct": a filter compares a field with a literal, not with another record.

**Risks of a "published aggregate" to D7's privacy guarantee:**

1. **It breaks D7's "same rule on every path".** That rule promises that summaries count only one's own entries. The exception would need an ADR-007 amendment and a change to notice v1, which today says only that the teacher sees entries.
2. **Small groups reveal entries.** A count or rank over a group of one, or a per-person score row, is that person's data in another form. A score against an answer key reveals each person's answers.
3. **Live updates leak individual entries.** A count that moves by one as a classmate presses Submit gives away that classmate's answer. Today a response event is not delivered to other students at all (`storage/sharing.rs:409-414`). A published view would need a new, coalesced "aggregate changed" hint, or it leaks when each person answers.
4. **Filters can isolate one person.** The interactive record filters (text, enum, date range) can narrow an aggregate to a single entry. Filters would have to be refused, or a threshold applied after filtering.
5. **It needs a new authority path.** The server would compute over rows the viewer may not read and release only the result. Every snapshot today is computed under the viewer's own rule (`record_components.rs:293-302`, `record_query.rs:134`). Every consumer (Ask, MCP, Slack, pinned answer cards, exports, guests) would have to be shown to receive only the released aggregate, with new bypass-style checks.
6. **Names make the board personal.** With D6 names, a leaderboard identifies people in the room. Public scores need consent or an opt-out.

## 5. Scale (25 members within about 10 seconds)

- **Per-member limits: not hit.** The command route has no per-member limiter (`commands/routes.rs:365-436`). `MEMBER_WRITES`, 120 an hour (`http/limits.rs:57`), covers the folder, share, notes and name routes only; the owner's role toggles would count against it. The daily model cap (D10) and the composer limits apply only to model calls.
- **Live-event fan-out: not a limit.**
  - Streams: one per session, at most 4 per member and 256 per process; broadcast capacity 256, per-connection queue 32 (`events/mod.rs:71-85`).
  - Delivery checks: one judgment read per event per organization, for at most 256 subscribers (`storage/sharing.rs:55`, `:391-430`); measured at 62–67 ms.
  - The hub is in-process, which is correct for the single service task (`events/mod.rs:46-53`).
- **Database: the binding limit.**
  - Each role has 2 pooled connections and admits at most 8 callers; the ninth concurrent caller is refused at once with `Unavailable` (`storage/pool.rs:166-168`, `:404-409`, `:731`). The command route then answers 503 (`commands/routes.rs:143`). The canvas looks up the outcome by key and, since nothing was written, shows "not confirmed" (`app/admin/src/canvas/commands.ts:155`).
  - Every commit of the organization also queues on the organization's commit-sequence row (`storage/commands.rs:1219`). The lock timeout is 1 s (`storage/pool.rs:613`), after which the client waits and retries with the same key (`commands.ts:146-148`).
  - Answers, delivery checks and page refreshes all share the data role's 8 places (`storage/sharing.rs:379`).
  - Measured: 25 answers spread over 1 s or 2.5 s all commit. 25 at the same instant commit 8 and refuse 17.
- **The page-refresh herd is the larger risk, and it is not specific to quizzes.** Any commit to a shared list makes every open page re-fetch at the same moment. Examples: an item advance, or Victor posting an assignment while 25 students have the app open. Measured with 26 simultaneous summary reads: 8 ok, 18 refused. A refused work-page refresh shows "Updates are unavailable… Try Refresh" (`document.ts:136`), and that page stays stale until the next event or the 30 s timer. A refused record-views refresh shows "Record views could not be refreshed" (`app/admin/src/record-components/controller.ts:114`). This was measured at storage level, not through HTTP and browsers. Network jitter spreads real arrivals somewhat, but a refresh costs several data transactions, which makes overlap more likely.

## 6. Composer

**Not today.** The composer grammar on `64234d10`:

- has record schemas without `visibility`, commands without `reviewer_only` and without `when` guards (`composer/prompt.rs:84-101`);
- offers only the nine classic view kinds (`prompt.rs:88`), so `records_list`, `record_summary` and `record_ranking` come only from first-party templates (`composer/templates.rs:133-160`);
- forbids "anything about permissions, roles, owners, tenants, members, grants or access" (`prompt.rs:103`).

From plain words it can build a *shared* responses list with a form and typed count views. It cannot build the private list or the owner-only advance. That is the W4 composer step in `docs/planning/TRIAL-25-READINESS.md`, and it is not on the branch yet. The formative quizzes need it too. Every primitive below would need its own prompt text, an example and admission tests. The "one current record" idea is a convention, not grammar, so a model would build it unreliably. A model is also likely to write "close" as a transition, which the owner then cannot fire on their own record (`storage/commands.rs:887`).

## Recommendation

**NO-GO for a game-style live quiz on Nov 29. The class uses formative quizzes: an `own` responses list plus a reviewer summary.**

1. **No single small primitive makes it a game.** Fair, timed answers need G1, G2 and G3 (and G4 for a clock). A leaderboard needs G5, which is large and opens the D7 risks above.
2. **The calendar does not allow it.** Each of these is another contract edition on top of W4's unmerged one, with a Tier A review, a recheck and composer support. It would have to land between W4's merge and the Nov 24 build day and the Nov 26 rehearsal: the window the formative path already needs.
3. **What would also have to be true even with the primitives:** G6 fixed, because each advance makes most student pages fail their refresh at once.

**After the class:** fix G6 first, because it affects every shared app at this size. Then build G1, which homework also needs. Then G2 with G3 (and G4) for a live, fairly timed poll. Build G5 only after an ADR decides the D7 exception.

A live-poll variant is possible today: Victor advances a one-row item and projects his own reviewer page, which updates as answers arrive. It has duplicates, late answers, no timer and the G6 herd. I would not rely on it in class unless G6 is fixed.

## Limits

- The test drove storage directly, with no HTTP session lookup, TLS, browser or network. It ran on local Docker Postgres on macOS with four async workers. The numbers show behavior (the 8-caller cap, refusals, the row rule), not beta latency.
- End-to-end time from commit to updated page was not measured, and no browser was used.
- The code read is W4's unmerged branch under review at `64234d10`. Line numbers may change at merge.
- The composer was judged from its prompt and templates, not run against the model.
- W2b's share route was checked only for an organization-wide route, at `da49efe9`.
- The spike test is kept only on the local, unpushed branch `spike/app-193`, commit `2e0cbd90` (`app/src/storage/live_quiz_spike.rs` plus one `mod` line). Its worktree was removed. It is not product code and must not be merged.
