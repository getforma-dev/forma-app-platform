## Bounds and semantics

Each request captures one read-only PostgreSQL `REPEATABLE READ` snapshot under current member or explicit `GuestAccess` authority. The server resolves declared input/schema IDs through exact-work bindings; definitions cannot supply collection UUIDs. At most 2,000 current rows and 512 KiB of canonical record values may be captured across the selected inputs. Source liveness and sponsor/member permissions follow the existing work-read checks. A fresh release check compares publication, work version, definition, policy and current authority after execution; final document assembly repeats its release check.

The same engine organization/task admission and empty-environment confined child used for source queries runs the closed record protocol. It has no SQL, arbitrary expressions, network access or database connection. Filters execute before paging. Text matching uses Unicode case folding; enum filters match exact admitted enum values; date filters use real calendar dates and `[start, end)` bounds. Timestamp bucketing is not implemented. Null filter fields do not match; null summands contribute no amount; empty count/sum is a successful zero. Null grouping keys remain separate from user text that resembles a missing-value label.

Counts and integer/money sums use exact integer strings, including signed and large admitted values. Ranking ties use a stable lexical label order. Monthly date groups are chronological. List limits and ranking top-N never change the full filtered total. Overflow, invalid inputs, queue/deadline failures and unreadable inputs expose no values. A zero preset budget has an unavailable percentage, not infinity or an invented percentage. There is no budget Set control, persistent budget-record input, join or formula language.

Seven focused Python tests cover actual isolated-child protocol execution, pagination/target scope, negative/large/null money, zero budget, null-group collisions, empty collections, invalid dates/filters, overflow, the collection bound and deadline refusal. Three focused Rust tests cover closed body/epoch rules, calendar validation, exact display formatting and one filter-control owner. Existing source-query receipts are unchanged; the additive `record_components_receipt` is checked by both Rust and the Python contract validator.
