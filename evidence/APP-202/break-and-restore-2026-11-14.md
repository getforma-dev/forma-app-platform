# APP-202: break-and-restore proofs and checks (builder B0, 2026-11-14)

Branch `release/c-participation`, built on `55333401` (ADR-020 and the Release C tickets). Edition `impl-2026-11-14.2` (ADR-020 §11) in `contracts/` and `app/src/admission/`; the commits are named in the ticket log.

## How each rule was proved

Tests first: the Python suite was written and the negative vectors authored before any `validate.py` rule existed. That first run failed as intended (`FAILED (failures=82, errors=3)` of 50 tests): every semantic vector was admitted, and the worked example was refused because `countdown`, `group_by` and `matches` were not yet routed. The schema-level vectors already refused, because `schema.py` was written first. The validator rules then made the suite pass (50 tests, OK).

Then every new rule was broken on its own, once in each validator, by a script (the session's `breaks.py`; results `breaks.log`, `breaks-all.json`). For each break it replaced exactly one occurrence of the rule's text (asserting the occurrence was unique), regenerated `schema.json` when the break was in `schema.py` or `record_components_contract.py`, and ran the language's suite: `contracts/.venv/bin/python -m unittest discover -s contracts -p 'test_*.py'` for Python, and `cargo test --locked -p forma-app-platform --lib admission::` for Rust. It recorded what failed, then restored the file with `git checkout --` (and `schema.json`), and required `git status --porcelain` to be empty before the next break. Every restore was byte-identical to `HEAD`. The check "seen" means the vector or test named in the row was among the failures. Rust's vector runner stops at the first refused vector of each test, so a Rust row names the tests that failed and the vector named in the first panic.

Rows P are `contracts/validate.py`, S the schema step (`contracts/schema.py`, `contracts/record_components_contract.py`, with `schema.json` regenerated), R Rust admission (`app/src/admission/validate.rs`, `record_receipt.rs`). The break column shows the changed span only.

## A gap the proofs found

Preparing the breaks showed that both vectors for "the matches key input is a records input" named an absent input (`ghost`). A validator that kept only the existence half of the rule would still have passed them. Commit `ff8198ee` adds `matches key_input naming a source input refused`, where the key input exists but is a source. P19 and R19, which drop only the records-kind half, then fail on exactly that vector. The first P9 break (an unconditional `continue`) also disabled the other two `set_now` rules. It was narrowed to `if field is None: continue`, and the table shows the narrowed run.

## Limits

- These are contract and admission checks. They prove no runtime behaviour: the replacing create, the `requires` judgment at the transaction's instant, the countdown's current record and the ranking by creator belong to APP-203 to APP-205 and their campaigns.
- Until B1 (APP-203) merges, storage reads a stored declaration by key (`storage::commands`, `declared.get(…)`). A definition admitted on this branch with `requires`, `set_now` or `one_per_creator` is stored, but those members are not enforced yet. Release C must not be promoted with B0 alone; ADR-020 §13 already merges B0 to the release branch first.
- `admit_problem` judges a nested recovery view by its member set, kind, version and reason, not by every member's type. Storage builds the view from typed values, and `commands::tests` checks the emitted bodies against `$defs.problem`.
- The Python and Rust suites agree on every authored vector and on the unit cases listed above. They are not a differential fuzz of the two validators.
- The independent review asked for by APP-202's last acceptance item is not part of this file.
