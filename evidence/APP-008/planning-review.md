The isolation goals are sound. The following interfaces must be settled in the plans before code; these are design blockers, not claims that implemented behavior failed.

1. **Separate request identity, authorization precheck and final transaction authority.** Native planning currently reads as acquiring membership locks immediately after BEGIN; schema planning preserves the command's outcome-before-membership order. Use a private initial context and nonfinal current-authorization precheck, then acquire a transaction-bound permit at the operation's actual fence. Never universally lock membership at pool checkout. APP-013 must retain current precheck → scoped outcome → membership → saved work → record ordering, without turning the early precheck into authority to commit. Rolling back before a fence must invalidate its permit. This follows [platform §6.3](../../design/forma-generative-app-platform-v2/design.md#63-data-service) and [C07](../../design/forma-generative-app-platform-v2/SHARED-CONTRACTS.md#c07-internal-record-mutation).

2. **Specify the lock principal and every caller.** Schema planning assigns functions to the all-schema `genui_owner`; root instead requires a narrowly privileged NOLOGIN/NOBYPASSRLS lock principal. Define its exact read/lock-column privileges, FORCE-RLS policy, function ownership and exact signature grants, without an IAM login, app membership in that role, or general mutation authority. The matrix gives workspace/control membership SELECT but only data explicit lock/read EXECUTE; every implemented authorizing caller needs its reviewed lock capability. Worker can remain closed until its actual execution contract exists. SELECT alone cannot perform locking SELECT; do not fix this by granting application membership UPDATE. Also distinguish read-only business behavior from SQL READ ONLY transactions, which cannot take these row locks. See [PostgreSQL SELECT privileges](https://www.postgresql.org/docs/16/sql-select.html) and [definer precautions](https://www.postgresql.org/docs/16/sql-createfunction.html).

3. **Name the premises protected by each epoch/fence.** Membership state and grant changes are covered, but organization suspension, source access, publication policy and later entitlement changes also affect relevant operations. The owners must specify which row/epoch each operation checks, which mutation paths update it, lock order, expiry semantics and delivery recheck. A membership lock cannot serialize a writer that changes another premise without participating in its fence. Avoid inventing blanket grants or locking every future table. Keep [C07/C11](../../design/forma-generative-app-platform-v2/SHARED-CONTRACTS.md#c11-sharing-access-and-revocation) and [ADR-003's admission/commit/delivery requirements](../../docs/architecture/ADR-003-PUBLIC-BETA-ACCESS.md#identity-membership-and-entitlement) explicit.

4. **Make lease ownership enforceable.** One private lease must own the pool object and driver lifecycle; no shared/raw client, cancellation token, transaction, live row stream or background query may escape to another request. Default non-reusable before any awaited initialization. Only confirmed commit/rollback, standalone reset and clean-state verification permit return. Cancellation during create, BEGIN, query, COMMIT or reset must remove the object before ordinary pool drop can recycle it. Specify how connection-capacity permits survive abort until transport/driver closure is observed; “abort requested” alone is not proof of closure or a strict eight-socket ceiling. An unknown COMMIT remains an unknown business outcome, never an automatic retry or asserted rollback ([C07](../../design/forma-generative-app-platform-v2/SHARED-CONTRACTS.md#c07-internal-record-mutation)).

5. **Close reset, IAM and deadline details.** Choose one absolute acquisition/create deadline covering the optional generation retry, plus explicit transaction/reset budgets; avoid silently doubling the proposed five-second create limit. Bind endpoint, database, role, hostname-verified TLS, supported schema and actual role identity/flags/memberships before admitting a new connection. State precisely when a generation is accepted and when an in-flight lease expires. Keep DISCARD ALL standalone, outside a transaction; define baseline reinstallation and custom-setting verification, statement-cache absence, and the treatment of savepoints. Locks/context acquired after a savepoint can disappear on rollback, so a permit cannot survive blindly ([PostgreSQL locking](https://www.postgresql.org/docs/16/explicit-locking.html)).

6. **Freeze the bootstrap/admission seam without a gate cycle.** Decide the registry's separate closed format, delivery, digest/version and mapping-change protocol; clarify whether the mapping is one-to-one or merely single-valued. DB confirmation must agree with that immutable request mapping. Publicly constructible verifier output is not trusted evidence by itself. APP-073 needs a narrowly scoped, same-transaction admission path for a verified but not-yet-member identity; it cannot require an existing member permit to create membership, or gain a generic bypass flag. APP-009/073 supply real sessions/entitlements later; missing production admission must deny work, while APP-008's fixture constructor remains isolated. This preserves [ADR-003's ordered delivery](../../docs/architecture/ADR-003-PUBLIC-BETA-ACCESS.md#ordered-delivery-and-evidence).

7. **Choose a reviewable schema tranche and version transition.** The proposed real contract relations are substantial. Decide the tranche/split before coding, with actual publication/record tables for their ACL evidence and an explicit list of still-unproved write/RLS/workflow obligations. A SELECT-only initial grant matrix cannot be described as successful application write isolation. Keep later APP-010/013 workflows and APP-073 atomic membership/entitlement/audit with their owners. Specify checksummed migration2, exact supported binary/readiness versions and rollback/forward-fix behavior together; preserve historical schema1 restore evidence. Candidate dependency pins still require registry resolution, locked build and declared-MSRV qualification when implementation is authorized.

Recommended next artifact: one agreed API/state/lock-order table covering request context → lease → operation fence → result/outcome → reset/discard, with exact role/function callers and admission-owner inputs. The plans' same-backend reuse and deterministic cancellation/revocation evidence then test that contract.

This review installed nothing, changed no implementation/dependency/ticket, made no cloud calls and performed no Git operation. Public primary PostgreSQL documentation was checked for the privilege/locking details above; the candidate pool release was not independently resolved or built.
