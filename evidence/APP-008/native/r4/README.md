# R4: validate catalog before application metadata

The independent R3 supplement reproduced an admission-ordering defect: the initial identity query read `genui_meta.schema_version` before validating its structure, and used unqualified catalog names under an unchecked startup search path. An operator-installed replacement view or a shadowed `pg_roles` view could execute a marker function before the later catalog comparison refused the connection. The reproduction remains in [the R3 review receipt](../r3/independent-review.json). It does not claim that application roles have DDL authority.

Native connections now supply PostgreSQL startup options fixing `search_path=pg_catalog` before any SQL, including driver metadata discovery. The initial identity/origin query uses explicitly qualified built-in catalog relations, functions and text casts; it also checks the actual search path. Only after the canonical logical catalog comparison succeeds does a separate query read the version relation and require version2. New connection admission, recycle and explicit readiness share this ordering. Recycle verifies the clean session baseline before admission checks. Reset's replication-mode check and baseline functions are also explicitly qualified, including when a test deliberately poisons the old session path. No privileged repair, runtime SQL configuration, raw-client API or new package is introduced.

Three tests extend the existing local PostgreSQL/TLS campaign:

1. Replace the metadata table with an executable marker view in the owned fixture. A direct fixture-role positive control demonstrates the trap, then the marker is cleared. Reused and fresh native pools for all four roles must refuse with zero marker executions. Restoring the table must restore readiness.
2. Install an executable shadow `pg_roles` view, a database-wide startup search path selecting it, and one poisoned idle session. After a positive control and clearing the marker, new/reused native role pools must refuse with zero marker executions. Restoring the owned fixture must restore readiness.
3. Set the version row to the legally constrained value1 while retaining the unchanged version2 structural catalog. Independently confirm catalog comparison succeeds, then require new connections, recycle and readiness to refuse until the row is restored to2. This specifically proves the post-catalog version check is necessary.
