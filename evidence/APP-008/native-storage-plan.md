Tradeoff: more lifecycle code and tests, fewer hidden credential/cache assumptions. Do not implement a new queue/pool from scratch.

## Fixed connection factories and TLS

Keep `Workspace`, `Control`, `Data`, `Worker` as separate private typed pool/store boundaries; fixed usernames remain `genui_workspace/control/data/worker`. No request selects a role, connection string or endpoint; no owner/migration/reset credential or `SET ROLE` multiplexing. Initial proposal: two connections per role, eight total, with at most eight admitted acquisitions per role including active leases; excess fails promptly. Bound checkout1s, complete DNS/TCP/TLS/auth/create5s, reset2s, statement2s, lock1s and transaction5s. These are trial parameters, not performance claims; account for the existing readiness helper's connections and measure actual RDS headroom.

Every `Manager::create` reloads the canonical private credential file immediately before connecting, selects only its fixed role and retains generation/hash/expiry metadata. Build `tokio_postgres::Config` through setters; never interpolate/log a DSN or truncate the IAM token. Compare the file's host/database/port against trusted deployment configuration, including the actual `*.us-east-1.rds.amazonaws.com` hostname; the current syntax-only guard is insufficient for this factory. Re-read after connection establishment; discard a changed/expired generation and permit at most one bounded retry using the newly loaded file. No SDK/token minting dependency belongs in Rust: the existing supervisor owns that delivery.

Use standard PostgreSQL TLS negotiation for PostgreSQL16, `SslMode::Require`, the real DNS hostname as the TLS server name, and a root store built only from the packaged RDS CA bundle. Bound its read, require at least one valid certificate, reject parse errors; no OS-root fallback, IP substitution, custom insecure verifier or plaintext fallback. Build rustls explicitly with ring and TLS1.2/1.3. The adapter [passes the hostname into rustls](https://docs.rs/tokio-postgres-rustls/latest/src/tokio_postgres_rustls/lib.rs.html); `Require` alone is merely encryption policy, not proof of hostname verification. The [driver configuration](https://docs.rs/tokio-postgres/latest/tokio_postgres/config/struct.Config.html) defaults to weaker TLS preference and supports direct negotiation intended for newer PostgreSQL, so set these deliberately.

At every checkout, require a current valid file and the fixed endpoint/role binding; retire idle connections from an older generation. A bounded in-flight transaction may finish before its original lease expiry while refresh occurs; it must not be returned for another request under the old generation. Stop new work when the file is invalid; cap each transaction before credential-file expiry with a safety margin. [AWS documents](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.IAMDBAuth.html) that token expiry does not end an authenticated session: retirement is our policy, and membership/entitlement revocation needs its own checks.

## Transaction authority and RLS

Only the authorizer creates the private trusted-principal type: provider issuer/subject and explicit server-owned provider-tenant→organization mapping, current member/epoch, closed action enum and resource scope. A callback identity receipt is not a session, membership or entitlement. Store APIs take this type and expose fixed operations, never raw clients or caller SQL.

Checkout a clean lease, begin READ COMMITTED, install bound tenant/principal/epoch values with transaction-local `set_config(..., true)`, then read current membership/action policy **on that same transaction/primary connection**. Hold the necessary membership/policy lock until commit; revocation uses the conflicting update lock and the same fixed lock order. Recheck forwarded epoch/action and actual resource ownership before writes; unknown/absent/revoked input denies. Return a transaction-bound authorized capability rather than a reusable authorization boolean. No provider/model call or long response streaming holds the database transaction.

Do not grant the data/worker role direct membership UPDATE merely to support `FOR SHARE`: [PostgreSQL requires UPDATE privilege for row locking](https://www.postgresql.org/docs/16/sql-select.html). Proposed resolution is one narrow lock-and-read SECURITY DEFINER function with no mutation/dynamic SQL, explicitly scoped arguments matching transaction context, safe fixed search path, PUBLIC execution revoked, bounded return fields and an independently reviewed NOLOGIN owner/RLS policy. Its exact owner/grants are an unresolved migration decision; using a broad bypass definer is unacceptable. Real consumer lock success **and** direct mutation refusal must be proved together. APP-013's saved-work/adoption fence extends this later.

All real tenant relations need tenant-leading keys/FKs, FORCE RLS and explicit role grants. Missing/empty context denies (`NULLIF(current_setting(..., true), '')` before UUID conversion); malformed values never grant access. Custom settings are not secret capabilities, so fixed stores and trusted principal construction remain essential. [FORCE RLS does not constrain superusers/BYPASSRLS or all whole-table operations](https://www.postgresql.org/docs/16/ddl-rowsecurity.html). Preserve the real publication/record schema ownership gate with APP-010/013; denied access to a fake/nonexistent relation is insufficient.

## Reuse, reset and cancellation

Wrap each pool object in an application lease that defaults to **non-reusable**. Await explicit commit/rollback, then execute standalone `DISCARD ALL` outside a transaction, restore fixed baseline settings and blank the reserved context settings, and verify fixed session/current user, `row_security=on`, safe search path and absent/empty tenant/principal/epoch. Only then mark reusable. Repeat the clean-state assertion before request queries. Use typed parameter queries without a retained statement cache; dropping prepared statements after server deallocation is not a valid cache strategy. [DISCARD ALL](https://www.postgresql.org/docs/16/sql-discard.html) clears plans/listeners/temp objects/advisory locks as well as settings; [SET LOCAL](https://www.postgresql.org/docs/16/sql-set.html) alone can reveal prior session values or be undone by an earlier savepoint.

On cancellation, panic/drop, timeout, protocol failure, failed reset or uncertain COMMIT, the lease synchronously removes its object with `Object::take`, drops the client and aborts its owned connection driver task. Cleanup uncertainty never reaches another borrower. The driver-task owner itself must abort on drop during create/recycle cancellation, so dropping a future cannot detach a live connection. Server-side statement/idle limits bound work after a broken client. A [CancelToken acknowledgment does not prove cancellation](https://docs.rs/tokio-postgres/latest/tokio_postgres/struct.CancelToken.html), and [transaction drop](https://docs.rs/tokio-postgres/latest/tokio_postgres/struct.Transaction.html) is not awaited rollback evidence. Do not automatically retry an ambiguous commit; APP-013 owns outcome/idempotency reconciliation. Catchable SQL errors can reuse the same connection only after awaited rollback and successful reset. Positive normal reuse must genuinely retain the same backend PID.

## Planned evidence and ownership gates

- **Local native PostgreSQL16.13/TLS:** four actual roles, wrong CA/hostname/plaintext refusal, no privileged selector; fresh connection observes rotated credentials through a test-only file/connector seam. Real IAM acceptance requires the later approved RDS run.
- **Pool size1:** alternate Northstar/canary/missing scope on the same PID after commit, explicit rollback and SQL error. Poison session settings/role/search path/listeners/advisory locks and any permitted temp/plan state; reset removes it. Confirm savepoint behavior; do not grant TEMP just for production convenience.
- **Cancellation barriers:** cancel during acquisition/connect/BEGIN/blocked query/COMMIT/reset; track driver-task closure and pool capacity. Uncertain cases require a different PID; the next request cannot inherit state. Kill the server connection, saturate the queue and inject reset failure. Never claim “reuse passed” by discarding every connection.
- **Authorization concurrency:** real connections/barriers for revoke-first versus operation-first membership locks; unknown permissions, stale epoch, same local IDs across tenants and scoped FK failures; uniform sanitized route denials. Use genuine schema relations/grants and catalog coverage, not RLS permission-denied-only tests.
- **Readiness:** native role/pool checks must be added when implemented; preserve existing managed S3/KMS checks and migration-version coupling. Migration0001 hard-codes schema version1, so schema/readiness/restore expectations must evolve deliberately.

APP-008 owns mappings, membership/epoch primitives, RLS, fixed pools and authorization. APP-009 owns ordinary sessions; APP-073 owns entitlement/code redemption and its atomic membership/audit integration; APP-006 owns accepted provider identity; APP-010/013 own persistence/command semantics. Fixture principals stay inside isolated tests/operator qualification with no public enabling header. These seams permit foundation work after APP-007 without inventing signup, admission or hosted journeys. Before selection, settle the lock-function privileges, actual initial schema and dependency-build gates; re-estimate/split if the full acceptance exceeds the ticket's five-day bound.
