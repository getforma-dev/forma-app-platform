# Catalog verification repair and empty identity registry

Author repair evidence; independent follow-up review and managed qualification remain pending. [The independent review](independent-review.md) found R1: valid version2 history could coexist with a missing permission table, disabled tenant RLS or an extra application UPDATE grant. ## One pinned logical catalog

The migration manifest now pins a canonical read-only query and readable expected catalogs for versions1 and2. [catalog-query.json](../../../app/migrations/catalog-query.json) returns one nullable text value containing normalized JSON; [catalog-v1.json](../../../app/migrations/catalog-v1.json) and [catalog-v2.json](../../../app/migrations/catalog-v2.json) contain logical facts, one row per line. The current version2 snapshot is 123,415 bytes and 1,115 facts. It is not an opaque whole-database hash or a baseline learned from the target being verified.

The comparison covers exact named application schemas, relations, columns/defaults/types, constraints, indexes, both tenant policy expressions, ENABLE/FORCE RLS, ownership, schema/table/column/type/function ACLs, helper definitions/options, user triggers/rules, logical internal FK-trigger enablement, fixed-role attributes, direct and transitive membership, default ACLs, role and all-role current-database settings, effective database/public-schema CREATE boundaries, and fixed-role SET/ALTER SYSTEM privileges for the FK-bypassing session_replication_role parameter. It includes incoming membership into owner/helper/application roles. Function and constraint definitions are deparsed with transaction-local `search_path=pg_catalog, pg_temp`; row order is normalized under C collation.

Only relevant logical catalog facts are read. The query excludes row data, credentials, `pg_authid`, OIDs, physical storage identifiers, ACL grantors, unrelated RDS roles and the managed database owner's global ACL representation. Internal trigger identities use constraint/function/event facts rather than OID-bearing generated trigger names. Each section has a 1,025-row projection limit, expected sections must remain below it, and the query returns NULL above 262,144 output bytes. All four actual application roles successfully execute and compare this same projection. Native connection admission/readiness embeds the same files; its independent integration remains owned by the native slice.

The atomic runner now takes these paths:

1. A legacy database without history must match the entire version1 logical catalog before metadata is read or history is created.
2. A database with history must already match the entire version2 catalog and the complete exact two-entry checksum/version ledger. A preexisting history1 state is refused: this runner creates history and advances to 2 in one transaction, so it cannot legitimately commit that intermediate state.
3. After applying migration2, the runner verifies the exact version2 catalog before its caller can commit. No comparison mismatch triggers repair, grant changes or adoption of a new expected baseline.

`generate_schema_catalog.py` builds review candidates from the exact migration sources in a fresh disposable local PostgreSQL16.13 container. It accepts only a new output directory and cannot target a managed connection or overwrite the authoritative files/manifest. It deliberately constructs candidate schema in that isolated fixture; candidate adoption requires source review and an explicit manifest update. [catalog-reproduction.json](catalog-reproduction.json) records its source/image identity, exact candidate hashes and container removal. The generated candidate files match the checked-in expected catalog bytes.

## Follow-up R3: effective foreign-key enforcement

Follow-up review reproduced an additional failure after the R1/R2 repair: a committed `ALTER DATABASE genui SET session_replication_role=replica` changed new application/operator sessions while FK-trigger catalog flags still appeared enabled. The query had excluded `pg_db_role_setting.setrole=0` through an inner role join. The earlier 142-check/30-test author receipts are preserved under [pre-r3](pre-r3/author-checks.json); they did not establish this refusal.

The canonical query now includes current-database all-role settings with an explicit `ALL_ROLES` logical sentinel, alongside the existing fixed-role global/current-database settings. Both the Python catalog verifier and migration runner require actual `SHOW session_replication_role` to return `origin`, before any migration write. They never SET the mode back as a repair. The fixed application/owner/helper role projection also requires the expected absence of SET and ALTER SYSTEM authority on this parameter, so a newly granted bypass privilege is rejected even while the current session is still in origin mode. The managed migration administrator and unrelated RDS system roles are excluded from that fixed-role privilege assumption.

Four new real cases bring the retained suite to 146: a committed benign all-role application_name default proves catalog coverage independently of replica mode; a committed replica default proves new application and operator connection refusal; a committed application SET grant is rejected while origin is still active; and an operator-enabled current-session replica mode is rejected by both verifier and migration without changing that mode. Default/privilege mutations and database/catalog state remain unchanged after refusal. Only the isolated test administrator explicitly resets fixture state, and the additional disposable container is removed.

Both readable expected catalogs were generated again from the clean pinned PostgreSQL16.13 fixture; the final generator receipt binds the query, migration, runtime and fixture-helper sources. Native admission/baseline/recycle incorporates the same catalog and explicit origin-mode requirement in its separately owned implementation. No managed operation or application grant was added by this repair.

## Explicit temporary-schema ordering and probe-before-use

Independent follow-up reproduced a temporary-schema shadow: `SET LOCAL search_path=pg_catalog` alone leaves pg_temp implicitly ahead of catalog relations. A temporary `pg_namespace` view executed a marker expression during verification even though its output looked like the real catalog. The pre-fix 154/30 evidence is retained under [pre-temp-path](pre-temp-path/author-checks.json), and the independent compatibility review retains the finding.

Migration and catalog verification now explicitly set `pg_catalog, pg_temp`, with pg_temp last, before catalog relation/type lookup. The query document's exact search_path metadata, both reader validators and the clean generator use that same contract; the canonical SQL and readable version1/version2 expected snapshots remain byte-for-byte unchanged. No additional membership normalization was introduced.

A real temporary-view regression first runs the canonical query under the old implicit ordering and observes its sequence marker fire. After resetting that marker, the fixed verifier and a repeated migration both succeed against the unchanged version2 catalog without invoking the temporary expression. Each entry point installs its own safe order. This positive control proves the test would detect the previous behavior.

The Python readiness probe now also requests explicit catalog-first startup options and delegates its fixed-role database checks to `probe_database`. That helper proves origin mode and the full pinned catalog before reading application metadata or its schema version, then checks actual role, TLS, memberships and exact version2. System functions, types and relations in those subsequent identity queries are explicitly pg_catalog-qualified. Storage/KMS checks still run only after all four database proofs pass.

A second actual PostgreSQL case grants the workspace role access to a malicious schema_version view. A read-write control proves the version expression can increment its marker. A production-like read-only control reaches the expression but fails with SQLSTATE 25006 at nextval. The actual read-only workspace probe instead raises the fixed catalog-refusal type before evaluating the view, with the marker untouched; a mere unchanged sequence under read-only execution is not counted as proof. Unit transport/storage tests isolate the catalog call explicitly, and a separate ordering test ensures catalog refusal prevents identity/storage work.

The final author campaign passes 156 real database checks and 31 runtime tests. All nine qualifier containers and the separate catalog generator are removed. Exact source hashes and reproduction results are retained in author-checks.json and catalog-reproduction.json; independent follow-up and managed acceptance remain separate.

## Private empty-registry handoff

The service supervisor now always provides the native child's `GENUI_IDENTITY_REGISTRY_FILE`. An explicitly supplied path, including an invalid/empty value, is preserved for native validation; the supervisor neither owns nor deletes that file. With the variable absent, it creates a unique 0600 file in the owned 0700 runtime directory with exactly `{schema_version:1, registry_version:<new UUID>, bindings:[]}`. Empty bindings authorize no provider-to-tenant mapping. There are no fake provider identifiers, raw registry JSON environment variables, new secrets or alternate authentication paths.

The file uses the existing private-file implementation with a distinct fixed `.identity-registry-` prefix. It preserves exclusive/no-follow creation, held inode/directory identities, pre-launch checks and cleanup of only its own unlinked-single inode. Replacement files are refused and preserved. The child receives only the path; explicit operator paths remain unchanged. APP-006 raw-auth consumption and secret handoff retain their existing behavior.

Six separate registry tests cover closed empty shape/private ownership, real subprocess default and explicit-path handoff, explicit empty-path preservation, replaced-file refusal before launch, collision/unsafe-directory refusal, and cleanup after startup dependency failure. The final runtime suite passes 31 tests, including all existing auth-file lifecycle cases. Root owns the native/main/readiness integration, image packaging and actual managed delivery. Actual provider mappings and session/admission integration remain APP-009/073 work.
