## Schema and authorization contract

Every tenant-bearing primary/unique key and index starts with `organization_id`; every tenant relationship carries the same organization in its foreign key. Scope columns are non-null. This applies to memberships and the eventual app, publication, work, binding, source, record, job and audit relations. Preserve the design's sole planned index exception for the later queued-job worker index. Test identical local IDs in both tenants so a globally unique UUID does not accidentally mask a missing composite key. The existing non-tenant operational schema-version row is an explicit metadata exception, not permission to add unscoped application rows.

All tenant relations are owned by `genui_owner`, with RLS enabled **and forced**, explicit visibility and write checks, no app-role ownership/BYPASSRLS, and no broad PUBLIC grants. Missing/empty transaction scope denies; malformed scope must never grant access. A policy may use a carefully defined transaction-local custom setting, with blank normalized to NULL before UUID conversion. Use bound values and fixed SQL identifiers. Do not allow a request header, body, path, model field or arbitrary SQL call to set its own organization.

RLS is one boundary, not authenticated identity verification. Ordinary PostgreSQL custom settings are not secret capabilities: code holding a role can set another value. The private trusted-context API, fixed store methods, reviewed queries and database role grants must therefore remain part of the claim. A compromised one-process binary can reach all four credentials; the demo accepts that deployment limitation, while preserving protection against logic mistakes.

Represent the accepted provider issuer, tenant ID and subject without lossy conversion. The current fAuth `ten_…`/`usr_…` identifiers are not GenUI organization UUIDs. Use an explicit server-owned provider-tenant-to-organization mapping and issuer/subject binding; never strip a prefix or accept a browser-provided destination. Define the bootstrap lookup narrowly so obtaining this trusted mapping does not require a global application read role or a public tenant selector.

Create a private-constructor authorized-principal type containing organization, principal, current membership epoch and the bounded action/resource context. Only the authorizer returns it after current primary-database membership checks. Store entry points require that type; control/data operations recheck membership/epoch within their transaction. Unknown action/role/grant values deny. C11 separates discover, run, source-read, record-read, record-write, definition-edit, review/publish, share-work, export and policy administration; write an explicit role/action matrix before coding. Do not infer all permissions from space membership, provider identity roles or possession of a link. Publication approval still follows the policy's independent-review restrictions.

Plan for APP-073's separate active entitlement and APP-009's current session checks without granting either from a verified identity alone. Fixture authorization may construct trusted inputs only inside a test/isolated operator harness; no public header, query parameter, demo password or alternate authentication route may activate it.

## Four-role boundaries and transaction lifecycle

Keep four fixed role pools in the existing single Rust process. Do not dispatch arbitrary request-specified database users, reuse one privileged pool through `SET ROLE`, add an application reset/owner role, or inject the migration credential into the application.

| Role | Intended boundary when the corresponding relation exists |
| --- | --- |
| workspace | Session/draft/work/personal-state writes and scoped publication SELECT; no publication or record writes. Later enqueue/grant/audit operations get explicit narrow grants. |
| control | Membership/governance/policy/publication writes; no record revision access. |
| data | Scoped record access and writes, query/outcome/record-audit operations; no membership/publication mutation or member-session access. |
| worker | Scoped job claim/result and its declared metadata operations; no publication writes, record revision reads or member sessions. |

Do not pregrant future tables through blanket default privileges. Audit writes remain insert-only by role/event kind; no application UPDATE/DELETE. Reconcile platform §10.5's shorthand “workspace reads … nothing” with §6.1's explicit publication SELECT contract; it cannot be read literally while implementing §6.1. The demo replaces cross-service signed tokens with a private typed principal and callee membership reread; splitting into processes later restores the signed caller/callee/org/principal/epoch token seam.

**Resolve row-lock privileges explicitly.** PostgreSQL requires UPDATE privilege on at least one column for `SELECT … FOR SHARE`, including the membership and saved-work locks required by the command design. Granting data-role UPDATE on membership/epoch or work pointers merely to make locking pass would violate the role boundary. A narrowly scoped, schema-qualified lock/read function with reviewed SECURITY DEFINER privileges is one possible solution: fixed safe search path, no dynamic SQL, no PUBLIC execution, scoped RLS including the definer's effective role, bounded return data, and no authority-setting/mutation capability. Select and independently review the exact mechanism before coding; test that the consumer can acquire its required lock while direct protected-row mutation remains denied. [PostgreSQL's SELECT privilege rule](https://www.postgresql.org/docs/16/sql-select.html) and [definer-function precautions](https://www.postgresql.org/docs/16/sql-createfunction.html) are the governing details.

For each checked-out connection: establish a known clean state before any request query; begin a transaction; install only the trusted tenant scope transaction-locally; perform the current membership/action checks and fixed store operation; commit or roll back explicitly; recycle only after cleanup is confirmed. Scope must not survive success, error, timeout, cancellation, panic/drop, rollback to an earlier savepoint or a failed commit. Discard an uncertain connection. Bound connection creation, checkout queue, SQL/lock waits and transaction duration, and define pool sizing before the managed trial.

`SET LOCAL` resets at transaction end, but an older session-level setting can reappear afterwards. Test and clear persistent custom settings, session role/search path, listeners, temporary objects and advisory locks to the extent the chosen driver exposes them; a health query alone is not a reset. Prepared-statement caching must remain compatible with the reset strategy. Make cleanup/cancellation behavior explicit rather than assuming asynchronous drop has finished before reuse. Positive same-connection reuse evidence must show the same backend PID; always discarding connections cannot pass the pool-reuse acceptance.

TLS must verify the actual RDS hostname and trusted certificate chain; a mode merely requiring encryption is insufficient. Preserve current private credential-file checks. New connections refuse expired generations and observe replacement generations, without logging tokens. Define how existing authenticated connections are retired; token expiry is not a substitute for per-request membership/entitlement revocation.

## Planned actual-RDS acceptance campaign

Use the approved synthetic RDS environment and existing operator/migration secret channel, bounded separately by root. Exercise the **native implementation**, not only helper SQL. Record source/image/migration/driver pins, role, organization, backend PID where relevant, expected/actual result and independent review; retain no credentials or raw identity tokens.

1. **Catalog and privileges:** inspect every tenant relation, composite key/FK/index, owner, RLS flags and policy; verify application role memberships/attributes and explicit grants. Attempt DDL, owner/sibling `SET ROLE`, role escalation, unauthorized TRUNCATE and writes. `row_security=off` must not expose rows. An operator acting as the actual NOLOGIN owner should also verify FORCE RLS; testing as a bypass administrator is not that proof.
2. **Two-tenant role matrix:** for every app role, positive access to an actual permitted tenant relation, then foreign/absent/missing-scope reads and writes, organization-changing updates, and cross-tenant parent references. A permission-denied role alone does not prove RLS: include a permitted operation whose rows are filtered. Assert workspace cannot write actual publications/records and worker cannot publish. Compare state before/after denials.
3. **Real pool reuse:** set pool size one per role; alternate Northstar/canary/missing scope on the same backend after commit, rollback and deliberate SQL errors. Exercise cancellation during a blocked query, deadline, connection loss, savepoint rollback and dirty session-level context; uncertain cleanup discards, and the next request never sees prior data or request metadata. Verify reset failures cannot return a usable connection.
4. **Concurrency:** use separate actual connections and barriers, not timing-only sleeps. Interleave different-tenant transactions and same-principal membership changes. Test both revoke-first and authorized-operation-first lock orders: current epoch checks and the membership `FOR SHARE`/revocation `FOR UPDATE` boundary must serialize consistently, with no post-revocation stale authorization commit. APP-013/014 later add full outcome/record/adoption semantics. Include pool saturation, timeout and rollback recovery without starvation or scope reuse.
5. **Native route/permission negatives:** cover anonymous, foreign, absent, guessed same-ID, unknown permission, stale epoch and forged context against the same handler/store entry points. Protected resource denials use the design's uniform 404/problem response without row counts, raw constraint errors, cache/header differences or private identifiers. Verify no-store on authenticated responses. A fixture harness's positive result is labeled fixture authorization, never actual login acceptance.
6. **Credential and restart boundaries:** force a fresh connection after credential-file rotation, refuse expired/wrong-role input, test wrong TLS trust/hostname, restart and reload persisted tenant state. Re-run actual role constraints after migrations. Raw SQL errors, file contents and tokens must not enter route bodies or retained evidence.

PostgreSQL foreign-key/uniqueness checks can bypass RLS, so tenant-bearing constraints and sanitized route errors both matter. Do not promise absence of timing side channels from a status-code assertion alone. Maintain a catalog-driven test that fails when a later migration adds a tenant relation without its required policy/grants.
