## Proposed initial slice

Establish real organization/member/permission state and the minimal **real contract-storage relations** required for tenant/FK and publication/record ACL qualification. Seed valid synthetic rows through the operator channel and exercise the native authorization/store read paths. APP-010 retains admission and durable definition/work workflow acceptance; APP-013 retains record commands/outcomes/audit atomicity. Creating these relations does not complete either workflow.

Do not create `test_publications`, `probe_records`, a catch-all untyped resource table or empty stand-ins solely to make denial tests green. The table shapes below come from actual contract objects or explicitly named design entities. If this complete boundary cannot fit the ticket's estimate, root must split the schema work and retain the corresponding acceptance gate; denial on a missing relation or a toy replacement is not a substitute. Future jobs, sessions, invitations, entitlements, receipts, idempotency outcomes, sharing UI and complete audit chains are not precreated or pregranted here.

Use three namespaces: `genui_meta` for non-tenant operational migration metadata; `genui` for tenant relations; `genui_private` for narrowly reviewed functions. `genui_owner` owns all three and remains NOLOGIN. The existing four constrained login roles and their `rds_iam` membership remain unchanged. No application role receives schema CREATE, TEMP, TRUNCATE, REFERENCES, trigger/function creation, owner membership or BYPASSRLS.

## Identity and authority relations

Notation: `o` is non-null `organization_id uuid`; `p` is the internal `principal_id uuid`. All listed PKs, unique indexes, lookup indexes and FKs lead with `o`. Stable public UUIDs retain the existing lowercase v4/v7 contract at the boundary; PostgreSQL's UUID type alone does not enforce that contract. Epoch/version counters are `bigint`, bounded to the contract's safe integer range `1..9007199254740991` where serialized. No model/client value supplies authority.

| Real relation | Key and required shape | Relationships / constraints |
| --- | --- | --- |
| `organizations` | PK `(o)`; bounded display name; explicit active/suspended state | Tenant root. Suspension is a refusal, not deletion of history. No default shared beta organization. |
| `provider_tenant_bindings` | PK `(o, issuer, provider_tenant_id)`; exact bounded issuer/provider ID strings; active flag | FK `(o)` to organization. Operator-owned scoped confirmation of the separate trusted routing registry described below. No global application lookup index. |
| `principals` | PK `(o,p)`; issuer, provider tenant ID, provider subject | FK `(o,issuer,provider_tenant_id)` to binding; UNIQUE `(o,issuer,provider_tenant_id,provider_subject)`. Subject remains a bounded provider string, not a stripped UUID. A principal row alone grants nothing. |
| `memberships` | PK `(o,p)`; active/revoked state, positive `membership_epoch` | FK `(o,p)` to principal. Revocation/permission change advances epoch atomically and never resets it. Current authorization reads the primary, not a cache. |
| `organization_permissions` | PK `(o,p,permission)` | FK to membership. Initial allowed permission is `admin_policy`; it is separate from ordinary app/data rights. No implicit grant from an identity-provider admin role. |
| `app_permissions` | PK `(o,p,app_id,permission)` | FKs to membership and actual app. Closed permissions: `discover`, `run`, `edit_definition`, `review_publish`. No organization-wide wildcard app ID. |
| `work_permissions` | PK `(o,p,app_id,work_id,permission)` | FKs to membership and actual saved work. Closed permissions: `record_read`, `record_write`, `share_work`, `export`. A work grant does not grant app access. |
| `source_permissions` | PK `(o,p,source_id,permission)` | FKs to membership and actual source. Only `source_read` in this slice. Discovery/run/record rights do not substitute for it. |

These permission literals are a proposed concrete encoding of C11's ten permissions, not additions to the model's AppDefinition. SQL CHECKs reject unknown values; the Rust closed action enum denies unknown wire values. `review_publish` covers that C11 capability category, while approve/publish operations still separately enforce current policy, author/reviewer identity and digest. An administrator is not automatically a reviewer. No fixture role implies “all permissions.”

Resource-specific permission tables are intentional: a polymorphic `(resource_kind, resource_id)` with no concrete FK would reintroduce dangling or cross-kind authority. More grant kinds require their owning migration and reviewed action matrix. Effective work access also requires the current app permission and current source dependencies; a persisted summary or work link is not a source-access bypass.

## Real contract-storage relations and tenant FKs

Every relation below has ENABLE and FORCE RLS. The proposed initial slice stores complete validated contract representations where those exist, with normalized identity/reference columns supporting FKs. Keep canonical immutable bytes/digests rather than hashing PostgreSQL's JSONB serialization; validate normalized columns against those bytes on write and reload. A JSON document must not hide authority or references that escape relational checks.

| Relation / actual source object | Initial key and relational requirements |
| --- | --- |
| `spaces` / C01 | PK `(o,space_id)`; FK organization. Bounded label only; no space-membership permission shortcut. |
| `apps` / C01 | PK `(o,app_id)`; FK `(o,space_id)`; owner FK `(o,owner_principal_id)`. Stable identity distinct from definition revision. Do not add a nullable publication pointer that is treated as an authorized publication. |
| `definition_revisions` / `app_definition` | PK `(o,app_id,revision_id)`; FK app; immutable schema version1, canonical `content` bytes and verified definition digest. A supporting unique key `(o,app_id,revision_id,digest)` binds publication references. Normalized declared inputs/record schemas must preserve the same validated content. |
| `publication_policies` / publication `policy` and platform §6.2 | PK `(o,policy_id,policy_version)`; immutable kind `owner_publish` or `independent_review`. No client-editable policy switch. This is stored policy identity, not the full policy administration workflow. |
| `publications` / `publication` | PK `(o,app_id,publication_id)`; FK `(o,app_id,definition_revision_id,definition_digest)`; FK `(o,policy_id,policy_version)` with kind consistency; tenant-bearing author/approver FKs. Preserve input-contract/record-schema digests, renderer/operator versions, admission digest, approver epoch and published time exactly. CHECK independent review cannot have equal author/approver. No concrete source revision in reusable publication. |
| `publication_inputs`, `publication_record_schemas` / publication's declared arrays | Keys `(o,app_id,publication_id,input_id)` and `(o,app_id,publication_id,schema_id,schema_version)`; FK publication; validate digests/definitions against the canonical definition. These are declared local names, not UUID resources or grants. |
| `saved_work` / `saved_work` | PK `(o,app_id,work_id)`; FK `(o,app_id,publication_id)`; positive work version and bounded context. The pin/version are the later adoption fence. Serialize the actual contract, not an invented draft publication ID. |
| `sources`, `source_revisions` / `source_revision` | PK `(o,source_id)` and `(o,source_id,revision_id)`; FK source. Revision carries the actual contract's metadata/digests/parser/mapping/formula policy and tombstone fields. A supporting tenant-leading unique key includes content digest for exact binding references. Synthetic placeholder source digests are never represented as imported bytes. |
| `record_collections` / saved-work `record_collections` | PK `(o,app_id,work_id,collection_id)`; FK saved work; schema ID/version constrained to its pinned publication's declared record schema. Include the relevant publication ID in the referencing key or an equivalent checked composite relation; do not validate schema by local name alone. |
| `work_bindings` / discriminated `binding` | PK `(o,app_id,work_id,input_id)`; FK saved work and the pinned publication input. A closed discriminator plus CHECK requires exactly the source branch or records branch. Source branch uses FK `(o,source_id,source_revision_id,source_digest)`; records branch uses FK `(o,app_id,work_id,collection_id)` and declared schema/version. Contract digest/revision policy must match the actual schema. No credential/path/URL is stored as a binding. |
| `work_source_dependencies` / `source_dependency` | PK begins `(o,app_id,work_id,input_id)` with exact source identity; FKs saved work, declared input and source revision/digest. Dependencies are not merely unchecked JSON citations. |
| `internal_records`, `internal_record_revisions` / C02 and platform §8 | Stable key `(o,app_id,work_id,collection_id,record_id)`; revision key appends record version. FK collection and same-scope actor/dependency references. Store schema identity, typed committed values, creator/updater and organization commit sequence from the design; current row points to an existing revision using a tenant-bearing FK. No invented workflow-specific record columns. |

Two boundaries need explicit implementation review before DDL: the publication/work schema reference must be enforceable when adoption changes its pin, and current-record/revision insertion must support atomic FK-consistent insertion without allowing a dangling current pointer. Deferrable constraints may serve the latter within one transaction; they do not replace current authorization or command validation. `InternalRecordRevision` is named in C02 but has no standalone APP-002 wire envelope: keep it internal and derive typed values from declared record schemas/command values, rather than inventing a public JSON contract in APP-008.

This inventory is intentionally larger than a two-table RLS demonstration. Root should use it to decide a reviewable schema split before selection. It is not authorization to implement every listed downstream API. If APP-008 only lands the identity/permission tranche initially, its real publication/record boundary checks remain incomplete until the corresponding actual relations are present.

## Minimum grants for this qualification slice

`S` means scoped SELECT on named tables/columns. `X` means EXECUTE on an exact, reviewed function signature. `—` means no table privilege. Every application role retains only the existing operational version SELECT. No blanket `ALL TABLES`, default future-table grants or public function execution.

| Relation group | workspace | control | data | worker |
| --- | --- | --- | --- | --- |
| `organizations` limited identity/status | S | S | S | S |
| `provider_tenant_bindings`, `principals` | Only exact scoped identity confirmation needed by authorizer | — | — | — |
| Current membership/permissions | S required current facts | S current facts; X reviewed authority mutation only when implemented | X member lock/read; no direct UPDATE | — initially; add exact execution-check capability with the job owner |
| Space/app identity, definitions/policy/publications | S needed authorized metadata | S | S only the pinned declaration/schema identities needed by the store | — initially |
| Saved work, collection/binding/dependency identities | S | — unless a later implemented control operation needs it | S + X work lock/read | — |
| Source revision metadata | S for authorized binding metadata | — | S needed authorized dependency checks | — until import/index work exists |
| Record current/revisions/values | —; workspace receives only authorized data-service results | — | S for actual record authorization qualification | — |
| INSERT/UPDATE/DELETE on business/authority tables | — in the initial read/ACL slice | — except a separately reviewed narrow authority mutation function | — until APP-013's atomic command boundary | — |

Operator seeding is separate from application grants. This minimum matrix proves real workspace/worker publication-write denial and workspace record-write denial without granting unimplemented public write workflows. It does **not** prove control publication success or data record mutation; those positive write grants arrive with the actual APP-010/013 code, constraints and audit tests. Record that distinction in APP-008 evidence. If root chooses to include a real current writer in APP-008, its exact columns/transaction/audit must be reviewed rather than assigning the future role's entire privilege set now.

## FORCE RLS and the narrow lock/read functions

The common tenant predicate compares the row's `organization_id` with the transaction-local `genui.organization_id`, normalizing an empty setting to NULL; missing scope returns no visible rows and refuses writes. Policies apply to the owner as well as granted login roles because FORCE RLS applies during definer calls. Use explicit USING and WITH CHECK, no permissive “owner=true” policy. Permission/membership reads for the authorizer are current scoped facts; normal native handlers receive only authorized results. Custom GUCs are not secret authority: private typed context and fixed SQL/store APIs are part of the boundary.

Use the parallel pool plan's fixed `genui.organization_id`, `genui.principal_id`, `genui.membership_epoch`. The proposed `AuthorizedPrincipal` has private construction and typed action/resource binding. No role/table/function name is supplied by a request. The verifier's current `VerifiedIdentity` fields are public strings; accepting an arbitrary constructed instance as proof would bypass identity verification. The trusted application adapter must own the verified-result-to-context transition and expose no public deserializer or fixture constructor.

PostgreSQL [requires UPDATE privilege for row-locking SELECT](https://www.postgresql.org/docs/16/sql-select.html). Therefore data receives **no UPDATE column merely to make FOR SHARE work**. Proposed narrowly reviewed functions:

- `lock_member_authority`: checks required transaction-local context and equality of supplied org/principal/expected epoch; locks only that membership `FOR SHARE`; returns bounded active/epoch/action facts. It cannot set scope, grant membership, enumerate users or return a provider capability. The native authorizer performs the closed action/resource decision.
- `lock_work_revision`: checks the same context, exact tenant/app/work and expected publication/version; locks that saved-work row `FOR SHARE`; returns only the pin/version match needed for the fence. No record values, bindings or unauthorized existence detail are returned to a route.

Own functions as `genui_owner`, use fixed schema-qualified SQL, an explicit safe search path with `pg_temp` last, VOLATILE/parallel-unsafe where appropriate, revoked PUBLIC EXECUTE and grants only to current callers. They are not generic SQL, role-switch, scope-set or arbitrary lock primitives. Owner FORCE RLS must match the validated scope; no owner bypass. Do not confuse the definer's `current_user` with the original login when validating caller roles. See [PostgreSQL definer-function precautions](https://www.postgresql.org/docs/16/sql-createfunction.html).

Control authority changes must acquire membership `FOR UPDATE` before changing effective grants/state and advancing epoch in the same transaction. Do not leave direct grant-table UPDATE able to skip the epoch fence. For APP-008 fixture races, the operator can execute the exact reviewed transaction through its separate channel; a general app administration function is not implied. APP-073 must use the chosen same-transaction authority primitive for redemption plus entitlement/audit, not wrap a separately committed membership call.

Generic transaction APIs must not impose an early lock order that conflicts with APP-013: current authorization precheck → scoped idempotency outcome → membership `FOR SHARE` → saved work `FOR SHARE` → record `FOR UPDATE`. APP-008 has no outcome rows yet. Savepoint rollback before a fence loses its locks/context; never continue under a stale “authorized” marker. Lock/revoke tests cover both orderings with barriers and actual PostgreSQL roles, including direct-mutation denial and successful narrow locking.

## Trusted provider mapping and operator fixtures

Avoid a global pre-auth application table scan or an unscoped special DB role. Proposed initial routing authority is a private operator-owned, fully validated registry of exact `(issuer, provider_tenant_id) → organization_id` pairs. Define a separate versioned server-configuration contract and delivery path during implementation; the current credential document and optional callback JSON are closed schemas, so this plan does not authorize adding undeclared fields to either. The registry is not model data, browser tenant selection, a database password or a provider invitation secret. Validate the whole registry as injective before use; a provider tenant cannot map to two app organizations. The DB's scoped binding row confirms the selected pair after scope is established. Both records must agree; mismatch denies. This explicit two-part scheme is necessary because an organization-leading unique index alone cannot enforce global uniqueness of `(issuer, provider_tenant_id)`.

The auth adapter consumes the already verified issuer/tenant/subject, matches server-bound signup/login state, resolves that registry, sets the chosen scoped transaction context and confirms the DB binding/principal/current membership. It neither strips `ten_`/`usr_` prefixes nor trusts provider roles as GenUI grants. APP-009 owns the real session transition; APP-073 owns invitation destination and entitlement. Mapping changes require explicit reconciliation/session invalidation; they cannot silently move an identity between organizations. A future dynamic registry would need a separate reviewed lookup/uniqueness design, not a broadly readable table added by convenience.

For APP-008 only, the approved operator channel seeds isolated synthetic organizations/principals and explicit per-resource grants, using fixed validated manifests and the existing migration execution secret channel. It does not add an application seeding endpoint or share its credential. Use the actual managed storage organization UUIDs ending `…0001` and `…0002`, and generate consistent contract envelopes for that scope. APP-002's Northstar/Spend Review specimen organization IDs end `…0064`/`…00c8`; do not blindly load those as the managed tenant map or rewrite frozen fixtures. Preserve the original fixtures and retain newly validated seed manifest/digests separately. Source placeholder digests remain labeled synthetic and cannot pass import/query provenance.

Reuse local app/work/record IDs across the two seeded organizations to expose missing tenant keys. Include a revoked/no-permission principal, actor-specific positive grants and unknown-action negatives. All changes are idempotent only for the exact same manifest; mismatched existing rows refuse rather than overwrite grants or reset epochs. Operator fixtures exercise native authorization/SQL only; they mint no fAuth identity, browser session or active trial entitlement. Never describe the fixture as hosted signup evidence.

## Migration version evolution and acceptance handoff

Preserve `0001_role_foundation.sql` and its historical hash. A reviewed next migration must first confirm the existing version1 role/schema baseline, replace the restrictive `CHECK(version = 1)` with the chosen version mechanism, and apply version2 atomically. Proposed `genui_meta.schema_migrations` records version, immutable source checksum and application time; this operational table is intentionally not tenant data. Only the operator migration channel writes it. Record the known 0001 checksum when introducing history and refuse unknown/mismatched already-applied bytes. Version2 must not become visible before tables, policies, functions and grants commit.

The migration runner currently invokes the single initial file and readiness expects version1. Update those as one owning implementation: ordered/checksummed migrations, exact supported schema version for the new binary, idempotent repeat, failure rollback and refusal of an unknown future version. Keep the current source/image/schema1 evidence reproducible. Do not relabel APP-007's version1 restore helper as version2 evidence or assume the old binary remains compatible. Record the new schema compatibility and forward-fix/restore choice before the managed update; no automatic downgrade of authority state.

Required proof before acceptance: catalog checks for every real tenant key/FK/index/RLS/owner/grant; all four fixed-role positive scoped reads plus foreign/missing-scope denials; actual publication/record wrong-role writes denied; same-connection tenant alternation and cancellation/error reset; narrow lock success with direct protected UPDATE denied; both membership-change race orders; unchanged authority after failed migration; restart/reload; and sanitized uniform route denials. APP-010/013 repeat the relevant matrix when they introduce writes, and APP-009/074 repeat it with actual identity/session/admission. This plan claims none of those checks passed.
