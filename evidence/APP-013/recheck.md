## New findings (ranked)

**N1 (minor, record) — ADR-007 D7.9 and ADR-002 still describe the pre-m6 key and the pre-decision-2 enum.** `ADR-007 …:72` defines `command_claims … PRIMARY KEY (organization_id, principal_id, work_id, command_id, idempotency_key)` (five columns) and `CommandResult { Committed, Replayed, Conflict, Stale, InFlight }` (five variants); `ADR-002 …:33` says "the idempotency scope is organization + principal + work + command + key". Migration 0007 now keys the claim and the outcome on six columns including `app_id`, and `CommandResult` has `Busy`. Both changes were accepted (m6 disposition; decision 2 agreed by the original review) but neither ADR carries the amendment, and the ticket's Decision field requires recording an amendment before changing its contracts. **Fix:** one sentence in D7.9 ("the claim and outcome keys include `app_id`, because `saved_work` is keyed by `(organization_id, app_id, work_id)`; APP-013 review m6") with the PK rewritten, `Busy` added to the enum text (D7.9 already describes its HTTP row), and "+ app" in ADR-002's scope sentence or a note that the work is identified under its app. No code change.

**N2 (nit) — the Rust `problem_conforms` does not recurse into `recovery_view`.** Python `validate_problem` (`validate.py:171-172`) runs `validate(body["recovery_view"])`; the port (`tests.rs:308-410`) checks the member's presence and pairing only. The recovery view's own shape is covered by `conflict_problems_carry_the_recovery_view_as_canonical_json` (`tests.rs:255`) and, over HTTP, by campaign check 18 through the Python validator, so nothing escapes; the port's docstring could say so, or the port could call the existing recovery-view check.

**N3 (nit) — README counts** (above).
