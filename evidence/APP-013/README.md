## How a command runs (D7.9 order)

`begin` (READ COMMITTED, ≤ 3 s, bounded by the 5 s handler deadline) → `precheck(record_write, work)` on current state → `INSERT INTO command_claims … ON CONFLICT DO NOTHING RETURNING 1` (one row: fresh; zero: the key is taken) → `lock_member_authority` (a 55P03 here is `Busy`) → on a taken key: read this principal's outcome → `Replayed` (same digest, horizon open) or `Conflict` (`payload_mismatch` / `retry_expired`) with the current record → `lock_work_revision(publication, expected_work_version)` (mismatch: `Stale` naming the work's current publication, revision, digest and version) → the declaration and schema from the pinned publication's content → `organization_sequences FOR UPDATE` (absent: `Configuration`; wait: `InFlight`) → `internal_records FOR UPDATE` (wait: `InFlight`; version 0 = absent; mismatch: `Conflict` `expected_version` with the current values) → operation rule (0 needs `create`; an existing record needs `update` or a command with declared transitions, and every changed enum field follows a declared `(field, from, to)`) → compose the whole state (writable fields, `compatible` typing, non-nullable fields present) → revision, current pointer, record source dependencies, `command.committed` on the data head (`record_id` set, `outcome_digest` = payload digest), sequence + 1, the outcome (FK to the claim) → COMMIT. Anything else rolls back and releases the claim; a lost COMMIT answer is `UnknownOutcome` (503 `unknown_outcome`) and the client re-reads by key.

## Decisions made in this slice (for review)

1. **No foreign key from `command_outcomes.audit_event_id` to `audit_events`.** The plan writes "FK audit_events"; ADR-007 D7.8 controls: `audit_events` is insert-only for every role, and a referencing row needs a KEY SHARE lock on it, so a foreign key cannot exist (the same reasoning dropped `code_redemptions.audit_event_id`'s key in 0003). `UNIQUE (organization_id, audit_event_id)` on the outcome plus the operator `verify` pairing (every outcome names its own `command.committed` event with the record, work, actor and payload digest) and campaign check 19 assert the pairing as a set.
2. **`CommandResult::Busy`.** D7.9's enum lists five variants and, in its HTTP rows, "a 55P03 on an authorization fence in any request → 409 `busy`". The typed carrier of that row is the sixth variant; the route maps it to 409 `busy` with `Retry-After: 2`. A 55P03 at the claim, the sequence or the record row stays `InFlight`. The operator's own member lock (D7.1, `memberships FOR UPDATE`) blocks the claim's foreign-key reference before the fence, so an operator revocation in progress answers `in_flight`, and an operator update of the row (FOR NO KEY UPDATE) answers `busy`; both are 409 with `Retry-After`, never 503 (check 12).
3. **No unique index on `internal_record_revisions (organization_id, commit_sequence)`.** It was in 0007's first draft; the operator seed places the canary organization's two placeholder revisions at commit_sequence 1, so the invariant holds only for command-written revisions. `command_outcomes` keeps `UNIQUE (organization_id, commit_sequence)`; `verify` requires the sequence row to be ahead of every revision.
4. **Operation rule for a `create` command on an existing record.** The S05 fixture declares one command (`record_decision`, `create`, transitions `needs_context → reviewed`); act 6 needs `reviewed` under `ik-2` at version 1. A `create` command creates at version 0 and may change an existing record only along its declared transitions (every changed enum field must match a declared `(field, from, to)`); an `update` command changes freely within its writable fields; `validate.py`'s bundle rule (`create` ⇔ expected version 0) stays a fixture-consistency rule. Open question 1.
5. **The record's stored state is the whole record.** `canonical_values` holds the forma-json-v1 `{field_id, value}` array of every schema field in schema order (nulls admitted only for nullable fields); an update merges supplied values over the current state. The seeded placeholder revisions hold only the command's values; no code reads them as state.
6. **Payload identity is the contract's.** `payload::digest` hashes the complete `command_request` document minus the key, so the Rust and Python identities agree (fixture vector reproduced).
7. **The form types its texts by an echoed spec.** Each row carries `spec.<field>` (the published `value_type` as JSON) so the route can build the typed value; storage re-judges it against the published schema, so a tampered echo only fails. The route's own problem codes: `missing_idempotency_key`, `malformed_idempotency_key`, `malformed_command` (400), `conflict`/`in_flight`/`busy` (409), `stale` (412), `payload_too_large` (413), `unknown_outcome`/`unavailable` (503).
8. **Form submissions redirect** (303 to the record page with `?notice=<closed set>`), so one page renders every state and the authorized recovery view is the record page itself; JSON callers get the problem bodies.
9. **Contract edition `impl-2026-10-29.3`** (D7.15) adds only the two wire shapes, `current_revision` and the codes; every earlier kind, domain and vector is unchanged; edition .2's four fixtures are retained byte-identically and embedded by the Rust lock tests.
10. **`read_outcome` needs `record_write`** (design §9: "outcome lookup by key … record write, rechecked at delivery") and returns only the scoped principal's row; the RESTRICTIVE `command_principal_read` policy makes other principals' rows invisible at the row level too.
11. **The record page URL names the record** (`/work/{app}/{work}/records/{collection}/{record}`); a record that does not exist yet is shown at version 0 with the create form, so the client names the record id (the contract's `command_request` carries one). How the demo reaches EXP-002's record id (a link from the work page or a seeded id) is APP-012/APP-076's wiring. Open question 2.
