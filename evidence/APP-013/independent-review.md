## Findings

### Blockers

None.

### Majors

**M1 — Decision 4 as implemented contradicts the contract's own rule and admits no-op and non-enum revisions through a `create` command.** `contracts/validate.py:446` requires `(operation == "create") == (expected_record_version == 0)`; edition `.3` records no amendment of that rule (`contracts/README.md` §Edition impl-2026-10-29.3 says "No existing kind changes shape or version"). The storage rule `app/src/storage/commands.rs:1100-1104` admits a `create` command on an existing record whenever the declaration has any transition, and `compose` (`commands.rs:725-731`) checks a declared transition only for enum fields that actually changed, so the S05 `record_decision` command rewrites `note` freely at any version and re-commits identical values as a new version (R3: v8 and v9). ADR-010 act 6 needs `reviewed` under `ik-2` at version 1, which decision 4 serves, but the ticket's Decision field ("record any amendment before changing its contracts") and ADR-002 ("explain any intentional … semantic change") require the record. **Fix (either, recorded in edition `.3`):** (a) amend `validate.py:446` to the implemented rule — `create` at version 0, or at version ≥ 1 only when the declaration has transitions — and add the row to the `.3` table in `contracts/README.md` (one sentence; vectors unchanged); and tighten `compose` so a `create` command on an existing record must change at least one enum field along a declared transition (`commands.rs:1100-1104`: track "a transition fired" in `compose` and `require` it when `declaration.operation == "create" && current_version > 0`), which removes the no-op and note-only revisions R3 produced; or (b) keep `validate.py` strict and declare an `update` command in the Spend Review fixture, which is a frozen edition-1 fixture and therefore also an edition change. (a) is the smaller change and matches the design's reading (design §6.2's example commands carry only `transitions`). Also align the page's command choice `app/src/commands/mod.rs:155` (`update || create`) with whatever rule is kept (today a `create` command without transitions would be offered on an existing record and always refused).

**M2 — The route's problem bodies violate the contract edition this slice opened.** `contracts/schema.json` `$defs.problem` requires `status`; `validate_problem` requires `retry_after_seconds` on `in_flight`/`busy`; the slice's own specimen `fixtures/command-recovery.json` shows `{"status": 409, "code": "in_flight", "retry_after_seconds": 2}` and `{"status": 400, "code": "missing_idempotency_key"}`. The route emits `{"code":"in_flight"}` (R10b), `{"code":"malformed_idempotency_key"}`, `{"code":"unknown_outcome"}` through `http::problem` (`app/src/http/mod.rs:46`), which writes `code` only; `validate_problem` rejects every one of them (`'status' is a required property`; `in_flight and busy are 409 with Retry-After seconds`). Only `conflict` and `stale` (via `problem_with`) conform. The campaign's check 17 asserts `status` on the 409 conflict only, so this was never exercised. **Fix:** in `app/src/commands/routes.rs:126-129` answer `InFlight`/`Busy` with `retry_after(http::problem_with(StatusCode::CONFLICT, "in_flight", json!({"retry_after_seconds": RETRY_AFTER_SECONDS})))` (and `"busy"`), and make `http::problem` (`http/mod.rs:46-55`) write `{"code":…,"status":<u16>}` — `status` is the contract's member for every edition-two and -three code and the APP-074 429 body already carries it through `problem_with`; the change is shared with the auth and query routes and is additive for them. Then extend check 17 (or `commands::tests`) to run `validate_problem` over one body of every code the route emits.

### Minors

**m1 — The JSON route accepts duplicate keys.** `routes.rs:172` parses with `serde_json::from_slice` (last member wins) and `submit` reparses the same way at `routes.rs:341`; ADR-002 says forma-json-v1 rejects duplicate keys and the Rust decoder (`admission::decode`, `canonical.rs:41`) does. R4b: a document with a duplicated member replays as the identity of its last-wins reading. No wrong write results (the digest is computed from the deduplicated value and the same bytes are what storage judges), but a client cannot rely on "reject incompatible input instead of coercing it". **Fix:** `from_json` and the pre-check use `crate::admission::decode(bytes)` (its 1 MiB and depth bounds are above the 256 KiB limit) and treat a decode error as `malformed_command`.

**m2 — A form submission that storage refuses becomes a bare 404 problem document.** `routes.rs:144` (`Mode::Form`, `Err(Denied) => return http::not_found()`): a typo in the status text or a tampered field answers the browser with `application/problem+json` 404 instead of the record page (R12). `Notice::Refused` exists (`mod.rs:36`) but is never produced, and `main.rs:171` maps it onto the `unknown` notice anyway. The uniform 404 protects callers who could not have loaded the page; a live session that did load it learns nothing new from a redirect that lands on the same page. **Fix:** `Err(storage::Error::Denied) => Notice::Refused` in the form arm, a `refused` prop and sentence in `app/admin/src/record/app.tsx` (and `main.rs:171` mapping `refused` to it), and extend check 16 with one refused post.

**m3 — The record form submits every schema field, writable or not.** `app.tsx:124` renders `value.<field>`/`spec.<field>` inputs for every row regardless of `row.writable`; `compose` (`commands.rs:708`) refuses a value for a field the command does not write. S05's two fields are both writable, so act 6 is unaffected, but any schema with a read-only field makes its form unusable (every post → `Denied` → m2's 404). **Fix:** render non-writable rows as text only (no inputs), or skip them in `from_form`; storage stays the judge.

**m4 — `Idempotency-Key` header leniency.** `routes.rs:332-336`: the header value is `trim`med (R10a: a space-padded key is accepted and committed), only the first of two `Idempotency-Key` headers is read (R10a: the second is ignored silently), and a non-JSON body without a header is reported as `missing_idempotency_key` rather than `malformed_command` because the key check (`routes.rs:341-345`) runs before the parse. **Fix:** `headers.get_all("idempotency-key")` must be exactly one value, used verbatim; parse the body once and report `malformed_command` first.

**m5 — Decision 2's classification is inverted for the D7.1 operator lock.** D7.9 names "a 55P03 on an authorization fence → `busy` (a conflicting operator or sign-out operation is in progress)". Because the claim's foreign key to `memberships` takes KEY SHARE before the fence, an operator `memberships FOR UPDATE` (the D7.1 revocation lock) is answered `in_flight` (check 12, second race), while an operator FOR NO KEY UPDATE is `busy`. Both are 409 with `Retry-After: 2`, never 503, so the client contract holds; the words in D7.9 and the README should say so. **Fix:** one sentence in ADR-007 D7.9 ("a wait on the claim's membership reference is `in_flight`") or classify a 55P03 on the claim insert as `busy` when the wait was on the referenced membership (not distinguishable without `pg_stat_activity`; the wording fix is the honest one).

**m6 — The claim's scope omits `app_id`.** `command_claims`/`command_outcomes` PK is `(organization_id, principal_id, work_id, command_id, idempotency_key)` as D7.9 and ADR-002 specify, but `saved_work`'s key is `(organization_id, app_id, work_id)`, so a `work_id` could in principle exist under two apps; a key committed under one would make the other's commit read no outcome and answer 503 (`commands.rs:969`, `.ok_or(Error::Unavailable)`). Work ids are server-minted (`definitions.rs:779`, `gen_random_uuid()`), so this is unreachable today. **Fix:** none required; note it in the README, or make the outcome lookup in the taken-key path fall back to `Conflict` with a `retry_expired`-style reason rather than 503.

### Nits

- README verification table: `cargo test` counts (90 / 9, bin 3) are stale at the merge (105 / 12, bin 4); the figures in the APP-013 commit's own run were presumably right before the APP-074/009 merge.
- `verify` proves outcome→event pairing and the sequence bound; it does not pair revisions with outcomes (a command-written revision without an outcome would pass). My R13 SQL does; one `EXISTS` in `admission_operator.py:1004-1012` would close it.
- `read_outcome` and the replay path take the member fence but not the work fence before delivering the stored outcome. ADR-004's "visibility before delivery" is about authority, which the member fence plus `permissions` re-check cover; recording that reading in the README would pre-empt the question.
