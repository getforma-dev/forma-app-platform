## Findings

### Major

1. **The note-privacy step cannot detect the failure it claims to rule out** (`app/src/storage/actions_campaign.rs:1551-1641`; `app/src/storage/queries.rs:1625`).
   - The step runs before anything is shared on purpose, so the teammate can open none of the author's works.
   - `own_works` keeps a work only if `open_many` lets the caller open it. The assertion "the teammate's GET does not list the author's notes work" is therefore implied by the 404 assertions. It has no failure mode of its own.
   - I removed `created_by=$3` from the `own_works` query, and the campaign still passed.
   - That filter is the property the route documents (`actions/routes.rs:41-42`: "A work shared with the member is never chosen, so a note stays private unless its author shares the work").
   - If it regresses, a teammate the author has shared a writable notes work with gets that work back from `/v1/notes`. Their `/note` entries then land in the author's work, which the author can read.
   - The lead's control grants `record_read`, which only shows that the 404 checks can fail. Because `notes_work` picks a work with `can_write`, that grant leaves the listing assertion passing under both the correct and the mutated query.
   - **Fix:** after the teammate's first `GET`, grant her `record_read` and `record_write` on the author's notes work, assert that her `GET /v1/notes` still answers `work_id: null`, then revoke both. I ran this as a temporary 12-line probe, using the campaign's own `grant` and `definition_qualification::revoke`. It passes on correct code and fails with the filter removed, and the later steps still pass. I then restored the file.
2. **Two kept Shortcuts rows describe paths that do not exist on `main`** (`app/admin/src/canvas/shortcut-tab.ts:45`, `:34`).
   - `:45` "Shape a card: ⋯ → Shape… on the card". On `main`, every placed app and standalone card is a whole-app view item. For such an item, `addressOfItem` returns the app's address (`shape.ts:135-137`), so ⋯ → Shape… puts `/shape expenses ` in the bar: a theme for the whole app, not a card's view. Components are no longer selectable canvas items (ADR-018; `controls.ts:164-166` acts on canvas items only). The command path (`/expenses.ledger …`) still works.
     - **Fix:** drop the ⋯ path from this row, or say that ⋯ → Shape… themes the app.
   - `:34` "… or Drop files or upload on an empty canvas". The empty-canvas choice is now labelled "Bring your files" (`app.tsx:378-381`). The old label survives only in comments (`boxes.ts:39`, `:1270`).
3. **GUIDE.md still teaches loose-card placement in unmarked passages, next to marked ones** (`docs/pitch/GUIDE.md:71`, `:124`).
   - `:71`, the `/app` row: "Places every card of an app … A bare `/<address>` does the same". On `main`, `/app` places the app in Card view (`library.ts:757-760`). The new section says so at `:19`, so the two passages contradict each other, and only the `/card` row below is marked.
   - `:124`: "Library: two sections. **Apps** (Category → App → numbered cards) … app rows read 'n of m cards'". On `main` there are three groups (`library.ts:986-996`), app components are hidden metadata (`app.tsx:796`), and rows read "Card view", "Browse view" or "Open view" (`library.ts:221-223`). The lines immediately above (`:123`) and below (`:125`) are marked; this one is not.
   - Both are exactly what "What changes" item 2 targets. The closure's statement that each stale passage is marked does not hold.
   - **Fix:** add the marker to both lines.
