# Deferred scope

These are candidate journeys after the first release, not scheduled implementation tickets or hidden prerequisites. Create a scoped ticket only when its trigger is met.

| Candidate | Trigger | Existing owner or required boundary |
|---|---|---|
| Executable/custom-widget markup tier | Repeated supported-language abstentions show a real customer need | Reconcile FORMA-237–242; separate admission, isolation, preview and publication design |
| Live read-only connector | Pilot names a source and stable recurring need | Connector credential scope, data revision, retention and revocation contract |
| Bounded external action | Validated workflow needs an external effect | Separate user approval, idempotency and outcome reconciliation; no implicit payment/email |
| MCP Apps host | Browser product is proven and host need established | Host capability/security/authority compatibility |
| Customer-managed model account | Customer demand and support model | Disclosure, billing, credentials, outage and adapter behavior |
| Coediting or scheduling | Repeated evidence current collaboration is insufficient | New conflict/authority and job semantics |
| Cells, second region, customer-specific hosting | Capacity/isolation or residency demand | Migration, key locality, deletion and recovery decisions |
| Pricing experiments | Real recurring use and measured cost exist | Hypotheses tested against actual effort/value, not demo success |

Public websites, a cross-company marketplace, autonomous remediation, arbitrary code execution, clinical decisions and a full accounting engine are outside this release. An incompatible record-schema migration gets its own deterministic migration ticket when needed; the initial behavior is safe refusal.
