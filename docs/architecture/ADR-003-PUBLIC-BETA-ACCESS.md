# ADR-003 — Public beta origin with explicit trial admission

Date: 2026-10-28. Owner: GenUI; fAuth registration and hosted identity remain FormaStack-owned. Status: accepted user direction, implementation and hosted qualification pending. Applies to APP-006/007/009/012/073/074 and subsequent work admission.

## Authority and scope

Victor selected `https://beta.getforma.dev`, public HTTPS access from anywhere, **invite-first** email/password registration and owner-issued invite or trial access codes, with a **$100/month GenUI operating limit**. This explicitly amends the manually provisioned first-release membership assumption in platform §4.1 and the scripted account setup in demo D6/§6.7 for the beta entry path. Frozen source documents and existing evidence remain unchanged. Manual synthetic provisioning remains useful for independent qualification; it does not demonstrate public signup.

Public network reachability is separate from permission to use GenUI. Visitors may reach the landing and invitation-entry surfaces. Registration is available only after a valid invitation yields a bounded, server-bound signup handoff; there is no generic public self-registration. App pages, private metadata and every query, import, generation, export or mutation require current identity, membership, entitlement and operation-specific authority. A browser button or obscured route is never the enforcement boundary. Invite-gated signup does not establish real-customer readiness or waive FORMA-248 and the later pilot/security gates.

## Deployment and budget

APP-007 retains the full design workload envelope and managed RDS/S3/organization-key requirements. The selected immediate deployment is **bounded Phase 1 Fargate qualification within the approved monthly allowance**, not a promise that the prior $150–170/month always-on plan now costs $100. The owning environment/cost record must specify operating hours, already-incurred and retained-resource cost, trial allowances, monitoring and cleanup/stop decisions before paid operation. A cost estimate, tag or AWS Budget notification is not a provider-enforced hard billing cap. Victor separately approved FormaStack's six-hour, $5 synthetic auth rehearsal and scoped cleanup; that $5 is included inside the $100 monthly allowance. Its start remains coordinated: FormaStack starts only after GenUI signals callback/environment readiness.

Public IPv4 HTTPS ingress is the intended mode. If the network restriction test is retained, use the execution host's actual public IPv4 `/32` only during that test and immediately restore `0.0.0.0/0` for HTTPS afterward. That temporary rule does not pass the application access trial. No public database, direct application port, debug interface or administration surface follows from public HTTPS. Until admission is implemented and tested, public routes expose only explicitly allowed inert/identity surfaces; protected work remains denied.

The GenUI origin is `https://beta.getforma.dev`; the exact proposed fAuth callback is **`https://beta.getforma.dev/auth/callback`**. FormaStack must register and qualify that exact value; wildcard redirects, client-selected tenant/redirect values and alternative paths are refused. DNS/TLS proof and provider deployment identity remain APP-007/006 evidence, not facts established by this ADR.

LLM calls remain disabled until APP-043 qualifies provider disclosure, atomic cost reservation, finite retries and configured spend limits. An access code is neither a provider credential nor an unlimited usage grant. Infrastructure cost continues while services run, even when no member is admitted. Later workload admission must reserve capacity/cost before execution and account for retries, unknown provider outcomes and concurrent callers rather than relying only on delayed billing alerts.

## Identity, membership and entitlement

fAuth owns email/password credentials, tenant-scoped **invite-only** registration, actual email-verification delivery and its recovery policy, authorization codes and signing keys. A valid GenUI invitation must be required by the actual provider registration path, not only by the landing UI; no simulated email verification counts as acceptance. GenUI consumes the reviewed code flow through backend PKCE exchange. Signup needs its own hosted registration evidence; the existing login-only qualification does not establish it. Verified-mailbox activation is the beta default. Phase 1 may use controlled synthetic inboxes, but must prove actual delivery and activation through the accepted provider contract; no fabricated delivery, verification bypass or invented JWT claim is permitted. APP-006 must identify how that provider contract attests/enforces verification before admission. No password, bearer token, raw access code or provider secret belongs in GenUI URLs, browser storage, analytics, public evidence or logs.

An authenticated but unadmitted person may hold a short-lived, opaque, Secure/HttpOnly pre-access session. Its authority is limited to completing the bound admission flow or logging out. It cannot read workspace/private existence information, mint a workspace session, enqueue work or call a model. Keep pre-access and workspace sessions distinct and bind the former to the verified issuer, subject, tenant, browser state and expiry. A workspace session is minted only after current membership and active entitlement are established; existing sessions recheck those states at requests, execution, commit and result delivery as applicable.

Current `tenant_id` remains the organization boundary. The operator preprovisions an isolated organization and issues its initial invite; the recipient creates an email/password identity bound to that organization. A later member invite joins its explicitly selected existing organization; an isolated trial code binds to its own preprovisioned trial organization and safe initial permissions. The operator controls access, limits, expiry and suspension. Unrelated trial users must not silently share one `beta` organization. A valid code selects a **server-bound** organization before tenant-scoped signup using a bounded opaque handoff; the client cannot supply an organization or role. The signup authorization is limited to that tenant and intended registration context, never a general tenant-management credential. Initial trial organizations are operator-provisioned. Automatic organization/fAuth-tenant creation requires a separate idempotent provisioning design and is not hidden inside public registration.

Membership grants describe permitted data/actions; the entitlement independently describes whether beta/trial usage is currently active, its expiry and configured limits. Changing a code does not rewrite an existing membership or extend a trial implicitly. Invitations do not grant reviewer, administrator or cross-organization authority through user-supplied fields.

## Proposed confidential provider handoff — not yet accepted

*Amendment 2026-10-29:* FormaStack merged the server-only invitation and PAR contract in gatewasm PR18/PR19 (reviewed source `dfba787`); in `server_only` mode the identity role is explicit and required. GenUI formally accepts it only after hash-binding the merged contract under `evidence/APP-006/upstream-auth-source/` (plan Task C0); hosted evidence remains open. The text below is retained as the original decision.

FormaStack is preparing server-only, email-bound invitations with an **explicit** identity role, followed by backend `POST /t/{slug}/oauth/par` carrying the confidential provider `invite_token` and PKCE fields. The browser would receive only the bounded `request_uri`, then the final authorization code and state. This is a proposed source contract still in progress; APP-006 must receive its actual reviewed implementation, limits and hosted evidence before GenUI relies on it. A name or URL in this decision is not proof the endpoint or mode is available.

The current `/manage/invites` default role is administrator and creation is not idempotent. GenUI's operator must select the verified provider's explicit least-privilege identity role and intended email; omission is refused by the operator workflow. The new proposed `delivery_mode: server_only` must suppress the legacy email URL containing a raw invitation token, with observed mail/HTTP evidence. Identity roles never become GenUI membership grants by copying claims.

For Phase 1 the authenticated operator provisions the organization and provider invitation, retaining the remote invitation ID, email/role/destination binding and private handoff through the approved secret channel. Ordinary public signup receives no tenant-management credential or broad invite-management authority. GenUI access codes remain digest-only. A **separate provider invitation capability**, if required for backend exchange, is confidential material: encrypt or use the approved secret store at rest, limit readers and lifetime, send only over the verified server-to-server channel, and exclude it from browser URLs/storage, email links, logs and public evidence. Do not claim it is recoverable from the GenUI code digest or place it unencrypted in the admission row.

Keep durable provider-operation state and the remote ID. A timed-out invite creation or revocation has an unknown outcome; reconcile through the provider's supported inspection/operator procedure rather than blindly creating another non-idempotent invite or treating timeout as success. If the outcome cannot be established, deny new handoff and keep the operation pending for reconciliation. Code expiry/revocation stops new GenUI handoff immediately and schedules or requires the operator's remote revocation; retain its pending/confirmed state and failure evidence. A failed remote revoke never restores GenUI authority.

The provider and GenUI databases do **not** share a transaction. Identity creation can finish from an already-issued provider capability while a code expires, is revoked or loses its last slot. GenUI must still refuse admission when its own current checks fail, record the partial outcome and reconcile the unused identity/invitation under the provider's supported workflow. Only slot consumption, membership/entitlement and audit inside GenUI commit atomically. No distributed-atomicity or instantaneous cross-service account-deletion guarantee is made.

Until APP-074 moves capabilities into AWS Secrets Manager under the tenant key (the approved store, readable by the GenUI service), the Phase 1 custody is: the 0600 file in a 0700 directory on the operator's FileVault-encrypted Mac, outside every synced or backed-up folder (the operator command refuses known sync folders), deleted on revocation or provider expiry, with only synthetic beta invitations. *Amendment 2026-10-30 (APP-074 review M1; supersedes the operator-host custody default for the MVP):* the deployed service must read each code's provider capability, so the capability moves into the approved secret store now rather than after the MVP. The operator command writes each capability into one AWS Secrets Manager secret per environment (a JSON map keyed by capability id, encrypted under the environment's KMS key, `PutSecretValue` from the operator's credentials only), the task definition injects that secret, and `runtime.py serve()` writes each entry as a mode-0600 file into a mode-0700 directory under `/run/genui` that only the service child reads (`GENUI_PROVIDER_CAPABILITY_DIR`). ## Code lifecycle and admission

APP-073 owns an organization-scoped persisted admission ledger and an operator-only issuance/revocation interface. A code has at least 128 bits of cryptographic entropy, a digest at rest, explicit expiry, maximum redemptions and server-fixed destination/permissions/entitlement. Show its secret only on creation. Listing and audit show identifiers, status and counts, never a recoverable code. Default to one successful redemption; a deliberate multi-use code still has a finite bound. The implementation records exact configured trial durations and limits before issuing codes.

Pre-signup code validation neither consumes a successful-redemption slot nor authorizes application work. Recheck expiry, revocation and remaining count when authenticated redemption commits. Any reservation is bounded, expires, and is tied to the intended admission/browser context; it cannot become an unbounded account-creation or capacity hold. Redemption requires the verified identity for the code's destination. Consume the slot, establish the scoped membership/entitlement and append the audit event in one database transaction, with uniqueness and locking that handle parallel redemptions. An identical retry returns the prior result without consuming a second slot. A different principal, changed destination or changed payload cannot reuse that outcome.

Expired, revoked, exhausted, malformed or foreign codes deny without disclosing another organization's existence. Code revocation blocks unused admissions; revoking an issued entitlement blocks its active sessions and future work. These are separate operator actions with explicit effects and audit. Preserve both orders of redemption/revocation and operation/revocation races; a late response or queued worker cannot revive access. Trial extension or reissuance is explicit, bounded and audited.

## Public entry and abuse bounds

APP-074 supplies the public landing/invite-entry and gated signup/admission flow, with clear pending, denied, expired, exhausted and retry states. Invalid or absent GenUI codes cannot obtain a fresh signup handoff; the provider must reject registration without its own valid, correctly bound invitation, including direct endpoint calls. An already-issued remote capability is governed by the cross-service reconciliation boundary above. Completing permitted signup alone still confers no GenUI access until current membership and entitlement are established. Apply finite request/body/deadline limits and server-side IP, account/admission and global rate bounds to signup, login and code redemption; trusted proxy configuration must prevent forwarded-IP spoofing. Include limits for verification/recovery mail and abandoned pending accounts/requests in the FormaStack handoff. Deny before expensive hashing, provisioning or model work where the applicable flow permits. Do not treat a CAPTCHA, a secret URL or the temporary network restriction as the sole abuse control.

APP-015/024/043 and later operations must consume current entitlements when admitting work, recheck at execution/delivery, release reservations safely on cancellation and avoid giving another tenant's limits or outcomes to the caller. Cached results, direct API calls and existing sessions use the same authority boundary. Provider spend reservations include maximum response cost and permitted retry cost; an uncertain provider outcome retains a conservative reservation until reconciled. Published deterministic work does not require an LLM, while inactive/revoked beta entitlement still denies protected usage.

## Ordered delivery and evidence

1. APP-007 qualifies the bounded, public-HTTPS-capable infrastructure and managed isolation within the recorded allowance; it does not implement signup.
2. APP-008 establishes the tenant/role boundary. APP-073 then adds the real admission ledger, operator code workflow and database concurrency/refusal evidence.
3. FormaStack supplies the scoped registration/login/client handoff to APP-006. APP-009 consumes that identity contract and APP-073's ledger for pre-access and workspace-session transitions.
4. APP-074 qualifies the actual public signup/admission path in installed Chrome, native Safari and Firefox (amended 2026-10-29: WebKit does not substitute for Safari), direct API denials and abuse/concurrency/revocation controls. APP-012 consumes the same gate before its real managed query path; APP-013/014 preserve atomic outcomes and races.
5. PH01's gate includes APP-073/074 and these public-entry proofs, in addition to every original APP-001–014 obligation. Later phases still own complete imports, model composition, application journeys and pilot readiness.

Receipt requirements: exact source/image/DNS/TLS/issuer/client/callback identities, sanitized enrollment and code lifecycle results, expected/actual API and browser denials, paired isolated organizations, both concurrency orders, restart persistence, bounded cost/rate behavior and independent review. No source-only signup assertion, mock identity, temporary `/32` test, green planning check or static landing page completes this gate.

Rollback disables new signup/admission or protected work while retaining audit and existing outcomes; it does not reopen ingress to an unguarded app, restore revoked entitlements, change tenant identity or introduce a fake organization picker. Public beta readiness remains unproved until the owning runtime and hosted acceptance evidence exists.
