# ADR-017: One-approval GitHub-to-beta promotion

Status: accepted; implementation and live acceptance are recorded by [APP-167](../../Tickets/4-done/APP-167.md). The deploy branch in the paragraph below is superseded by [ADR-019](ADR-019-MAIN-TRUNK-AND-RESERVATION-CAP.md): `main` is now the only branch whose push starts this pipeline.

Victor authorized implementing, testing, reviewing and operating a merge-triggered Promote to beta stage. This supersedes ADR-013's local-build/manual-only sequencing for the bounded promotion path. It does not unfreeze product `main`, create production, broaden application authority or waive qualification.

The active trunk remains `pivot/pitch-mvp`. Its push event starts the pipeline, so no default-branch workflow-dispatch bootstrap is required. It verifies the exact merged commit's required successful push workflows, builds and qualifies the three ARM64 images without AWS authority, then binds their immutable artifacts to that source. Preparation may publish those exact bytes and create a closed runtime-only CloudFormation change set. The protected `beta` environment requires one reviewer approval of the concrete immutable packet before execution. Self-approval remains available to the sole authorized human owner; automation must not fabricate a human approval record.

The initial automatic path permits only qualified image replacement and the existing bounded expiry adjustment. It refuses schema, infrastructure, identity, secret and tenant-configuration changes. The original trial, aliases and existing data remain intact. Other changes retain a separately reviewed operator release path.

Dedicated OIDC preparation/execution roles use the actual immutable repository subject format and environment branch restrictions. Preparation cannot execute a change set or update ECS services. Execution cannot supply arbitrary templates or reuse the administrator CloudFormation execution role. A dedicated restricted CloudFormation role is required. AWS authority stays out of PR builds and public artifacts; workflow actions are pinned.

One private, encrypted durable state store holds the canonical ledger and write-ahead release journal. A whole-deployment lease serializes automation and manual operations. Do not duplicate the workstation ledger into independent runner ledgers. Import preserves all history and money and retains the original as evidence. The lease remains held while approval is pending; cancellation/rejection may abandon only an unactivated release with proved outcomes. An unknown mutation outcome holds the lease for reconciliation rather than expiring into another deployment.

Execution revalidates the packet, predecessor, ledger and observed stack; proves both services stopped; executes the exact reviewed change-set ARN; checks the stopped updated boundary; persists activation intent before the AWS call; and verifies running images, health and HTTPS probes. The release becomes successful only after actual live verification. No automatic database rollback is implied. Public summaries exclude private state and bind to private receipts through hashes.

Implementation must prove the denial, concurrency, cancellation and recovery paths with tests and independent review before bootstrap enables cloud authority. End-to-end completion requires a real GitHub run through the approval gate; merely installing YAML or preparing roles is insufficient.

## Amendment 2026-11-06: reviewed schema releases

Victor chose on 2026-11-05 to ship migrations 21 and 22 with one approval, on the CI-qualified images, by teaching this pipeline a reviewed schema-release mode ([APP-175](../../Tickets/0-backlog/APP-175.md)). The paragraph above that refuses schema changes still holds for every other change.

A schema release is one committed file, `ops/promotion/schema-release.json`, that names the exact baseline (schema manifest and deployment contract digests, database version) and the exact candidate (the same digests, the target version), the unchanged CDK source digest and an expiry. Every value is also pinned in source, so a JSON edit can neither widen nor retarget it, and a CI test binds the file to the tree. Preparation accepts a changed schema manifest or contract only when all of it matches the canonical baseline, policy schema version, qualified source binding and the candidate's own checkout, before the lock; execution rechecks it before the snapshot and again before the outage. The approval summary names the versions and the file's hash.

Execution takes a manual RDS snapshot after every pre-execution recheck but while beta still serves, so a refused or slow snapshot never causes an outage: the release stays `prepared` and may be abandoned. Abandonment accepts that one snapshot entry, reads back an unknown outcome by its deterministic name, and keeps any snapshot. After the rechecks are repeated, the outage proceeds as before, and between the stopped boundary and activation intent the stack's migration task runs once on the candidate image. Both steps are journaled mutations with immutable receipts, and exit code 0 is required within a bound. A migration failure keeps both services stopped and the lock held with no activation, retry or replay, as for a failed stack update. Success admits the candidate's schema manifest and contract into the baseline and sets the policy schema version.

Recovery from a failed or unstarted migration is the operator command `maintenance restore-after-failed-migration`. It is hash-bound, fenced 65 minutes after the run, planned before it is applied, and never replays. It requires the stopped execution with no migration or a migration observed to stop with a known non-zero exit code, and refuses an unknown outcome or exit 0, which means the migration committed and only fixing forward remains. It puts the stack back on the baseline template with the previous release's parameters through a change set run by the restricted CloudFormation role, activates both services and requires them healthy. Because the previous images require the prior schema version on every connection, their health proves the database did not move. It abandons the failed window with its reservation kept and leaves the baseline and schema policy unchanged. Any failure keeps the lock and records the outcome. It restores images and template, never data.

The runner step of execution carries one 55-minute budget that clips every wait, and the execute job's timeout is 75 minutes so its other steps fit beside it; the boundary reads, probes and receipts after the health wait fall outside the budget.

The execute role gains only the migration task's `ecs:RunTask` on this cluster, `iam:PassRole` of its two roles to ECS tasks, snapshot create/describe on the database and `forma-schema-release-*` snapshots, and tagging of those snapshots alone (the instance copies its tags to them). IAM has no condition key that forbids RunTask container overrides, so that permission could start the migration task definition with another command; the trust rests on the reviewed trunk code that alone uses the execute role. No role in this design can query the database before the outage, so the shared-tenant condition that fails migration 0021 is an accepted limit, evidenced by the schema campaign rather than checked live. The pipeline still never changes the template, infrastructure, identity or secrets, and still performs no automatic database rollback.
