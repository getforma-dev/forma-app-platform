# ADR-007 — Phase 1 write authority, schema layout and query execution

Date: 2026-10-29, revised the same day after the [independent review](../../evidence/APP-073/adr-007-review.md) (2 blockers, 10 majors, 13 minors; every finding's disposition is in the table at the end). Owner: GenUI. Status: accepted implementation direction; it authorizes no runtime result. It extends [ADR-004](ADR-004-TENANT-TRANSACTIONS.md) for the writes that APP-073, APP-009, APP-010, APP-012 and APP-013 must perform. Every ADR-004 numeric bound (two connections per role, eight total, 5 s acquisition, 3 s transaction, 2 s cleanup, `statement_timeout` 2000, `lock_timeout` 1000) is unchanged, and so are "no raw client or SQL leaves the storage module", "`TrustedRequest` is constructed only by storage" and "`genui_lock` is unchanged". ADR-004 is **amended** in exactly four named places, each marked **A1–A4** below: A1 one retry of a control publication on SQLSTATE 40001 (D7.6); A2 two digest-leading relations without RLS, readable only through definer functions (D7.2); A3 the six-role catalog normalization extends to `genui_admit` (D7.12); A4 `genui_admit` holds lock-enabling UPDATE columns that no function body writes (D7.1). [ADR-003](ADR-003-PUBLIC-BETA-ACCESS.md), [ADR-005](ADR-005-PHASE-1-SEQUENCING.md), [ADR-006](ADR-006-SIGNIN-AND-VERIFICATION-PENDING.md) and [ADR-008](ADR-008-YC-DEMO-AND-BETA-MVP.md) remain controlling for their subjects. The [execution plan](../planning/PHASE-1-EXECUTION-PLAN.md) assigns D7.1–D7.19 to tasks; where the plan restates a signature, this document controls.

## Why a decision is needed

Migration 0002 grants the four application roles SELECT only; the only non-read privileges belong to `genui_lock`, which ADR-004 confines to fixed row-locking functions and forbids from owning mutation functions. ADR-004 also forbids direct application mutation of the grant tables and requires every membership change to take `organizations FOR SHARE` then the member row `FOR UPDATE` and advance that member's epoch in the same transaction. The remaining Phase 1 tickets must create principals, memberships, permissions, entitlements, sessions, definitions, publications, saved work, records, outcomes and audit rows, must look up an access code or a sign-in handle before any organization scope exists, and must hold a bounded pre-signup reservation and a 24-hour pending admission between invitation entry and verified sign-in (ADR-006). Without one recorded decision, each ticket would invent its own write path.

## Decisions

### D7.1 A dedicated definer principal for authority writes

Create `genui_admit` — `NOLOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, with no IAM membership and no application-role membership — owning exactly six `SECURITY DEFINER STRICT VOLATILE` functions with `SET search_path = pg_catalog, pg_temp` (every relation named schema-qualified) and `PUBLIC` revoked. Inside them RLS is evaluated with the caller's transaction-local scope, which the reviewer confirmed (review C3); each function nevertheless requires `current_setting('genui.organization_id')` to equal `p_org` as defense in depth. Every function returns a typed `outcome` and never raises for a business refusal.

| Function | Purpose | EXECUTE |
| --- | --- | --- |
| `genui_private.resolve_code(p_code_digest text) RETURNS uuid` | Returns the organization of a known code digest from `genui_private.code_index`, or NULL; reads nothing else. | `genui_workspace` |
| `genui_private.resolve_handle(p_handle_digest text) RETURNS uuid` | Returns the organization of a live sign-in handle digest from `genui_private.handle_index`, or NULL; reads nothing else. | `genui_workspace` |
| `genui_private.reserve_code(p_org uuid, p_code_digest text, p_context_digest text) RETURNS TABLE(reservation_id uuid, expires_at timestamptz, outcome text)` | Locks `genui.organizations FOR SHARE`, then the `genui.access_codes` row `FOR UPDATE`; judges expiry, revocation and exhaustion on the scoped row; refuses when 10 pre-signup reservations are already live for the code; otherwise inserts a `genui.code_reservations` row of kind `presignup`, bound to `p_context_digest` (the pre-login flow), expiring in 10 minutes. | `genui_private.advance_member_epoch(p_org uuid, p_principal uuid, p_reason text) RETURNS bigint` | `p_reason` ∈ `session.sign_out`, `session.sign_out_all` only. Requires the transaction's `genui.organization_id`, `genui.principal_id` and `genui.membership_epoch` to equal `p_org`, `p_principal` and the member's current epoch, exactly as `lock_member_authority` does (0002:247–249); locks `organizations FOR SHARE` then the membership `FOR UPDATE`, increments `membership_epoch`, writes one audit event on the `admission` chain and returns the new epoch. A member can advance only its own epoch. | `genui_workspace` |

**Grants of `genui_admit` (A4).** Column-limited INSERT on `principals`, `memberships`, the four `*_permissions` tables, `entitlements`, `code_reservations`, `code_redemptions` and `audit_events`; UPDATE(`redeemed_count`, `status`) on `access_codes`; UPDATE(`membership_epoch`) on `memberships`; UPDATE(`state`, `consumed_at`) on `code_reservations`; UPDATE(`status`) on `genui.organizations` as a **lock-enabling column only** (PostgreSQL requires an UPDATE column for `FOR SHARE`/`FOR UPDATE`; 0002:236–237 gives `genui_lock` the same column for the same reason); UPDATE(`chain_sequence`, `head_hash`) on `audit_heads` for its own chain; and SELECT on the columns those functions read. No `genui_admit` function body updates `genui.organizations`, and the schema campaign asserts it by inspecting the function bodies and by a negative test. `genui_lock` is unchanged. These functions perform no generic SQL, accept no permission names from callers and expose no bypass flag; a verified nonmember reaches `record_pending_admission` and `admit_redemption` only through the storage module's private nonmember entry, which installs organization scope (and no principal) for the definer call and never issues a member `Permit`.

**Revocation stays with the operator.** Membership and entitlement revocation, code revocation and extension, organization provisioning and handle rotation are **operator-channel transactions** run by the operator package (APP-077) as the migration identity under explicit organization scope, in the order `organizations FOR SHARE` → member or code row `FOR UPDATE` → status change with `membership_epoch + 1` → one audit event on the `operator` chain. No application role and no `genui_admit` function revokes anything. **Named deviation:** the design (§6.1, §10.6; schema-plan §authority) places membership changes with the control tier; Phase 1 creates memberships from the sign-in callback, which is a workspace request, through `admit_redemption`, because ADR-003 §pre-access and ADR-006 §callback complete admission there. Revocation is not moved.

### D7.2 Lookups before organization scope (A2)

FORCE RLS keyed on `genui.organization_id` makes a code or handle lookup impossible before scope is set. Two relations are the only exceptions to ADR-004's organization-leading, RLS-protected rule: `genui_private.code_index(code_digest genui.digest PRIMARY KEY, organization_id uuid NOT NULL REFERENCES genui.organizations)` and `genui_private.handle_index(handle_digest genui.digest PRIMARY KEY, organization_id uuid NOT NULL REFERENCES genui.organizations, retired_at timestamptz)`. Both carry no RLS, are owned by `genui_owner`, grant nothing to any application role (USAGE on the schema grants no SELECT), and are readable only through `resolve_code` and `resolve_handle`; the campaign asserts that no application role can read them directly. The operator issuance command inserts the code index row and the scoped `genui.access_codes` row in one transaction; the provisioning and handle-rotation commands write `handle_index`, keeping both handles live during a rotation (ADR-006 §handle) and retiring the old one afterwards. Revocation and expiry are judged on the scoped row after scope is set; an unknown digest returns NULL and the caller renders the same neutral answer as any other refusal (review C4: a digest reveals only the organization of a code the caller already holds). The tenant slug and client id for the sign-in page are read after scope is set.

### D7.3 Business grants arrive with their owning ticket

Grants are added by the migration of the ticket whose transaction and audit implementation uses them, never earlier, and every new relation in `genui` has `ENABLE` and `FORCE ROW LEVEL SECURITY` with the `tenant_scope` policy (`USING` and `WITH CHECK`) stated explicitly in that migration, because the 0002 loop covers only 0002's tables. Reads are granted by column where a ticket needs them; nothing beyond this table is readable or writable by an application role.

In Phase 1, INSERT on `apps` and `publication_policies` is an operator write (`create-app`, policy seeding), not an application grant (APP-010 review m2). Permission-table rows are written only by `admit_redemption` and by the operator channel. The schema campaign asserts this table literally: the set of (role, relation, privilege, column) tuples in the catalog equals the set this ADR grants.

Publications gain `publication_sequence genui.safe_counter NOT NULL`, unique per `(organization_id, app_id)` and assigned under the publish transaction's control-head lock, and `PublishResult::Stale` names the publication with the highest sequence; the `publication.published` audit event records the publication id. These change migration 0005 in place, which has been applied only to disposable databases.

Consumption still happens only inside `admit_redemption`. Migration 0006 carries the grant.

### D7.4 Adoption stays operator and test-only in Phase 1

No application write path bumps `saved_work.version` before PH03 (C10). APP-014's adoption race uses a test-only writer through the owner channel, exactly as the current campaign drives revocation.

### D7.5 Every new `genui` relation is organization-leading

Pre-login flows, reservations, pending admissions and pre-access sessions know their organization when they are created (from the sign-in handle through `resolve_handle`, or from the code through `resolve_code`) and are tenant-leading like every other `genui` relation; the callback confirms the organization from the verified token through the registry. The only non-leading relations are the two `genui_private` indexes of D7.2. Rate-limit counters are in-process for the single-task deployment of D7.18 and are a recorded limitation, not a table.

### D7.6 Isolation levels (A1)

`Transaction::begin_serializable` exists for the control role only. **A1 amends ADR-004 §Request and operation states (READ COMMITTED) and §Pool and driver lifecycle (no automatic retry) for one case only:** a control-role publication transaction that fails with SQLSTATE 40001 at any statement, including `COMMIT`, has definitely rolled back (PostgreSQL reports 40001 only for a transaction it has aborted); it is retried once in a new transaction on a freshly verified lease, within the D7.14 handler deadline. A second 40001 returns `PublishResult::Stale` (412 naming the current revision, design §6.2). A `COMMIT` that fails for a transport reason remains `Error::UnknownOutcome` and is never retried; the storage module therefore classifies 40001 at `COMMIT` separately from transport ambiguity (D7.9). Everything else stays `READ COMMITTED READ WRITE` with no automatic retry.

### D7.7 Commit sequence

`genui.organization_sequences(organization_id uuid PRIMARY KEY REFERENCES genui.organizations, next_commit_sequence genui.safe_counter NOT NULL)` is locked `FOR UPDATE` inside the command transaction after both fences and before the record row (lock order, D7.9). This serializes commands per organization; accepted for Phase 1 and revisited with APP-015's job model. **Row creation:** the operator provisioning transaction creates the organization's `organization_sequences` row and its five `audit_heads` rows (D7.8) in the same transaction as the organization. For the two existing organizations, the operator package (APP-077) inserts them under scope with `next_commit_sequence = 1 + max(internal_record_revisions.commit_sequence)` (1 if there is none) and genesis heads. A command that finds no row returns `Error::Configuration` and writes nothing.

### D7.8 Audit

`genui.audit_events(organization_id uuid, event_id uuid, writer_role text CHECK (writer_role IN ('workspace','control','data','admission','operator')), chain_sequence genui.safe_counter NOT NULL, kind text NOT NULL, actor_principal_id uuid NULL, app_id uuid NULL, work_id uuid NULL, record_id uuid NULL, code_id uuid NULL, outcome_digest genui.digest, occurred_at timestamptz NOT NULL, previous_hash text NOT NULL, hash text NOT NULL, PRIMARY KEY (organization_id, event_id), UNIQUE (organization_id, writer_role, chain_sequence), UNIQUE (organization_id, writer_role, previous_hash))` is insert-only for every role. Each organization has one chain per writer role, with its tail in `genui.audit_heads(organization_id uuid, writer_role text, chain_sequence genui.safe_counter NOT NULL, head_hash text NOT NULL, PRIMARY KEY (organization_id, writer_role))`. **Append protocol:** lock the head row `FOR UPDATE`; `chain_sequence = head.chain_sequence + 1`; `previous_hash = head.head_hash`; `hash = sha256("forma:audit-event:v1" ‖ 0x00 ‖ previous_hash ‖ canonical event bytes)` where the canonical event bytes are the forma-json-v1 encoding (ADR-002) of every column except `hash`; insert the event; update the head. The genesis `head_hash` is `sha256("forma:audit-genesis:v1" ‖ 0x00 ‖ organization_id text ‖ 0x00 ‖ writer_role)`. Every hash is written in the `sha256:<64 lowercase hex>` form and typed `genui.digest` (`previous_hash`, `hash`, `head_hash`); a genesis head sits at `chain_sequence = 1`, so the first event of a chain is sequence 2; the canonical event stores `occurred_at` as whole-second UTC; the operator package (D7.19) uses the same conventions (0003 review m4). Because `audit_events` is insert-only for every role including its owner, no row referencing it can carry a foreign key that needs UPDATE on it, and an organization with audit rows cannot be deleted; deletion is APP-065's (PH05) explicit procedure, and the schema campaign instead asserts as a set that every `code_redemptions.audit_event_id` exists (0003 review m5). The head-row lock, not an advisory lock, serializes appenders: READ COMMITTED appenders queue on the row, and a SERIALIZABLE publication that loses the race gets 40001 and D7.6's single retry instead of forking the chain (review T3). **Role binding:** every role that holds INSERT on `audit_events` has a RESTRICTIVE INSERT policy `TO <role>` with `WITH CHECK (writer_role = '<its chain>' AND kind = ANY('<its kinds>'))` and a RESTRICTIVE UPDATE policy on `audit_heads` with `USING (writer_role = '<its chain>')`; the campaign asserts the set of INSERT-holding roles equals the set of policy targets. **Chains and kinds (closed; a new kind is an amendment of this ADR):** `workspace` (`genui_workspace`): `session.signed_in`, `app.created`, `definition.drafted`, `work.saved`, `work.bound`; `control` (`genui_control`): `publication.published`, `policy.changed`; `data` (`genui_data`): `command.committed`; `admission` (`genui_admit`): `admission.pending`, `admission.redeemed`, `admission.denied_for_reconciliation`, `session.sign_out`, `session.sign_out_all`; `operator` (the migration identity): `organization.provisioned`, `handle.rotated`, `code.issued`, `code.revoked`, `code.extended`, `membership.revoked`, `entitlement.revoked`, `permission.granted`, `permission.revoked`, `creator_authority.revoked` (the last three added by migration 0005 under the 2026-10-29 creator-authority amendment). Object Lock anchoring stays with APP-053/057 (QUALITY-GATES); PH01's SR10 obligation is the insert-only chains and their verification (recompute every hash in `chain_sequence` order and compare the tail with the head).

### D7.9 Typed results instead of disclosing errors

`storage::Error` keeps its five variants; the storage module classifies SQLSTATEs internally (23505 unique violation, 40001 serialization failure, 55P03 lock not available, 40P01 deadlock) and never lets them out. Admission returns `Ok(Admission)` with `pub enum Admission { Admitted { principal: String, epoch: i64, entitlement: String }, Pending { reason: PendingReason }, AlreadyMember, Refused }`. Commands return `Ok(CommandResult)` with `pub enum CommandResult { Committed(CommandOutcome), Replayed(CommandOutcome), Conflict(RecoveryView), Stale(CurrentRevision), InFlight }`: `Conflict` means an `expected_record_version` mismatch or the same idempotency key with a different `payload_digest` (409 with the recovery view; S05's stale request expecting version 0 is this case); `Stale` means the saved work's publication or version premise has moved (412 naming the current revision); `InFlight` means a lock wait past `lock_timeout` on the idempotency claim, the organization sequence or the record row (409, code `in_flight`, `Retry-After: 2`). Publications return `pub enum PublishResult { Published(Publication), Stale(CurrentRevision) }` (412 on `Stale`, D7.6). **Idempotency claim:** `genui.command_claims(organization_id uuid, principal_id uuid, app_id uuid, work_id uuid, command_id text, idempotency_key text, payload_digest genui.digest, claimed_at timestamptz, PRIMARY KEY (organization_id, principal_id, work_id, command_id, idempotency_key))` is insert-only; immediately after the shared precheck and before the fences, the command runs `INSERT … ON CONFLICT DO NOTHING RETURNING 1` with no savepoint (ADR-004 §no savepoints): one row means a fresh claim; zero rows means the key is taken, so the command reads the committed `command_outcomes` row for `Replayed` (same digest) or `Conflict` (different digest); a wait on the in-flight claim past `lock_timeout` is `InFlight`; a rolled-back command releases its claim with the transaction. `command_outcomes` is inserted once at the end with a foreign key to the claim. **Lock order for every command:** `organizations FOR SHARE` → member `FOR SHARE` → work `FOR SHARE` (the 0002 fences) → `organization_sequences FOR UPDATE` → record row `FOR UPDATE` → `audit_heads FOR UPDATE`. **Lock order for sessions:** the member fence always precedes any session-row write, and sign-out advances the epoch (`advance_member_epoch`) before deleting session rows, calling it directly without first taking `lock_member_authority` (two sign-outs that each took the fence first deadlocked in the 0003 review's probe; m1). **HTTP:** `Committed`/`Replayed` → 200; `Conflict` → 409 with the recovery view; `Stale` → 412 with the current revision; `InFlight` → 409 `in_flight` with `Retry-After: 2`; a 55P03 on an authorization fence in any request → 409 `busy` with `Retry-After: 2` (an operator membership change holding the member row `FOR UPDATE` blocks the claim's foreign-key check first and therefore surfaces as `in_flight`, which is also 409 with `Retry-After: 2`; APP-013 review m5); in Phase 1 a lock wait past `lock_timeout` during session resolution itself (before any command runs) answers the uniform 404 like any other session-lookup failure, which fails closed (APP-014 finding F1); a typed busy answer on every session route is follow-up APP-086 (a conflicting operator or sign-out operation is in progress; not 503, which design §9 reserves for provider or store outage); `Error::Unavailable`, `Error::Configuration` and transport failures → 503; `Error::UnknownOutcome` → 503 and the client re-reads the outcome by key under current authority (ADR-002).

### D7.10 Query execution

Phase 1 runs typed queries through the qualified APP-005 DuckDB executor packaged into the runtime image (`duckdb==2.0.0` hash-locked; executor copied to `app/runtime/query_engine.py` with its source identity recorded) as a per-request engine child spawned by the Rust binary: `python3 /app/runtime.py query` with a closed JSON request on stdin and exactly one JSON result line on stdout. **Named deviation:** design D11 ("one binary holds every component"), §6.3's in-process data service and APP-D05 ("one process initially") are not followed, and APP-005's container boundary (no credentials, no network, read-only filesystem) is **not reproduced inside the Fargate task**; the engine runs as a child process of the same UID. The compensating controls are therefore mandatory: (1) APP-005's `POLICY` is copied verbatim: `threads=2`, `memory_limit='1GiB'`, `max_temp_directory_size='2GiB'`, an exact source allowlist followed by `enable_external_access=false`, `lock_configuration=true`, extension autoloading off, no httpfs, read-only database; (2) fetch is separated from execution: a credentialed step in the Rust binary fetches the source bytes once per revision from S3 key `o/<organization>/sources/<source_id>/<revision_id>` through the tenant role, verifies `source_revisions.normalized_digest`, and renames the file atomically into the read-only cache `/run/genui/cache/o/<organization>/`; the engine child is spawned with `env_clear()` and a minimal environment (no `GENUI_RUNTIME_CONFIG_FILE`, no `AWS_*`, no inherited descriptors beyond its pipes) and a private scratch directory outside the cache that is removed on exit or kill; `runtime.py`'s own scope note is amended in the same slice to name the engine subcommand; (3) admission: at most 2 running queries per organization and 4 per task, a queue of 20, and 429 with `Retry-After` beyond it; (4) the child is interrupted at 1.8 s, then killed and reaped with APP-005's 5 s backstop; (5) APP-012 measures the per-request interpreter cost against design §5.2 before acceptance and records it; if it fails the budget, APP-012 adopts APP-005's supervised broker (two running, twenty queued) in the same ticket. The minimal Phase 1 queries are the Northstar `total` and `timeline` views, the only fixture views inside the qualified operator subset; CIDR lookup, ratio and money literals stay refused until PH02. The operator package normalizes the fixture CSV to the contract `events_v1` shape as Parquet through the reviewed APP-004/005 adapter and records real digests, replacing the seeded placeholders for the Northstar organization. No DuckDB dependency enters the Rust binary.

### D7.11 Refresh-token custody

As ADR-006: encrypted with a random key held only in process memory, referenced from the session row, never sent to the browser, revoked through provider logout when the GenUI record is destroyed; a restart invalidates stored tokens and the user starts a fresh sign-in. D7.18's single-task deployment is what makes "process memory" well defined.

### D7.12 Migration numbering, runner and catalog budget (A3)

Migration numbers are assigned in landing order (0003 admission and 0004 entitlement reads have landed with APP-073; planned 0005 definitions/work grants, 0006 sessions, 0007 commands); a ticket that lands earlier renames its file first, and renumbering regenerates every later cumulative snapshot. The runner is generalized once to N versions before 0003: `migration_sources` accepts the manifest's N files; `apply_migrations` upgrades from any recorded version to the latest with a catalog proof after each step on the fresh path and on the upgrade path alike; `initialize_migration_history` keeps writing the historical baseline `BETWEEN 1 AND 2` on both version `CHECK`s (so a fresh database after 0002 equals `catalog-v2`), and each migration `000k` `ALTER`s both `CHECK`s to `BETWEEN 1 AND k`. Each version ships its `catalog-vN.json`. **Catalog budget:** the reviewer's estimate puts v7 at 200–220 KB against the 209,715-byte guard, so the cap moves once, in 0003's slice, coordinately: `octet_length(body) <= 524288` in `catalog-query.json`, `BOUND` in `catalog.rs`, the limit in `runtime.py`, and the generator's 80 % guard at 419,430 bytes measured on the database's `jsonb::text` body length, not the file size; `catalog-v1`/`v2` content is unchanged by the cap. **A3:** migration 0003 adds `genui_admit` to every fixed-role list in `catalog-query.json` and in `qualify_tenant_schema.py`'s normalization, extending ADR-004 §Migration and recovery's six-role normalization to seven roles so RDS and local catalogs stay equal; it records `GRANT genui_admit TO genui_migration WITH INHERIT FALSE, SET TRUE` and the temporary `CREATE ON SCHEMA genui_private` with its revocation, as 0002 did for `genui_lock`; `catalog-query.json` is re-pinned. `scripts/check-schema-pins.py` fails unless every place that carries the schema-version literal agrees; the script's own list of places is the authoritative pin list.

### D7.13 Harness retirement

`auth_qualification` compiles only behind Cargo feature `qualification-harness`, which release builds do not enable; release startup refuses `GENUI_AUTH_QUALIFICATION_CONFIG_FILE`; the product `auth` module owns `/auth/callback`. The published harness image `18c33f5` remains the artifact for the deferred identity rehearsal (APP-079).

### D7.14 Trusted proxy and limits

`axum::serve(..).into_make_service_with_connect_info::<SocketAddr>()`; the client address is the rightmost `X-Forwarded-For` hop because only the ALB can reach the task and the ALB appends the peer address (review C10); in-process token buckets per address class, per account and global with the ADR-006 values. Body limits: ≤ 4 KiB on auth and admission forms; ≤ 64 KiB on JSON query routes; ≤ 256 KiB on the JSON command route, sized from the maximum canonical command (32 values of up to 2,000 characters, UTF-8); an oversize body is refused with 413 `payload_too_large`, a transport-level refusal added to design §9's application errors. Handler deadline 5 s.

### D7.15 HTTP contract

JSON routes live under `/v1/`, pages are unversioned; errors are `application/problem+json` carrying a stable `code` plus only the class-specific authorized fields design §9 names (the recovery view on 409, the current revision on 412, the rule name on 403); authenticated responses are `Cache-Control: no-store`; a fallback answers unknown paths with the uniform 404 and the security headers (design §9). The recovery view and the claim are new wire shapes, so APP-013 ships them in a new contract edition per ADR-002, and the Phase 2 edition follows it.

### D7.16 Idempotency key for pre-activation forms

The key travels as a typed prop rendered into a hidden field (static SSR routes refuse `config_json`); an active island mints its own key.

### D7.17 Admission defaults and arithmetic

Trial entitlement 30 days; code expiry 14 days with an operator maximum of 30 (`CHECK (expires_at <= issued_at + interval '30 days')`); `max_redemptions` default 1 (`CHECK (max_redemptions BETWEEN 1 AND 10)`); pre-signup reservation 10 minutes, not counted against remaining redemptions, at most 10 live per code; post-signup pending admission 24 hours, bound to the provider identity and committing nothing until an exchange reports `email_verified` true. **Remaining redemptions** `= max_redemptions − redeemed_count − (live pending admissions other than the one being judged)`; a code with `remaining = 0` refuses new pending admissions as `exhausted` while existing pending admissions may still redeem. A resend requested after the pending admission expired destroys the pre-access record and answers `303 /signin/{handle}` (ADR-006); `/auth/pending` shows the time remaining. List and audit pages 100 rows; resend cooldown 60 s and 5 per 24 hours.

### D7.18 Deployment mode in Phase 1

The service deploys stop-then-start (`minHealthyPercent 0`, `maxHealthyPercent 100`) so exactly one task runs at any moment; this keeps D7.5's in-process rate limits and D7.11's process-memory key well defined. A deployment is therefore a brief outage that signs every member out, accepted for the synthetic beta and recorded as a limitation; rolling deployment with shared state is APP-061's (PH05).

### D7.19 Operator channel

The operator package (APP-077) is the only writer of `handle_index`, `code_index`, `access_codes` issuance, `code_grant_templates`, organization provisioning (`organizations`, `organization_sequences`, the five `audit_heads`), membership and entitlement revocation, code revocation and extension, and the backfill of D7.7. It connects as the migration identity, sets explicit organization scope for every tenant write, follows the lock orders of D7.1 and D7.9, and writes the `operator` audit chain. Its commands are closed subcommands, never generic SQL. Trial extension is a code operation only (`extend` moves a code's expiry later and never shortens it; a member's entitlement is extended by issuing a new code), and the backfill of genesis heads writes no audit event because the genesis heads are themselves the record (APP-073 review).

## Consequences

APP-073 (0003: `code_index`, `handle_index`, `code_grant_templates`, `code_reservations`, `code_redemptions`, `entitlements`, `audit_events`, `audit_heads`, `genui_admit` and its six functions, A3 catalog changes and the cap move), APP-010 (0005), APP-009 (0006), APP-013 (0007: `command_claims`, `command_outcomes`, `organization_sequences`, `query_receipts`) implement their migrations against this layout; APP-012 implements the query worker with its five controls; APP-077 implements the operator channel. The schema campaign (`qualify_tenant_schema.py`) gains assertions that every `genui` table has RLS, FORCE and the policy; that the (role, relation, privilege, column) grant set equals D7.3 plus D7.1; that `genui_admit` holds exactly its grants and no function body updates `organizations`; that `code_index` and `handle_index` are reachable only through their functions; that every INSERT-holding role on `audit_events` has its RESTRICTIVE policies; and that the two existing organizations have `organization_sequences` and `audit_heads` rows. Nothing here weakens ADR-003's admission rules or ADR-006's session contract; ADR-004 is amended only at A1–A4. On 2026-10-29, 0004_entitlement_reads.sql (SELECT on `entitlements` for `genui_workspace`, `genui_control` and `genui_data`) landed with APP-073, so every later planned migration moved up by one; the operator backfill writes no audit event by design (D7.8's kinds are closed, and the genesis heads are the record).
