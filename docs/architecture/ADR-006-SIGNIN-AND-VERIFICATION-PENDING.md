# ADR-006 — Ordinary sign-in, verification-pending state and backend-mediated resend

Date: 2026-10-29. Owner: GenUI (APP-009 implements, APP-074 proves hosted, APP-076 proves integrated). Status: accepted route and state contract for implementation; nothing here is deployed, tested or accepted. It answers the FormaStack [mailbox follow-on plan](../../evidence/APP-006/upstream-auth-source/MAIL-VERIFICATION-FOLLOW-ON-PLAN.txt) step 1, which requires GenUI to fix the ordinary sign-in entry, the restricted pending-verification state and the authenticated resend route before the provider implements its return step. [ADR-003](ADR-003-PUBLIC-BETA-ACCESS.md) is controlling; the consumed provider facts come from the hash-bound [GenUI identity contract](../../evidence/APP-006/upstream-auth-source/GENUI-IDENTITY-CONTRACT-2026-10-28.md). Sequencing is in [ADR-005](ADR-005-PHASE-1-SEQUENCING.md).

## Principals and sessions

All cookies are `__Host-` prefixed, `Secure`, `HttpOnly`, `Path=/`, opaque random identifiers of at least 128 bits whose server-side records hold the state. No fAuth access token, refresh token, authorization code, `request_uri`, invitation or GenUI access code is ever placed in a cookie, URL, browser storage, log or public receipt. The fAuth token JSON and issuer `Set-Cookie` headers returned by the backend exchange are never forwarded to the browser.

| State | Cookie | Bound to | Lifetime | Permitted |
| --- | --- | --- | --- | --- |
| Anonymous | none | — | — | Landing, invitation entry, sign-in entry pages, health, assets. Every protected route returns the uniform refusal. |
| Pre-login flow | `__Host-genui_prelogin`, `SameSite=Lax` | one server-side flow record: organization, fAuth tenant slug, client id, `state`, `nonce`, PKCE verifier, flow kind (sign-in or invited signup with its signup-handoff id), creation time, client address class | 10 minutes absolute, single use; consumed or discarded at the callback | Only `GET /auth/callback` for that exact `state`. |
| Pre-access session | `__Host-genui_pre`, `SameSite=Lax` | verified issuer, subject, fAuth tenant id, mapped organization, backend `user.email_verified`, the admission flow it may finish, encrypted server-side fAuth refresh token reference | 10 minutes idle, 30 minutes absolute, one browser | `GET /auth/pending`, `POST /auth/pending/resend`, `POST /auth/signout`, and completing its own bound admission. Nothing else: no workspace or private metadata read, no work, no model, no upgrade through client-supplied grants. |
| Workspace session | `__Host-genui_session`, `SameSite=Lax` | verified identity, organization, membership epoch, entitlement id, registry version | 1 hour idle, 12 hours absolute | Protected routes, rechecking current membership, epoch and entitlement at request, execution, commit and delivery. |
| Organization routing hint | `__Host-genui_org`, `SameSite=Lax` | opaque per-organization sign-in handle only | 30 days | Lets `GET /signin` prefill the handle. It is routing convenience, never authority. |

The workspace session's 12-hour absolute and 1-hour idle lifetimes and its opaque `__Host-`, HttpOnly, Secure, SameSite=Lax cookie are pinned by the platform design (§6.1 and M24); the 10-minute pre-login state matches the design's pre-session cookie. The pre-access lifetimes are Phase 1 defaults chosen here, because ADR-003 pins only "short-lived"; the fAuth hosted request lasts five minutes and the tenant idle default is 30 minutes, so both fit. Idle and absolute expiry, sign-out and sign-out-everywhere delete the server-side record; a cookie without a live record is treated exactly like no cookie. Cross-site protection does not rely on the cookie attribute: every state-changing request is checked as described under Routes.

## Organization sign-in handle

Each operator-provisioned organization receives a random handle of at least 128 bits, stored only as a digest on the organization row and compared in constant time. The handle appears in that organization's sign-in URL `https://beta.getforma.dev/signin/{handle}`, in operator-issued invitation material and in the per-client return URL registered with fAuth. It selects routing (fAuth tenant slug and client id); it grants nothing. The session's organization never comes from the path, a header or a body: the callback derives it from the verified token's `(issuer, tenant_id)` through the closed registry and refuses when that organization differs from the one the flow record expected. An unknown handle renders the same neutral sign-in page as a known one and starts no provider request, so GenUI discloses no organization's existence. The operator can rotate a handle; the old one stops routing immediately.

## Routes

All routes are served by the production binary on `https://beta.getforma.dev`. Every `POST` requires `Sec-Fetch-Site: same-origin` (or an exact `Origin` match when absent) and a per-form synchronizer token tied to the current cookie; a failure answers `403` with the problem code `cross_site` (design §9). Protected-route refusals for anonymous, pre-access, expired, revoked and foreign-tenant callers answer the design's uniform `404` with `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and an `application/problem+json` body carrying only a stable code; denied, foreign and absent are indistinguishable. Request bodies are bounded (4 KiB for these forms), handlers have deadlines, and limits below are server-side per client address class, per account and global, with trusted-proxy address extraction only from the ALB. Denied requests perform no provider call, hashing or database work beyond the limit check itself.

| Route | Who | Effect | Refusals and limits |
| --- | --- | --- | --- |
| `GET /signin` and `GET /signin/{handle}` | anonymous | Renders the neutral sign-in page with one same-origin form. Prefills the handle from the path or routing hint. No provider call, no state. | Unknown handle renders the same page; the form then fails uniformly. |
| `POST /signin/{handle}` | anonymous | Creates the pre-login flow record, sets `__Host-genui_prelogin`, performs the backend hosted request (`POST /t/{slug}/oauth/par` with `client_id`, exact `redirect_uri`, `code_challenge` S256, `state`, `nonce`, no invitation) and answers `303` to the returned provider `redirect_uri`. | Unknown handle, missing token, provider refusal or deadline → uniform neutral failure page. Limits: 10/minute and 60/hour per address class, 600/hour global. |
| `GET /invite` | anonymous | Invitation-entry page (APP-074). | — |
| `POST /invite/validate` | anonymous | Validates a GenUI access code by digest without consuming a redemption slot; on success creates a bounded signup handoff (code digest, server-bound organization, provider invitation reference, 10-minute expiry) and the pre-login flow, then performs the backend hosted request with the confidential provider `invite_token` only in the backend body and answers `303`. | Malformed, unknown, expired, revoked or exhausted codes and foreign organizations receive the same neutral answer with no existence disclosure. Limits: 5/minute and 20/day per address class, 200/day global; a code reservation never authorizes work. |
| `GET /auth/callback?code=…&state=…` | browser returning from fAuth | Requires the pre-login cookie whose record matches `state`; exchanges at `POST /t/{slug}/auth/token` with `grant_type=authorization_code`, `code`, `code_verifier`, `client_id`, `redirect_uri`; verifies the access JWT (EdDSA, `kid` in the access-only JWKS, `iss` `gatewasm`, `aud` `gatewasm-app`, `typ` `JWT`, `exp`/`iat` with bounded skew), requires JWT `sub` to equal `user.id`, maps `(issuer, tenant_id)` through the closed registry to the organization bound in the flow record, stores the refresh token encrypted server-side, destroys the flow record and mints a pre-access session. Then admission: invited-signup flows run APP-073's atomic authenticated redemption; existing-member flows read current membership. If `user.email_verified` is false → `303 /auth/pending`. Else if membership and entitlement are current → mint the workspace session, destroy the pre-access record, `303` to the workspace. Else → neutral denial page with signout only. | Missing or mismatched cookie/state, replayed code, unknown key, failed signature, wrong issuer/audience, expired token, unmapped tenant, `sub`≠`user.id`, provider error or deadline → uniform failure; no session. JWKS refresh follows the verifier's bounded cooldown; unknown keys fail closed. The flow record is single-use, so a replayed callback cannot mint anything. |
| `GET /auth/pending` | pre-access session | Restricted page: identity is verified but the mailbox is not; shows resend availability and signout. Reads nothing from the workspace. | No pre-access session → uniform refusal. |
| `POST /auth/pending/resend` | pre-access session | Backend refreshes the stored fAuth session if needed (`grant_type=refresh_token`, serialized per session, token replaced atomically) and calls `POST /t/{slug}/auth/resend-verification` with the account's current access token. Maps the provider's reported outcomes to two fixed sanitized results and never presents either as delivery: `202 status=provider_accepted` → `requested` (the previous link is dead, a new message may arrive); `200 status=already_verified` → destroy the pre-access record and `303 /signin/{handle}` so a fresh sign-in establishes the verified metadata; `429 resend_cooldown`/`too_many_requests`, `503 email_unavailable` (nothing rotated), `502 email_failed` (old link replaced, no new mail) and any timeout → `unavailable`. The exact provider status is retained server-side in sanitized form for evidence. | Cooldown 60 seconds per account mirrored on the GenUI side ahead of fAuth's own atomic 60-second cooldown and IP limiter; at most 5 requests per pending identity per 24 hours. |
| `POST /auth/signout` | any session | Deletes the GenUI session record and advances the identity's membership epoch under the ADR-004 fence (organization FOR SHARE, member FOR UPDATE) so queued or in-flight work fails its current-authority check, calls backend `POST /t/{slug}/auth/logout` with the stored refresh token, discards it, clears cookies, answers `303 /` (design §6.1: sign-out and sign-out-everywhere delete the rows and bump the epoch). | Idempotent; a missing record still clears cookies. |
| `POST /auth/signout-all` | workspace session | Deletes every GenUI session of the identity in this organization, advances the membership epoch once under the same fence, and discards each stored refresh token after the backend logout call. | — |
| Protected routes | workspace session | Recheck organization state, membership epoch and active entitlement before admission, at execution and at delivery (ADR-004 fences). | Anonymous, pre-access, expired, revoked and foreign-tenant callers receive the same designated refusal status, body and headers with no existence disclosure. |

## Flows

1. **Ordinary sign-in.** Browser `GET /signin/{handle}` → `POST` → provider authorize with `request_uri` → fAuth hosted login (existing member) → `GET /auth/callback` → exchange and verification → pre-access → membership and entitlement current → workspace session. Each attempt is a fresh `state`/verifier/flow record; nothing from a previous attempt is reused.
2. **Invited signup.** `GET /invite` → `POST /invite/validate` → provider hosted registration bound to the operator-provisioned, email-bound, explicit-role, `server_only` invitation → `GET /auth/callback` → exchange → pre-access → APP-073 redemption rechecks expiry, revocation and remaining count and commits slot, membership, entitlement and audit in one transaction. A completed provider identity whose GenUI code has meanwhile expired, been revoked or exhausted is denied admission; the partial outcome is recorded for operator reconciliation. The hosted signup's `user.email_verified` is false, so this flow always lands on `/auth/pending`.
3. **Verification pending and resend.** The pre-access user reads `/auth/pending`; resend is backend-mediated as above. The browser never holds a provider bearer.
4. **Mailbox confirmation and return.** The user opens the provider's one-use verification link, confirms on the provider's same-origin page (a preview `GET` activates nothing), and the provider shows "Continue to GenUI" pointing at the GenUI entry URL configured for that client at provisioning: `https://beta.getforma.dev/signin/{handle}`. GenUI accepts no `return_to`, token, code, state or verification parameter on that entry; it simply starts a new flow. The second exchange returns `email_verified` true, and admission proceeds only if membership and entitlement are current. Any browser or profile works because nothing from the first flow is required. A query parameter, webhook, stale earlier response or another browser's session never activates anything.
5. **Signout.** GenUI revokes its own record first, then the provider refresh token. A provider `204` is not the negative receipt; APP-009 proves that a subsequent provider refresh with the revoked token is refused and that the GenUI cookie no longer admits anything.

## Storage consequences

Flow, pre-access and workspace session rows are tenant-leading like every other `genui` relation: the organization is known when the flow starts (from the handle or the code's server-bound destination) and is confirmed at the callback. The workspace role receives narrow INSERT/UPDATE/DELETE on those session tables only, each under FORCE RLS; membership-epoch advancement uses a fixed SECURITY DEFINER function owned by a dedicated definer principal, never a direct application UPDATE on `genui.memberships`. The fAuth refresh token is stored encrypted with a random key held only in process memory: a service restart makes stored refresh tokens unusable, the pending user simply starts a fresh sign-in, and no KMS or secret-store client is added to the Rust binary in Phase 1; fAuth's own 30-minute idle timeout bounds any orphaned token. Resolving a session to a `TrustedRequest` happens inside the storage module (the only place that may construct one), reading the session row, the current membership epoch and the registry identity; a pre-access record is a distinct type that can never become a `TrustedRequest`.

## Provider facts consumed and requests to FormaStack

Consumed as pinned: literal issuer `gatewasm` and audience `gatewasm-app`; 900-second access tokens; access-only `/auth/jwks` with OKP/Ed25519 keys and `Cache-Control: public,max-age=3600`; `/ssf/jwks` never merged into the access verifier; token response `user.id` equal to `sub`, `user.email_verified` as backend metadata (not a claim); refresh rotation with family revocation on reuse; `POST /t/{slug}/auth/logout {refresh_token}`; `POST /manage/users/{usr_id}/revoke-sessions` for operator revocation; `ten_`/`usr_` prefixed provider identifiers mapped through GenUI's registry, never compared to application UUIDs.

FormaStack reported on 2026-10-29 (local branch `claude/forma-247-mail-verification`, worktree `work/FORMA-247/gatewasm-mail`, consumer contract `handoff/forma-247/MAIL-VERIFICATION.md`; unpushed and unreviewed, not the rehearsal image `dfba787`): `POST /t/{slug}/auth/resend-verification` with the account's bearer always uses the stored address, claims a 60-second per-account cooldown atomically, keeps the IP limiter and answers with the five outcomes mapped above; the verification link's `GET` only shows a confirmation page and its `POST` consumes the challenge one-use, bound to tenant, user and issuance address with wall-clock expiry, creating no session. GenUI pins these facts only when that source merges with CI and review; until then they are a reported contract.

Requested from FormaStack inside FORMA-247 and its mail follow-on, with the answers FormaStack reported on 2026-10-29 from local branch `claude/forma-247-mail-verification` (two commits, independent review in progress, unpushed and unmerged; the rehearsal image stays `dfba787` with no SMTP). GenUI pins each answer only when that source merges with CI and review:

1. **Per-client return entry URL.** Implemented: `POST /manage/oauth-clients` accepts an optional `return_entry_url` that must share the client callback's exact origin, carry no userinfo, query or fragment and be at most 2,048 bytes; re-registering the same client with a new value replaces it (GenUI's handle rotation), omitting it leaves it unchanged, and `GET /manage/oauth-clients` returns it. Invited hosted signup records the client of the consumed, validated hosted request on the account; after verification the page shows "Continue to {app}" linking (`rel=noreferrer`, no parameters) to that entry URL only while the client still exists in the tenant and the entry still validates against its current callback, otherwise a no-link "Return to {app} and sign in" page. `provision.py` accepts a per-tenant `return_entry_url`, so GenUI supplies `https://beta.getforma.dev/signin/{handle}` per organization at provisioning. The handle is stored in plaintext on the provider side because it renders as a link; it is non-secret routing, as this record already requires.
2. **Truthful delivery outcomes and the hashed one-use challenge.** Implemented as described in the resend mapping above.
3. **`delivery_mode: server_only`.** Confirmed from source: no invitation mail is sent and the management response reports `email_delivery: suppressed` (test `hosted_signup::server_only_invitation_suppresses_real_transport_and_validates_before_writes` asserts zero captured messages). The verification mail after hosted signup is therefore the only message to the invitee; in the no-SMTP rehearsal it is recorded as `unconfigured` and nothing is sent.
4. **Exact lifetimes and limits** (identical at `dfba787` and on the branch): PAR `request_uri` 60 seconds; hosted authorization request 5 minutes; authorization code 60 seconds; verification link 24 hours; resend per-account cooldown 60 seconds claimed atomically plus the per-IP `register_limiter` (burst 5, one token every 12 seconds, env `REGISTER_RATE_LIMIT_BURST` overrides), which also covers `GET`/`POST /auth/verify-email` and `/auth/register`; access token 900 seconds; refresh token 30 days with the 30-minute idle policy. GenUI's bounds fit inside them: the backend performs PAR and answers the `303` in the same request, so the 60-second `request_uri` is never outlived; the callback exchanges immediately, inside the 60-second code window; the 10-minute single-use flow record merely outlives the provider windows and cannot be replayed; GenUI's invitation-entry limit (5 per minute per address class) stays under the provider's registration burst, and any provider `429` is a uniform neutral failure.

## Retirement of the operator qualification callback

The APP-006 operator harness mounts `/auth/qualification/start`, `/auth/callback`, `/auth/qualification/status` and `/auth/qualification/result` behind `GENUI_AUTH_QUALIFICATION_CONFIG_FILE` (`app/src/auth_qualification.rs:295-298`). When APP-009 lands, the production router owns `/auth/callback` and the harness routes are not mounted in the service binary; the harness remains available only to the isolated qualification executable for the FORMA-248 key campaign, and its image pins stay as recorded. The harness never becomes a product login, and the product login never exposes a test identity.
