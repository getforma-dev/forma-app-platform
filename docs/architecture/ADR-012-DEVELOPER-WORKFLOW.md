## Context

The inventory's short answer stands: until 2026-10-30 22:54 (`326d56c`) the product could not run locally; changes were seen through eight beta redeploys in one day (inventory §C.1). What exists now is a `#[ignore]` **test** run as an 8-hour server (`app/src/storage/dev_stand.rs:145-161`), launched by 281 lines of bash with pid files (`app/scripts/dev_stand.sh`), signed in through four Python cookie proxies, on a tmpfs Postgres that a Rust destructor removes (`qualification.rs:122-144, 232-247`). Every incident in the inventory's root-cause table is one assumption of that harness failing when used as a dev environment: the 600 s credential file (`config.rs:118`), the once-at-startup asset manifest (`forma-server assets.rs:63-69`), proxies that keep old code because `start` skips a live pid (`dev_stand.sh:156`), fixed ports and one machine-wide state directory (`dev_stand.sh:31-36`), a scratchpad path compiled into the binary (`dev_stand.rs:93`).

Five facts decide most of what follows:

1. **The release binary refuses to be a dev server by design** (`main.rs:32, 75-94`; ADR-007 D7.13 keeps harnesses out of it). So a dev environment must be a *separate* entry point, the way the qualification harness already is a feature (`--features qualification-harness`). It cannot be a flag on `main`.
2. **Nothing is pinned where cargo, node or python look.** No `rust-toolchain.toml` in `app/` (while `parser/rust-toolchain.toml` pins 1.93.1 with components and the wasm target), no `.node-version`, no `.python-version`; CI pins 1.93.1 on each command line (inventory §B.1). Four venvs are hand-made; none is created by any script in the repo (§B.2).
3. **Cross-checkout borrowing is in Git.** `contracts/.venv` is a **committed symlink** (`git ls-tree HEAD contracts/.venv` → mode `120000`) to `/Users/victorvillacis/dev/FormaBuiltApps/forma-app-platform/contracts/.venv`, merged in `4825e7f`. That is why "Contract qualification" fails on every run: `python3 -m venv contracts/.venv` → `[Errno 17] File exists` (run 41210420545). The inventory's other borrowings are the same pattern: the operator venv, `$PRIV` and the redeploy scripts live in the *other* clone's `.cache` (§C.1), the image build script in a Claude scratchpad.
4. **The one deploy process we run well is the OVH one**: a `Makefile` whose every target is a script in Git, one release directory per deploy, `build / deploy / verify / rollback` (`getforma-infra/Makefile`, inventory §C.2). The AWS path has stronger safety machinery (preflight, ledger, change-set review, per-action approval) and no packaging at all (§C.3).
5. **Disk is a profile problem, not a cleanup problem.** 32 GB of the 33 GB `app/target` is `debug/deps` object files kept by macOS's default `split-debuginfo = "unpacked"` across 41 build hashes (§B.7); the sweep script removed 43 GB at 08:37 and it grew back in two hours.

Constraints: AGENTS.md:13 (new tools and commands belong in an owning ticket, with pinned released versions); ADR-011 (the demo is a concept car; MVP first; no long verification campaigns — Victor, 2026-10-29); the forma-stack skill's caps (`CARGO_BUILD_JOBS=3`, no duplicate servers). No guidance forbids just, process-compose, Compose, uv or a toolchain file (inventory, "Constraints found in our own guidance").

## Decision

### D12.1 Local dev environment: a dev binary of the product, not a test run as a server

- **A `genui-dev` binary** (`app/src/bin/genui-dev.rs`) behind a cargo feature `dev-stand`, mirroring how `qualification-harness` is kept out of the release (`main.rs:32`). It calls the same `genui::product::routes` composition `main.rs` calls, so what runs locally is the product. The Dockerfile never enables the feature; `cargo build` without it contains none of this code. The seed, operator and session-minting helpers the stand borrows from `qualification.rs` today (`dev_stand.rs:37-63`) move into a `dev` module compiled under `cfg(any(test, feature = "dev-stand"))`; `Fixture` (tmpfs Postgres, 600 s credentials) stays test-only. Credentials for the dev database are written by the dev binary itself with a long expiry, under the feature only, which removes the 60 s rewrite loop (`dev_stand.rs:687-689`).
- **Postgres is a Compose service with a named volume**, `compose.dev.yaml` at the repo root, the gatewasm shape (inventory, "A Postgres dev database"), digest-pinned image as `qualification.rs:24-25` already is, healthcheck, project name `genui-dev-<instance>`. Data survives server restarts, so a code change no longer reseeds (`GUIDE.md:141`), and its lifecycle is Compose, not `Drop`. Containers carry labels `genui.scope=dev` (campaign fixtures add `genui.scope=campaign`) so a sweep finds strays by label (root-cause row "Leaked `genui-native` containers").
- **Instance identity is the checkout.** State lives in `<checkout>/.cache/dev/` (`.cache/` is already gitignored) and the Compose project and port base derive from it; a second checkout or worktree runs beside the first (fixes APP-119:100 and root-cause row "A second stand or worktree cannot run"). Defaults: port base 4000, overridable per checkout in a gitignored `.env.dev`.
- **Personas and sessions, in process.** The dev binary mints the personas' sessions and serves one loopback listener per persona (4001 Diego, 4002 Sarah, 4003 Priya), each with a tower layer that adds that persona's session cookie to the request — the same trick the Python proxies do (`dev_stand_proxy.py:4-8`), done once in Rust, so there is no proxy to go stale. The "8 sessions per persona, one per browser" slot behavior of `e7dda41` is kept. Real sign-in (fAuth) is not part of the dev loop; that is a deliberate, labeled difference from beta, as `GUIDE.md` already states.
- **The clean slate is truly clean.** The `fresh` profile becomes the **`clean` profile**: a second instance (`just dev clean`, port base 4010, own Compose project), one new customer Alex Rivera in a new organization, **no library seeded** — the `seed-library` call and the `assert_eq!(apps, 20)` (`dev_stand.rs:293-295`) are removed from this profile — no records, no folders, demo mode off. The pitch profile keeps the 20-app library and the seeded Northstar scenario. `just dev clean reset` drops the volume and reseeds in seconds; the `Clear-Site-Data` behavior for the :4010 origin moves into the dev listener.
- **Front-end changes are picked up without a manual step.** The supervisor (D12.2) runs the framework's own watcher, `npm run dev` (`build.ts:72`, unused today), and the dev binary polls `admin/dist/manifest.json`'s mtime once a second and exits with code 75 when it changes; the supervisor restarts it in about two seconds (no Rust rebuild, database untouched, browser slot cookie kept). This follows the framework rule that embedded assets are read at start (`building-and-verification.md:36-37`) instead of contradicting it (`GUIDE.md:144` is corrected). A Rust change is `just restart`: the supervisor restarts the `server` process, which is `cargo run --features dev-stand --bin genui-dev`, so cargo rebuilds incrementally.
- **One command each**: `just dev` (start, foreground TUI or `-d`), `just dev stop`, `just dev reset`, `just dev clean …` for the clean instance, `just restart`, `just status`. `.claude/launch.json` gets one entry per instance that **runs** `just dev` (today's entries only attach, inventory §D).

Rejected: keeping the test harness as the server with more patches (every incident so far is one more patch); a dev config path in `main` (breaks D7.13); Docker-built server for the inner loop (the VM is the resource that already filled, root-cause row 6); mkcert/https for real `__Host-` cookies (a new tool for no demo value — revisit with real sign-in).

### D12.2 Process orchestration: process-compose

**process-compose** (`process-compose.yaml` at the repo root) owns the dev processes: `db` (Compose Postgres, `docker compose up`), `migrate` (runs once after `db` is healthy), `server` (the dev binary, depends on `migrate`, readiness `GET /health/live`, `restart: on_failure` which is what turns exit 75 into a reload), `admin` (`npm run dev`), and `server-clean` plus `db-clean` as a second group for the clean instance. One YAML replaces pid files, `kill -0`, `nohup`, the 600 s wait loop and the "skip a live proxy" bug (`dev_stand.sh:47, 133-146, 156`).

Why this one (inventory, "Process orchestrators"): it has what our startup order needs and the alternatives lack — dependencies with readiness probes (DB → migrate → server), restart policies, per-process logs and a TUI, in a single Go binary. overmind needs tmux; Procfile tools have no readiness; `concurrently` is npm in a Rust and Python repo and has no restart; mprocs is mid-rename. Docker Compose stays for the **database only**: building Rust in the VM is the disk incident. The YAML dialect is one we already use (getforma-infra `compose.yaml`, gatewasm `docker-compose.yml`). Fit with AGENTS.md:13: it is a new tool, so it is adopted through the owning ticket (plan step 4) with a pinned release (v1.124.0 was the latest at writing, 2026-10-26) and checked by `just doctor`.

### D12.3 Task runner and entry points: just, one `justfile`, scripts in Git

**just** over make and cargo-xtask. Our recipes take arguments (`just campaign mcp`, `just deploy change-set <window>`, `just dev clean reset`) and must list themselves (`just --list` *is* the campaign catalog the inventory says does not exist, §B.4); make's argumentless targets fit getforma-infra, not this. cargo-xtask would add a crate to a repository whose build size is the problem and `app/` is not a workspace. `just` loads `.env`, has no tab or `.PHONY` ceremony, and is one binary (1.59.0 was the latest at writing). It is a new tool: ticketed and pinned like D12.2. Every recipe is a thin call into a script kept in Git (`scripts/dev/*.sh`, `ops/beta/*`), the Makefile→`scripts/` shape of getforma-infra, so the recipes stay readable and the scripts stay testable (`bash -n` in `just check`, as `getforma-infra/Makefile` does).

**Canonical command list** (the only commands DEVELOPMENT.md, GUIDE.md and the runbook may name; each is a recipe):

| Recipe | Does |
| --- | --- |
| `just setup` | Toolchains present (rustup reads `rust-toolchain.toml`; `.node-version`; `uv python install` from `.python-version`), `uv venv` + `uv pip sync --require-hashes` for `app/runtime/.venv` (runtime + contracts locks, exactly `tenant-foundation.yml:26-27`) and `contracts/.venv`, `npm ci` in `app/admin` and `infra`, Docker reachable. Idempotent. |
| `just doctor` | Versions of rustc, node, python, uv, just, process-compose, docker against `tools.versions`; prints what differs, exits non-zero. |
| `just dev [clean] [stop\|reset\|status]` | The pitch instance (default) or the clean instance; start is the process-compose TUI, `-d` detaches. |

The eight command lines of `DEPLOY-RUNBOOK.md:57-65`, once. |

### D12.4 Environment pinning: files cargo, node and uv already read; no mise yet

- **`rust-toolchain.toml`** at the repo root: `channel = "1.93.1"`, `profile = "minimal"`, components clippy and rustfmt, target `wasm32-unknown-unknown` — the file `parser/` already has, moved up so `app/`, the spikes and the dev binary share it. CI's `cargo +1.93.1` lines become plain `cargo`. The MSRV check (`cargo +1.85.0 check`, `tenant-foundation.yml:47`) keeps its explicit toolchain. This is the Rust "venv": `rustup update` can no longer move a checkout off CI's compiler (inventory §B.1).
- **`.node-version`** `22.21.0` (the Dockerfile's `node:22.21.0`, `app/Dockerfile:1`; the convention the Forma framework and getforma-site use). **`.python-version`** `3.11.14` (the image's `python:3.11.14`, `app/Dockerfile:52`).
- **uv with the existing hashed locks** (`uv venv`, `uv pip sync --require-hashes --only-binary=:all: -r …lock`). No lock changes; `--require-hashes` is kept. `just setup` creates both venvs per checkout, so a worktree is never without one (root-cause row "Python venvs missing in worktrees"). The `PYTHONPATH` splice (`dev_stand.sh:121-125`) goes: the runtime venv gets both locks, as CI does.
- **No cross-checkout borrowing, by rule**: no venv, `target/`, `.cache/`, `$PRIV` or script of one checkout is referenced from another. The committed `contracts/.venv` symlink is deleted (plan step 1); `scratchpad/op-python` and the other clone's `opvenv` are retired by `just setup`. The one shared thing a *worktree* may read from its main checkout is `.env` through `git rev-parse --git-common-dir` (`dev_stand.sh:94-101`): a worktree is the same repository by definition and secrets are not build output.
- **Build profile**, in `app/Cargo.toml`: `[profile.dev] debug = "line-tables-only"`, `split-debuginfo = "packed"`, `[profile.dev.package."*"] debug = false`. This is the fix for the 33 GB (inventory §B.7): no more per-unit `.o` debuginfo retained across hashes; backtraces keep line numbers. `app/.cargo/config.toml` sets `[build] jobs = 3` (the forma-stack cap the stand never applied). Release profiles and images are unaffected.
- **Worktrees keep their own `target/`.** A shared `CARGO_TARGET_DIR` serializes builds across checkouts and lets branches churn each other's artifacts; with the profile fix a per-checkout target is affordable. `build.build-dir` and sccache are **deferred** until the profile fix has been measured for a week.
- **mise: not now.** rustup, `.node-version` and uv already pin each language in a file its own tool reads, with no new shell hook; mise would be a fourth version manager beside pyenv, rustup and Homebrew. `just` and `process-compose` are installed by Homebrew and their versions are recorded in `tools.versions`, which `just doctor` enforces. Revisit mise when a second developer onboards; it is the natural step up from `tools.versions`.

### D12.5 VS Code: one multi-root workspace in this repo, tasks bound to recipes

Yes. `forma-pitch-mvp.code-workspace` at the repo root replaces the single-folder `forma-app-platform.code-workspace` copies (inventory §D), modeled on `gatewasm.code-workspace`: roots `app` (Rust), `app/admin` (canvas), `infra` (CDK), `parser`, `Tickets`, `docs`, and **optional sibling roots** `../forma-app-platform`, `../../Forma`, `../../FormaDeploy` (relative; VS Code shows a missing one greyed, harmless). Settings: `rust-analyzer.linkedProjects` `app/Cargo.toml` and `parser/Cargo.toml`, `rust-analyzer.check.command: clippy`, `rust-analyzer.cargo.features: ["dev-stand"]`, excludes for `target`, `node_modules`, `dist`, `.cache`, `cdk.out`. Tasks: `dev`, `dev: clean`, `restart`, `check`, `campaign…` (prompt), `clean` — each `just <recipe>`, so the editor and the terminal run the same thing. Extension recommendations: rust-analyzer, Even Better TOML, Docker, Playwright. Context switching across repos is this workspace plus `FormaDeploy.code-workspace`; no third workspace file is added.

### D12.6 Deployment: the beta deploy lives in this repo, packaged like OVH, gated like today

- **`ops/beta/`** in Git holds every script the inventory found outside it (§C.1): `build-images.sh` (from the scratchpad `pitch-images/build.sh`, candidate and clone paths as arguments, `set -euo pipefail`), `redeploy.sh` split into the `just deploy <step>` steps, `run-step.sh` with `--window` **required** (the `WIN_gov` hard-code goes), `env.example.sh` naming the 22 variables with no values, and `verify.sh` (runbook 6.2's four curls). `infra/scripts/*.py` stay where they are.
- **`$PRIV` moves to this checkout**: `.cache/ops/beta/` (gitignored, 0700), with `windows/<window-id>/` per deploy exactly as the runbook prescribes (`DEPLOY-RUNBOOK.md:70`), each holding `deployment-input.json`, `receipt.json`, `template*.json`, `change-set-*.json`, `stack-*.json`, `activation.json`, `run-<step>.*` and a `release.json` (candidate sha, three digests, window id, supersedes, times) — the OVH release directory, for AWS. `approvals.md` and `budget-ledger.json` move with it, once, and the other clone's flat 564-file directory is copied into `windows/_pre-adr-012/` as history and never reorganized.
- **Approval gate unchanged and enforced by the tool**: every mutating step prints the exact AWS command and refuses unless `--approved "<Victor's verbatim word>"` is given; the word is appended to `$PRIV/approvals.md` before the call. Secret steps stay Victor's (runbook §4) and keep piping through `read_env.py`. The runbook's checklist stays the authority; each item gains the recipe that performs it.
- **Verify and rollback become commands**: `just deploy verify` (6.2) and `just deploy rollback-deny` (the deny-all task revision, the only fast rollback the runbook recognizes). The slower stack-level rollbacks stay a documented procedure, because they are judgment calls, not a script.
- **The scratchpad parser path** `DEFAULT_PARSER` (`dev_stand.rs:93`, `box_campaign.rs:66`) becomes `.cache/parser-target/` relative to the repo, built by `just parser`.
- **CI policy**: a workflow on `pivot/pitch-mvp` is green or quarantined; never red-and-ignored. Quarantine means `on: workflow_dispatch` only, a ticket, and a line in DEVELOPMENT.md. Of the three red workflows (inventory §B.6): *Contract qualification* is fixed by deleting the symlink (step 1); *Foundation preparation* fails in `app/runtime` unittests (run 41209555995) and *Tenant foundation* in `native_command_campaign` ("expected a committed command: Err(Denied)", `command_qualification.rs:204`, a command-authority behavior change from the pitch work — invariant I4 territory, so it gets a ticket, not a quarantine). Both are reproduced locally with `just check` / `just campaign command` and either fixed inside a day or quarantined by the rule. The pitch-era campaigns get a `pitch.yml` on `workflow_dispatch` later (deferred); their catalog exists now through `just campaigns`.

### D12.7 Separation of concerns and the cleanup policy

| Concern | Lives in | Never in |
| --- | --- | --- |
| Test harness (fixtures, campaigns, qualification) | `app/src/**/*qualification*.rs`, `cfg(test)`; `app/qualification/` | the dev binary's startup path |
| Dev environment | `app/src/bin/genui-dev.rs`, `app/src/dev/` (feature `dev-stand`), `compose.dev.yaml`, `process-compose.yaml`, `scripts/dev/` | the Dockerfile, release profiles |
| Dev tooling and pins | `justfile`, `rust-toolchain.toml`, `.node-version`, `.python-version`, `tools.versions`, `app/.cargo/config.toml` | per-session shell |
| Operations (beta deploy) | `ops/beta/`, `infra/`, `docs/pitch/DEPLOY-RUNBOOK.md` | scratchpads, other clones |
| Private per-checkout state | `.cache/dev/`, `.cache/ops/beta/`, `.cache/parser-target/`, `.cache/reports/` (gitignored) | `$TMPDIR`, `/private/tmp/claude-*` |
| Procedures | `docs/DEVELOPMENT.md` (developer), `DEPLOY-RUNBOOK.md` (operator), `GUIDE.md` (product; its "Local dev stand" section becomes a pointer) | ticket logs as the only record |

Rules: (1) a script run twice is committed; a scratchpad is for one session; (2) nothing in `.cache/`, a scratchpad or another checkout is referenced from code or from another checkout; (3) Docker resources carry `genui.scope` labels and are swept by label; (4) `~/dev/Forma/work/_maintenance/clean-space.sh` and `clean-build-artifacts.sh` stay where they are — they are machine-wide and shared with the Codex lead — but their special cases for `parser-target`, `pitch-images` and `upload_library.py` (`clean-space.sh:160`) are removed once step 3 lands, because those paths stop existing; `just clean` is the per-repo sweep and DEVELOPMENT.md points at the machine-wide one; (5) `app/scripts/dev_stand.sh`, `fresh_stand.sh` and `dev_stand_proxy.py` are deleted when step 4 lands, not kept as fallbacks.

### D12.8 Product: an app gallery is v2; the clean slate shows the composer, and templates are an operator install

A cross-company marketplace is already outside this release (`docs/planning/DEFERRED.md:16`), and the concept-car stance (ADR-011 amendment) says to spend November on the pitch flows, not on a storefront. Decision for the MVP:

- **No gallery UI now.** A clean-slate customer (the `clean` profile, and a real new organization after onboarding) sees an empty canvas with the composer bar and the empty-state line "Describe the app you need"; a sentence goes to the model and generation (labeled, typed, through admission) builds the first app. That *is* the product story for a new customer, and it exercises the generation path the pitch otherwise hides behind the library.
- **Templates are installed, audited, by the operator**: the existing `seed-library --organization <org>` is the "install the template apps" action, idempotent (`changed: false` on repeat, runbook 5.3), followed by `grant-library-access`. `just dev clean seed-library` does it on the dev instance so both states — empty and with templates — can be tested on demand. No new code.
- **The gallery ("app shop") is a v2 ticket for the Nov 3 revisit (APP-097)**: an in-product page listing admitted template apps with "Add to my workspace", which writes the same grants `seed-library` + `grant-library-access` write today, audited the same way; a cross-organization marketplace needs the publication, provenance and billing decisions DEFERRED.md names and is not implied by the clean slate.

## Consequences

- Localhost is one command and survives a code change without losing data; the inventory's eleven incidents each have a structural fix rather than a patch, and the bash, proxies and pid files are deleted.
- Two new tools (just, process-compose) enter under AGENTS.md:13 with pins; three pin files make every cargo, node and uv call deterministic across checkouts and CI; no tool from another checkout or a scratchpad is referenced anywhere.
- The deploy keeps all of its safety (per-action approval, preflight, ledger, change-set review) and gains packaging: scripts in Git, one directory per window, verify and rollback-deny as commands. The runbook gets shorter, not weaker.
- `app/target` stops growing by hundreds of object files per hash; the sweep becomes rare instead of daily.
- CI on the pitch branch becomes a signal again; the APP-013 campaign regression is surfaced as a ticket instead of noise.
- Cost: about four working days of implementation spread over the plan below, each step shippable alone; the dev binary (step 4) is the only step with real engineering risk (feature plumbing of the harness helpers) and it is scheduled after the deploy is in Git, because deploying correctly matters more to Nov 2 than a nicer inner loop.
- Debt acknowledged: dev sign-in is still minted, not fAuth; the clean profile's "new organization" is synthetic; the gallery is unbuilt and the empty state says so plainly.
